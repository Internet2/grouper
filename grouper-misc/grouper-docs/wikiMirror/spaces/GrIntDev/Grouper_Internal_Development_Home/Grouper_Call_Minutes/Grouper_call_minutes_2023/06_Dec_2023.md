Composites and performance issues

If you make a change in Grouper, create a composite, add a group to another group, it can cause changes in the repository. Now done transactionally. Screen might even time out. Has taken up to 2 hours. To address that, thinking about a fix

Shilen suggests

- Any changes you make are just the immediate changes
- Composite would happen on the daemon
- Go thru temp changelog first
- Then to new daemon to handle composites
- Run the daemons more frequently to reduce delay
- regex approach
- Some folks might have conditions , expect composites get updated immediately
- For example with an exclude group
- If org is expecting no delay
- Workaround:
- Have a regex of group names to be excluded from the new way of doing composites
- Would only impact immediate group membership
- If group you are adding to is part of regex, then composites would get taken care of immediately
- or (Matt suggests) use an attribute on the group instead of a regex
- Now the default change log runs every minute, seems like a long time
- Could have it run more frequently, or have it a long running job that gets notified of work to do
- Changelog temp processor - need to make sure it works well  
  Messaging:
- M. Gettes believes in messaging
- Messages get received in near real time
- Must stand up RabbitMQ
- Chris Hyzer: A design issue: if there is a lot in the queue and things changed at later point in time… stateful versus stateless messages
- Want stateless messages as much as possible
- What percentage of groups impact composites?
- Could be helpful to figure that out, use a query and run it for a few institutions
- Immediates and unions are fine, the issue is all about composites
- Shilen and Chris Hyzer, agree on direction for this composites performance issue
- Will discuss metrics for success

## **Detailed discussion summary from Zoom AI**

**Azure Provisioner and Team Integration**

Chris Hyzer discussed the potential for integrating Teams and Channels into the Azure Provisioner, a topic of interest for Ben and Bert. Chris also mentioned the possibility of creating a distribution list group in Azure, which is currently deprecated but may be reintroduced in the future. Shilen asked about managing memberships within Teams, which Chris and Ben had previously struggled with. Chris also mentioned the need for an Azure Provisioner for Octa, as Harvard is migrating from Shibboleth to Octa. The team also discussed the pros and cons of using Midpoint versus Grouper, with Bert noting that Grouper is more user-friendly and customizable, while Midpoint is an identity management platform. Chris Hubing shared feedback from Chris Sutherland about the need for a "scroll to top" button in the configuration interface. Lastly, Chris Hyzer proposed focusing on payback and then moving on to provisioner things and lifecycle events.

**Managing User Data and Group Changes**

Chris Hyzer discussed the need for a system to manage changes in user data at institutions. He proposed a policy that would determine who should be in a group, which groups are manual, and how the includes and excludes get stitched together.

Chris suggested a feature called 'membership eligibility' where changes could be made directly to a group. He also proposed a 'lifecycle' feature that would handle user changes based on their security level, with different actions for different lifecycle events such as leaving the institution, department, or position. Bert added the concept of priority precedence to the lifecycle events.

**Designing Departmental Group Security System**

The team discussed the design of a system that involves a tree of groups, with each group representing a department. They considered how to handle lifecycle events, such as leaving a department, and how to apply different security levels to different departments.

The team agreed that the system should allow for different configurations for each department, with the possibility of more specific configurations for certain departments. They also discussed the need for simplicity in the system, suggesting the use of radio buttons for security levels and checkboxes for actions. The team agreed to avoid the term "policy" to prevent confusion.

**Handling Multiple Actions in Lifecycle**

The team discussed the configuration of group security levels and the potential for different access controls. They also discussed the concept of a 'membership lifecycle policy' and how it could be triggered by various events, leading to multiple actions. The team agreed on the need for a system that can handle multiple actions for a single lifecycle event. They also discussed the idea of a 'cache' to quickly pull up information during attestation or reporting.

**Exploring Grace Period and Membership**

The team discussed the concept of a 'grace period' and its application in different security groups. They clarified that the 'grace period' is not the same as the'recent membership' logic, but rather a feature that allows for a specified time period before a user's membership is removed. They also discussed the idea of creating a '5 Day Grace Period' group and nesting it into the security group. The team also discussed the possibility of creating a screen to view and manage memberships, and the need for a more comprehensive system to handle different membership lifecycle actions. They also touched on the idea of using a Jexel script to define certain membership events.

**Lifecycle Events and Group Notifications**

The group discussed the concept of lifecycle events and their implications. They agreed that each column in the lifecycle event should only have one event, and that the lifecycle event should be singular. They also discussed the idea of notifying managers or admins about changes in group memberships.

Chris proposed a new privilege called "owner" for groups and folders, which would be used to notify specific individuals about changes.

Carey suggested using the term "manager" instead of "owner" for better clarity.

They also discussed the possibility of applying these lifecycle events to non-manual groups, but decided that it would be more appropriate for manual groups.

The team agreed to further explore the concept of lifecycle events and their applications.

**Improving Membership Requirements and System**

The group discussed the need for more robust membership requirements to handle changes in job roles and employee status. They agreed that the current system, which relies on alerts and grace periods, is not sufficient and needs improvement.

Chris suggested that the system should automatically remove access if an employee leaves or changes roles, and that the system should be able to detect and respond to changes in job roles.

Bert agreed that the system should be able to handle these changes and suggested that the system should set different expiration dates for different roles.

They also discussed the need for a new Confluence table to outline these situations and their corresponding actions.

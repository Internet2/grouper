- **Cache Tables**
  
  - Decision was to store every group and flattened membership in the cache tables
  - (Now only stored if attribute is set on the group)
  - Use cache group table
  - When membership are added or removed all flattened memberships will be added to cache group table
  - Daemon job for full sync
  - Still working on this.
  - Need to do performance testing
  - May have tens of millions of rows in the table
  - How to make the membership table as minimal as possible?
  - It is 3 columns
  - Flattened point in time for memberships?
  - Shilen will work on this after the cache table
- Performance versus consistency
  
  - Race conditions, hibernate
  - New classes
  - New stuff to use existing hibernate connection, so it is part of same transaction
  - Chris will work on this
  - Whatever transaction is in use, it should use that
  - Chad: main issue might be with the full sync
  - For long running job
  - Optimistic locking
  - Could lock your whole database while update is happening
  - Shilen: Full sync won’t use long transactions
  - Chad: could lead to problem results
  - Shilen: hope to have full sync compare cache tables w point in time data
  - It should be in sync
  - If it finds issues, then address them
  - Need incremental running all the time
  - Need to think of solution so there are no race conditions

- **History Table**
  
  - history table (not like real point in time) is a flattened table with start and end dates flattened for a user
  - It does not have current state
  - Does not have all the relationships
  - Can do efficient queries in ABAC
  - When Grouper started, it was flattened
  - Moving away from flattened caused problems
  - Point it time tables and membership table will still exist
  - The New, lightweight, minimal flattened history table will be used for ABAC and maybe some other things

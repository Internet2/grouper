## Overview

Reduced downtime major upgrade of `penngrouper` (Aurora PostgreSQL but does not need to be Aurora for this procedure) via **self-managed logical replication + single cutover**. Prod is 16.11; test is 17.7. The current prod database is the “blue” database which will stay at the old version: 16.11. The new prod database is the “green” which will be upgraded to 17.7 with two brief downtimes (pre-upgrade and post-upgrade). Direct (Aurora) managed Blue/Green can't do the 16 -> 17 hop here (see below); once on 17+, try managed Blue/Green for future majors. Method validated end-to-end in an Aurora lab (June 2026).

Each SQL block is tagged `[cluster | database | user]`. Prod DB is `mydb`, Grouper schema is `penngrouper`, master (rds_superuser) user is `postgres`. Console/app actions are tagged `[console]` / `[Grouper]` / `[downstream IdP]`.

## Named objects (use these exact names)

| Object | Name | Where |
| --- | --- | --- |
| Upgrade publication (whole DB) | `penngrouper_upgrade_pub` | blue, `mydb` |
| Upgrade slot (blue -> green) | `penngrouper_upgrade_slot` | blue |
| Upgrade subscription | `penngrouper_upgrade_sub` | green, `mydb` |
| Shib publications | `shib_entitlements`, `shib_front_door` | green |
| Shib downstream slots | `grouperprodorigin_epe_sub` (epe), `grouperprodorigin_devidp_epe_sub` (devidp) | green |
| Shib replication user | `shib_replication_prod` | downstream |
| Verification canary | `penngrouper.upgrade_canary` | blue, `mydb` |

(Confirm the exact Shib publication <-> slot <-> consumer mapping with Garick against the live config before cutover.)

## Why not managed Blue/Green for 16 -> 17

- Its provisioning creates an `rds_*` slot on green; pre-17 `pg_upgrade` refuses to run while a slot exists -> blocked (confirmed with AWS Support). That slot is in the protected `rds` namespace and **cannot be dropped**.
- PostgreSQL 17 preserves slots across `pg_upgrade`, so upgrades **from 17+** are fine.
- Self-managed works because the slot green inherits is **ours and droppable** -- we drop it on green before upgrading (step 1). Managed BG's `rds_` slot can't be dropped, which is the whole difference.

## Primary plan (16 -> 17)

### 1. Build green (quiet-window PITR)

**1a. Prep (no downtime)** -- create the whole-DB publication and the canary:

`-- [blue | mydb | postgres] CREATE PUBLICATION penngrouper_upgrade_pub FOR ALL TABLES; CREATE TABLE penngrouper.upgrade_canary (  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,  note text,  created timestamptz DEFAULT now() );`

**1b. Quiet window (~1-2 min, brief Grouper outage -- no writes):**

- `[Grouper]` stop systems writing to Grouper database (e.g. IIQ), then stop Grouper (no writes hit blue)
- create the slot and record the canary point and exact time:

`-- [blue | mydb | postgres] (during the quiet window) SELECT pg_create_logical_replication_slot('penngrouper_upgrade_slot','pgoutput'); SELECT max(id), count(*) FROM penngrouper.upgrade_canary; -- RECORD these two numbers`

- `[Grouper]` resume Grouper (and IIQ)

**1c. PITR-restore green** -- `[console]` RDS -> blue cluster -> Actions -> Restore to point in time -> pick a time in the **middle of the quiet window** -> new cluster (green), `db.r6g` class, public, same SG, 16.x param group. (Wait ~5 min first; `LatestRestorableTime` lags.)

**1d. Verify alignment + drop the inherited slot** (green is still 16.x):

`-- [green | mydb | postgres] SELECT count(*) FROM penngrouper.upgrade_canary; -- MUST equal the recorded value SELECT pg_drop_replication_slot('penngrouper_upgrade_slot'); -- unblocks pg_upgrade; does NOT affect blue's slot`

**1e. Upgrade green to 17** -- `[console]` Modify green -> engine version 17.x -> v17 cluster parameter group (with `rds.logical_replication = 1`) -> Apply immediately. Then:

`-- [green | mydb | postgres] SELECT version(); -- expect 17.x`

Why PITR not a snapshot: an Aurora snapshot's consistency point floats (captures writes after you think it froze), so a slot can't be reliably aligned to it. PITR + the quiet window make it deterministic.

### 2. Stream the delta (no downtime)

`-- [green | mydb | postgres] CREATE SUBSCRIPTION penngrouper_upgrade_sub  CONNECTION 'host=<blue-writer> port=5432 dbname=mydb user=postgres password=<pw>'  PUBLICATION penngrouper_upgrade_pub  WITH (copy_data=false, create_slot=false, slot_name='penngrouper_upgrade_slot');`

Watch it catch up (canary on green climbs to match blue; slot goes active on blue):

`-- [green | mydb | postgres] SELECT count(*) FROM penngrouper.upgrade_canary; SELECT subname, received_lsn, latest_end_lsn FROM pg_stat_subscription;`  
   
 `-- [blue | mydb | postgres] SELECT count(*) FROM penngrouper.upgrade_canary; SELECT slot_name, active FROM pg_replication_slots; -- penngrouper_upgrade_slot active = t`

### 3. Add green's read-only replica (no downtime)

`[console]` Add a reader instance to the green cluster, so the read-only endpoint exists to flip at cutover.

### 3a. Vacuum green and green read-only replica

vacuumdb --analyze-in-stages

### 4. Cutover (brief outage, ~5-10 min)

**4a.** `[Grouper]` stop Grouper (app + daemons); stop IIQ.

**4b. Confirm green is fully drained** (counts equal):

`-- [green | mydb | postgres] SELECT count(*) FROM penngrouper.upgrade_canary; -- [blue | mydb | postgres] SELECT count(*) FROM penngrouper.upgrade_canary; -- equal => 0 lag`

**4c.** `[downstream IdP]` drain the Shib subscribers (epe, devidp) to the same point, then stop them.

**4d. Stop the upgrade replication:**

`-- [green | mydb | postgres] DROP SUBSCRIPTION penngrouper_upgrade_sub;`

**4e. Create the Shib downstream slots on green** (publications come over via PITR; recreate only if missing):

`-- [green | mydb | postgres] SELECT pg_create_logical_replication_slot('grouperprodorigin_epe_sub','pgoutput'); SELECT pg_create_logical_replication_slot('grouperprodorigin_devidp_epe_sub','pgoutput');`

**4f. Sync sequences** -- generate on blue, run the output on green:

`-- [blue | mydb | postgres] (generate; copy the result rows) SELECT format('SELECT setval(%L, %s, true);', schemaname||'.'||sequencename, last_value) FROM pg_sequences WHERE schemaname NOT IN ('pg_catalog','information_schema') AND last_value IS NOT NULL ORDER BY 1; -- [green | mydb | postgres] paste and run the generated SELECT setval(...) statements`

**4g. Swap endpoints by renaming the clusters** -- `[console]` this transfers blue's exact writer **and** reader endpoint hostnames to green (the `cluster-<suffix>` is account-wide, so the names become identical). Grouper's connection string and SSL `verify-full` keep working unchanged -- no DNS or cert change needed:

- Rename blue: `penngroupsproddb` -> `penngroupsproddb-old`
- Rename green: `<green-cluster-id>` -> `penngroupsproddb`

Rename blue **off** the name first (two clusters can't share an identifier). The RDS endpoint DNS re-resolves within its short TTL, and the Grouper restart in 4j clears the JVM DNS cache. Confirm Grouper (and the Shib subscribers) connect via the **cluster/reader endpoints**, not instance endpoints.

**4h. Rebind the Shib subscribers to green** (`[downstream IdP]`, Garick) -- on each subscriber, recreate against green's slot, e.g.:

`-- [downstream IdP subscriber | shib_replication_prod] (confirm pub<->slot<->consumer mapping) CREATE SUBSCRIPTION <epe_sub>  CONNECTION 'host=<grouper-rw-domain-name> port=5432 dbname=mydb user=shib_replication_prod password=<pw>'  PUBLICATION shib_entitlements  WITH (copy_data=false, create_slot=false, slot_name='grouperprodorigin_epe_sub');`

Verify each subscriber is connected at 0 lag **before reopening Grouper**.

**4i. Smoke test on green:**

`-- [green | mydb | postgres] INSERT INTO penngrouper.upgrade_canary(note) VALUES ('cutover check') RETURNING id; -- fresh id, no conflict`

**4j.** `[Grouper]` start Grouper (now on green/v17); start IIQ.

### 5. Retain old blue

Keep blue for the rollback window, then delete. (Drop `penngrouper.upgrade_canary` afterward, or keep it as a permanent replication heartbeat.)

## Must-haves

- Every table needs a primary key or `REPLICA IDENTITY FULL` (done; PENNGROUPS-682)
- **Drop**`penngrouper_upgrade_slot` on green before upgrading green (1d) -- pre-17 `pg_upgrade` is blocked by it
- Quiet window must have **zero writes** (Grouper + dependents off) so the PITR point aligns with the slot
- Keep blue's `penngrouper_upgrade_slot` retained until cutover
- Sync sequences at cutover (~9, all `id` columns) -- logical replication does not advance sequences
- DDL freeze for the window (Grouper does no DDL under normal operations)
- Shib slot rebind: blue's LSNs don't carry to green; rebind to green's slot, don't reuse an LSN (Garick; validate in test)

## Downtime profiles

| Step | Downtime |
| --- | --- |
| Build (quiet window: slot + PITR alignment) | ~2-4 min write pause (Grouper down) |
| Cutover | ~5-7 min |
| In-place upgrade (alternative) | ~1-2 hours |

## Schema readiness check (re-run before any upgrade)

`-- [blue | mydb | postgres] SELECT n.nspname, c.relname FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace WHERE c.relkind='r' AND n.nspname NOT IN ('pg_catalog','information_schema','pg_toast')  AND NOT EXISTS (SELECT 1 FROM pg_index i WHERE i.indrelid=c.oid AND i.indisprimary)  AND c.relreplident = 'd';`

Any row needs a PK or `REPLICA IDENTITY FULL`.

## Prerequisites

- `rds.logical_replication = 1` on the cluster parameter group (static -- needs a reboot to take effect)
- Automated backups / PITR enabled on blue (required to restore green to the quiet-window point)
- v17 cluster parameter group (with `rds.logical_replication = 1`) created for the green upgrade
- Master password set manually (managed Blue/Green doesn't support Secrets Manager-managed passwords)

## Rollback

- Clean rollback only **before Grouper restarts on green**. After green takes writes, blue diverges -- no clean switch-back without reverse replication.
- Keep old blue for a short period before deleting.

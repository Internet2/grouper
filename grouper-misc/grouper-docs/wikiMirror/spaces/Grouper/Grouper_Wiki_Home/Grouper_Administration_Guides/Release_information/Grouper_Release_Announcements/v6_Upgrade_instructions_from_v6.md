When upgrading from Grouper v6 to another v6 container, this wiki will consolidate all the steps needed to perform that upgrade.

When upgrading from Grouper v4 to v6, also see [v6 Upgrade Instructions from v4](https://grouper.atlassian.net/wiki/spaces/Grouper/pages/28547828/v6+Upgrade+Instructions+from+v4+v5) for additional instructions which must be applied first. Also see the [v5 to v5 upgrade steps](https://grouper.atlassian.net/wiki/spaces/Grouper/pages/28549165/v5+Upgrade+instructions+from+v5).

[v6 release notes](https://grouper.atlassian.net/wiki/spaces/Grouper/pages/28547614/v6+Release+Notes)

> See information on [Grouper Versioning here](https://grouper.atlassian.net/wiki/spaces/Grouper/pages/28544481/Versioning+Support+Policy)

| 2026/11/28 | ALL | ALL | 6.6.0 | Important | [GRP-7596](https://grouper.atlassian.net/browse/GRP-7596) | You have rules with if or then expression language (EL), send email rules with more than the predefined variables, or you set `rules.accessToApiInEl.group` | Only a Grouper sysadmin (wheel or root) can now save, change or delete values of a rule that has if or then EL, through the UI, WS, GSH or the API. Rule EL still runs in the restricted sandbox by default, as in the security release before this one.  If your rules need constructors (new), class objects, or the group, member, membership, subject or rule objects (for example the veto delete membership if immediate membership has attribute value pattern), set `rules.allowUnrestrictedEl = true` in grouper.properties. Without it such a rule fails with an error that names this property.  `rules.accessToApiInEl.group` is no longer used: rules that relied on it need `rules.allowUnrestrictedEl = true` instead. Clear it.  Before turning it on, run the read-only ruleElCheck.gsh (attached to [GRP-7596](https://grouper.atlassian.net/browse/GRP-7596)) and sendEmailRuleTemplateCheck.gsh in GSH as an administrator. Rules saved before only sysadmins could save them also run unrestricted, so delete any they mark REVIEW that nobody you trust wrote. |
| 2026/11/28 | ALL | ALL | 6.6.0 | Medium important | [GRP-7580](https://grouper.atlassian.net/browse/GRP-7580) | You use RabbitMQ messaging with TLS and a trust store (`grouper.messaging.system.<name>.pathToTrustStore` in grouper.client.properties) | Before upgrading, check that the broker certificate names the host Grouper connects to (`grouper.messaging.system.<name>.host`), for example with `openssl s_client -connect <host>:<port>` and look at the certificate subject and subject alternative names. | 2026/11/18 | ALL | ALL | 6.5.1 | Important | [GRP-7585](https://grouper.atlassian.net/browse/GRP-7585) | You use workflow or external subjects | Workflow and external subjects are now off by default. How to tell: workflow may be in use if `select gadn.name, count(*) from grouper_attribute_assign gaa join grouper_attribute_def_name gadn on gaa.attribute_def_name_id = gadn.id where gadn.extension in ('workflowConfigMarker', 'workflowInstanceMarker') group by gadn.name` returns rows or people use the Workflow screens. | 2026/11/18 | ALL | ALL | 6.5.1 | Important | [GRP-7577](https://grouper.atlassian.net/browse/GRP-7577) | You have WS clients that change data with HTTP GET or HEAD | The WS now refuses an operation that changes data when it is sent with HTTP GET or HEAD. Reads with GET still work. A refused call gets HTTP 400 with result code INVALID_QUERY, and the WS log has an ERROR "Refused a WS REST write sent with HTTP GET" naming the WS user and client IP. Clients built on grouperClient or the WS samples send POST or PUT and are not affected.  To find such clients, search the WS access log: `grep -E '"(GET\|HEAD) /grouper-ws/servicesRest/[^"]*wsLiteObjectType=' localhost_access_log.* \| grep -vE 'wsLiteObjectType=Ws(Rest)?(Get\|Find\|HasMember)'`. Change them to POST or PUT. If you cannot do that before upgrading, set `ws.rest.allowWritesWithGet = true` in grouper-ws.properties: it keeps the old behavior and logs a WARN naming each client. Remove it once the clients are changed. |
| 2026/11/18 | ALL | ALL | 6.5.1 | Important | [GRP-7577](https://grouper.atlassian.net/browse/GRP-7577) | WS callers log in with OAuth tokens (the WS authentication class is `edu.internet2.middleware.grouper.ws.security.WsGrouperOauthAuthentication`) | Grouper now checks that a WS OAuth token was issued for Grouper WS. | 2026/11/18 | ALL | ALL | 6.5.1 | Important | [GRP-7572](https://grouper.atlassian.net/browse/GRP-7572) | You use membership requirements (`grouper.membershipRequirement.<id>.attributeName` in grouper.properties) | A membership requirement on a folder is now enforced on groups in all of its subfolders, not only on groups directly in that folder. The job has no dry-run mode.  Before upgrading, list the folders that have a requirement: `select gaasv.attribute_def_name_name, gaasv.stem_name from grouper_attr_asn_stem_v gaasv where gaasv.enabled = 'T' and gaasv.attribute_def_name_name in ('<attributeName 1>', '<attributeName 2>') order by gaasv.stem_name`. If you want to run v6 locally, you can do something like this (change port, version, database url if not on mac): (use a random password, not 'ymxHNQnH0aYgxlcQx1iQ')

```
$ docker run --name postgres -e POSTGRES_PASSWORD=ymxHNQnH0aYgxlcQx1iQ -d -p 5432:5432 postgres:14
$ docker exec -it -u postgres postgres psql
# CREATE USER grouper PASSWORD 'ymxHNQnH0aYgxlcQx1iQ';
# CREATE DATABASE grouper;
# GRANT ALL PRIVILEGES ON DATABASE grouper TO grouper;
# \q
```

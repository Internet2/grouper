# GRP-6930  Provisioner incremental misses population-group events when groupIdOfUsersToProvision is configured by group name

* When a provisioner config sets groupIdOfUsersToProvision to a group name (the colon form, e.g. penn:isc:ts:chatGPT:service:policy:chatGPT_provisionable) instead of a UUID, the per-event handler in GrouperProvisioningLogicIncremental compared esbEvent.getGroupId() (always a UUID) directly to the config string, so flattened MEMBERSHIP_ADD/DELETE events on the population group never matched and addIncrementalEntity was never called.
 * Effect: in entity-only provisioners (selectAllEntities=true, no provisioned target groups, only a population gate) such as chatgpt_prod, the incremental read those events but produced zero inserts; affected users only got provisioned at the next hourly full sync, sometimes a 20+ minute gap.
 * Fix: in GrouperProvisioningLogicIncremental, also compare esbEvent.getGroupName() against the config value, so the population match works whether the config holds a UUID or a name. Mirrors the existing dual-form handling in GrouperProvisioningGrouperDao and GrouperProvisioningConfigurationValidation.
 * Test: new testGithubIncrementalAddToPopulation in GrouperGithubProvisionerTest reproduces the chatgpt scenario (centerGroup → usersAllowGroup, deprovisionGroup, provisionGroup as composite usersAllow MINUS deprovision) with groupIdOfUsersToProvision set by name; asserts the incremental provisions the user when they're removed from the deprovision group, without waiting for full sync. Test fails before the fix and passes after.

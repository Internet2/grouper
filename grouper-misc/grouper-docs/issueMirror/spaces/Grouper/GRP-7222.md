# GRP-7222  Grouper OAuth authorization responses should include the iss parameter

MCP spec revision 2026-07-28 says authorization servers SHOULD include the iss parameter in authorization responses per RFC 9207 ([https://datatracker.ietf.org/doc/html/rfc9207|https://datatracker.ietf.org/doc/html/rfc9207|smart-link] ), and that MCP clients MUST validate a present iss against the recorded issuer before redeeming the authorization code. Grouper's authorization responses carried only code and state, so a client configured with more than one authorization server could not tell which one issued a code, leaving it open to a mix-up attack where a code issued by one server is redeemed at another.



The authorization response now carries iss, on the success redirect, the user-denied redirect, and the generic error redirect. Error responses are included because a client that validated iss only on success would still be exposed to the mix-up this prevents.



The value has to match the issuer published in the authorization server metadata exactly, or a conforming client rejects the response — a wrong value is worse than none. Both are therefore read from a single new accessor, GrouperOAuthStore.retrieveIssuerIdentifier(), rather than being computed separately. That accessor is configuration-only (grouper.ws.url) and deliberately does not derive a URL from the request: the metadata is served by the web services application and the authorization response is sent by the UI application, so a request-derived value could differ between them behind a reverse proxy or on a different context path.



When grouper.ws.url is not configured the iss parameter is left off entirely, which RFC 9207 permits, and a warning is logged once so the disabled hardening is diagnosable. The authorization server metadata keeps its existing request-derived fallback, so discovery behavior is unchanged.



Clients that do not know about iss ignore the extra parameter, so there is no impact on existing clients.

# GRP-7019  Loader jobs should have a config option to choose whether membership inserts or deletes happen first

* Group/membership loader jobs in {{GrouperLoaderType}} currently always remove members before adding members during membership reconciliation (see {{//first remove members}} at line ~3451/3492 and {{//then add new members}} at line ~3531 in {{{}GrouperLoaderType.java{}}}).
 * The remove-before-add ordering is hardcoded and undocumented — there is no comment or config explaining the rationale, and no way to reverse it.
 * The intermediate state matters operationally: with deletes committed first (default {{{}loader.use.transactions=false{}}}), there is a window where the group is smaller than its final size. Downstream provisioners and change-log consumers can react to that transient under-membership.
 * Add a config property (e.g. {{loader.membership.applyOrder}} with values {{deletesFirst}} / {{{}insertsFirst{}}}, defaulting to {{deletesFirst}} to preserve current behavior) to control whether the add phase or the remove phase runs first.
 * Apply the same ordering choice consistently in both the threaded and transactional code paths, and ensure the existing failsafe diff/abort check (lines ~3432–3447) still runs before any changes regardless of order.
 * Add the property to {{grouper-loader.base.properties}} with documentation describing the trade-off (insertsFirst avoids transient under-membership but may briefly over-count; deletesFirst is the historical behavior).
 * Add a comment in the code explaining what the config controls and why each order might be chosen.

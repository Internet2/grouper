# GRP-7355  Sweep the UI jsps for EL method invocations, which do uncached reflection on every evaluation

Calling a method in EL, meaning anything with parentheses such as ${someBean.someMethod(x)} or ${someList.size()}, is not cached the way property access is. It goes through Util.findMethod, which calls Class.getMethods() on every evaluation. Class.getMethods() is required by its contract to return a fresh array of fresh Method objects, so each call allocates in proportion to the method count of the receiving class. BeanELResolver caches property descriptors, so ${bean.foo} is cheap while ${bean.foo(x)} is not, for the same bean and the same underlying method.

Measured cost of Class.getMethods(), using com.sun.management.ThreadMXBean.getThreadAllocatedBytes over 10000 iterations on a 213 method class after warmup: 19616 bytes per call, identical on JDK 11, 17, 18 and 21. That is about 92 bytes per method on the class, so a 600 method utility class such as GrouperUtil costs roughly 55 kB per EL method invocation. Verified in the shipped jars that this is not fixed in newer Tomcat either: javax.el.Util.findMethod in Tomcat 9.0.115 and jakarta.el.Util.findMethod in Tomcat 10.1.5 both call Class.getMethods() with no method cache. Raised upstream as Tomcat bugzilla 70241.

One instance of this was fixed under GRP-7347 in configure.jsp, where ${grouperUtil.containsNewline(guiConfigProperty.propertyValue)} ran once per row. On a screen rendering about 4600 rows it accounted for 251 of 409 allocation samples in a JFR recording, all in Method.copy and Class.copyMethods, and replacing it with a bean property took the request from about 719 MB to about 459 MB allocated. A second expression on the same page, ${guiConfigSection.guiConfigProperties.size() > 0}, was the same pattern on a smaller receiver and was replaced with the empty operator.

This issue is to sweep the rest. A scan of grouper-ui/webapp/WEB-INF/grouperUi2 finds EL method invocations in 35 jsp files, excluding taglib functions like ${grouper:escapeHtml(x)} which use a different mechanism and are fine. The most frequent receivers, with occurrence counts: guiDaemonJobs.get 23, grouperProvisioner.retrieveGrouperProvisioningConfiguration 11, textContainer.retrieveFromRequest 10, grouperProvisioner.retrieveGrouperProvisioningBehavior 7, GrouperUiFilter.retrieveLocale 5, grouperUtil.xmlEscape 4, guiRuleDefinitions.size 2, guiPITMembershipView.getStartTimeLabel 2, guiReportInstance.processSubjects 2.

Prioritise by whether the expression is inside a loop and by how many methods the receiving class has, since the cost is the product of the two. guiDaemonJobs.get at 23 occurrences and the guiPITMembershipView getters look like list rendering and are the obvious first candidates. Note that a jsp fragment can be rendered in a loop without that being visible in the file being edited, which is now the case for configurationFileRowContents.jsp, so do not assume a file without a c:forEach is safe.

Fix pattern: add a getter to the bean and use property access, or for the size case use ${!empty someList}. To verify, take a JFR recording of the screen and check that Method.copy and Class.copyMethods no longer appear in jdk.ObjectAllocationSample events. Trust sample counts rather than the weight field, which extrapolates from single samples and can be badly misleading.

This is now written up in the Grouper developers coding standards page under UI, so new code should not add more of these.

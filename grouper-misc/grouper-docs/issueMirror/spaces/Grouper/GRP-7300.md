# GRP-7300  Allow look ups by displayName / displayExtension in the WS


I can find groups using real names, which aren’t particularly friendly in our case (e.g. {{app:mcomm:123-4567890123-001)}}, but not by display name (e.g. {{app:mcomm:Liams Group}}).  These groups are mirrored copies of LDAP group object (that may eventually become the authoritative versions).

Claude posited…


{quote}why can't i look things up by display extension?  if I have the exact "display" path?{quote}

Because Grouper's WS API doesn't expose a lookup keyed on displayName/displayExtension at all — only on the real identity fields.

Looking at the swagger schema again: WsGroupLookup (what GroupLookup.to_ws() builds, used for exact lookups) only has three fields — name, uuid, idIndex. There's no displayName or displayExtension slot in that request shape. displayName/displayExtension aren't treated as identifiers in Grouper's data model at all — they're cosmetic, computed from the folder hierarchy's own display labels plus the group's displayExtension, and they're not guaranteed unique (as we just saw: two unrelated groups both display as "IAM Matrix Team").

The only WS mechanism that touches displayExtension is wsQueryFilter's general search (FIND_BY_GROUP_NAME_APPROXIMATE), and that's not an exact-match primitive — it's a fuzzy/substring search across several fields at once (name, extension, and apparently displayExtension), which is why one query for "IAM Matrix Team" also pulled back IAM_MatrixTeam_allow and IAM_MatrixTeam_deny as substring hits. There's no FIND_BY_DISPLAY_NAME_EXACT in the queryFilterType enum — the closest exact option, FIND_BY_GROUP_NAME_EXACT, matches the real name/extension fields, not the display ones.

So the disambiguation-by-stem step in resolve_by_display_extension isn't a workaround for a limitation in this SDK — it's compensating for the fact that Grouper WS has no exact "find by display path" operation to begin with.

*Claude:*
Checked exhaustively now — searched every schema for a display* field, every *Lookup schema for a lookup key, and every occurrence of "display" across the whole spec (157 hits). Confirmed:

* No *Lookup schema (WsGroupLookup, WsStemLookup, etc.) has a displayName/displayExtension field anywhere in the API — not just for groups. Attribute defs and stems have the exact same asymmetry: display fields exist only as output properties on WsGroup/WsStem/WsAttributeDefName, never as an input you can look up by.
* Every other appearance of displayExtension in a request body is for writing it (Group Save/Stem Save formData — setting the display extension when creating/updating a group), or for sortString (sorting results you already have).
* The one other place display fields appear in a request is a scope parameter on what looks like a separate lite/GET-style find endpoint, explicitly documented as "search string with % as wildcards will search name, display name, description" — that's the same category as the queryFilter approximate search we already found: a fuzzy scope search, not an exact-match lookup.

So the answer holds up under the exhaustive check: Grouper WS has no request type anywhere that takes a display name/extension as an equality lookup key. Every path to it is fuzzy search.

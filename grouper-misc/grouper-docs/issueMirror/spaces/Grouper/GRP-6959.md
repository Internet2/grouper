# GRP-6959  Drop unused string02..string12 indexes on grouper_change_log_entry_temp to reduce write amplification for ABAC and other high-volume change-log producers

Experiment: drop unused string02..string12 indexes on grouper_change_log_entry_temp to reduce write amplification for ABAC and other high-volume change-log producers

*Description*

Background

{{grouper_change_log_entry_temp}} has 12 single-column secondary indexes, one each on {{string01}} through {{{}string12{}}}. A codebase scan of every non-test Java/XML in {{grouper/src/grouper}} shows:
 * *string01* — 36 references across {{Hib3PIT*DAO}} classes (PIT reconciliation {{NOT EXISTS}} subqueries). Index is actively used.
 * *string02..string12* — zero references. No production code filters the temp table on these columns.
 * Raw-SQL queries against the temp table only filter on {{created_on}} and {{{}id{}}}.

Why the indexes exist on string02..string12 is historical. They were created uniformly with the table; the actual query pattern only ever needed string01. The change-log type metadata makes string01 the primary lookup id of the affected object for every change-log category (membershipId for memberships, groupId for groups, attributeAssignId for attribute assigns, etc.), and the supporting metadata fields in string02..string12 are descriptive payload meant for change-log _consumers_ — which read {{grouper_change_log_entry}} (the real table), not the temp table.

Cost today

Every row inserted into the temp table updates 12 secondary indexes. Every row deleted from it (by the {{changeLogTempToChangeLog}} daemon) updates the same 12 indexes. 11 of those are dead weight: writes with no read benefit. For a 1M-row ABAC backlog that is approximately 22M wasted secondary-index modifications.

Experiment

Drop the 11 unused indexes in a test environment, run a representative ABAC workload (ideally near the 1M-row shape that motivated GRP-6907 and GRP-6956), and measure:
 * Wall time to bulk-insert N rows into {{{}grouper_change_log_entry_temp{}}}.
 * Wall time of the {{changeLogTempToChangeLog}} daemon to drain N rows (with the GRP-6956 page-size already in effect).
 * That PIT reconciliation queries (still using {{{}string01_idx{}}}) remain fast.
 * That no monitoring / DBA / external integrator query depends on the dropped indexes.

If the results are favorable and nothing breaks, follow up with a permanent change: remove the {{CREATE INDEX}} lines from install SQL for postgres/oracle/mysql, add a {{GrouperDdl}} version class entry, add an {{UpgradeTaskVNN}} that runs the DROPs idempotently, and update the AI DDL reference. That permanent change lands under a separate JIRA once the experiment is green.

Safety / risk
 * The 11 dropped indexes are unused by all non-test code in {{{}grouper/src/grouper{}}}. The table is small and short-lived (rows live only between insert and daemon drain), so even if some unknown query did a full scan it would be a few-page scan, not a problem.
 * The PIT reconciliation pattern that needs an index uses {{string01}} and only {{string01}} — left untouched.
 * Fully reversible. The rollback script above recreates each index in seconds on a short-lived temp table.
 * The Grouper schema-compare daemon will report the dropped indexes as "missing" until a matching {{GrouperDdl}} version class change ships. That's expected during the experiment and is the same noise level as any pre-release schema change.

Acceptance criteria
 * Drop script runs cleanly on all three DBs in test.
 * Representative ABAC bulk insert and {{changeLogTempToChangeLog}} daemon run show measurable improvement (or are confirmed flat — either way the indexes are still safe to drop, but a measurable improvement is what justifies a follow-up permanent change).
 * PIT reconciliation queries ({{{}Hib3PIT*DAO.findMissingActivePIT*{}}}) still complete in the same order of magnitude as before.
 * Rollback script verified by re-running it and confirming the indexes are back.

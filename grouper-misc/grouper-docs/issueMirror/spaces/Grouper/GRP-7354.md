# GRP-7354  Add a sysadmin action to clear the config cache on all nodes, alongside the existing clear in this UI

There is no way to tell every node to drop everything it has cached. GrouperCacheUtils.clearAllCaches() exists and is called from GrouperUiRestServlet, GrouperStartup and GrouperDdlUtils, but it only clears the JVM it runs in. GrouperCacheDatabase only exposes per cache name notification, so today the only fleet wide remedy for a node serving something stale is a rolling restart.

Proposal: a Clear all caches on all nodes action, restricted to sysadmins (wheel), that notifies every registered cache name through GrouperCacheDatabase so each node runs its registered clearables, and clears this node locally as well. Sit it near the existing Clear config cache in this UI action added in GRP-7352, but make it clearly a heavier, fleet wide operation rather than a neighbouring convenience.

Why this is worth having now. Cache invalidation is getting more granular: GRP-7346 scopes the config cache notification per config file, GRP-7348 would go further and apply only the changed rows. Granular invalidation has more failure modes than clearing everything, and each of them shows up as one node quietly serving stale data rather than as an error. Recent examples from this area, all of which were silent: GRP-7353, where the text config cache was never invalidated so other nodes served stale text indefinitely; and during GRP-7346 work, a scoped cache name that was not registered would have made customNotifyDatabaseOfChanges silently skip the notification entirely, since it checks for an exact registered name and the prefix fallback in GrouperCacheDatabase is on the receiving side only. An operator escape hatch that does not need a rolling restart is cheap insurance against the next one.

Access: sysadmins only. It clears caches across the whole environment, so every node pays a rebuild, and on a large installation that is not free; it should not be somewhere an ordinary admin lands on by accident.

Things to work out. Whether to notify every registered cache name one at a time or add a single overall signal that means clear everything (grouper_cache_overall already exists as the cheap probe, but it is currently a has anything changed marker rather than a command). Whether to log who pressed it, which seems worthwhile for something with this blast radius. And what the screen says afterwards, since the local node clears immediately while other nodes pick it up on their next poll, so the confirmation should not imply the whole fleet is already done.

Related: GRP-7352 added the per node Clear config cache in this UI action. GRP-7346 and GRP-7348 are the granular invalidation work this is insurance for.

### Chris Hyzer - 2026-09-20T14:14:45.050-0400

Narrowing this to config caches only. The original title said all caches, meaning GrouperCacheUtils.clearAllCaches(), which also flushes ehcache, subject sources, GSH template class loaders and attestation caches. That is a much bigger hammer, its cost has not been measured, and it addresses a different problem (something is generally odd) from the one this was opened for (a node serving stale CONFIG because invalidation is now granular).

Config only is also nearly free to build, because GRP-7346 already left the mechanism in place. GrouperConfigHibernate.clear treats an UNSCOPED cache name as meaning all config, which is the backward compatibility path kept when the notification was scoped per file. So notifying ConfigDatabaseLogic.DATABASE_CACHE_KEY with no file suffix, plus clearing this node directly, makes every other node drop all config objects and all text locales within about five seconds. No new cache name, no new registration, no new clear handler.

It also reads as a clean sibling to what GRP-7352 added: Clear config cache in this UI for this node, and Clear config cache on all nodes for the environment.

If the broader clear everything on all nodes is wanted later it should be a separate issue with its own argument, since the blast radius is different.

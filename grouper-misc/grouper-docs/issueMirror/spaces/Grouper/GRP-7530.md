# GRP-7530  Startup auto-create of built-in objects races across JVMs (ORA-00001 GROUP_NAME_IDX on etc:abacGlobal)

When several Grouper JVMs (UI, WS, daemon) start at the same time after an upgrade that adds a new built-in object, the losing JVM logs an exception from GrouperCheckConfig. Reported on Slack: 6.2.0 to 6.5.0 on Oracle threw "Problem saving group: etc:abacGlobal ... ORA-00001: unique constraint (GROUP_NAME_IDX) violated". The group did get created (by the other JVM), and a redeploy started cleanly. UVA reports the same thing now and then on 7.x upgrades.

Cause: GrouperCheckConfig.checkConfig() runs in every JVM. The DDL step and upgrade tasks are serialized across JVMs by the grouper_ddl_worker lock, but checkFields / checkStems / checkGroups / checkAttributeDefs / checkAttributeDefNames / checkMisc are not. They call *SaveBatch with assignMakeChangesIfExist(false), which is a find-then-insert. Two JVMs can both see an object as missing, both insert it, and the second one hits the unique index. The exception escapes the batch, so the losing JVM also skips every later object in that batch.

Suggested design: one grouper_ddl_worker lock for all of check config, taken only if there is work, and taken lazily.

To be explicit: this does NOT lock on every startup. A normal startup, where every built-in object already exists, only does read-only finds and never reads or writes grouper_ddl_worker, so it pays no lock wait and no 3-second acquire sleep. The lock is taken only on a startup where check config actually has something to create, which in practice means the first boot after an upgrade that adds built-in objects, or a fresh install.

Why lazily and not "find all the work up front": stems on their own could be found up front, since every built-in stem name comes from config and a find by name needs nothing to exist. But the later phases build their save objects from objects the earlier phases return. For example AttributeDefNameSave(attributeDef) uses nameOfAttributeDefToAttributeDef.get(...), and messages code uses stemNameToStem.get(...). On a fresh install or an upgrade those parents don't exist yet, so the later phases' work list can't be fully built before the earlier phases run. Pulling every name out into a separate pre-pass would be a large refactor of GrouperCheckConfig and would drift from the real save code.

1. Run the object phases in order as today: checkFields, checkStems, checkGroups, checkAttributeDefs, checkAttributeDefNames, checkMisc. In each phase, before calling the *SaveBatch, do the read-only find (the batch already does this; expose the missing names or add an up-front Finder call by name).

2. If a phase has nothing missing and the lock isn't held, use the found objects and go on. A normal startup goes through every phase this way: read-only, never touches grouper_ddl_worker, and no 3-second acquire sleep.

3. The first time any phase finds something missing, take the lock using the same pattern as GrouperDdlEngine.runUpgradeTasks(): waitForOtherJvmsOrLockInDatabase(), with a heartbeat while held. Expose it as a small reusable method in GrouperDdlEngine instead of copying it, with a fresh engine instance (new locking uuid, done=false). Hold the lock for the rest of the object phases. One lock per check config.

4. With the lock held, run that phase's batch and all later phases normally. The *SaveBatch calls with makeChangesIfExist(false) re-find before inserting and skip anything that already exists, so the work is idempotent.

5. Release the lock in a finally block at the end of the object phases in checkConfig(): done=true, then join the heartbeat thread, the same as runUpgradeTasks.

6. No loops. If another JVM held the lock, waitForOtherJvmsOrLockInDatabase() waits until that JVM releases it (existing behavior, already bounded by its timeout and stale-heartbeat takeover). Then restart the object phases from checkStems in read-only mode, once. Usually nothing is left, since the other JVM did it. If something is still missing (for example the other JVM was a different version or config), make exactly one more lock attempt. If that attempt also has to wait on another JVM, don't retry again: log one clear ERROR naming the objects that are still missing, skip creating them, and continue startup. The next startup will create them. At most two lock attempts per check config, no unbounded retry.

Notes:
- Don't change GroupSaveBatch and the other batch classes. Other callers use them, and the locking belongs in check config.
- Any other writes the phases make without a missing object (e.g. autocreate group subjects, attribute assignments in checkMisc) should either count as work (take the lock) or be confirmed idempotent and safe to run concurrently.
- checkObjects() and direct callers of checkGroups (tests, line ~2581) should take and release the lock the same way.
- Make sure the lock isn't still held from runDdl / runUpgradeTasks when this runs. They release (done=true, heartbeat cleared) before the object checks start.
- Keep configuration.autocreate.system.groups=false as is: read-only, never needs the lock.

Testing: a JUnit where two or more threads, each with its own root session, call the check-config object path at the same time behind a CountDownLatch, with config that adds new stems, groups (including a new parent stem), attribute defs and names. Assert there are no exceptions, each object exists once, and every thread ends up with all of them. Also assert that when nothing is missing, grouper_ddl_worker is not written (heartbeat and last_updated stay unchanged).

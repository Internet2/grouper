# GRP-7283  RuleTest.testRuleLonghandDaemon fails: rules daemon does not remove an invalid rule from the enabled rule set

RuleTest.testRuleLonghandDaemon fails reproducibly, both inside a suite and run on its own:

{noformat}junit.framework.AssertionFailedError: expected:<0> but was:<1>
  at edu.internet2.middleware.grouper.rules.RuleTest.testRuleLonghandDaemon(RuleTest.java:1694){noformat}

What the test does: creates a longhand rule on a group, confirms it fires, runs the OTHER_JOB_rules daemon and confirms 1 rule is present. It then corrupts the rule with raw SQL (updating grouper_attribute_assign_value.value_string from thisGroupHasImmediateEnabledMembership to thisGroupHasImmediateEnabledMembershipabcksjdf, deliberately bypassing the hook), runs the daemon again, and asserts the rule is gone. It sees 1.

Where the analysis stalls, in case it saves time. RuleEngine.daemon() calls RuleDefinition.validate(), gets a non-blank reason for the corrupted enum, and assigns ruleValid = INVALID: ... on the type attribute assign. But the query behind RuleEngine.allRulesAttributeAssignValueContainers - Hib3AttributeAssignDAO.findByAttributeTypeDefNameId - filters only on aa_attr.enabledDb = T and aa_type.enabledDb = T. It has no ruleValid condition, and nothing in the rules or hooks packages sets an assign disabled. So it is not clear by reading how the count is ever expected to drop to 0. Someone who knows the rule validation lifecycle should confirm whether the daemon is supposed to disable the assign, or whether the query is supposed to exclude invalid rules.

Important: this is NOT specific to v6 and was not introduced by the v6 6.4.0 backport. Every file the test exercises is byte-identical between GROUPER_6_BRANCH and GROUPER_RELEASE_7.4.0: the entire rules package, GrouperAttributeAssignValueRulesConfigHook, GrouperHooksUtils, Hib3AttributeAssignDAO, AttributeAssign, AttributeValueDelegate, and RuleTest.testRuleLonghandDaemon itself. So v7 should reproduce it too - worth confirming against a v7 database, which is the one check not yet done.

Environment where it reproduces: GROUPER_6_BRANCH at 6.4.0 backport, Postgres, schema freshly rebuilt from v6 DDL.

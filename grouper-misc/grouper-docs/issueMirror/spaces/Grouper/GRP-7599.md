# GRP-7599  Explore forbidding (or limiting to wheel) delegated privileges on built-in attribute defs that Grouper acts on as root, e.g. rules

Explore (not scheduled): should delegating privileges on certain built-in attribute definitions be forbidden, or limited to wheel/root?

Some attribute definitions hold config that Grouper later acts on as GrouperSystem, so ATTR_UPDATE (or ATTR_ADMIN) on them is close to root-equivalent. For example the rules attribute defs (etc:attribute:rules:rulesTypeDef and rulesAttrDef): anyone with ATTR_UPDATE on them, plus attribute update on a group or folder, can write rule values through WS, GSH or the API. GRP-7596 (and GRP-7359, GRP-7575 before it) close this with checks in GrouperAttributeAssignValueRulesConfigHook, but each new rule field or write path needs its own check, and assign-level changes (enabling or disabling a rule's attribute assignment) are not covered by a value hook at all.

Questions to explore:

1. Which built-in attribute defs are like this? Candidates: rules, loader (grouperLoader, LDAP loader), scripted group (ABAC), provisioning, GSH template and custom UI config, workflow, attestation, deprovisioning, object types, permission limit defs.

2. For each one, is there a legitimate reason to delegate ATTR_UPDATE or ATTR_ADMIN to a non-wheel subject, e.g. a WS client that creates rules through RuleApi, or a delegated admin for attestation or deprovisioning?

3. Options: refuse the grant (a privilege hook on those defs, like security.types.<type>.wheelOnly), a config allowlist of who may hold it, a configuration review warning when a non-wheel subject has it, or leave it as is and keep relying on per-field hooks.

3a. Rather than forbidding the grant outright, allow delegated assignments that can be shown to be safe, and refuse the rest. For rules that could mean: a non-wheel holder may write a rule only if it matches a predefined pattern, its act-as is the writer or a subject they may act as, every object it names is one they manage at the level the rule uses, and it has no if/then EL or non-predefined email expressions (much of this already exists in RuleService for the UI, and could be shared with the WS/GSH/API path). Each attribute def would need its own definition of safe, and anything that cannot be decided stays wheel only.

4. Upgrade impact: existing grants would need to be found (a query), reported, and possibly revoked by an upgrade task (precedent: UpgradeTaskV9 revokes a broad grant), with a release note since some subjects would lose access.

Not planned for now; this is a placeholder so it is considered later.

# GRP-2473  PSPNG cannot parse Regex containing {}, while contained in ${}

Encountered in grouper-loader.properties.  If a ${group.attribute} is called with additional commands that use regex, an issue occurs if the regex contains \{,}.  

[stackoverflow post |https://stackoverflow.com/questions/717644/regular-expression-that-doesnt-contain-certain-string]details the issue as well in general.

 

Steps to reproduce:

In your provisioner configuration of choice, replace groupCreationLdifTemplate with the following:

 
{code:java}
changeLog.consumer.pspng_campusOrgLdap.groupCreationLdifTemplate = dn:${utils.bushyDn(group.name.replaceFirst("^path:to:(GOOD|BETTER|BEST|BESTER)","ref:$1").replaceFirst("^path:to:GOOD-[a-zA-Z]{0,16}-[0-9]{1,6}:ref","ref").replaceFirst("^path:to:GOOD-[a-zA-Z]{0,16}-[0-9]{1,6}:org:.*:([0-9A-Za-z].*)$","dept:$1"),"CN","OU")}||objectclass:group||description:${group.description}||displayName:${group.displayName.replace(group.parentStemName.toString()+":","")}||gidNumber:${group.idIndex}{code}

### Chad Redman  (unc.edu) - 2019-12-05T22:03:10.416+0000

Yes, ignore my incorrect analysis above :)

GrouperUtil.substituteExpressionLanguage() has special logic to count balanced brackets within ${}, and that logic works. The same template with the same object map works fine in GrouperUtil.substituteExpressionLanguage() that the Provisioner is calling. The PSPNG parser has a feature of nesting ${} expressions, and a ":-defaultProperty" syntax, but other than that could have been passed to the GrouperUtil parser. So yes, the bracket counting logic should be added to the Provisioner, rather than a regexp which inherently can't handle token balancing.

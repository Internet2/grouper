# GRP-7112  SCIM entity update: recover from 409 "uniqueness" on rename by re-linking to the existing account and disposing the orphan

When a provisioned person's userName/email changes and a different, pre-existing target account already holds the new identity, the SCIM PATCH that would rename the linked account is rejected by the target with 409 scimType "uniqueness". Today Grouper rethrows this, so the entity errors on every run -- an error storm -- and never reconciles.

Example (Atlassian Cloud, gpf_atlassianCloud): renaming the linked account from kserpico@example.com to kimberley_serpico@example.com fails because a separate account already owns the new address.

Desired behavior: treat this like the create-side recovery (GRP-7062). On a 409 uniqueness during update, look up the pre-existing account that holds the desired identity, re-link the entity onto it, and dispose of the now-orphaned old account per the provisioner's delete settings (leave / disable-instead-of-delete / delete-if-grouper-created). Always on, no config. Works in both full and incremental sync.

Implementation (as built, Grouper v7):

- GrouperScim2ApiCommands.patchScimUser -- allow 409; on scimType uniqueness, re-fetch the existing account (externalId, then userName) and stash \{oldTargetId -> existingUser} on the shared ScimSettings (do not throw).
- GrouperScim2TargetDao.updateEntity -- forward the stash into a new generic framework collection as a re-link request; mark the entity resolved.
- Generic framework (target-agnostic): new ProvisioningEntityRelinkRequest, an entityRelinkRequests list on GrouperProvisioningData, and a new drainEntityRelinks() in GrouperProvisioningLogic (wired into both provisionFull and provisionIncremental, before storeAllObjects). It re-links via updateEntityLink and disposes the orphan through the standard entity-delete decision (isDeleteEntity), so all delete settings incl. disableEntitiesInsteadOfDelete are honored. INFO logging plus debug-map counters (entityRelinkCount, entityRelinkOrphanDisposedCount) and up to 10 oldId -> newId examples.
- Mock (GenericScim2MockServiceHandler.patchUser) now returns 409 uniqueness on a rename collision.
- Tests (GrouperAwsProvisionerTest2): testAWS2UpdateUserConflictStashesForRelink (API detect+stash), testAWS2FullSyncUpdateConflictRelinksAndDisposesOrphan (full, orphan deleted), testAWS2IncrementalUpdateConflictRelinksAndDisablesOrphan (incremental, orphan disabled). All passing.

Note: only SCIM detection + one forwarding call are target-specific; any future provisioner can reuse the re-link/disposal by detecting its own conflict signal and calling addEntityRelinkRequest(...).

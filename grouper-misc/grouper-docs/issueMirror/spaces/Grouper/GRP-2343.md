# GRP-2343  LdapSystem.performLdapSearchRequest doesn't return any members when group has more than 1500 memberships

We are in patch a72-u43-w7-p9.

LdapSystem.performLdapSearchRequest returns empty list of member when group has more than 1500 memberships.

Our settings in grouper-loader.properties:
{code:java}
ldap.active_directory.searchResultHandlers=org.ldaptive.handler.DnAttributeEntryHandler,edu.internet2.middleware.grouper.ldap.ldaptive.GrouperRangeEntryHandler
ldap.active_directory.pagedResultsSize = 1000
ldap.active_directory.searchResultPagingEnabled=true
ldap.active_directory.searchResultPagingSize=1000
changeLog.consumer.pspng_activedirectory.memberAttributeName = member
{code}
 

Logs like:
Full-sync comparison for psrwi.auckland.ac.nz:Employee/#128662(Existing): Target-subject count: Correct/Actual: 12713/0
Group psrwi.auckland.ac.nz:Employee/#128662(Existing) has 0 extra values
Group psrwi.auckland.ac.nz:Employee/#128662(Existing) has 128662 missing values
 
This issue cause the following code in LdapGroupProvisioner wont be invoked when grouper has members > 1500, and members never get delete from target system
{code:java}
LOG.info("{}: Group {} has {} extra values",
    new Object[] {getDisplayName(), grouperGroupInfo, extraValues.size()});

}
{code}
This issue seems happen after p6.

### Wenlai Wang - 2019-09-30T23:02:03.743+0000

In LdapGroupProvisioner.fetchTargetSystemGroups, it calls getLdapSystem().performLdapSearchRequest to fetch AD groups, this method doesn't return member attribute when group has more than 1500 memberships. 

LdapSystem.performLdapRead is working fine to return all the members. We customized LdapGroupProvision.fetchTargetSystemGroups to call performLdapRead instead of performLdapSearchRequest, it fixed our current problem, but that also disables the AD group bulk search feature.

### Dominique Petitpierre - 2020-09-29T12:24:40.073+0000

In Bert Bee-Lindgren comment above, the cited code line refers to the method performTestLdapRead which probably behaves properly:
 [https://github.com/Internet2/grouper/blob/master/grouper-misc/grouper-pspng/src/main/java/edu/internet2/middleware/grouper/pspng/LdapSystem.java#L236]

But in the method performLdapSearchRequest the object SearchEntryHandlers is not set correctly:

SearchEntryHandlers is first set correctly to RangeEntryHandler (line 741), but then SearchEntryHandlers is set to something else, which effectively removes RangeEntryHandler from the handlers (line 744, cf also [https://code.vt.edu/dfisher/ldaptive/-/blob/master/core/src/main/java/org/ldaptive/SearchRequest.java#L363):]

 

!image-2020-09-29-14-05-23-768.png!

 

Evidence that it causes problems in PSPNG when handling Active Directory groups larger than MaxValRange (1500 by default) was provided on grouper-users: [https://lists.internet2.edu/sympa/arc/grouper-users/2020-09/msg00042.html
 ]and [https://lists.internet2.edu/sympa/arc/grouper-users/2020-09/msg00050.html] (test to show that discrepancies are not resolved by full sync).

 

It is critical because  PSPNG full sync does not do its job: it does not synchronize large Active Directory groups if there is a discrepancy.

The  problem code on lines 744-746 was added on March 3rd 2019, and the compiled LdapSystem class including that change was incorporated in Grouper PSPNG 2.4.0 patch 8 in June 2019. It certainly affects also PSPNG in Grouper 2.5.x because that problem code has not been corrected since.

Here is a proposed fix (original from [https://github.com/Internet2/grouper/archive/grouper_2_4_0-a95-u57-w11-p12.zip).]
 It was tested successfully with Grouper 2.4.0 with the latest patches available (cf. [https://lists.internet2.edu/sympa/arc/grouper-users/2020-09/msg00057.html]).

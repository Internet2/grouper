# GRP-7464  Okta incremental: target id change recalculates every group the user is in, causing multi-hour incremental runs


I cherry picked 7052/7412 and applied them the 7.5.1 release (we see similar behavior in non-cherry-picked 7.8.0)

After GRP-7052/7412, when a user's Okta id changes, incremental flags all of the user's groups for full membership recalc, because the Okta DAO can only retrieve memberships by group. For users in large groups (about 1.27M memberships across 10 groups in QA) this means thousands of Okta API calls and a 2.5+ hour incremental run that blocks the daemon.

*Proposed:* (1) add {{GET /users/{id}/groups}} to GrouperOktaApiCommands, implement {{retrieveMembershipsByEntity}} in GrouperOktaTargetDao, set {{CanRetrieveMembershipsAllByEntity}}. (2) In {{retrieveIndividualTargetMembershipsIfNeeded}}, also run the by-entity branch for entities flagged {{selectAllMemberships}} instead of {{if/else-if}} choosing group over entity; scope so group-only DAOs are unchanged.

*Verify*: GRP-7412 bystander-delete scenario, {{deleteMembershipsOnlyInTrackedGroups}} protecting unmanaged groups, delete-and-recreate against eventually-consistent login search.

## Comments

### Liam Hoekenga - 2026-10-13T13:29:45.299-0400

Supplemental data: where the time goes (QA reproduction, 2026-10-13)

Setup: 7.5.1 with GRP-7052/7357/7412 cherry-picked, Okta provisioner, Oracle (RAC). One user's Okta id changed. The incremental ran 12:00:00 to 13:06:47 (container clock), tookMillis=4007572. Okta DAO capabilities as in the description: canRetrieveMembershipsWithEntity=false, selectMembershipsAllForGroup=true.

WHERE THE 66m47s WENT

* Second reload (reloadGrouperMembershipsAttachSyncTranslateAndIndex, GrouperProvisioningLogicIncremental line 1715, the GRP-7412 pass): batched GrouperProvisioningGrouperDao.retrieveMembers (line 412): about 60 min, about 90%.
* Sync-membership lookup and translate (mostly Java CPU): about 2 min, about 3%.
* Okta target fetch (retrieveMembershipsByGroups): 3m50s, about 6%.
* Compare and store: about 45 s, about 1%.

EVIDENCE

* Provisioner debug log: the reload loaded 1,267,506 Grouper memberships (23 s) and 402,095 members (grouperEntity2Count=402095, retrieveGrouperEntities2Millis=3598001, which is 59.97 min). Okta side: retrieveOktaGroupMembers_calls=1276, 1,267,505 memberships, 3m50s wall. Compare result: 1 insert, 0 deletes. syncObjectStoreCount=402098, queryCount=3697.
* p6spy: 447 executions of the retrieveMembers statement, 900 member ids each (402,095 distinct ids, no repeats), 3,593 s total, average 8.0 s (range 7.0 to 10.8 s), steady for the whole hour (7.4 to 8.7 s per 10 minutes). This accounts for essentially all of retrieveGrouperEntities2Millis.
* Thread dumps every 30 s: the worker was in retrieveMembers:412, blocked on the Oracle socket, in all of about 85 consecutive samples, using about 0.03 s of CPU per interval.
* DBA (gv$sql): the daemon's 900-bind cursor (cxu4rbtaa2pxq) uses plan 1392065553. Instance 4: 1,761 executions, 5.13 s per execution (5.07 s CPU), 1.45M buffer gets per execution. Instance 3: 1,169 executions, 3.68 s per execution, 3.06M gets per execution. Cluster wait is about 0.01 s and I/O about 0 per execution. The same statement and ids run manually from a SQL client (literals) use plan 1289085130 and take 1.0 to 1.5 s with about 600K gets. The final batch (695 ids, a different cursor) took 1.36 s versus 7.0 to 7.7 s for the 900-id batches just before it. Cursor figures are lifetime averages across runs, not just this run.

WHAT THIS SUGGESTS

* The cost is Grouper-side and scales with the number of members in the user's groups, not with Okta calls (Okta was about 6% here). *_The reload ends up comparing about 1.27M memberships on each side to apply one insert._*
* Retrieving memberships by entity (GET /users/{id}/groups), as proposed, would avoid the brp for recalc, and so would avoid this reload as well as the per-group Okta fetches.
* Separately, the 900-bind statement's plan is about 5 times more expensive than the plan a literal run gets. Even so, 447 batches of about 1.2 s would still be about 9 minutes for one user's id change.

NOT YET KNOWN

* What plan 1392065553 actually is, and why the bind cursor picked it (DBA is pulling dbms_x
* About 3 s per batch of the 8 s client-side time is not accounted for by the DB's average elapsed time (3.7 to 5.1 s). The log shows it is inside executeQuery, not in row fetching.
* Whether a plan baseline or statistics change brings the batches down to about 1 s.

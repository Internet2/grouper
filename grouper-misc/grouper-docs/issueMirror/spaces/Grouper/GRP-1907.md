# GRP-1907  possible index improvement to GROUP_SET

Tracking down a problem with our custom UI led to a query that was hanging. The Oracle tuning advisor recommended the following index be created:

{{CREATE INDEX "GROUPERTST"."IDX$$_1A2830001" ON "GROUPERTST"."GROUPER_GROUP_SET" ("MEMBER_ID", "MEMBER_FIELD_ID") }}

This query uses GROUPER_MEMBERSHIPS_V which walking back uses GROUPER_MEMBERSHIPS_ALL_V. Looking at the query execution plans, it looks like the new index helps with 

{{where ms.owner_id = gs.member_id and ms.field_id = gs.member_field_id;}}

at the end of GROUPER_MEMBERSHIPS_ALL_V

 

We have made extensive use of GROUPER_MEMBERSHIPS_V for years without issue (including the hanging query has been in place for years) suggesting that a recent database upgrade took the database down a road of choosing a poor way to execute that query. The index seems to help it pick the much quicker way at least. I can't speak to performance improvements pre/post unfortunately since we have no data prior to this issue.

We are running on Oracle 12.2. Let me know if there are any other details about the environment that would help in determining if this index would be helpful to others too or not.

### cer28 - 2018-10-08T16:01:25.595+0000

We just discovered the same performance issue after upgrading last week. General subject searches for non-wheel users are timing out after 30 seconds. The problem isn't the LDAP subject lookups. It's the secure groupFinder lookup that takes 20 seconds to find no groups matching a string pattern, and then another 20 seconds to get a count of that zero.

 

The bad query look like:

 

  select distinct group0_.id as col_0_0_ from grouper_groups group0_ cross join grouper_memberships_all_v membership1_ where membership1_.owner_group_id=group0_.id and (membership1_.field_id in (

      '2b1adc3430514462a816d7a38328ff38', '739079c2541a4651a31db8bbf26882ad',

      '4e119b2e2f264e4ebf126713a3fb50f5', '8e84d9e72a984a37967cbb889319e8dc',

      '1d86d9c855804990850a4e1ba44c7776', '025402e07ae3462e8f8382aaab8b2acc',

      'e9eadd91f7e647d69d815f10e91b640d', '8fa7e74fbd8047ba9c461732f1cf2525')) /* admins, optouts, readers, optins, updaters, viewers, groupAttrReaders, groupAttrUpdaters */

      and (membership1_.member_id in ('a25d179025df474ca335eb85c1892be6', '453443b2c6cf40ddb0e3ed6ac5b760e6')) /* GrouperAll, 71074xxxx*/

      and membership1_.immediate_mship_enabled='T' and (group0_.id='%cer37' or lower(group0_.name) like '%%cer37'

      or lower(group0_.alternate_name) like '%%cer37' or lower(group0_.display_name) like '%%cer37' or lower(group0_.description) like '%%cer37') and (group0_.type_of_group in ('role', 'group'))

 

Despite the wildcard, the group lookup is the fastest part and returns zero rows very quickly. But the query plan thinks there is a low cost to doing the membership lookup first and looping through it. However, GrouperAll has 28,000 memberships, so the statistics are wrong. This is just after recalculating them.

Our solution that is working so far is to add histogram data to the membership.member_id:

{{begin}}
{{  DBMS_STATS.GATHER_TABLE_STATS (ownname => 'GROUPER', tabname => 'GROUPER_MEMBERSHIPS', method_opt => 'FOR COLUMNS MEMBER_ID'}}
{{);}}
{{end;}}
{{/}}

The original query then went down from 20 seconds to 0.17.

# GRP-6870  Azure provisioner incremental sync should handle 404 when retrieving groups for a user that no longer exists in Azure

When a user is removed from Azure/Entra but still has a cached Azure object ID in Grouper, the incremental sync calls {{POST /users/\{id}/getMemberGroups}} which returns a 404. The {{retrieveUserGroupsHelper}} method only expects 200 or 429 response codes, so the 404 causes a RuntimeException that kills the incremental sync run.

This results in incremental sync runs taking 6-10 seconds instead of sub-1-second, effectively breaking incremental provisioning for 24+ hours until the full sync cleans up the stale cache entries in {{{}grouper_sync_member{}}}.

Fix: Add 404 to the allowed return codes in {{retrieveUserGroupsHelper}} (consistent with {{executeGetMethod}} which already allows 404). When a 404 is received, log it and return an empty result set — the user doesn't exist in Azure so they are a member of no groups. The incremental sync continues processing the remaining changes normally.

Reported by Temple University on the Grouper Slack channel.

# GRP-7522  Provisioners use the target's rate-limit headers to recover from a 429 faster (and optionally pace)

Provisioners that call cloud APIs only react to throttling. They wait for a 429 or 503, sleep (60s by default, growing with each retry), and try again. They never look at the rate-limit headers that many services send on every response.

Evidence (Okta full sync, UMich, 2026-10-23)

* The GET /api/v1/groups/{id}/skinny_users quota is 600 per minute. In a full sync, the group-member fetch phase makes about 3,767 calls, covering about 3.74M memberships. The phase took about 11 minutes in this run.
* Okta's rate limit dashboard shows 4 violations for that endpoint during the run, all from one IP. Usage peaks at 600 per minute, separated by about a minute at zero. That matches the 60s retry sleep with all threads stalling together.

Limits of this evidence (added after review)

* Other consumers. The Okta quota is shared by everything in the org that calls this endpoint. That includes other Grouper nodes and jobs, other provisioners, and non-Grouper clients. Our evidence only shows that this run hit the limit. It doesn't show that this run was the only consumer. The dashboard shows one IP for the violations, but it doesn't tell us who else used the budget.
* Burst limits. Okta may also enforce burst or dynamic limits. These are not reflected in the x-rate-limit-* headers. A client can see plenty of remaining and still get a 429.

Current behavior (code)

* GrouperHttpClient (retry loop around lines 1079–1145) retries on 429, or on whatever the caller's throttling callback returns. It honors Retry-After. It does not read any x-rate-limit-* / RateLimit-* header.
* GrouperOktaApiCommands (around lines 84–97) treats 429 and 503 as throttled and sets a 60s retry sleep.
* Other targets handle throttling on their own. Duo, Adobe, Google, Box, CCure and TeamDynamix use the shared client's callback and retry settings. Azure and Smartsheet have their own retry logic.
* Nothing in the provisioning framework (app/provisioning) refers to throttling.

Other services use similar headers, with variations

The convention is common but not a standard. Okta and Twitter/X use x-rate-limit-_. GitHub and Discord use X-RateLimit-_. An IETF draft defines RateLimit-* without the X- prefix. Some services send only Retry-After. reset can be an epoch timestamp (Okta) or a number of seconds until the window reopens. The limit's scope can be per endpoint, per token or per IP. Any shared code has to be opt-in per target and let the target say which headers to read and what reset means.

Proposed approach (to be refined)

Reactive handling stays the safety net in every case. Pacing is only an optimization on top of it.

# Recover from a 429 using the headers (low risk). On a 429, sleep until x-rate-limit-reset (plus a small margin) instead of a fixed 60s that grows with each retry. This is correct whether the 429 came from other consumers or from a burst limit, because it only uses what the server said. It also lets the threads resume as soon as the window reopens, not up to 60s later.
# Log and report the throttle count in the provisioner logs and metrics, so throttling is visible after a run. Include the number of 429s, the total seconds slept, and the lowest remaining seen.
# Optional pacing, off by default. Per target, when remaining falls below a configurable threshold, sleep until reset. Coordinate across the threads in a JVM, so the threads don't stall together. Treat the header as a hint, since other clients and nodes spend the same budget. Okta would be the first target. The other targets could opt in later, one at a time.
# Measure before enabling pacing. Pacing could slow a sync with no benefit in two cases:
#* A burst limit trips regardless of remaining.
#* Other consumers drain the bucket whether or not we back off.
# Before turning pacing on for a target, compare run time and 429 count with and without it. If a run gets slower with no drop in 429s, leave pacing off for that target.
# Alternative to consider. Cap concurrency on the member-fetch phase, as a config option. It reduces the 429s without depending on headers.

Open questions

* Who else calls skinny_users or groups endpoints in the org, and how much of the 600 per minute do they use at the time of the sync? Okta's System Log or rate limit dashboard may break usage down by client.
* Does the org's Okta plan enforce burst limits? What are they?
* How many Grouper nodes or jobs share the quota at once?

Acceptance criteria

* After a 429, the Okta provisioner resumes at the reset time from the response, not after a fixed 60s.
* Throttle count and total sleep time show in the provisioner log or metrics for each run.
* With pacing enabled, a full sync of about 3,767 member-fetch calls has fewer 429s and no longer a run time than today. This is measured and recorded on the ticket, not assumed.
* No behavior change for targets that don't opt in.

### Gail H Lift - 2026-10-25T14:55:05.551-0400

The are some things that Claude may not know:

Any process within your Okta tenant that calls the same api, including processes running within Okta workflows and jobs, counts against the rate limit. That can make it had to guess how close to the limit you really are.

When you have burst rates enabled, the rate limits returned by the api calls do NOT reflect that. The first tier of burst limits seems to be 2x (yes, the Okta provisioner can hit that too). A change to the provisioner to stop before the rate limit would prevent it from benefiting from the burst limit. We would need an ‘off switch’ for this proposed change.

When you request higher rate limits from Okta, you need to be frequently hitting the rate limit. Otherwise the vendor won’t believe you need the increase.

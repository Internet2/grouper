# GRP-7388  Review UI, WS and MCP entry points that look up a folder from a request and confirm they check folder visibility

Follow up to GRP-7336 and GRP-7387. The static StemFinder finders (findByUuid, findByName, findByIdIndex, findByUuids, ...) are lookups, not authorization. GRP-7336 was one screen (the visualization screen) that looked up a folder from a request parameter and showed it without checking the user can see it. Any other entry point doing the same has the same leak.

Review every entry point that turns request input into a folder and shows or returns it, and confirm each checks visibility:

* UI controllers (UiV2*) that read stemId, stemName, stemIndex, parentStemId or similar and call StemFinder directly. Code that goes through {{UiV2Stem.retrieveStemHelper}} is fine, it checks StemContainer.isCanViewPrivileges().
* Web services: {{WsStemLookup}} and operations that take a stem lookup (find stems, stem scoped queries): do they return folder details to a caller who cannot see the folder?
* MCP tools that take a folder name or id (e.g. folder_find, group_find with a stem scope).

Fix any that do not check with {{PrivilegeHelper.canViewStemOrObjectInside(subject, stem)}} (added in GRP-7387, same rule as the folder screen), or route through retrieveStemHelper. When a folder is not visible, answer the same as not found so the response does not reveal which. Add a unit test per fix where practical.

This is hardening: no second leak is confirmed yet.

# GRP-7106  SCIM provisioner diagnostics: verify each configured match/search attribute resolves the object in the target

*Background*

SCIM provisioning diagnostics confirms that objects can be selected from the target, but it does not verify that each attribute the provisioner is configured to _match_ on actually resolves an object via the target's filter. So a match/search attribute that the target does not support filtering by (or does not return uniquely) is invisible until it causes duplicate creates or missed matches at sync time.

This is the retrieve-side complement to the schema cross-check: the schema cross-check confirms an attribute exists and is writable; this confirms the target actually resolves a filter on it. Verified against a live CrowdStrike SCIM tenant that {{filter=externalId eq "..."}} returns the object, so a target really can support matching by externalId - diagnostics should prove that per configured attribute rather than assuming it.

*Change*

Add a "Search/match attribute verification (SCIM filter)" section to provisioning diagnostics, run after the diagnostic entity/group is selected from the target. For the diagnostic entity and group it looks each one up by every configured match/search attribute and reports whether the target's filter returns the same object:
 * Entities: {{id}} and {{userName}} (always), plus the configured entity search attributes (e.g. {{{}emailValue{}}}, {{{}externalId{}}}).
 * Groups: {{id}} and {{displayName}} (always), plus the configured group search attributes (e.g. {{{}externalId{}}}).

Per attribute the report shows:
 * *Works* - the filter returned the same object.
 * *Does not resolve* - the target returned nothing for that filter (matching on it will not work).
 * *Warning* - the filter returned a different object (not unique) or the lookup threw an error.
 * *Skip* - the target object has no value for that attribute to look up by.

It reuses the same {{retrieveScimUser}} / {{retrieveScimGroup}} calls the provisioner uses to match (mapping {{emailValue}} to the configured email filter strategy), so it exercises the real matching code path.

New pieces:
 * {{GrouperProvisioningDiagnosticsContainer.appendScimSearchAttributeVerification}} plus per-attribute helpers, wired into the diagnostics run after the target entity/group select.
 * Test that provisions an entity with {{externalId}} set and configured as the entity search attribute, then asserts diagnostics reports that both {{externalId}} and {{userName}} resolve the entity.

*Failsafe*

Best-effort and fully self-contained: the section is wrapped in try/catch/finally, and each individual lookup is wrapped as well, so a target that does not support a filter, or any error, degrades to a note rather than affecting the rest of the diagnostics run. When there is no diagnostic entity or group in the target, the section emits a note and makes no lookups.

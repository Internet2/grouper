# GRP-7272  WS: findGroups with includeGroupDetail throws RuntimeException when the caller cannot VIEW a composite factor group

A web service caller that requests includeGroupDetail on a composite group gets an EXCEPTION result and HTTP 500 if it is not allowed to VIEW one of the two factor groups. Being ADMIN on the composite owner while having no privilege on a factor is a normal privilege arrangement, so the whole request should not fail.

Composite.getLeftGroup() and getRightGroup() do a canView check and throw GroupNotFoundException when the session subject cannot VIEW the factor. WsGroupDetail catches that exception around the block that sets the left and right groups, but rethrows it as a RuntimeException with the comment saying this means something bad is happening. It is not something bad, it is exactly this privilege case.

Reproduce with grouperClient, as a subject that is ADMIN on the composite owner and cannot VIEW at least one factor. The group looked up has to be the composite OWNER, since the block is gated on group.hasComposite(), and includeGroupDetail is what makes the WS build a WsGroupDetail at all:

{noformat}java -jar grouperClient.jar --operation=findGroupsWs --groupNames=some:folder:compositeOwner --includeGroupDetail=true --debug=true{noformat}

On an unpatched server the response is HTTP 500 with X-Grouper-resultCode EXCEPTION and this in the resultMessage. Confirmed against a running 7.4.0 web service, not just read off the source:

{noformat}java.lang.RuntimeException: edu.internet2.middleware.grouper.exception.GroupNotFoundException: Cant view group: <uuid of the hidden factor>
    at edu.internet2.middleware.grouper.ws.coresoap.WsGroupDetail.<init>(WsGroupDetail.java:210)
    at edu.internet2.middleware.grouper.ws.coresoap.WsGroup.<init>(WsGroup.java:211)
    at edu.internet2.middleware.grouper.ws.coresoap.WsGroup.convertGroups(WsGroup.java:92)
    at edu.internet2.middleware.grouper.ws.coresoap.WsFindGroupsResults.assignGroupResult(WsFindGroupsResults.java:116)
    at edu.internet2.middleware.grouper.ws.GrouperServiceLogic.findGroups(GrouperServiceLogic.java:856){noformat}

Fix: give each factor its own try/catch, log a warning, and leave the unviewable factor out of the detail rather than failing the request. That mirrors how GrouperMcpFindGroups already handles the same call, and how the UI handles it (GuiGroup.getCompositeOwnerText and the Show composite factors block in RelationGraph both catch and degrade).

Related: GRP-7270 covers the same root cause on the UI side (group summary tab, edit composite screen, and the relation graph). This issue is the grouper-ws half, split out so the WS change can be committed on its own.

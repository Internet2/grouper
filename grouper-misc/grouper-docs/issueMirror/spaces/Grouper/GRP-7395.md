# GRP-7395  Config delete notified other JVMs before it committed, so a node polling in between kept the deleted value

h3. Root cause

Config deletes notified the other JVMs before the delete was committed. Both keys in the timeline were removed in the UI, i.e. deleted (grouper_pit_config shows grouperDataProviderDefault.readOnly = true ending at 06:39:58.358 and the delete row at 06:39:58.361). GrouperConfigHibernate.delete() used READ_WRITE_OR_USE_EXISTING, so the UI delete joined the outer transaction in DbConfigEngine. delete() then called updateLastUpdated(), which writes grouper_cache_instance and grouper_cache_overall through GcDbAccess on its own connection and commits immediately. The outer transaction only committed later, after configurationFileItemDeleteHelper rebuilt grouper.properties (configExistsNotInBaseOrDatabase) and cleared the cache again.

A JVM whose 5 second GrouperCacheDatabase poll landed in that window saw the notification, dropped its config, reloaded from the database where the row was not yet deleted, got the old value back, and recorded the notification as seen, so it never reloaded again until the next notification or periodic refresh. That is the WS node here; the daemon polled after the commit. It is timing dependent and not specific to the GRP-7346 scoped names: an unscoped notification sent by a delete had the same ordering. Updates and inserts were not affected, since saveOrUpdate() already used READ_WRITE_NEW and committed before notifying.

The receiving side was checked and works: in a plain JVM, a scoped notification for a directly changed grouper_config row was picked up in about 6 seconds and an unscoped one in about 5 seconds (checkIncrementalAfterSeconds = 5), with the update checks at 600 seconds so only the notification could explain the pickup. The MCP admin_config_search regex mode reads GrouperConfig.retrieveConfig(), the same live object, so the WS observation was accurate.

h3. Fix

GrouperConfigHibernate.delete() now uses READ_WRITE_NEW, like saveOrUpdate(), so the delete is committed before updateLastUpdated() notifies. Trade off: a caller's transaction that fails after the delete no longer rolls the delete back (same as saves already behaved).

h3. Original report

After a config edit in the UI, a PennGroups prod WS node kept serving the old grouper.properties values for about 2.5 minutes, while the daemon nodes picked the change up within seconds. The per-file cache notifications from GRP-7346 were written, so the problem looks to be on the receiving side of some nodes.

Timeline (2026-09-28, 7.6.0, prod): grouperDataProviderDefault.readOnly and otherJob.grouperLoaderJexlScriptFullSync.jexlDaemonsReadonly were removed in the UI. grouper_cache_instance got custom__edu.internet2.middleware.grouperClient.config.db.ConfigDatabaseLogic.databaseConfigs____grouper.properties and ...____grouper-loader.properties at 06:39:58. The daemon nodes acted on it: OTHER_JOB_pennperson_dataProvider_incremental (runs every 15 seconds) logged READONLY MODE through 06:39:55 and not from 06:40:10. The WS node (live config read via ConfigFileName.getConfig(), the MCP admin_config_search regex mode) still returned grouperDataProviderDefault.readOnly = true at 06:40:09, 06:41:37 and 06:42:01, and was correct only after an unscoped ...databaseConfigs notification at 06:42:31 (clear config cache on all nodes).

Both WS and daemon run GrouperStartup, which calls GrouperConfigHibernate.registerDatabaseCache() (registers the base name and one name per ConfigFileName) and GrouperCacheDatabase.startThreadIfNotStarted(), so startup does not explain the difference. Places to look: whether the GrouperCacheDatabase polling thread is running in the WS webapp; GrouperCacheDatabase.clearCacheFromDatabase for the scoped name (exact lookup, then prefix fallback); GrouperConfigHibernate.clear() -> clearConfigsInMemory(configFileName) -> ConfigDatabaseLogic.clearCache(false) and ConfigPropertiesCascadeBase.clearCacheThisOnly(configFileName), and whether that leaves a stale ConfigPropertiesCascadeBase object for the WS JVM (e.g. a different cache key or hierarchy).

Reproduce: in one JVM, start Grouper, read a grouper.properties key, change its value directly in grouper_config (simulating another node), then call GrouperCacheDatabase.notifyDatabaseOfCacheUpdate with the scoped name and updateLastUpdatedNanos=false so this JVM also receives it. Poll the value every second and log when it changes, then repeat with the unscoped name. Run it in a WS or UI webapp as well as a plain JVM.

Workaround in PennGroups prod until fixed: grouper.config.secondsBetweenFullRefresh = 120, grouper.config.secondsBetweenUpdateChecks = 120, loader.config.secondsBetweenUpdateChecks = 120. Related: GRP-7393 (MCP config search Lucene index not refreshed on config change).

# GRP-7551  Entity attribute provisioning full sync does not re-add membership values missing from target when in_target is T

Originally reported by: Dominic Sanchez <[dominics@example.com|mailto:dominics@example.com]>

Reportedly affects versions: 4.17.7 - 4.26.0, 5.17.2+, 6.x, 7.x (regression from [https://todos.grouper.internet2.edu/browse/GRP-6081|https://todos.grouper.internet2.edu/browse/GRP-6081|smart-link])

h3. Summary from reporter

{quote}Our LDAP has a value called ucIsMemberOf on entities. The full provisioner run of this is supposed to reconcile this multi-valued attribute, but it does not. To repro I just remove a random ucIsMemberOf value from a test account that has been sync'd with grouper already via full run, then run the full run again. It should re-add it, but it does not. This bug appears to have been introduced by  GRP-6081 which trusts the sync tables over the LDAP souce. It's only for entity provisioner stuff, not groups I think.{quote}

h3. Description

For an entityAttributes provisioner whose membership value comes from a group attribute value cache (e.g. {{entityMembershipAttributeValue = groupAttributeValueCache0}}), if a value disappears from the target outside of Grouper (entity deleted and recreated, or value removed by another process), the full sync does not add it back while {{grouper_sync_membership.in_target = 'T'}}. The incremental does not re-add it either. Only a member sync message (UI "Fix entity in target") restores it.

h3. Cause

# {{GrouperProvisioningGrouperSyncDao.processResultsSelectMembershipsFull}}: in the entityAttributes branch, in_target is only reset from the selected target values when {{isSelect()}}, which only the incremental sets. After a full sync select, in_target stays T for values that are not in the target.
# [https://todos.grouper.internet2.edu/browse/GRP-6081|https://todos.grouper.internet2.edu/browse/GRP-6081|smart-link] added a check in{{GrouperProvisioningCompare.compareAttributeForUpdateValueMembershipOnlyDeleteBeforeAdd}}: {{if (GrouperUtil.equals(value, oldValue)) return false;}}. With (1), this suppresses the insert of an unchanged value that the full sync just saw is missing.

Before 4.17.7, the full sync added missing values regardless of in_target, so (1) had no visible effect.

h3. Steps to reproduce

# Configure an LDAP entityAttributes provisioner with {{groupAttributeValueCache0}} (source grouper) as the membership value
# Add a subject to 2 provisionable groups and run the full sync twice. Both values are in LDAP and in_target is T.
# Remove one value directly in LDAP
# Run the full sync

*Expected:* the value is re-added
*Actual:* the value is not re-added; the sync membership still has in_target T

h3. Proposed fix

In {{GrouperProvisioningCompare}}, when the compare is working from values actually selected from the target for that membership ({{isSelectResultProcessed()}}), insert an unchanged value that is missing instead of skipping it. Rename handling (value changed) is unchanged.

{code:java}// new overload, existing 3-arg method delegates with false
public boolean compareAttributeForUpdateValueMembershipOnlyDeleteBeforeAdd(ProvisioningUpdatable provisioningUpdatable,
    ProvisioningAttribute provisioningAttribute, Object value, boolean valueKnownMissingFromTarget) {
  ...
  if (GrouperUtil.equals(value, oldValue)) {
    return valueKnownMissingFromTarget;
  }
  ...
}
// at the 3 call sites (multi-valued and single-valued targetAttribute == null branches, recalc inserts loop)
boolean valueKnownMissingFromTarget = provisioningMembershipWrapper != null
    && provisioningMembershipWrapper.getProvisioningStateMembership().isSelectResultProcessed();{code}

Changing (1) instead (resetting in_target when {{isSelect() || isSelectResultProcessed()}}) breaks the GRP-6081 rename tests (the old value is left behind), so the fix is in the compare.

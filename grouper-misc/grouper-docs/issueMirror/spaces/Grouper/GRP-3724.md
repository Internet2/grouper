## Comments

### Chris Hyzer - 2021-12-10T20:56:15.084+0000

The Java version we have is not susceptible to the ldap vulnerability which is the published one.  If someone went through the source code of Grouper and our libraries there is probably another one.  So, that is good but not complete.

Tomcat uses the affected log4j, so to be sure, you need to use 2.5.59.1+ or 2.6.5.1+. 

If you want to not upgrade the container and set a system property, do this (see link below about this being discredited):
{code:java}GROUPER_EXTRA_CATALINA_OPTS=-Dlog4j2.formatMsgNoLookups=true {code}
If you want to swap jars, feel free
{code:java}[tomcat@04a541055e66 bin]$ ls /opt/tomee/bin/log4j-*
/opt/tomee/bin/log4j-api-2.13.1.jar  /opt/tomee/bin/log4j-core-2.13.1.jar  /opt/tomee/bin/log4j-jul-2.13.1.jar {code}
Use 2.15.0 on those...

[https://repo1.maven.org/maven2/org/apache/logging/log4j/log4j-core/2.15.0/log4j-core-2.15.0.jar]

[https://repo1.maven.org/maven2/org/apache/logging/log4j/log4j-api/2.15.0/log4j-api-2.15.0.jar]

[https://repo1.maven.org/maven2/org/apache/logging/log4j/log4j-jul/2.15.0/log4j-jul-2.15.0.jar]

Just remove the old ones (2.13), and copy the new ones in (2.15)

### Andrew Morgan - 2021-12-13T06:48:06.928+0000

[~ryan.larscheidt@example.com] I noticed the same thing just now.  After a lot of digging, I discovered that the /usr/local/bin/librarySetupFilesTomcat.sh script has a function setupFilesTomcat_log4j() that runs:
{code:java}
rm -f /opt/tomee/bin/log4j-*
cp /opt/tier-support/log4j_fix/*.jar /opt/tomee/bin/
{code}
The fix is applied whenever that script is called, presumably only when the container is started with an entrypoint that needs Tomcat.  Maybe the release notes can be clarified so that it is clear when the fix is applied.

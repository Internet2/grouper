# GRP-7100  Provisioning: `retrieveAllData()` bulk member retrieval is single-threaded

I think that Claude figured out the performance issue that U-M is having with the okta provisioner.  Note, this should be fixed as a generic feature in the provisioning framework, not Okta specific.  Lets discuss if it is not straightforward.  It should use the number of threads configured for the provisioner.  If it needs to be provisioner specific then we need to also add in provisioners too.

 

 
----
 h2. Okta connector: {{retrieveAllData()}} bulk member retrieval is single-threaded

*Type:* Bug / Performance
*Component:* provisioning / Okta connector
*Affected branch:* {{GROUPER_7_BRANCH}} (verified against current source)
*Environment observed:* Grouper 7.2.1 in production; reproduced in QA
h3. Summary

{{GrouperOktaTargetDao.retrieveAllData()}} fetches group members in a plain sequential {{for}} loop with no {{GrouperCallable}} or executor, so a full sync with {{selectAllGroups = true}} is pinned to a single thread regardless of {{{}threadPoolSize{}}}. On a tenant with ~105K groups, this makes the target-read phase ~26 hours (~85% of total run time).
h3. Steps to reproduce / observed behavior

Full sync of {{Okta_MCOMM_UserGroups}} with {{{}selectAllGroups = true{}}}, threadPoolSize=5. Measured across three runs (source logs on file):
||Run||Env||{{selectAllGroups}}||Read path||{{retrieveOktaGroupMembers}}||Effective threads||
|{{w05h3caa}}|PROD|true|{{retrieveAllData}}|111,644 calls / 25.6h thread-time / 29.9h wall|*1.00×*|
|{{w07kzrr5}}|QA|true|{{retrieveAllData}}|79,304 calls / 12.5h thread-time / 14.6h wall|*1.00×*|
|{{w1bvaloh}}|QA|false|individual (threaded)|76,330 group + partial member calls|*7.00×*|

Effective threads = API thread-time ÷ phase wall-clock. Same provisioner, same tenant, only the flag changed between the last two — reads went from 1× to 7×.
h3. Root cause (in the source)

{{{}grouper/src/grouper/edu/internet2/middleware/grouper/app/okta/GrouperOktaTargetDao.java{}}}, method {{retrieveAllData()}} (approx. lines 145–229). The member-fetch loop (approx. lines 180–193):
{code:java}List<GrouperOktaGroup> grouperOktaGroups = GrouperOktaApiCommands.retrieveOktaGroups(...);
// ...
for (GrouperOktaGroup grouperOktaGroup : grouperOktaGroups) {
    Set<String> groupMemberIds =
        GrouperOktaApiCommands.retrieveOktaGroupMembers(..., grouperOktaGroup.getId());
    for (String groupMemberId : groupMemberIds) {
        // add to shared targetMemberships list
    }
    GrouperOktaProvisioningTargetNativeSync.captureMembershipsForGroupForCurrentProvisioner(
        grouperOktaGroup.getId(), groupMemberIds);
}
{code}
No {{{}GrouperCallable{}}}, no executor, no batching. The framework adapter invokes it as a single blocking call ({{{}GrouperProvisionerTargetDaoAdapter.java{}}} approx. line 748: {{{}this.wrappedDao.retrieveAllData(targetDaoRetrieveAllDataRequest){}}}).
h3. Why the work is parallelizable
 * {{retrieveOktaGroups(...)}} returns a fully-materialized {{List<GrouperOktaGroup>}} — it runs its own pagination loop to completion and returns the finished list before the member loop begins.
 * Each iteration of the member loop needs only one input it already holds: the group's ID. The call for group A does not depend on the result of group B. The per-group calls are independent units of work, keyed by group ID.
 * The framework already threads this identical Okta call on the other path. {{GrouperProvisionerTargetDaoAdapter.retrieveMembershipsByGroups()}} (approx. lines 1482–1568) builds one {{GrouperCallable}} per group and submits them to {{retrieveExecutorService()}} — a fixed thread pool sized by {{threadPoolSize}} ({{{}GrouperProvisioner.java{}}} approx. lines 104–142, default 5).
 * The sibling Okta provisioner ({{{}selectAllGroups = false{}}}, same PROD tenant) measured ~3.8× on this exact call. The QA flag-flip measured ~7.0× on the same call. So the endpoint tolerates concurrent reads and the framework already has the plumbing.

h3. Suggested fix

Parallelize the member-fetch loop in {{retrieveAllData()}} the same way {{GrouperProvisionerTargetDaoAdapter.retrieveMembershipsByGroups()}} already does: build one {{GrouperCallable}} per group (or per batch), submit to {{{}retrieveExecutorService(){}}}, and synchronize only the small result-collection step. The adapter's {{synchronized(...)}} blocks (approx. lines 1509 and 1538) show the existing pattern for the shared response object.

Points that need care under concurrency:
 * Shared collections: {{targetMemberships}} (and, upstream, {{{}targetGroups{}}}/{{{}targetEntities{}}}) — synchronize the add step, or accumulate per-callable and merge at join.
 * {{GrouperOktaProvisioningTargetNativeSync.captureMembershipsForGroupForCurrentProvisioner(...)}} — is this safe to call concurrently for different groups, or does it need external synchronization? (We didn't verify.)

h3. Expected impact

At 5-thread parallelism on the read alone, ~25.6h of thread-time on PROD collapses toward ~5h wall-clock. Combined with the unavoidable ~4.2h serial {{retrieveOktaUsers}} cursor pagination and the existing ~5h write phase, a full sync moves from ~35h to a range that fits inside a daily window again.
h3. Scope

This is *not* an Okta throttling issue — same Okta tenant serves concurrent reads fine on the other path. It is *not* a config issue — {{retrieveAllData()}} never touches {{{}retrieveExecutorService(){}}}, so {{threadPoolSize}} is irrelevant on that path. {{selectAllGroups=false}} is not an acceptable workaround (see companion ticket / notes: it trades serial-cheap for threaded-but-huge-work, and hits the {{GrouperHttpClient}} retry ticket hard).

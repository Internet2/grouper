# GRP-7482  Changes made through MCP are audited with no logged in user, so the config history and other screens which read the logged in member show nobody as making the change

h2. Problem

Changes made through MCP are audited with *no logged in member*. Screens which show who made a change from the logged in member show nobody for anything done over MCP. For example, after editing an MCP recipe over MCP, the *Changed by* column on the configuration history screen ({{UiV2Configure.history}}) is empty.

This was not a complete gap in auditing. For most MCP changes the caller was still recorded, as the *act as* member: a tool runs in a Grouper session as the caller, and when nobody is logged in, Grouper records the session's user as act as. So the UI's audit search for a user's actions, which matches logged in or act as, already found most of them. What was missing:

* the logged in member on every MCP change, which some screens, such as the configuration history, are the only thing they read
* any record of the caller for changes made in a root session, and for GSH templates which run as GrouperSystem, since Grouper does not record a root session as act as
* the caller, for GSH templates which run as a configured subject: act as named that subject, and nothing named the caller

h2. Cause

* Every MCP request gets a fresh Grouper context from the web service filter ({{GrouperServiceJ2ee}}), with engine {{MCP}} and nobody in it.
* A normal web service call then sets the context's logged in member ({{GrouperServiceJ2ee.retrieveSubjectLoggedInFromRequest}}) and act as member ({{GrouperWsSubjectUtils.retrieveSubjectActAs}}), both from {{GrouperServiceUtils}} when it starts the operation's session.
* For MCP, {{GrouperServiceUtils}} uses the tool's own session and returns before either is set, and tools which call the Grouper API directly (such as {{group_save}}, recipe and config edits) never go that way at all.
* So every audit entry written during an MCP call had an empty logged in member, and act as came only from Grouper's fallback, which uses the session's user unless it is a root session.

h2. Fix

* {{GrouperMcpServlet}} sets the request context's logged in member to the caller, once, right after the request is authenticated and before anything is dispatched. The caller's member id is kept on {{GrouperMcpAuthUser}} when authentication looks the member up, so this needs no second lookup.
* Only the logged in member is set, as the UI does. Act as is left for Grouper to fill in when a change runs as someone else, such as a GSH template which runs as a configured subject, and otherwise Grouper sets it to the logged in member when the audit entry is saved.
* After the fix, an MCP change records the caller as logged in, and as act as unless it ran as someone else. A GSH template which runs as a configured subject records the caller as logged in and that subject as act as.
* The AI assistant in the UI sets its own context and does not go through this servlet, so it is unchanged.

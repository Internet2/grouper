# GRP-7536  AI assistant: tell the model today's date, so date ranges like "the last 30 days" are filtered

h2. Summary

The AI assistant in the Grouper UI never tells the model what today's date is. A request with a relative date, such as "show the attestation audit entries for group ref:hr:staff from the last 30 days", can't be turned into a {{fromDate}}. The model either asks the user for the date or leaves the date filter out and returns everything. Seen in testing: the model called {{audit_get}} with the right {{auditType}} and group but no {{fromDate}}. On a group with older entries, that answer would include entries outside the range the user asked for.

MCP clients are not affected: they run their own model, and the client tells it the date.



h2. Fix

* *Each user message is sent with when it was sent in front:* {{[sent 2026/10/27 14:05:30 -04:00]}}, then the user's text. The model always has the date and time of the question it is answering, so "the last 30 days" and "the last 2 hours" both work.
* *Written once:* the time is stored on the message ({{GrouperAiAgentMessage.sentAt}}) when it comes in and never changed, so every request sends the history byte for byte the same. Nothing earlier in the request changes, so the provider's prompt cache keeps working and, on models which check that earlier history is unchanged (preserved thinking), earlier reasoning stays valid. A date in the message at the front, or in the system prompt, would change part way through a conversation that runs past midnight.
* *Only sent to the model:* added in {{GrouperAiAgent.messagesForRequest}}. The stored text, what the user sees in the chat, and the counting of exchanges for summaries are unchanged. A separate stamp message would have shown in the chat and been counted as an exchange.
* *Format:* {{yyyy/MM/dd HH:mm:ss}}, close to the {{yyyy/MM/dd HH:mm:ss.SSS}} the tools take, with the UTC offset, in a fixed locale so the year and digits are always Western. The time is in the server's (JVM's) time zone, which is the one the tools read dates in. That is not necessarily the user's own time zone, which the model is not told: in a container running in UTC, "today" near midnight is the server's today. To the second, so a range which ends when the user asked, e.g. "added in the last 10 minutes", includes what happened earlier in that minute. Readable rather than epoch, so the model does not have to convert it.
* *Cost:* about 14 tokens per user message, read from the cache after the first call. When older messages are summarized, the text given to the summarizer has each user message's time ("User (sent ...): ..."), and the latest message is always kept word for word with its stamp.
* *Older conversations:* a message stored before this has no time and is sent as it was.

h2. Tests

* {{GrouperAiAgentTest.testUserMessageSentAt}}: the stored message keeps the user's text and a time in the expected format, the message is sent with the time in front, the same on the next call, and a message with no time is sent as it is.
* Existing tests which check the exact text of a user message sent to the model allow for the time in front.

h2. Manual test

# In the Grouper UI assistant, start a new conversation and ask: "Show only the attestation audit entries for group ref:hr:staff from the last 30 days."
# Expand the {{audit_get}} call. Before the fix: no {{fromDate}}, or the model asks for today's date. After the fix: {{fromDate}} is 30 days before today, e.g. {{2026/09/27 00:00:00.000}}.
# Ask "what time is it?" and check the answer matches the server's time when the message was sent.
# Check the chat shows only what you typed, with no time in front.
# Check the token counts shown under the answer, to confirm a second question in the same conversation still mostly comes from cache.

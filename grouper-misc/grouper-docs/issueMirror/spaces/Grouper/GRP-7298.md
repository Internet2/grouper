# GRP-7298  Config import clears the config cache; the screen it redirects to then rebuilds all config, allocating 700-850 MB in one request

Importing configuration through the UI clears the config cache, and the config file listing screen that the import redirects to then rebuilds the entire configuration from scratch, allocating 700 to 850 MB in a single request. The import itself is cheap by comparison. On a memory-limited container this is enough to get the JVM OOM-killed by the kernel: exit code 137 with no Java OutOfMemoryError and no stack trace, because the allocation is transient churn rather than retained memory. Originally found on a Grouper UI container with a 4 GB memory limit and a 2800m max heap, where submitting a config import killed the task reproducibly.

Measurement method: com.sun.management.ThreadMXBean.getThreadAllocatedBytes was sampled at the start and end of each request in a servlet filter, and the delta logged for any request allocating more than 20 MB. This is an exact per-thread JVM counter, not a sampled or extrapolated estimate.

Per-request allocation, two consecutive import runs on a local Grouper 7 instance:

* UiV2Configure.configurationFileImportSubmit: 130 MB in 302 ms, then 81 MB in 233 ms on the second run. This is the import itself.
* UiV2Configure.configure with configFile GROUPER_LOADER_PROPERTIES: 847 MB in 990 ms, then 697 MB in 392 ms. This is the config file listing screen the import redirects to.
* For scale, ordinary screens in the same session: home page 26 MB, UiV2Main.indexMain 30 MB, UiV2Group.viewGroup 27 MB.

Critically, the same config listing screen is cheap when the config cache is warm. Loading UiV2Configure.configure repeatedly with no import in between produced no entries at all in a log that records every request allocating more than 20 MB, and the requests were confirmed to have been issued and returned HTTP 200. So the screen costs under 20 MB warm and 700 to 850 MB cold, roughly a fortyfold difference. The cost is in the cold rebuild, not in rendering the screen.

Mechanism: the config import path calls ConfigPropertiesCascadeBase.clearCache, from four call sites in GrouperConfigurationModuleBase. That empties configFileCache. The next code path that calls retrieveConfig therefore misses the cache and calls retrieveFromConfigFiles, which re-reads and re-parses every config file and rebuilds the merged configuration. The config listing screen reads configuration heavily, so it absorbs the entire rebuild cost in one request.

Suggested directions, in rough order of expected benefit:

* Do not invalidate the whole cascade for a database-only change. A config import writes rows to grouper_config; the properties files on disk are byte identical before and after, so their cached contents remain valid and only the database overlay needs refreshing.
* Probe for database config changes cheaply instead of rebuilding. grouper_config already has a last_updated column that is currently never referenced anywhere in the config database logic, which issues select star from grouper_config where config_file_hierarchy = ? and pulls every row. An aggregate of count(*), max(last_updated) and sum(hibernate_version_number) is one cheap row and detects inserts, updates and deletes, including same-millisecond updates that a max alone would miss.
* If a full rebuild is unavoidable, rebuild the merged view from already-cached file contents rather than re-reading files from disk.

Causes investigated and ruled OUT, recorded so they are not re-investigated. Note that several of these were previously asserted in this issue and later disproven; see the comment history:

* In-process javac from compiled GSH template validation. Metaspace stayed between 74 and 89 MB across all runs.
* Database config volume. Going from 68 to 5828 rows in grouper-loader.properties did not meaningfully change peak memory.
* O(n^2) string concatenation in ConfigFileName.configFileMetadata(). In the environment investigated the grouperExtraProvisionerConfiguration and grouperExtraExternalSystem counts it loops over are both zero, so it never executes.
* The configuration.cacheJsonMetadata condition. Cold JVM runs at production config scale gave 1332 MB peak RSS with the flag true versus 1280 MB with it false, within noise.
* Config files being re-read on every pooled database connection acquisition. GrouperLoaderDb.initProperties uses the cached config object and the re-read is correctly gated by loader.config.secondsBetweenUpdateChecks, which is 600 in the base properties.
* Per-property-read overhead, such as the .elConfig probe performed on every property get and uncached EL evaluation. A counter placed in propertyValueStringHelper recorded fewer than 100000 calls for JVM startup plus login plus a full config import plus twenty config screen loads, and a background rate of only 46 calls per second. Property reads are far too few to account for the allocation.

Workaround for sites hitting the OOM: lower the max heap so the collector is forced to reclaim rather than expand within the container limit, and size the container to leave more than 1 GB of headroom above the max heap. Lowering the max heap from 2800m to 2400m inside a 4096 MB limit was sufficient in the case that prompted this issue.

### Chris Hyzer - 2026-09-02T15:48:46.821-0400

RETRACTION. The current summary and description of this issue are not supported by the evidence and should not be acted on until they are rewritten. The JFR allocation profiling they are based on was re-examined and does not show what the previous comment claimed.

The recording captured only 742 ObjectAllocationSample events over 92 seconds. JFR allocation sampling assigns each sample an extrapolated weight estimating bytes allocated at that site since the last sample there, so a single sample can carry an enormous and misleading weight. Breaking the reported sites down by sample count shows nearly all of the reported totals came from one outlier sample each:

* filesNeedReloadingBasedOnContents: 39 samples, 2368 MB total, of which a single sample accounted for 2300 MB, or 97 percent. Median sample 1.2 MB.
* GrouperConfigurationModuleBase.retrieveAllConfigurations: 16 samples, 254 MB total, one sample accounted for 250 MB, or 98 percent. Median sample 0.3 MB.
* sun.nio.ch.SocketOptionRegistry under Tomcat socket close: 2 samples, 5002 MB total, one sample accounted for 100 percent. Already flagged as an artifact.
* GrouperUiUtils.convertJspToString: 121 samples, 347 MB total, largest sample 39 percent of it. Median 0.9 MB.
* Class.copyMethods via javax.el.BeanELResolver: 78 samples, 220 MB total, largest sample 62 percent of it. Median 0.3 MB.

Consequence: the claim that config files are re-read on every pooled database connection acquisition, causing continuous churn of roughly 26 MB per second, is withdrawn. Excluding the single outlier, that path accounted for about 68 MB across 38 samples spread evenly over the recording, roughly 0.3 MB per second, which is consistent with a cheap periodic poll rather than a defect.

The mechanism was also re-checked in code and works as designed. GrouperLoaderDb.initProperties calls GrouperLoaderConfig.retrieveConfig, which returns the cached config object. The re-read is gated by needToCheckIfFilesNeedReloading using loader.config.secondsBetweenUpdateChecks, which is 600 in the base properties, and retrieveFromConfigFiles throws if that key is missing so it cannot silently default to zero. There is no per-connection file re-read.

What still stands, from direct measurement rather than sampling: importing config through the UI produces a repeatable resident memory spike of roughly 600 to 700 MB, measured by sampling RSS and heap once per second across several cold-JVM runs, and that spike does not scale with the number of database config rows (68 rows versus 5828 rows gave comparable peaks). The allocation site responsible is NOT identified. The previous profiling attempt was too sparse to attribute it, and a longer recording accumulating hundreds of samples per site would be needed.

The ruled-out list in the description remains valid and is worth keeping: in-process javac, database config volume, the O(n^2) concatenation in ConfigFileName.configFileMetadata(), the configuration.cacheJsonMetadata condition, and cumulative back-to-back imports have each been tested and none explains the spike.

Root cause found and the description rewritten accordingly. This supersedes the earlier retraction; the summary and description are now backed by exact measurement rather than sampling or code reading.

Method that finally worked: instead of JFR allocation sampling, which extrapolates weights and misled this investigation three separate times, a servlet filter recorded com.sun.management.ThreadMXBean.getThreadAllocatedBytes at the start and end of every request and logged the delta. That is an exact JVM counter per thread, so there are no sampling artifacts and it also cleanly separates request-thread allocation from background-thread allocation, which was a recurring source of confusion here.

Result: the config import request allocates only 81 to 130 MB. The config file listing screen it redirects to, UiV2Configure.configure, allocates 697 to 847 MB in a single request. Every earlier hypothesis in this issue was aimed at the import logic, which was never where the memory went.

The follow-up test that pinned the mechanism: loading that same screen repeatedly with no import in between produced no entries in a log recording every request over 20 MB, with the requests confirmed issued and returning HTTP 200. So the screen is under 20 MB warm and 700 to 850 MB cold. The cost is the cold rebuild triggered by the import calling ConfigPropertiesCascadeBase.clearCache, not the screen rendering.

Also worth recording as a clean negative result: a counter placed directly in propertyValueStringHelper showed fewer than 100000 property reads for JVM startup plus login plus a full config import plus twenty config screen loads, with a background rate of 46 per second. ### Chris Hyzer - 2026-09-19T17:40:10.904-0400

Fixed. Root cause: a config cache clear was happening once per property written, not once per import.

The clear that mattered was not the one in ConfigPropertiesCascadeBase.clearCache(). Every config row save calls GrouperConfigHibernate.updateLastUpdated(), which calls clearConfigsInMemory(), which calls ConfigPropertiesCascadeBase.clearCacheThisOnly() directly. That path never goes through clearCache(), so the cache was emptied once per property and the next read of each config class rebuilt the entire configuration.

Fix: a per thread suppression flag (suppressClearCacheStart / suppressClearCacheStop) checked in BOTH clearCache() and clearCacheThisOnly(). UiV2Configure brackets the import loop with it and does a single clearCache() in a finally, so one rebuild happens at the end instead of one per property. Also made the static configFileCache a ConcurrentHashMap (it was a plain HashMap read and written with no synchronization, and its lazy init could discard entries), and added a lock so concurrent misses on the same config class result in one rebuild rather than one per thread.

Measured on a 200 property import into grouper.text.fr.fr.properties:

before: 1798 full config rebuilds, 5787 MB allocated, 15.6 seconds

after: 9 full config rebuilds, 3503 MB allocated, 12.0 seconds

9 is one rebuild per config class, so a single full pass. Rebuild count no longer scales with the number of properties imported.

Worth noting for anyone reading this later: allocation only dropped about 40 percent, so config rebuilds were not the whole cost. Roughly 3.5 GB for a 200 property import remains, and it is not config rebuilds. That is filed separately, along with making database config invalidation per config file rather than all or nothing.

The instrumentation used to measure this is committed but compiled out, behind the constant ConfigPropertiesCascadeBase.CONFIG_CACHE_INSTRUMENTATION (false). Set it to true and rebuild to count config cache clears and rebuilds per request.

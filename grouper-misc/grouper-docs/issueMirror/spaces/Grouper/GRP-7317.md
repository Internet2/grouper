# GRP-7317  Subject source config wizard does not reliably warn when a sortAttribute/subjectIdentifierAttribute mapping is nullified by an attribute rename

*summay by Claude:*

In the Subject Sources configuration screen, if you rename/change an attribute in the subject source's attribute list, any existing config value that referenced the old attribute name becomes stale — because the old name no longer appears in the attribute dropdown, the underlying config value is treated as empty/nullified.

For sort attributes (sortAttribute.i.attributeName), the "this field is required" warning only appears if the page has re-rendered the section heading for that attribute — which happens, for example, if you change the attribute's translation type and the UI redraws the section with the new attribute name. If the UI is not redrawn before you hit save, the bad configuration saves silently with no warning at all. So the validation exists but is triggered by an incidental UI redraw, not reliably enforced on save.

For subjectIdentifierAttribute0/1/2, no equivalent warning appears under any circumstance observed so far — the save proceeds silently and the mapping is lost, meaning subject_identifier0/1/2 stops being populated/refreshed for that source going forward, with no indication to the admin that anything changed.

The only signal observed was an unrelated, easily-missed message on a later attempt:

▎ Warning: subject.properties property 'subjectApi.source.ldapPeople.param.subjectIdentifierAttribute1.value' was deleted from the database, but there is still a configuration value in the non built-in config file


That message is about a config-file/database precedence conflict (configurationFilesDeletedButStillExists in grouper.textNg.en.us.base.properties), not about the mapping being empty — it doesn't communicate the real problem and only shows up in some circumstances.

Steps to reproduce:

# Go to Subject Sources configuration for a source (e.g. ldapPeople).
# Rename/change an attribute that is currently mapped to IdentifierAttribute0/1/2 value.
# Save the configuration without triggering any action that redraws the affected section (e.g. don't touch translation type).
# Observe: no warning is shown for either the sort attribute; the config saves with both mappings silently nullified.

(Separately: changing translation type first, so the UI redraws the sort attribute's section heading, does surface a "required" warning for the
sort attribute — but this appears to be an accidental side deliberate save-time validation.)

Expected: On save, the config wizard should always validate and subjectIdentifierAttribute0/1/2 mapping still resolves to a real attribute in the source's current attribute list, and block/flag the save if not — regardless of whether the UI happened to redraw that section.

Actual: Validation for both fields is unreliable: it doesn’t fire on save itself, only incidentally when a UI redraw happens to re-check the field (sort attribute), or never at all (identifier attributes). Renamed attributes silently orphan both types of mapping.

Impact: Silent data-quality regression — downstream consumers relying on subject_identifier1 (e.g. ID number-based lookups) go stale with no warning at the point of misconfiguration, and sort-attribute breakage can likewise go unnoticed depending on how the admin interacts with the form. 

Suggested fix: Move mapping validation (for both sortAttribute and subjectIdentifierAttribute0/1/2) out of whatever UI-redraw-triggered check currently exists and into deliberate save-time server-side validation, so it fires consistently regardless of what else happened in the form beforehand.

*_Would failsafes have helped, and is "missing subject identifier" a special case?_*

Investigated both angles in code:

Failsafes (percentage-based safety net): GrouperProvisioningFailsafe aborts a sync if removals exceed a threshold (default maxPercentRemove=30% on groups above minGroupSize=200, plus overall-percent ceilings across managed groups/memberships). This is purely magnitude-based — it doesn't know why memberships vanished, just how many. If the affected groups/targets were large enough and the removal percentage crossed the threshold, a failsafe would likely have caught this. However, failsafeUse (loader.failsafe.use) defaults to false and is also gated per-provisioner by showFailsafe — worth confirming whether failsafes were actually enabled on the targets hit here.

Unresolvable-subject handling (exists, but too narrow to have caught this): Grouper does special-case missing subjects via ProvisioningStateEntity.isUnresolvable(), and when set, unresolvableSubjectsRemove (default false) leaves the target-side membership alone instead of deleting it. But this only fires when Grouper's own resolution flag (subject_resolution_resolvable on grouper_members) is explicitly false at query time. A subject identifier edit doesn't necessarily trip that flag — resolution can still "succeed" (against nothing, or against the wrong thing), so the diff logic falls straight into ordinary delete branches. There's a live // TODO come back to unresolvable at GrouperProvisioningCompare.java:876 marking this exact gap: an isUnresolvableSubject value is computed there and then never actually branches on for the delete path.

Root issue — no churn detection: The provisioning diff is stateless: it compares current Grouper membership vs. current target state fresh every run. grouper_sync_member/grouper_sync_membership store the last-synced subject identifier per memberId, but that data is only used to reconstruct deletes when a member disappears — it's never diffed against the entity's newly-resolved identifier to detect "this identifier changed since last successful sync."

Feasibility of a fix: If the same underlying member.uuid/memberId persisted and just had its identifier edited in place, a targeted fix is realistic — compare grouper_sync_member's stored identifier against the freshly resolved one for the same memberId at diff time, and flag a mismatch as suspicious rather than routing to plain delete. If the edit caused the old member row to be replaced/recreated instead, memberId continuity breaks and this narrower fix wouldn't catch it; that case would need a broader check against the member changelog (identifier changes are recorded there via MEMBER_UPDATE entries) or USDU's duplicate/deleted-subject bookkeeping, neither of which provisioning currently reads.

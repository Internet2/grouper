# GRP-7154  Provisioner heartbeat progress labels in job_message and 15 second first heartbeat

Running provisioners now report a live progress label (what they are doing right now) in the debug map that the heartbeat writes into grouper_loader_log job_message about once a minute, so an operator can see current status without a thread dump. The big debug map lands in job_message_clob (the short job_message varchar stays null), which is what the daemon log screen already displays.

The framework sets a target-side and a grouper-side label at each long running phase: retrieving all data from target, retrieving all data from grouper, and inserting/updating/deleting batches reported as N of M. Slow paginated web service retrieves in the DAO command classes (okta, azure, google, duo and duo role, zoom, box, dropbox, scim2, remedyV2, datadog, truefoundry, freshService, adobe, interfolio) report page number and count-so-far via the existing thread-scoped current provisioner accessor.

Heartbeat cadence: the first heartbeat store now happens at 15 seconds and then every 60 seconds, so job_message and grouper_sync_job show real status shortly after a job starts instead of a blank first minute.

The queued message (waiting for other jobs to finish) is written only when another related sync job is actually running or pending, so a job never falsely claims to be waiting when there is no contention.

Also hardened the debug map serialization with synchronized blocks so the additional progress-label writes from worker threads cannot cause a ConcurrentModificationException when the heartbeat thread serializes the map. No DDL changes.

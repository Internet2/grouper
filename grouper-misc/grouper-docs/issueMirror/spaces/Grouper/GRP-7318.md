# GRP-7318  add “email” option to group exports

“group actions → export members” should have the option to email the results to the user, offloading the job to a daemon server and returning the user to the UI.

i tried to export a large group (+100k) with “all details” and it spun and spun until the browser timed out.  curiously the actions in my UI seemed to suggest that i downloaded the group hours after I requested it.

## Comments

### Chris Hyzer - 2026-09-28T02:06:22.190-0400

Notes from the 7.6.0 pre-release review, to look at when the export is refactored (not changed for 7.6.0):

h3. Subject attribute security

The emailed export runs in GrouperReportJob as a root session (GrouperReportJob.java around line 75). Subject attribute filtering keys off the session subject: {{SubjectFinder.filterSubjectAttributesBasedOnGroup}} returns early for wheel or root, and SubjectCustomizer.filterSubjects gets the root session. So a user with READ who is not in a source's attribute viewer group, or whose view is masked by a subject customizer, gets those attributes in the emailed file, while Download now (SimpleMembershipUpdateImportExport, runs as the user) hides them. Fix idea: build the report data as the requester, or apply filterSubjects and filterSubjectAttributesBasedOnGroup for the requester.

h3. Cleanup

* Each Email me a download link click (any READ user, run as root) creates a report config attribute assignment on the group, a durable Quartz job (grouper_report_<groupId>_<markerId>) and a stored file.
* Cleanup only happens on first download. If nobody downloads it, GrouperReportClearJob deletes the report instance after 30 days, but the config assignment and the Quartz job stay forever, and with database storage the grouper_file row is orphaned (the commit's own comment notes instance deletion does not remove it).
* No rate limit, so repeated clicks accumulate jobs, assignments, audits and change log entries.

h3. Download link

* The download re-checks READ on the group and that the instance's owner group matches, but not that the downloader is the requester (the requester is in the config), so any READ user with the link can download it, and doing so deletes it.
* groupExportDownload is a GET that deletes data and is not CSRF protected (Owasp.CsrfGuard.overlay.properties).
* Ids are UUIDs, so guessing is not practical. The link works for up to 30 days until first use.

h3. Smaller

* GrouperReportLogic.sendGroupMembersExportLinkViaEmail puts $$groupName$$ and $$groupDisplayName$$ into the email without escaping. GrouperEmail switches to text/html when the body starts with <, so a deployer who configures an HTML {{groupMembersExport.email.body}} enables HTML injection by anyone who can name a group. The subject line is fine.
* GROUP_MEMBERS_EXPORT now appears in the wheel-only report type dropdown (GrouperReportContainer.getAllReportConfigTypes).

h3. What was fine

Triggering requires READ (VIEW only is blocked). Download re-checks READ and the owner group. GROUP_MEMBERS_EXPORT report configs have no viewers group, so downloadReportForGroup is wheel only for them.

### Chris Hyzer - 2026-09-28T02:10:34.534-0400

Follow up on the cleanup point after discussing with Vivek. Vivek agrees the download link and the unprotected GET points are valid. On cleanup, for an export that is never downloaded:

* {{GrouperReportClearJob}} only deletes report instances (older than 30 days, or beyond 100 per config). {{GrouperReportInstanceService.deleteReportInstances}} deletes the instance file (S3 or file system) and the instance attribute assignment, nothing else. So the instance and file do go away after 30 days.
* The report config and the durable Quartz job are only removed by {{GrouperReportConfigService.deleteGrouperReportConfig}} (which also calls deleteJob). Its callers are the download (UiV2GroupImport around line 509) and the two manual report delete screens in UiV2GrouperReport, nothing scheduled. So an undownloaded export leaves its config assignment and Quartz job behind.
* Not verified: whether a database stored file (grouper_file row) is removed on the instance delete path.

Suggestion for the refactor: have the clear job (or the export itself) delete the whole config via deleteGrouperReportConfig for GROUP_MEMBERS_EXPORT once its instance expires, and make the download a POST that checks the downloader is the requester.

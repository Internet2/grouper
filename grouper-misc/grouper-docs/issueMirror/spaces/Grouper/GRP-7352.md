# GRP-7352  Viewing a config screen should not clear the JVM wide config cache; add an explicit refresh action instead

UiV2Configure.buildConfigFileAndMetadata begins with ConfigPropertiesCascadeBase.clearCache() and GrouperUiApiTextConfig.clearCache(), under a comment saying get the latest and greatest. Those are global caches, so an administrator who merely VIEWS a config file page discards the cached configuration for every thread in that JVM and they all rebuild. It is a read only page causing a JVM wide cache stampede.

Measured on a dev instance with about 476 properties in grouper-loader.properties: a config screen render allocates roughly 750 MB, of which about 15 percent by JFR allocation samples is full config rebuilds, and every render logs 9 or more rebuilds. The cost landing on OTHER requests in the JVM is not captured by that number at all.

The clear is also close to redundant, because the screen already sees current values three other ways. Local config saves clear the cache themselves through DbConfigEngine and GrouperConfigHibernate.updateLastUpdated. Changes made in another JVM propagate on their own, since GrouperConfigHibernate is registered with GrouperCacheDatabase.customRegisterDatabaseClearable and its clear method calls clearConfigsInMemory. And there is a periodic re-check, with grouper.config.secondsBetweenUpdateChecksToDb defaulting to 600 seconds.

Proposal: stop clearing the caches when simply displaying a config screen, and add an explicit action to the configuration files actions menu, alongside Add config entry, Config history and Import config file, that clears the config caches and redisplays the screen. Anyone who knows something changed outside this JVM and does not want to wait can click it, which should be rare, and the normal page view becomes much cheaper for everyone else.

Implementation sketch: give buildConfigFileAndMetadata a flag (or an overload) for whether to clear first, default not to clear, add a new operation in UiV2Configure for the refresh action that passes true, add the link to the more actions dropdown jsp, and add an externalized text key for the label and a tooltip explaining that it re-reads configuration from the database.

Related: GRP-7347 (config screen allocation), GRP-7351 (mutations should confirm rather than redraw), GRP-7346 and GRP-7348 (making config invalidation and rebuild cheaper).

## Comments

### Chris Hyzer - 2026-09-20T11:53:20.714-0400

Fixed in commit c4eb4d7d50bc on GROUPER_7_BRANCH, together with GRP-7353 (they had to ship together, since dropping the forced clear is only safe once config changes invalidate the text config cache themselves).

buildConfigFileAndMetadata no longer calls ConfigPropertiesCascadeBase.clearCache() and GrouperUiApiTextConfig.clearCache(). A new Clear config cache in this UI action was added to the configuration files actions menu, in alphabetical order after Add config entry, which clears both caches and redisplays the screen.

Measured on a dev instance, config screen view: before 748 to 761 MB with 9 config rebuilds and 1 clear; after 719 MB with 0 rebuilds and 0 clears. Note the allocation only fell about 4 percent, so those 9 rebuilds were only worth roughly 40 MB on that request. The point of the change is not that 4 percent: it is that viewing a read only page no longer discards JVM wide config for every other thread, and that cost never showed up in the per request number because it lands on other requests.

Verified that config changes are still picked up without the forced clear: a config screen view does 0 rebuilds, and a view immediately after a config change does 4, so it rebuilds when it needs to and not otherwise. Also verified end to end that editing grouper.text.en.us.properties shows the new text immediately, and that deleting a row directly in SQL (so the application is never notified) leaves the screen stale until the new action is used, which then picks it up.

Still open: a config screen view allocates about 719 MB to produce a 6 to 14 kB response, all of it now in JSP rendering and JSON serialization. That remains under GRP-7347, with GRP-7351 covering not redrawing the listing on mutations.

# GRP-7381  Rules UI: default-closed gate for who can create sendEmail rules

h3. On upgrade

If both rules.restrictRulesUiToMembersOfThisGroupName and rules.restrictRulesEmailSendersToMembersOfThisGroupName are blank, only sysadmins (wheel/root) can create rules that send email. To allow others, set one of those two properties to a trusted group, or set rules.allowSendEmailRulesWhenNoGroupConfigured=true to keep the previous behavior (any rule editor may create email rules). No change if you already set rules.restrictRulesUiToMembersOfThisGroupName.

h3. Technical details

A sendEmail rule sends email to arbitrary recipients with an arbitrary subject and body, and those args are evaluated as expression language (including ruleElUtils, which can mutate Grouper) at fire time as the actAs subject (GrouperSystem). sendEmail is exposed as a rule pattern, so a non-sysadmin could create one; the EL lives in the pattern args, not thenEl, so it bypasses the EL=wheel-only gate. The only gate, rules.restrictRulesEmailSendersToMembersOfThisGroupName, was default-open (blank meant no restriction).

Fix: a single shared helper (RuleService.allowedToCreateEmailRule) used by all five sendEmail patterns, default-closed and layered: wheel/root always; else members of rules.restrictRulesEmailSendersToMembersOfThisGroupName if set; else members of rules.restrictRulesUiToMembersOfThisGroupName if set (a subject who reached the rules UI is already a vetted rule editor); else both blank means wheel/root only unless rules.allowSendEmailRulesWhenNoGroupConfigured=true. A configured-but-missing group fails closed. Related: GRP-7359 (rules UI hardening) and GRP-7380 (configuration review screen).

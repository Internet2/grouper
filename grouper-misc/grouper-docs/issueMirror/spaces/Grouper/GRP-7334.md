# GRP-7334  FreshRequesterApiCommands caches GrouperLoaderConfig in a static, so a newly added Freshservice external system fails until daemon restart

FreshRequesterApiCommands holds the loader config in a static field that is initialized once at class load:

{code:java}// FreshRequesterApiCommands.java line 31
public static GrouperLoaderConfig grouperLoaderConfig = GrouperLoaderConfig.retrieveConfig();{code}

ConfigPropertiesCascadeBase builds a NEW instance when config reloads, so this cached reference keeps pointing at the snapshot taken when the class was first loaded in that JVM. It never picks up config added afterward. The staleness is class-load scoped, not time scoped, so waiting does not help.

Impact. Add a new Freshservice external system in a running environment whose daemon JVM has already loaded this class (for example because another Freshservice provisioner already runs there). Every call then reads the stale config. httpAuthnType is not found for the new configId, so it falls through to the bearerToken default in WsBearerTokenExternalSystem.attachAuthenticationToHttpClient and demands a bearer token, even though the external system is configured for basicAuth.

The resulting error is misleading. It names a property that should not apply to a basicAuth external system and points the admin at a config problem that does not exist:

{noformat}ERROR: error querying target: dpsFreshService
java.lang.RuntimeException: Cant find property:
  grouper.wsBearerToken.dpsFreshService.accessTokenPassword
  in properties file: grouper-loader.properties, it is required
  at ConfigPropertiesCascadeBase.propertyValueStringRequired(...:422)
  at WsBearerTokenExternalSystem.attachAuthenticationToHttpClient(...:362)
  at FreshRequesterApiCommands.executeMethod(...:83)
  at FreshRequesterApiCommands.retrieveRequesterGroups(...:618)
  at FreshRequesterTargetDao.retrieveAllGroups(...:75){noformat}

Ruled out during diagnosis. The config rows were correct and complete in grouper_config (all seven keys, config_file_name grouper-loader.properties, httpAuthnType basicAuth, not encrypted), and byte for byte identical in shape to an existing working Freshservice external system in the same environment. The config was written about 36 minutes before the failing run, so this is not a refresh interval race. The same config read correctly from the UI and WS JVM at the same moment the daemon JVM was failing. Restarting the daemon container clears it.

Suggested fix. Call GrouperLoaderConfig.retrieveConfig() at the point of use rather than caching it in a static field. Note the stale instance also propagates outward: WsBearerTokenExternalSystem.attachAuthenticationToHttpClient takes a config argument and uses it when non null, so the stale snapshot is handed to the shared authentication code as well. Other classes that cache the config in a static may have the same problem and are worth a sweep.

Secondary suggestion. When httpAuthnType is absent but basicAuthUser or basicAuthPassword is present for the same configId, that combination is almost certainly a stale or partial config rather than a genuine bearerToken setup. Detecting it and saying so would turn a confusing error into an actionable one.

Found in PennGroups production on a Grouper 7 container while standing up a second Freshservice provisioner alongside an existing one.

# GRP-7269  MCP SQL tools should have no default database, each database is made available by configuration

  Problem



The MCP SQL tools (sql_select, sql_get_schema) defaulted to the Grouper database. externalSystemId was optional, and blank or "grouper" resolved through grouper.mcp.sqlGrouperExternalSystem to a live connection. Any deployment that enabled MCP and put a user in the SQL readonly group therefore exposed the whole Grouper schema by default, with no administrator action required to make that happen.



  Two things make that default worse than it first appears:



* No row-level security. These queries run as the connection's database user, so a default pointing at the main Grouper connection lets the AI read everything Grouper itself can read.

* "Read-only" is not guaranteed by the tool alone. The tool rejects non-SELECT statements and asks JDBC for a read-only connection, but neither is a hard boundary. If the underlying connection is a read/write database user, a sufficiently clever SELECT can still cause writes — a select that invokes a function or procedure that performs DML, an autonomous-transaction routine, or other vendor-specific paths that mutate from inside what parses as a query. Statement inspection is a filter, not a sandbox; the only durable guarantee is a database user that lacks write permission.



So the database connection the tools use must be a deliberate administrator choice, not something Grouper picks on the deployment's behalf. An administrator who has to name the connection is an administrator who can point it at a read-only user or a read replica, which is where the actual protection comes from.



What changes

  

No database is available to the MCP SQL tools out of the box — not even the Grouper database. A database becomes available only when the administrator configures it, and availability means "has tables the AI can discover":



* grouper.mcp.sql.<externalSystemId>.grouperDatabase = true — a Grouper database; tables/views come from the built-in Grouper DDL

* grouper.mcp.sql.<externalSystemId>.sqlTablesViews — explicit comma-separated list

* grouper.mcp.sql.<externalSystemId>.sqlTablesViewsQuery — list from a query



Other grouper.mcp.sql.<id>.* properties describe a system but do not make it available on their own, since a system with no discoverable tables is of no use to the AI. The configuration documentation states the preference for a read-only user or read replica, and why.



Related changes:



* The external system ID is the grouperClient.jdbc.<id>.* connection name. The indirection through grouper.mcp.sqlGrouperExternalSystem is removed, along with the special-cased literal "grouper" ID and the resolveConnectionName / isGrouperDb pair.

* GrouperMcpSqlSelect.externalSystemIds() becomes the single source of truth for which systems are available; GrouperMcpSqlGetSchema consumes it instead of doing its own config scan.

* When nothing is configured, sql_select and sql_get_schema are not advertised to the client at all (GrouperMcpServlet gates on GrouperMcpSqlSelect.anyConfigured()), rather than being offered and failing on use.

* Error messages name the available systems and the property an administrator would set.



New: Grouper schema qualification



grouper.mcp.sql.<externalSystemId>.grouperDatabaseSchema handles the case where the Grouper tables do not live in the connection's default schema. Discovery then returns qualified names (my_schema.grouper_groups) so the SQL the AI writes actually resolves, tableInfo prefixes the DDL with a -- query this as <qualified name> line since the DDL body carries the bare name, and tableInfo accepts either the qualified or unqualified form. Names from sqlTablesViews / sqlTablesViewsQuery are used exactly as configured and are never auto-prefixed.



Upgrade impact (breaking)



grouper.mcp.sqlGrouperExternalSystem is removed. Any existing deployment relying on the implicit Grouper database will lose MCP SQL access until it adds grouper.mcp.sql.<id>.grouperDatabase = true. This is intentional — the point of the ticket is that the access should be opt-in — but it needs a line in the release notes / upgrade instructions.

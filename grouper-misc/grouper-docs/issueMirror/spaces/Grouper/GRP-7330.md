# GRP-7330  DDL Deep Check on Oracle: NUMBER(38) precision false positive returns when the jdbc driver reports the column as NUMERIC or DECIMAL instead of BIGINT

GRP-7175 suppressed a cosmetic precision mismatch that Deep Check reports on Oracle for the grouper_audit_entry columns int01..int05, duration_microseconds and hibernate_version_number ("size '38' should be '19'"). Those columns go through ddlutilsFixSizeColumn, which pins the modeled size to 19, while the Oracle ddlutils platform bakes NUMBER(38) into the native type for BIGINT, so the installed column is always NUMBER(38) and the difference is not real.

The suppression only fires when the database side of the compare reads back as Types.BIGINT, and that is not reliable. JdbcModelReader takes the type code straight from the driver's DATA_TYPE, and BIGINT only appears because Oracle8ModelReader back-maps it — which it does only when the driver reported DECIMAL. Older ojdbc jars (10g/11g, which that back-map was written against) report NUMBER that way; newer ones can report NUMERIC. Nothing re-normalizes it in this code path: PlatformInfo.getTargetJdbcType, which maps NUMERIC to DECIMAL for Oracle, is only consulted by ModelComparator/SqlBuilder when generating scripts, not by GrouperDdlCompare. So the same database compares clean or dirty depending on which ojdbc jar is on the classpath, and sites on a newer driver still see the warnings.

Fix: in GrouperDdlCompare.compareColumns, accept BIGINT, DECIMAL or NUMERIC on the database side (all the labels an Oracle NUMBER can arrive as) when the java side is BIGINT and the database size is 38, and treat the size/precision difference as equal.

Scope is unchanged otherwise: narrower integers still compare normally (SMALLINT maps to NUMBER(5), DECIMAL/NUMERIC to NUMBER(size), so a genuinely narrower column does not read back as 38), and scale is deliberately left out of the suppression so a scaled NUMBER(38,n) is still caught by the scale comparison.

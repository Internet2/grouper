# GRP-2918  rabbitMQ  support for extra arguments

_Note: see updates below; if your rabbitmq is asking for extra arguments for a queue that already exists, first try setting loader.messaging.settings.autocreate.objects=false in grouper-loader.properties_
----
If we have an existing rabbitMq queue with feature arguments `x-queue-type: quorum`, the grouper messaging system fails with an error:
{code}com.rabbitmq.client.ShutdownSignalException: channel error; protocol method: #method<channel.close>(reply-code=406, reply-text=PRECONDITION_FAILED - inequivalent arg 'x-queue-type' for queue 'grouperChangeLog' in vhost '/midPoint': received none but current is the value 'quorum' of type 'longstr', class-id=50, method-id=10)
{code}
When the Grouper rabbitmq messaging system creates a channel, it passes null in the extra arguments field. If we could add extra properties in the loader config, and then send them with the channel, this would fix the issue (tested and confirmed).

E.g.
{code}changeLog.consumer.rabbitMqMessaging.queueArgs.0.key = x-queue-type
changeLog.consumer.rabbitMqMessaging.queueArgs.0.value = quorum
{code}

### Chad Redman  (unc.edu) - 2020-08-10T05:49:31.377+0000

As it turns out, the reason extra arguments are required is that loader.messaging.settings.autocreate.objects defaults to true if not explicitly set to false. When true, it will call a version of the message connection setup that attempts to create a new queue, or match an existing one. And even though our specific case was connecting to an existing queue, the rabbitmq server still insisted on the extra values as a formality. When false, it will connect to an existing queue, but won't create a new one, and in this case it doesn't need the extra parameters. And indeed, if autocreate.objects is set to false, my messages get published without an error, so it would have been the preferred solution for this. But there may be other cases where a queue argument may be needed.

Note that I only discovered this because the WS messaging interface doesn't have a default other than what is in the wsRequest beans, so it was the one messaging implementation that defaulted to false instead of true. Thus, you can quickly verify that the true/false autocreate value is the thing that matters:

 
{code}https://localhost:8443/grouper-ws/servicesRest/v2_5_000/messaging

{
  "WsRestSendMessageRequest":{
    "messageSystemName":"rabbitmqSystem",
    "queueOrTopicName":"grouper-queue",
    "queueType":"queue",
    "routingKey":"",
    "autocreateObjects": true,
    "queueArguments": {"x-queue-type":"quorum"},
    "messages":[
      {
        "messageBody":"Test message body"
      }
    ]
  }
}
{code}
If autocreateObjects is true, then queueArguments is required to avoid a message rejection, if the existing queue was set up with the same parameter. If false, the message is published even without queueArguments.

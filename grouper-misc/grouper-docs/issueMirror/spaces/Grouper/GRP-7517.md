# GRP-7517  LogicGate records provisioner full sync works through work tables, resumes link scan, retries LogicGate errors

Follow up to GRP-7512. The first full sync with the LogicGate cleanup held every contact record (about 226k, mostly inactive copies) and all link lookups in memory and ran a 40GB daemon out of heap. A later run was stopped after 7 hours by a single 502 from LogicGate's load balancer, losing the whole link scan.

The full sync now works through database tables so memory stays at about one page of records:
- prov_logicgate_record_work: every contact record in every step. Each page read from LogicGate is upserted as it is read; links, the plan per record (keep, delete, reactivate) and the result are kept here. People who need work are selected with SQL and fixed in batches of 500.
- prov_logicgate_link_scan: the reverse link scan (which contacts each contact group / action plan / ... record links to). Each answer is written as soon as it is fetched and is reused for logicGateApi.linkMaxAgeHours, so a run that fails part way resumes where it stopped and later runs do not rescan.

Also:
- LogicGate calls are retried on 429, 502, 503, 504 and network errors (5 tries, 2s to 60s back off). A record create is only retried on 429, since after a 5xx it may already exist.
- Progress counters and heap use are written to the provisioner debug map, so they show in the job message while the job runs.
- logicGateApi.maxHeapPercent (default 80): the cleanup stops cleanly with an error instead of running the daemon out of memory.
- main() runs the full sync read only against the configured LogicGate for testing.
- New settings logicGateApi.linkMaxAgeHours and maxHeapPercent documented in grouper.base.properties.

Result at Penn: about 196k extra copies and records of people who left deleted, one live record per person, with every action audited in prov_logicgate_audit.

# GRP-7495  Box access token cache keyed on config id only, so changing box credentials keeps using the old app for up to an hour

BoxGrouperExternalSystem caches the Box bearer token in an ExpirableCache keyed on the box config id alone. The token is therefore reused for up to an hour regardless of which credentials the config currently holds.

If a box external system is repointed at a different Box application, or its keypair is rotated, calls keep authenticating as the PREVIOUS application until the cached token expires. The configuration change appears to have had no effect at all.

This is very hard to diagnose, because every symptom points at the new application's setup rather than at the cache. In the case that found this, a provisioner was moved to a different Box app to pick up the content scopes it needed, and the content transfer kept failing with the same 400 Cannot transfer to folder afterwards. Time was spent checking scopes, re-authorization, archive account type and archive account role before the cache was suspected. Clearing it is also awkward in practice, since the cache is a static in whichever JVM is running, so clearing it from a GSH console in the UI does not affect the daemon container.

Fix: include the credentials in the cache key, so a configuration change is an ordinary cache miss. The key becomes config id plus client id plus public key id. Client id covers being repointed at a different app, and public key id covers a keypair rotation on the same app. Only non-secret identifiers are used, so the client secret and private key are not placed in a cache key.

No new configuration and no invalidation step, so there is nothing for an administrator to remember to do after changing Box credentials.

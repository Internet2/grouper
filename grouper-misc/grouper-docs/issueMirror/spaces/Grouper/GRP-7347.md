# GRP-7347  Config screen render allocates hundreds of MB to produce a response of a few kB

Follow on from GRP-7298. That issue fixed the config cache being cleared once per property, which cut full config rebuilds for a 200 property import from 1798 down to 9.

Allocation improved far less than rebuild count did. Measured on the same 200 property import into grouper.text.fr.fr.properties:

before GRP-7298: 1798 rebuilds, 5787 MB allocated, 15.6 seconds

after GRP-7298: 9 rebuilds, 3503 MB allocated, 12.0 seconds

So roughly 3.5 GB is allocated by a single 200 property import request and it is NOT config rebuilds, since those are now down to a single pass. Something else in the per property path is responsible. Likely candidates are the per property Hibernate work in DbConfigEngine and the config file metadata lookups in configurationFileAddEditHelper2, but that has not been profiled, so this needs measurement before any fix is designed.

Note the original report on GRP-7298 was 700 to 850 MB in one request. That was a smaller import than the 200 property one used here, so the numbers are not directly comparable; the point is only that a large import still allocates heavily after the rebuild storm is gone.

ConfigPropertiesCascadeBase.CONFIG_CACHE_INSTRUMENTATION (set true and rebuild) plus the per request logging in GrouperUiFilter give allocated bytes, rebuild count and clear count per request, which is how the numbers above were obtained.

## Comments

### Chris Hyzer - 2026-09-20T12:18:04.057-0400

Retitled. The original title said about 3.5 GB for a 200 property import, and that number turned out to be an artifact of how it was measured: the test import went into grouper.text.fr.fr.properties, and text configs are by far the largest config family. The same 200 property import into grouper-loader.properties allocated 304 MB, roughly 11 times less, at the same rebuild count. So the problem was never specific to import size.

What it actually is: rendering a config screen allocates hundreds of MB to produce a response of 6 to 14 kB, and the cost tracks the number of properties in the file rather than the size of any change. A one property import and a four hundred property import produced the same roughly 960 MB render.

Progress so far, all measured with ConfigPropertiesCascadeBase.CONFIG_CACHE_INSTRUMENTATION and JFR allocation profiling:

1. Commit 2d402a4c44ad. UiV2Configure.buildConfigFileAndMetadata compiled a regex per (property x section x item) in a triple nested loop, from static metadata that never changes. 130 of 139 allocation samples in that method were Pattern.compile internals. Added GrouperClientCommonUtils.patternCompile with a 24 hour ExpirableCache, delegated from GrouperUtil. Saved about 200 MB per screen render (963 to 761 MB). Also in that commit: config import no longer redraws the whole listing (460 to 208 MB for a 400 property import), and an import of more than 50 properties reports a summary rather than one success line per property.

2. Commit 969a9c9bccbd. Two EL expressions in configure.jsp were METHOD invocations rather than property access. An EL method invocation is not cached the way a property is: it goes through javax.el.Util.findMethod to Class.getMethods(), which defensively copies every Method on the receiving class. One of them called GrouperUtil, which has about 600 methods, once per property row. 251 of 409 allocation samples were java.lang.reflect.Method.copy. Replacing them with a property getter and the empty operator took a 464 property screen from 719 MB to 459 MB, about 36 percent, and Method.copy went to zero samples.

General lesson worth keeping: an EL method invocation inside a jsp loop does uncached reflection over the whole receiving class, and a large utility class is the worst possible receiver. EL property access is cached and fine.

Still open. A config screen view is around 460 to 560 MB depending on file size, for a response of a few kB. After the two fixes above the remaining allocation profile is convertJspToString and GrouperUtil.jsonConvertToNoWrap in roughly equal share, and the JSON serialization has not been looked at yet. Related: GRP-7351 (do not redraw the listing on add, edit, delete), GRP-7346 and GRP-7348 (make config invalidation and rebuild cheaper).

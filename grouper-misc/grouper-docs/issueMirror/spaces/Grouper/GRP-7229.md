# GRP-7229  OAuth confidential client secret is issued but never verified

Grouper can register an OAuth client with a client secret, but the token endpoint never checks it, so a client registered as confidential is authenticated exactly as a public one.



Secrets are issued in two places. An administrator can register a confidential client through the Grouper UI (UiV2Mcp.java:454-460), which the externalized text describes as being for server-side applications such as LibreChat, and which is gated on membership in grouper.mcp.users.canRegisterConfidentialOAuthClient. A dynamic registration request asking for token_endpoint_auth_method of client_secret_post or client_secret_basic also gets one (GrouperOAuthServlet.java:354-370). In both cases the secret is returned to the caller once and stored, and handleToken never reads client_secret at all.



This is not currently a privilege escalation. PKCE with S256 is mandatory on every authorization and is what binds a token request to the authorization request that preceded it, and the authorization server metadata correctly advertises only none in token_endpoint_auth_methods_supported (GrouperMcpWellKnownServlet.java:91). The problem is that everything around the feature — the UI wording, the once-only display of the secret, the group gate — tells an administrator they have configured a credential, when in fact whether their integration sends it makes no difference.



No MCP client is affected. MCP clients are installed on end-user machines, cannot hold a secret, and register as public clients; Claude Code and every other client we tested register with no secret. The feature only concerns server-side integrations.



There is a second defect that has to be fixed at the same time. UiV2OAuth.java:475 persists the whole client object when an authorization code is issued, and GrouperOAuthStore.retrieveClientByInternalId has already decrypted the secret onto that object, so the decrypted value is written straight back to grouper_oauth_client.client_secret. A confidential client's secret is therefore encrypted at rest only until its first authorization and stored in the clear from then on. This dates from the original MCP commit (fe22c97fc530, GRP-6704). Because nothing reads the secret today it has no effect, but any change that starts verifying it will compare against a value that may be either ciphertext or plaintext depending on whether the client has ever been used. Writing only the columns that change, rather than persisting the client object, fixes it.



  Notes for whoever implements this:



* Client authentication has to happen before the authorization code is looked up. Doing it afterwards both leaves the check unreachable for a request with a bad code and lets an unauthenticated caller learn whether a code exists from which error comes back. RFC 6749 section 4.1.3 authenticates the client first.
* The secret should be accepted both as a client_secret parameter and as the password half of HTTP Basic (RFC 6749 section 2.3.1), compared with MessageDigest.isEqual rather than String.equals.

* Failures should be 401 with invalid_client, and identical for an unknown client and a wrong secret so the two cannot be told apart. WWW-Authenticate belongs on the response only when the client attempted Basic (RFC 6749 section 5.2).

* token_endpoint_auth_methods_supported needs to list the supported methods, and the registration response should return token_endpoint_auth_method so a client knows what it registered as rather than inferring it from whether a secret came back.

* Migration: any client already holding a secret has to start sending it. Find them with select client_id, client_name from grouper_oauth_client where client_secret is not null.



A working implementation of all of the above, with the plaintext write-back fixed, was written and verified against a live server, then set aside as out of scope. It is not in the repository.

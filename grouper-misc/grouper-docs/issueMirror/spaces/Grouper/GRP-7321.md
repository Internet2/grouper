# GRP-7321  Filter Apply/Reset throws 'Cant find form by id' when the results/paging region is cleared or not yet loaded

In the v2 UI, filter Apply/Reset buttons pass a paging form id in the required formIds of the ajax() helper. That paging form lives inside the ajax-loaded results region, so when the region is empty (not yet loaded, load failed, or deliberately cleared), ajax() alerts 'Cant find form by id: "...PagingFormId"!' and aborts.

*Deterministic reproduction (My groups):*

# My groups > Groups I manage; wait for the list to load.
# Type a single character in Filter for and click Apply filter. You get the 'enter 2 or more characters' validation and the results area clears (removing the paging form).
# Type a second character and click Apply filter again -> alert: Cant find form by id: "myGroupsPagingFormId"!

*Root cause:* UiV2MyGroups.myGroupsHelper (the myGroupsFilter.length()==1 branch) does newInnerHtml("#myGroupsResultsId", ""), which deletes the paging form. The Apply button's formIds still requires ...PagingFormId. In grouperUi.js ajax() the required-form loop alerts and returns when a formId is missing (the optional-form loop already skips missing ones silently). Note the FORM onsubmit sends only the filter form, so pressing Enter works while clicking the button fails - an inconsistency that confirms the diagnosis.

*Decided fix (optional form ids):* move the paging form ids (the *Paging*FormId and *PageNumberId entries) out of formIds and into formIdsOptional on these buttons/onsubmits, keeping the always-present filter form in formIds. The ajax() helper already skips optional forms that are absent, so Apply/Reset then work whether or not results are currently rendered (paging simply defaults / the search re-runs). No change to grouperUi.js required.

*Scope:* ~113 occurrences of a formIds string containing a paging form id across the v2 UI - My groups / My folders, group/stem/attributeDef privileges, daemon jobs, membership & privilege audits, config history, unresolved subjects, etc. All should have their paging form id(s) moved to formIdsOptional.

This is a pre-existing bug, independent of the recent accessibility anchor-to-button conversions (the onclick strings are unchanged - the original anchors failed identically).

# GRP-7325  Authorization checks count disabled memberships as membership

Five authorization checks look up group membership with {{MembershipFinder}} without calling {{assignEnabled(true)}}. {{MembershipFinder.enabled}} defaults to null, which means "all memberships" (see the {{assignEnabled}} javadoc). So a membership whose end date has passed, or whose start date has not arrived yet, still counts as membership. The future-dated case means a subject given a later start date passes the check today.

h2. Part 1 - Privilege inheritance finders (privilege over-grant)

{{findAssignedPrivileges()}} in:

* {{PrivilegeGroupInheritanceFinder}}
* {{PrivilegeStemInheritanceFinder}}
* {{PrivilegeAttributeDefInheritanceFinder}}

{code:java}MembershipResult membershipResult = new MembershipFinder()
    .assignGroupIds(groupIds).addSubject(subject).findMembershipResult();
Set<String> groupIdsTheUserIsMemberOf = membershipResult.groupIds();{code}

These decide whether a subject gets a privilege through a {{groupCreate}} rule that assigns privileges to a group ({{assignGroupPrivilegeToGroupId}}). Because disabled memberships count, a subject whose membership in that group has ended, or has not started yet, is treated as having the inherited privilege.

Why it matters - this is an authorization decision, not a display hint:

{noformat}RulePattern / RuleConfig  canSubjectViewStem(...)
  -> StemPrivilegeStrategy.adminOrInheritedGroupAdmin / inheritedRead
    -> PrivilegeGroupInheritanceFinder.hasEffectivePrivilege()
      -> findEffectivePrivileges() -> findAssignedPrivileges(){noformat}

{{StemPrivilegeStrategy}} checks {{PrivilegeHelper.canStemAdmin()}} first and only falls through to the inheritance finder when the subject does not hold the privilege directly, so this is the "granted by inheritance" branch. A false result in {{RulePattern}} produces the "cannot admin stem" validation error, and {{RuleConfig}} uses it to gate viewing. Over-matching lets a subject configure rules on a folder they should not administer, and rules are themselves privilege-granting machinery.

Scope is bounded: it requires a {{groupCreate}} rule with {{assignGroupPrivilegeToGroupId}}, root act-as, and valid attributes, naming a {{g:gsa}} subject.

h2. Part 2 - MCP institutional tools (information disclosure)

{{GrouperMcpInstitutionalTools.retrieveAvailableToolNames()}} and {{GrouperMcpInstitutionalTools.schema()}}:

{code:java}membershipFinder = new MembershipFinder()
    .addSubject(subject)
    .addField(Group.getDefaultList())
    .assignCheckSecurity(false);{code}

Both gate {{specifiedGroup}} GSH templates on membership in {{groupThatCanRun}}, and both omit {{assignEnabled(true)}}.

Impact is lower than Part 1 because execution is enforced separately: {{GshTemplateValidationService.validateSecurityRunType}} re-checks {{groupThatCanRun.hasMember(...)}}, which only counts enabled memberships. A subject with a lapsed or not-yet-started membership gets the template listed with its full schema (config id, description, input parameter names and types) and is then refused at run time. This is disclosure of institutional template details, not unauthorized execution.

The same defect was found and fixed in {{GrouperMcpRecipe}} under GRP-7324; the fix was not applied to these two sites.

h2. Fix

Part 1, all three finders - only count enabled memberships, and name the members list explicitly instead of relying on the finder's default:

{code:java}MembershipResult membershipResult = new MembershipFinder()
    .assignGroupIds(groupIds).addSubject(subject)
    .addField(Group.getDefaultList()).assignEnabled(true)
    .findMembershipResult();{code}

Part 2, both sites: add {{.assignEnabled(true)}} to the existing chain.

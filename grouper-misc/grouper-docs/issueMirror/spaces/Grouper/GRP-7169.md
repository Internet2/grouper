## Comments

### Chris Hyzer - 2026-07-21T18:46:05.827-0400

*Diagnosis*

Deleting a folder that has a rule fails with AttributeAssignNotFoundException (Cant find attribute assign by id: ...), thrown from RuleService.deleteRuleAttributes -> AttributeAssignFinder.findById, called by Stem.delete. The delete does attribute cleanup in two phases:

Phase 1 (Stem.delete): as root, sweep and delete every attribute assign owned by the stem via findByOwnerStemId. The rule marker assign lives on the folder, so this is where it actually gets deleted.

Phase 2 (Stem.delete): RuleFinder.retrieveRuleDefinitionsToBeDeletedForGrouperObject reads the RuleEngine in-memory cache (ruleEngine.getRuleDefinitions(false)), which still holds the rule pointing at the assign id that Phase 1 just deleted. It then calls RuleService.deleteRuleAttributes(id), which does AttributeAssignFinder.findById(id, true) -- the true means throw if missing -- so it throws AttributeAssignNotFoundException and aborts the whole delete transaction. The folder never deletes.

Why the cache is stale: ruleEngineCache is a plain time-based GrouperCache (5 minute TTL, keyed on a single Boolean). Its only push-based invalidation is GrouperAttributeAssignValueRulesConfigHook.attributeAssignValuePostDelete, which calls clearRuleEngineCache(). But that hook early-returns when a rule type assign is being torn down (the guard that says: if deleting the attribute rule type, then dont worry about validations), and that early return happens before it reaches clearRuleEngineCache(). So the delete path deliberately leaves the stale rule definition in the cache, and Phase 2 trips over it.

This is why the reporter saw it succeed only after manually deleting the rule in the UI and waiting -- once enough time passed for the 5 minute TTL to expire and rebuild the cache, the stale entry was gone. Same code path exists in Group.delete and AttributeDef.delete, so groups and attribute defs with rules can hit the same failure.

*Fix*

Make RuleService.deleteRuleAttributes tolerant of an already-deleted marker assign: look it up with findById(id, false) and only delete when present, but keep the clearRuleEngineCache() call unconditional so the stale definition the hook left behind is always flushed. One change, covers all three callers (Stem, Group, AttributeDef).

{code:java}public static void deleteRuleAttributes(String attributeAssignId) {
  AttributeAssign attributeAssign = AttributeAssignFinder.findById(attributeAssignId, false);
  if (attributeAssign != null) {
    attributeAssign.delete();
  }
  RuleEngine.clearRuleEngineCache();
}{code}

The cache clear stays outside the if on purpose: the null branch is exactly the stale-cache case (Phase 1 already deleted the row), so that is precisely when the flush is needed.

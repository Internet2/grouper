# GRP-7238  Require grouper.ws.url and grouper.ui.url when MCP is enabled

  SUMMARY



grouper.ws.url is declared as an optional string in grouper.base.properties (line 63, valueType "string") and ships blank. MCP starts and serves requests without it. When it is unset, five behaviors change, four of them security relevant, and none is visible to a running deployment beyond a warn-once log line. Two of the four are the exact properties that GRP-7224 and GRP-7230 were opened to establish, so an unconfigured deployment silently reverts that work. This ticket proposes making the property required whenever MCP is enabled.



  WHAT DEGRADES WHEN IT IS UNSET



# Access tokens are neither bound to nor checked against the MCP resource. GrouperOAuthStore.retrieveMcpResourceIdentifier (line 489) returns null when the issuer identifier is null. GrouperOAuthSigningKey.createSignedJwt then skips withAudience (lines 292-297) and verifyAndDecodeJwt skips withAudience (lines 406-409). A token minted for any other resource that trusts the same signing key is accepted by MCP. This is the property GRP-7224 established, and it is absent whenever this config is blank. The code's own warning states it: "MCP access tokens are neither bound to nor checked against the MCP resource" (GrouperOAuthStore line 496).



# The issuer claim is omitted on mint and unchecked on verify. retrieveIssuerIdentifier (line 265) returns null, so createSignedJwt skips withIssuer (lines 287-290) and verifyAndDecodeJwt skips withIssuer (lines 401-404). Combined with item 1, token verification degrades to signature plus expiry only removing every check that distinguishes one Grouper's tokens from another's. The RFC 9207 iss parameter is also left off authorization responses, so a client cannot detect a mix-up.



# Published OAuth metadata is built from the request. GrouperMcpWellKnownServlet (lines 58-65) falls back to request.getScheme(), getServerName(), getServerPort() and getContextPath() when the issuer is blank. The issuer, token_endpoint, registration_endpoint and jwks_uri it advertises then come from the Host header. This fallback logs nothing itself; the only warning comes indirectly from the retrieveIssuerIdentifier call it makes.



# The unauthenticated challenge points at a request-derived URL. GrouperMcpServlet.resourceMetadataUrl (lines 725-739) does the same for the resource_metadata parameter of the WWW-Authenticate header. This is the GRP-7230 area.



# Origin enforcement cannot recognize its own origin. GrouperMcpServlet.configuredOrigin (line 927) returns null, so rejectIfOriginNotAllowed never takes its same-origin shortcut and every browser request must match a grouper.mcp.allowedOrigin.<configId>.regex pattern (documented at grouper.base.properties line 5948). With no such pattern configured, every browser-originated MCP request is rejected with 403. Non-browser clients send no Origin header and return early, so they are unaffected. This is a functional break rather than a weakening, and it is the only one of the five a deployer is likely to notice, by which point they have been running without items 1 through 4.

# The authorization endpoint published to clients points into the WS context. This one concerns grouper.ui.url rather than grouper.ws.url, but has the same trigger and the same remedy. GrouperMcpWellKnownServlet (lines 70-75) falls back to baseUrl plus a slash when grouper.ui.url is blank, and line 79 builds authorization_endpoint as that value plus "grouperUi/app/UiV2OAuth.authorize". Because baseUrl is the WS URL, the published authorization endpoint resolves into the WS context, for example [https://host/grouper-ws/grouperUi/app/UiV2OAuth.authorize|https://host/grouper-ws/grouperUi/app/UiV2OAuth.authorize], which does not serve the UI. The client sends the user there and receives a 404, so the OAuth flow cannot start. The fallback is only correct when UI and WS share a container and context path, which is not the normal deployment. Unlike items 1 through 4 this fails visibly on first use rather than degrading silently, so the argument for requiring grouper.ui.url is correctness rather than security. It only inherits Host header influence in the case where grouper.ws.url is also unset.

  

THREAT

  

Items 3 and 4 mean the addresses this server publishes for discovery are taken from the Host header rather than from configuration. The scope of that is bounded and worth stating precisely, because the existing javadoc on resourceMetadataUrl already does: the response goes back to whoever made the request, so poisoning it for somebody else "needs something in front of this server which caches without regard to Host, or which passes on a Host from one request to another; neither should be relied on not to be there." So this is not exploitable by setting a Host header alone. It requires an intermediary, which is a normal thing to find in front of a deployed Grouper.

  

  Items 1 and 2 are what make that worth acting on. They remove the checks that would let a client or the server notice a substitution after the fact, because the token then carries neither an audience naming the resource nor an issuer naming the server. Individually each item is a hardening gap. Together they are the difference between "a token proves this Grouper issued it for this resource" and "a token proves someone holding the signing key issued it for something."

  

  WHY THE EXISTING WARNINGS ARE NOT SUFFICIENT

  

Each of the affected paths logs a clear and accurate warning. That is right for a diagnostic and wrong as the only control on a setting that disables authentication binding. Each warning fires once per JVM, so it lands in startup noise and never repeats. Grouper runs UI, WS and daemon in separate containers with multiple nodes each, so the warning appears only in whichever container served the first affected request. Nothing surfaces the condition in the UI, in daemon status, or on the MCP info page. And a deployment in this state works, so there is no failure prompting anyone to look.

  

  PROPOSED CHANGE

  

  a. Treat grouper.ws.url as required whenever MCP is enabled. It cannot simply become required unconditionally, because non-MCP deployments have always run without it. The requirement is conditional.

  

  b. Validate at startup in GrouperCheckConfig, alongside the existing MCP checks that create the grouper.mcp.users.* groups (the "MCP (Model Context Protocol) authorization groups" block, around line 1466). Note that grouper.is.mcp lives in grouper.hibernate.properties (line 70) and is read through GrouperHibernateConfig.retrieveConfig(), not GrouperConfig.retrieveConfig() which that block currently uses. Report the problem through the same mechanism as other configuration errors so it surfaces in the UI rather than only in a log.

  

  c. Decide runtime behavior. This is the open question on this ticket. Option one, refuse to serve MCP: GrouperMcpServlet and GrouperOAuthServlet return an error for every request while the property is blank. Fails closed and confines the impact to MCP, leaving UI and WS unaffected. Recommended. Option two, fail startup: more literally "required", but takes down UI and WS for a property only MCP needs, and will surprise anyone who enabled MCP casually.

  

  d. If option c lands, the request-derived fallbacks in resourceMetadataUrl, GrouperMcpWellKnownServlet and configuredOrigin become unreachable and should be removed rather than left as dead paths implying the unconfigured case is supported.

  

  e. Update grouper.base.properties lines 60-63 to state that the property is required when MCP is enabled and what is disabled without it.

# GRP-7367  Move web service logic and MCP tools from grouper-ws into grouper core so the UI can use them

The Grouper UI is going to run the same MCP tools as the MCP endpoint, for an AI agent in the UI. Today those tools, and the web service logic they depend on, live in grouper-ws, and they depend on the servlet filter for per-request state. This change moves that code into grouper core and gives every tool call a single path, so the UI and MCP can share one tool layer. It is refactoring only: no UI features are added here.

h2. What moved

* 189 classes moved from grouper-ws to grouper core with their package names unchanged, as pure renames: {{ws/coresoap}} (127), {{ws/mcp}} (35), {{ws/rest}} (10), {{ws/util}}, {{ws/query}}, {{ws/exceptions}}, plus {{GrouperServiceLogic}}, {{GrouperWsConfig}}, {{WsResultCode}} and {{ResultMetadataHolder}}.
* {{swagger-annotations}} was added to {{grouper/pom.xml}}, because the request/response beans that now live in core carry those annotations.
* {{GrouperServiceUtils}} was split. Its servlet-dependent parts ({{marshalHttpParamsToObject}}, {{addResponseHeaders}}, {{currentServiceClass}}) moved to a new {{GrouperWsHttpUtils}} in grouper-ws.

h2. Per-request state no longer depends on the servlet filter

* New {{GrouperWsRequestContext}} (core) holds per-request state: debug map, request start time, REST flag and remote address. {{GrouperServiceJ2ee}} fills it in and clears it at the end of each request, rather than owning it.
* New {{GrouperWsSubjectResolver}}: each front end registers how it works out the logged-in subject. grouper-ws registers one in {{GrouperServiceJ2ee.init()}} that reads the servlet request, exactly as before. It is not cached, because servlet threads are pooled.
* The actAs logic moved unchanged from {{GrouperServiceJ2ee}} to the new {{GrouperWsSubjectUtils}} (core).

h2. One path for running tools

* New in core:
** {{GrouperTool}}, {{GrouperToolRegistry}} and {{GrouperToolRegistration}}: all 31 tools are registered through adapters, and no tool was rewritten.
** {{GrouperToolCategory}}, {{GrouperToolAccess}}, {{GrouperMcpGroupMembership}} and {{GrouperToolExecutor}}.
* Each tool now declares its own category (readonly, readwrite, sql, admin_readonly, admin_readwrite). This replaces the category switch in {{GrouperMcpToolLog}}.
* {{GrouperMcpServlet}} tools/list and tools/call now go through the registry and {{GrouperToolExecutor}}. This replaces the dispatch switch, the per-tool access checks and the logging wrapper that were in the servlet.

h2. Behavior

The intent is no functional change for WS or MCP clients. Differences found in review:

* *Tool list:* the MCP tool list is the same tools in the same order, filtered by the same conditions.
* *tools/call:* it keeps the same order of checks: throttle, allow/deny config, unknown tool, access, run. Throttle categories, audit log rows and error codes are unchanged.
* *Minor MCP differences:*
** A recipe {{update}} without readwrite access is now refused by the access check, with the standard "readwrite group is required" message rather than the recipe tool's own message.
** For {{folder_delete}}/{{group_delete}}/{{group_save}}, the OAuth group/folder scope error may now come after argument validation errors.
* *MCP requests now populate the WS debug log* (debug level), and {{WsResponseMeta}} timing is now correct for MCP requests.
* *Renamed caches:* the internal membership and actAs caches have new names. No configuration referenced the old ones.
* *GSH template remote address:* GSH templates run through WS/MCP still get the socket address ({{getRemoteAddr()}}), not {{X-Forwarded-For}}, matching the UI.

h2. Not in this change

* The AI agent in the UI itself.
* Recording which front end made each call (an {{entry_path}} column on {{grouper_mcp_tool_log}}), which needs DDL.
* Making {{GrouperServiceUtils.retrieveGrouperSession}} reuse the executor's session for UI-engine calls, not only when the engine is MCP.

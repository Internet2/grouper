# GRP-7231  MCP OAuth accepts redirect URIs which are neither https nor loopback

The MCP specification has required since revision 2025-03-26, which is the revision this support was written against, that a redirect URI be either a localhost URL or an HTTPS URL, and that all authorization endpoints be served over HTTPS. Grouper enforced neither. A redirect URI was accepted purely on whether it matched a configured pattern, so a deployment whose pattern allowed an http address on another host would have this authorization server send an authorization code across the network in the clear.



Redirect URIs continue to be controlled by grouper.oauth.redrectUri.<configId>.regex, one entry per pattern, and a URI is still allowed only if it matches at least one of them. If no pattern is configured then every redirect URI is refused, which is unchanged. What changes is that a check now runs before the patterns, and a URI which does not pass it is refused whatever the patterns say. A pattern can therefore still narrow what is allowed but can no longer widen it past this point. The check requires:



* a URI which parses, with a scheme and a host, and with no fragment, as RFC 6749 section 3.1.2 requires of a redirection endpoint

* either the https scheme, or the http scheme with a loopback host



A loopback host is localhost, ::1, or an address written as IPv4 in 127.0.0.0/8. That last is decided from the text of the host, so 127.attacker.example is refused: it is a name somebody else controls which happens to begin the same way as an address. No name lookup is done, deliberately, since a lookup answers where a name points at the moment it is asked, and that can differ between when a redirect URI is registered and when a code is sent to it.



Private use URI schemes, which RFC 8252 allows a native application to register with its operating system, such as com.example.app:/callback, are refused. Those are valid OAuth but the MCP rule names only localhost and https, and this follows MCP. A deployer cannot re-admit them through the regex.



Separately, the requirement that authorization endpoints be served over HTTPS cannot be enforced from inside the application, since TLS is normally terminated in front of it and what arrives is plain HTTP either way. What the application can see is the address it publishes to clients, which comes from grouper.ws.url for the issuer, token, registration and resource metadata endpoints and from grouper.ui.url for the authorization endpoint. When either is an http address on a host which is not loopback, a warning naming that property is now logged once, and nothing is refused. Publishing an http address is either a deployment which really is unprotected or a configuration which does not describe the deployment, and both are worth saying out loud.



Migration



This refuses redirect URIs which Grouper previously accepted, and the check runs on every authorization and not only at registration, so an OAuth client already registered with an affected redirect URI stops being able to authorize rather than merely being unable to register again. Such a client has been non-conformant since MCP support was added rather than being newly so, but it will have been working. Find them with:



select client_id, client_name, redirect_uris from grouper_oauth_client;



Any row whose redirect_uris is http on a host other than localhost or 127.x.x.x needs its redirect URI moved to https before this is deployed. Clients which register a loopback redirect URI, which is what an MCP client installed on somebody's machine does, are unaffected.

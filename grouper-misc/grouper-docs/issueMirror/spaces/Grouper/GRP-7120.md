# GRP-7120  Sync-back mirror drain can DELETE a grouper_prov_group/grouper_prov_user row when a written object can't be resolved back for re-read, causing phantom re-create next run

*Component:* Provisioning framework - sync-back mirror write-capture (GRP-7113/7114 area)

*Affects:* 7.3.0

*Severity:* Potential data loss (mirror table row), self-inflicted phantom re-create on the next sync. Not observed in normal full-sync runs; reachable only when a marked id fails to round-trip.
h3. What happens

On an attribute update to a group (or user), the write-hook {{recordTargetNativeGroupWrite(id, null)}} does two things unconditionally:
 # marks the id for end-of-run re-read, and
 # removes the pre-write native object from {{targetGroupIdToNativeGroup}} (via {{{}removeTargetNativeGroup{}}}).

At end of run, the drain re-reads only the ids it can map back to a {{ProvisioningGroup}} in {{{}TargetObjectInserts/Updates/Deletes{}}}. Any marked id it cannot map is counted as {{{}unresolved{}}}, logged, and its mark is cleared with {*}no re-read{*}.

The subsequent flush ({{{}syncGenericProvisionerTable{}}}) rebuilds {{grouper_prov_group}} as a full table-sync from exactly that map -- and that sync includes a DELETE phase. So an id that was marked-and-removed but then failed to re-resolve has {*}no row in the map{*}, and its mirror row (plus its attribute rows) gets deleted.

Next run, groups-from-sync-back-cache treats that group as absent from the target, producing a phantom group re-insert (and, if it feeds the group-centric membership recompute, membership churn).

This is the "mark only safe if by-object retrieve captures" gotcha: the mark+remove is unconditional, but the capture (re-read) is best-effort, and the failure path degrades to a row delete instead of preserving the prior row.
h3. Where
 * {{edu.internet2.middleware.grouper.app.provisioning.GrouperProvisioningLogic}} -- drain, groups path ~line 1410; users path ~line 1473
 * {{edu.internet2.middleware.grouper.app.provisioning.GrouperProvisioningTargetNativeSync}} -- write-hook / {{removeTargetNativeGroup}} ~lines 457, 488
 * Flush / full table-sync (DELETE phase) in {{GrouperProvisioningLogic}} ~lines 1806 (users), 1840 (groups)

h3. Failure scenario
 * Provisioner with {{fullSyncGroupsFromSyncBack=true}} (e.g. Google, Box, Azure, Duo).
 * A group's attributes are updated this run.
 * The written id does not round-trip in the update list -- e.g. an id-normalization mismatch ({{{}normalizeTargetId{}}} skew between the marked id and {{{}writtenGroup.getId(){}}}), or a write path that updates the target without populating {{{}TargetObjectUpdates.getProvisioningGroups(){}}}.
 * Result: the group's {{grouper_prov_group}} row and its attribute rows are deleted at flush; next run re-creates the group as a phantom insert / drives membership churn.

Note: on the common full-sync update path, updates _do_ land in {{{}getTargetObjectUpdates().getProvisioningGroups(){}}}, which the drain iterates -- so the {{unresolved}} branch is an edge case, not the normal path. That is why it has not shown up in steady-state prod runs.
h3. Why it matters

Every other failure mode found in this cluster is a leak / phantom-insert that self-heals. This one is the only path that is *destructive* to the mirror tables, and mirror-row loss silently feeds a phantom re-create on the following run. It depends on an id round-trip that is currently asserted by construction but not enforced.
h3. Suggested fix

In the drain, treat an {{unresolved}} marked id conservatively: re-insert the pre-write native object (or exclude that id from the flush's DELETE phase) rather than dropping it. Principle: a "mark for re-read" that fails to re-read must never result in a mirror-table delete -- fall back to keeping the prior row (and log at WARN so the round-trip gap is visible).

As a secondary hardening, verify that the marked id and {{writtenGroup.getId()}} agree (post-{{{}normalizeTargetId{}}}) for every target DAO, so the resolve step cannot miss on id form alone.
h3. Confidence / verification needed

PLAUSIBLE, not yet reproduced. The destructive branch is real in code but is not exercised by the common update path. Before closing, a human should confirm whether any DAO can (a) mark an id whose form differs from the resolvable {{ProvisioningGroup}} id, or (b) update the target without populating the update list -- either of which makes the {{unresolved}} -> delete window reachable.

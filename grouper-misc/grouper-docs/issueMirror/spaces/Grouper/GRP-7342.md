# GRP-7342  Provisioning diff computes isUnresolvableSubject but never branches on it for deletes

*Claude:*

While investigating GRP-7317 (subject source config wizard silently orphaning attribute
mappings), we looked at whether Grouper's provisioning failsafe or unresolvable-subject handling
would have caught the resulting silent membership deletions. Two related mechanisms exist:

* *Failsafe* ({{GrouperProvisioningFailsafe}}): purely magnitude-based (aborts if removals exceed
a percent threshold). Doesn't know _why_ memberships vanished, only how many. Also off by
default ({{loader.failsafe.use}} defaults to false, gated per-provisioner by {{showFailsafe}}).
* *Unresolvable-subject handling* ({{ProvisioningStateEntity.isUnresolvable()}} /
{{unresolvableSubjectsRemove}}, default false): when a subject is flagged unresolvable, target-side
memberships are left alone instead of deleted. But this only fires when Grouper's own
{{subject_resolution_resolvable}} flag on {{grouper_members}} is explicitly false at query time. An
identifier edit/rename doesn't necessarily trip that flag — resolution can still "succeed"
(against nothing, or against the wrong subject), so the diff falls straight into ordinary delete
branches.

There is a live TODO in {{GrouperProvisioningCompare.java:876}} — {{isUnresolvableSubject}} is computed
during the diff and then *never actually used* to change the delete-path decision:

{noformat}// TODO come back to unresolvable{noformat}

h2. Suggested fix

Wire the already-computed {{isUnresolvableSubject}} value into the delete-path branch in
{{GrouperProvisioningCompare.java}}, so a subject Grouper can't cleanly resolve is treated
consistently with the existing {{unresolvableSubjectsRemove}} config instead of falling through to
an ordinary delete. This doesn't fix the broader "no churn detection" problem (see separate
identifier-drift ticket) — it only closes the specific gap where a computed unresolvable signal is
silently discarded.

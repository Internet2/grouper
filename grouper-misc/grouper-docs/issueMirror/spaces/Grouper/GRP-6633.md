# GRP-6633  OSGi refactor: Lazy class loading to avoid ClassNotFoundException

The OSGi initialization code was moved from inline in onStartup() to a separate private method initOsgiServlets(), and the imports for BundleContext, InvalidSyntaxException, and FrameworkStarter were removed from the top-level imports in favor of fully-qualified references inside that method.

Why: When OSGi JARs are not on the classpath (they are provided scope in Maven), the JVM would fail at class-load time because the old code had direct imports of org.osgi.framework.BundleContext and org.osgi.framework.InvalidSyntaxException at the top of the file. Even though the OSGi code path was guarded by an if (grouper.osgi.enable) check, the JVM resolves imported classes when the class is loaded, not when the code path executes. By moving all OSGi references into a separate method with fully-qualified class names, the JVM only attempts to resolve those classes when initOsgiServlets() is actually called — making it safe to run without OSGi JARs present.

The catch was also changed from InvalidSyntaxException to NoClassDefFoundError as a safety net, logging an error instead of crashing if OSGi is enabled but the JARs are missing.

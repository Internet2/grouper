# GRP-7239  GTE self-signed cert has no subjectAltName and CN=localhost.localdomain; consider a non-SSL port

The Grouper Training Environment (GTE) container generates its httpd cert in base/Dockerfile with -subj /commonName=localhost.localdomain and no -addext for subjectAltName. Browsers based on Chromium have required subjectAltName since Chrome 58 and ignore commonName entirely for hostname matching, so the cert is not merely untrusted, it is invalid for every hostname. Firefox and Safari behave the same way.

Symptom: browsing to https://localhost:8443/grouper fails hostname validation. In a normal browser you can click through the interstitial, so this has been easy to miss. In an embedded or automation-driven browser there is no proceed button, so the training environment is simply unreachable until the cert is replaced by hand.

Suggested fix, one line in base/Dockerfile: change the subject to /CN=localhost and add -addext subjectAltName=DNS:localhost,IP:127.0.0.1 to the openssl req command. Verified working: after regenerating with those options inside a running container and reloading with httpd -k graceful, the cert is accepted once trusted, and the Grouper UI and Shibboleth login render normally.

Even with a correct subjectAltName, a self-signed cert still requires each trainee to trust it in the OS keystore or click through a warning, since no public CA will issue for localhost.

Question: would it be possible to also expose a plain non-SSL HTTP port on the container? AI assistants and MCP or browser-automation clients are becoming a common way to drive GTE, and TLS trust is the single biggest obstacle for that workflow. For a throwaway local training container with no real data, a plain HTTP port would make AI-assisted training a great deal easier. The concern is whether Shibboleth SSO and any absolute https URLs in the Grouper UI config would tolerate it, so it may need more than just opening a port.

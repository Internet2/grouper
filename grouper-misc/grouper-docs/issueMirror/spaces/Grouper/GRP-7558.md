# GRP-7558  Provisioner sync-back deletes and re-inserts changed attribute values, so readers see no value for long stretches during a sync

When the provisioner sync-back writes attribute values to grouper_prov_user_attr_value / grouper_prov_group_attr_value, a value that changed since the last run is deleted and then re-inserted as a new row, instead of being updated in place. Anything reading the tables in between sees no value at all for that attribute.

Full sync: GRP-7474 reuses an existing value row only when the value is identical (GrouperProvisioningLogic.buildProvisioningAttributeValueRowData). A changed value (e.g. the Duo lastLogin epoch, which changes every time a user authenticates) gets a new internal_id, so GcTableSync deletes the old row first (GcTableSyncSubtype.runInsertsUpdatesDeletes runs all deletes before inserts) and inserts the new row afterwards.

Incremental: the incremental flush calls buildProvisioningAttributeValueRowData without the existing rows, so every value of every user or group touched by the run is deleted and re-inserted, changed or not.

The gap is long, not a few seconds. Observed in production with a Duo provisioner (about 227k users with sync-back) during a full sync: the lastLogin row count dropped steadily (201,605 then 201,572 a minute later), no value rows were inserted for over two hours, and users with a blank lastLogin in a report built on these tables went from 196 to 1,316 over about 30 minutes, growing about 35 per minute. A daily report built during a sync had about 3,000 users with a blank last login. The values come back after the run finishes.

Fix: when there is no exact match, reuse an unused existing value row for the same object and attribute (a single-valued attribute, or any leftover row of a multi-valued attribute), keeping its internal_id with the new value and last_updated = now, so the table sync does an UPDATE in place. Exact matches are matched first so unchanged multi-valued values keep their rows. Only values beyond the existing row count get new ids, and only rows with no value left are deleted. There is no unique index on (attribute, object, value), so in-place updates cannot collide. For incremental, fetch the existing value rows scoped to the users and groups in the run (batched IN lists, not the whole provisioner) and pass them in, so unchanged values are left alone and changed ones are updated. Same for group attribute values.

Also worth checking: why the deletes run so slowly during a full sync (about one every 2 seconds), since that is what stretches the gap to tens of minutes.

Tests: changed single-valued attribute keeps its internal_id with the new value, in full and incremental; multi-valued add, remove, and swap reuse rows sensibly; existing GRP-7474 tests still pass.

# GRP-6569  Add new indexes on grouper_groups table to Grouper DDL

The developers on my team have found it beneficial for performance to add these indexes on the grouper_groups table in our PostgreSQL database:
{code:java}
CREATE INDEX IF NOT EXISTS group_its_alternate_name_idx
    ON public.grouper_groups USING btree
    (lower(alternate_name::text) COLLATE pg_catalog."default" ASC NULLS LAST)
    WITH (deduplicate_items=True)
    TABLESPACE pg_default;
    
CREATE INDEX IF NOT EXISTS group_its_display_name_idx
    ON public.grouper_groups USING btree
    (lower(display_name::text) COLLATE pg_catalog."default" ASC NULLS LAST)
    WITH (deduplicate_items=True)
    TABLESPACE pg_default;
    
CREATE INDEX IF NOT EXISTS group_its_name_idx
    ON public.grouper_groups USING btree
    (lower(name::text) COLLATE pg_catalog."default" ASC NULLS LAST)
    WITH (deduplicate_items=True)
    TABLESPACE pg_default; {code}

## Comments

### Chris Hyzer - 2026-06-30T01:36:10.398+0000

hanks for the suggestion. Before this could go into the core Grouper DDL there are a couple of blockers and some questions worth working through.

*Cross-database portability is the hard blocker.* Grouper's DDL is generated through ddlutils and must produce equivalent schema for Oracle, MySQL/MariaDB, and Postgres. The proposed statements are Postgres-only:
 * {{WITH (deduplicate_items=True)}} and {{TABLESPACE pg_default}} have no Oracle/MySQL equivalent
 * {{COLLATE pg_catalog."default"}} is Postgres-specific
 * function-based / expression indexes on {{lower(col)}} are expressed differently in each engine, and ddlutils' schema-compare doesn't cleanly round-trip expression indexes — so even where they're creatable, they tend to show up as perpetual "schema out of date" diffs on every install

If an index can't be expressed for all three supported databases, it can't really live in the shared DDL. So at minimum these would need an Oracle and MySQL form, and confirmation that the DDL-compare doesn't flag them on every startup.

*Question: which queries are actually benefiting?* Looking at how core Grouper queries these columns ({{{}Hib3GroupDAO{}}}):
 * The case-insensitive {{display_name}} and {{alternate_name}} searches are all leading-wildcard, e.g. {{{}lower(display_name) like '%term%'{}}}. A plain btree functional index can't be used for a leading-wildcard LIKE, so {{lower(display_name)}} and {{lower(alternate_name)}} btree indexes wouldn't be picked by Grouper's own queries. For {{%term%}} matching the right tool would be a {{pg_trgm}} GIN index, not a btree on {{{}lower(){}}}.
 * The left-anchored {{name}} prefix searches Grouper does ({{{}name like 'scope%'{}}}) are case-sensitive and already served by the existing unique {{{}group_name_idx{}}}.
 * The one core path a {{lower(name)}} btree index would actually help is the case-insensitive left-anchored scope search ({{{}lower(name) like 'scope%'{}}}).

So could you share more detail on the analysis behind these? Specifically:
 * Are these speeding up core Grouper code paths, or custom direct-SQL reporting/integration queries against {{{}grouper_groups{}}}?
 * {{EXPLAIN (ANALYZE, BUFFERS)}} before/after for the queries you saw improve, so we can see which index is actually chosen and for what predicate (equality vs {{term%}} vs {{{}%term%{}}}).
 * Rough table size where the benefit showed up.

If these are helping site-local queries (custom reports, integrations) rather than Grouper's own queries, the cleanest path is to add them directly in your own database — Grouper won't drop indexes it doesn't manage, so site-local indexes are fully supported and don't need to ship in core. If there's a genuine core benefit, let's scope it to the specific index(es) that core queries can use, with Oracle/MySQL/Postgres forms.

# GRP-7270  UI: group summary tab fails with GroupNotFoundException when the admin cannot VIEW a composite factor group

A user who is ADMIN on a composite owner group, but who does not have VIEW on one of the factor groups of that composite, cannot open the group summary tab at all. The screen renders the breadcrumb and header, then shows an error banner: Error: Cant view group: (groupId), Problem calling method viewGroup on edu.internet2.middleware.grouper.grouperUi.serviceLogic.UiV2Group. The whole summary body is missing.

Cause: in UiV2Group.viewGroupSummary the composite section runs when isAdmin is true and calls composite.getLeftGroup() and composite.getRightGroup() unguarded. Composite._getGroup throws GroupNotFoundException (Cant view group: ...) when the session subject cannot view the factor, and that exception escapes the whole action. The same applies to the getOwnerGroup() call in the loop over CompositeFinder.findAsFactor(group) just below it.

Note that GuiGroup.getCompositeOwnerText() and GuiGroup.getCompositeFactorOfOtherGroupsText() already handle this correctly: they catch GroupNotFoundException and return the text groupLabelNotAllowedToViewAllGroups. That is why the composite note line above the tabs still renders fine while the summary body blows up. UiV2Group never got the same treatment.

Steps to reproduce: 1) create a composite owner group with two factor groups. 2) grant a user ADMIN on the composite owner group. 3) make sure that user has no VIEW on one of the factor groups. 4) as that user, open the group and go to the Summary tab.

Expected: the summary tab loads, and the Composites row says the user is not allowed to VIEW all the groups in the composite. Actual: the entire summary tab fails to render and an error banner is shown.

Proposed fix: catch GroupNotFoundException around the factor lookups in the composite section of UiV2Group.viewGroupSummary, and around getOwnerGroup() in the composite factor loop. Add flags compositeFactorsNotViewable and compositeOwnersNotViewable to GroupSummaryContainer, and have groupSummary.jsp render the existing text keys groupLabelNotAllowedToViewAllGroups and groupLabelNotAllowedToViewOwner in those cases. No new externalized text is needed since both keys already exist.

### Chris Hyzer - 2026-08-26T02:19:13.783-0400

Swept every non-test call site of Composite.getLeftGroup(), getRightGroup() and getOwnerGroup() across the codebase. Two more findings beyond the group summary tab.

1) RelationGraph.buildParentNodes() (app/graph/RelationGraph.java, the block commented 'get groups where this is a composite factor'). CompositeFinder.findAsFactor() already filters to composites whose OWNER the caller can view, so getOwnerGroup() there is fine. But the loop then called composite.getLeftGroup() and composite.getRightGroup() purely to decide which side the current group was on, and those resolve the OTHER factor, which the caller may not be allowed to VIEW. So building the relation graph of a group that is the right factor of a complement or intersection whose left factor is not viewable throws GroupNotFoundException and fails the whole graph. Note the same file already handles this correctly about 200 lines further down in the 'Show composite factors' block, which catches GroupNotFoundException and logs 'maybe no privileges?'. Fixed by comparing composite.getLeftFactorUuid() / getRightFactorUuid() against the current group id instead of resolving the factor groups at all, which also avoids two unnecessary group lookups.

2) WsGroupDetail (grouper-ws, coresoap/WsGroupDetail.java, around the composite factor block). It does catch GroupNotFoundException, but rethrows it as a RuntimeException with the comment 'this means something bad is happening'. That is not something bad, it is exactly this scenario: a web service caller who requests includeGroupDetail and is ADMIN on a composite owner but lacks VIEW on a factor gets a RuntimeException instead of a graceful response. A fix is drafted locally (per factor try/catch, warn and omit the factor, mirroring GrouperMcpFindGroups) but is not committed, pending a decision on whether WS should be covered by this issue.

Also fixed in the UI while in here: groupEditComposite() in UiV2Group had the identical unguarded getLeftGroup()/getRightGroup() pair, so the edit composite screen failed the same way for the same users. It now shows the groupLabelNotAllowedToViewAllGroups error and returns, matching the two guard clauses already above it. And GuiGroup.getCompositeFactorOfOtherGroupsText() returned on the first unviewable owner, discarding the lines already built for the composites the user could see; it now appends groupLabelNotAllowedToViewOwner for that entry and keeps listing the rest.

Call sites confirmed already safe, for the record: CompositeFinder.findAsFactor and findAsOwner (both filter on canView and swallow GroupNotFoundException), Group.java lines around 931 and 2382 (catch and fall back to the raw uuid), Stem.java stem copy (catches and skips), MembershipPathGroup (runs under internal_callbackRootGrouperSession with its own canHavePrivilege and secure-group filtering), GrouperMcpFindGroups (per factor try/catch, field just omitted), and the delete group path in UiV2Group (catches, prints groupLabelNotAllowedToViewOwner). Two left alone: Group.java line ~8507 (unguarded getLeftGroup().hasMember() in system of record include/exclude logic, session context unclear), and XmlExporter._writeComposite, which declares throws GroupNotFoundException and propagates it (legacy export path).

Added a regression test in the grouper project: grouper/src/test/edu/internet2/middleware/grouper/app/graph/RelationGraphCompositePrivilegeTest. It builds a composite where the test subject can VIEW the owner and the right factor but not the left factor, then asserts that resolving the hidden factor through the composite throws (pinning the API contract, which was only covered on the root session happy path before), and that RelationGraph.build() from the right factor succeeds for both INTERSECTION and COMPLEMENT. The test has been run and passes. The UI and WS call sites are not unit testable from the grouper project.

Both the group summary tab and the relation graph failures were reproduced against a live composite in our production environment, as a user who is ADMIN on the composite owner and can VIEW only one of the two factors. ADMIN on the owner is required to hit it: the summary tab block is gated on isAdmin, so a VIEW only user just does not see that section. For the relation graph the reproduction has to start from the RIGHT factor, since the code resolves getLeftGroup() first.

### Chris Hyzer - 2026-08-26T02:25:15.533-0400

Command line reproduction of the WS case (2) above, using grouperClient:

{noformat}java -jar grouperClient.jar --operation=findGroupsWs --groupNames=some:folder:compositeOwner --includeGroupDetail=true --debug=true{noformat}

Run it as a subject that is ADMIN on the composite owner and cannot VIEW at least one of the two factor groups. Notes on the arguments: --includeGroupDetail=true is what makes the WS build a WsGroupDetail, and without it the composite block never runs and the call succeeds; the group looked up has to be the composite OWNER, since the block is gated on group.hasComposite(); and no --queryFilterType is needed when --groupNames is passed, since that takes the group lookup path. To run as a different subject than the authenticated WS user, add --actAsSubjectId=... --actAsSubjectSource=... (the client flag is actAsSubjectSource, while the equivalent REST body field is subjectSourceId), which requires the WS user to be authorized to act as that subject.

On unpatched code the response is HTTP 500 with X-Grouper-resultCode EXCEPTION, and the resultMessage carries a RuntimeException wrapping GroupNotFoundException thrown out of WsGroupDetail where it sets the left and right groups. Note that unlike the RelationGraph case this one is not order sensitive: both factors are resolved inside the same try block, so hiding either factor reproduces it.

Two things that can mask the bug behind an unrelated authorization failure, both checked in GrouperServiceJ2ee.retrieveSubjectActAsHelper before any of this code is reached: the authenticated WS user must be a member of the group named by ws.client.user.group.name (if that property is set), and passing an actAsSubject requires act as authorization even when the subject named is the authenticated user itself. Either one fails with 'User is not authorized' and a stack ending in retrieveSubjectActAsHelper, which is a different failure than the one this issue is about.

# GRP-7156  External systems view details: add a References section showing where the external system is used

h3. Goal

On the external system view details screen (Miscellaneous > External systems > Actions > View details), add a References section at the top, above the existing config section. It lists everywhere in Grouper that this external system (by its config id) is used, as a table of Type, Link, and Description. The purpose is to let an admin see the impact of an external system before editing or deleting it.

h3. UI

* Add a References table above the existing config table in viewExternalSystemConfigDetails.jsp.
* Columns: Type, Link, Description.
* Group rows by Type. If any single Type has more than 100 references, show only the first 100 for that type and display one info note at the top of the References section indicating the list was truncated.
* If a referenced config has its own view page, Link goes to it; if a type has no view page, show the config id (or owner) as plain text with no link.

h3. Scope and rules

* Config references only. Do NOT include runtime data such as grouper_sync rows or loader run logs.
* Include disabled configs (a disabled provisioner or loader still references the system, and deleting the system would break it if re-enabled). Exclude commented-out config; commenting only applies to file-style grouper_config entries.
* Each row has a human-readable Description: the referencing config plus its role, for example: Provisioner myLdapProv - ldapExternalSystemConfigId.
* No caching is needed; this screen is low traffic. Compute on page load.
* For the built-in grouper DB connection (config id grouper), match explicit stored values only. Do NOT treat a blank/defaulted loader or report field as a reference to grouper, or the grouper system would list nearly every loader and report in the registry.

h3. How references are found: two scans, unioned

Scan A - config editor references (grouper_config), metadata driven. Every config attribute that points at an external system declares it in metadata via optionValuesFromClass naming the external-system Java class. This is the same metadata that populates the config-editor dropdowns, so it is complete and maintained. Enumerate all configured module instances via GrouperConfigurationModuleBase.retrieveAllConfigurations(...). For each instance, iterate retrieveAttributes(). A reference exists when attribute.getConfigItemMetadata().getOptionValuesFromClass() equals the viewed system's class AND attribute.getValue() equals the viewed config id. Type label = module getTitle(); Link = that module's view operation plus config id.

Important: resolve references by the metadata class, NOT by key-name patterns. The same external-system class is referenced under many differently named keys. For example WsBearerTokenExternalSystem is referenced by seven different app provisioners (SCIM, Adobe, Okta, Datadog, Dropbox, FreshService, TrueFoundry), each with its own key suffix named after the app. Reading optionValuesFromClass per attribute handles all of these; a key-name heuristic would miss cases and risk false matches.

Scan B - attribute-value references (grouper_attribute_assign_value). Group loaders and report configs are stored as attribute values, not in grouper_config, and they do NOT carry the optionValuesFromClass metadata, so use a fixed map of attribute def name to external-system class to type label:

* grouperLoaderDbName -> DatabaseGrouperExternalSystem -> SQL group loader
* attributeLoaderDbName -> DatabaseGrouperExternalSystem -> Attribute/permission loader
* grouperLoaderLdapServerId -> LdapGrouperExternalSystem -> LDAP group loader
* reportConfigSqlConfig -> DatabaseGrouperExternalSystem -> Report config

Only scan the attribute names whose class matches the viewed system's class (a DB external system matches the three db/report rows; an LDAP external system matches only grouperLoaderLdapServerId). The owner group or folder gives the Link (its loader or report config page) and drives the Type. These four are the complete set of external-system-valued attribute def names.

h3. Reference channels confirmed by source sweep

Channel A (optionValuesFromClass, grouper_config) is provably exhaustive for dropdown-driven references: ConfigItemMetadata has only two option mechanisms, hardcoded optionValues (enums, never external systems) and optionValuesFromClass. There is no EL/elConfig option path, and every non-external-system option driver resolves to its own config type. External-system classes referenced this way and their type labels:

* DatabaseGrouperExternalSystem - SQL provisioner, SQL entity resolver, data provider query, several otherJob daemons (notification email db, sql-sync, ldap-to-sql, sftp-to-sql, subject-change), custom UI SQL query
* LdapGrouperExternalSystem - LDAP provisioner, LDAP entity resolver, LDAP data provider query
* WsBearerTokenExternalSystem - generic bearer-token provisioners (SCIM, Adobe, Okta, Datadog, Dropbox, FreshService, TrueFoundry); keys are named per app but resolve to this one class
* Azure, Box, Google, Duo, Remedy, RemedyDigitalMarketplace, Interfolio, TeamDynamix, Sftp - their respective provisioners and daemons
* ActiveMq, Sqs, RabbitMq - messaging provisioner

Subject sources also reference external systems: subjectApi.source.<id>.param.jdbcConfigId.value (DB) and subjectApi.source.<id>.param.ldapServerId.value (LDAP). When managed in the config UI these live in grouper_config and Scan A covers them. File-based subject.properties sources are a known gap (see limitations).

h3. Known limitations and special cases

* Code-only computed default: the messaging provisioner hardcodes messagingExternalSystemConfigId = grouperBuiltinMessaging when messagingType is builtin (GrouperMessagingConfiguration). No config key or dropdown holds this value, so no config scan surfaces it. Either special-case the builtin messaging external system or accept it as a documented gap.
* File-based config: references defined only in flat files (grouper-loader.properties, subject.properties) rather than the grouper_config table will not appear. Most current deployments use DB config.
* Singleton / prefix external systems (SMTP, OIDC, builtin internal messaging) are read by a fixed config prefix and are never selected from another config via a dropdown, so their References section will legitimately be empty. This is expected, not a bug.

h3. Implementation touch points

* viewExternalSystemConfigDetails action in UiV2ExternalSystem (grouper-ui serviceLogic) already has externalSystemConfigId and the type class in hand; compute references there and set them on ExternalSystemContainer.
* Add a references getter (grouped by type) on ExternalSystemContainer (or GuiGrouperExternalSystem).
* viewExternalSystemConfigDetails.jsp: render the References table above the existing config table.
* New helper for the type-to-view-operation map; config modules do not self-declare a UI view operation, so this is the main new piece of glue. Fall back to plain text when a type has no view page.
* Add externalized text keys for the section title, column headers, and the over-100 info note.

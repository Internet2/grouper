# GRP-1376  PSPNG: Support groups that require a member

From Akki Kumar, grouper-users Sept 21, 2016

Does PSPNG support member addition while creating a group in LDAP? Our LDAP system requires adding members during group creation and I couldn't find a way do it through PSPNG. 

changeLog.consumer.pspng_testOne.groupCreationLdifTemplate = dn: cn=${grouperUtil.extensionFromName(name)}||cn: ${grouperUtil.extensionFromName(name)}||objectclass: groupOfNames||member: <CONFIGURATION_TO_ADD_MEMBER>

### jgasper - 2016-10-18T19:05:43.775+0000

+1 ing the issue. Working with a client that uses OpenLDAP which uses the default X.500 schema which requires one or more _member_ attributes when a group is created.

The current work around is to use an _groupCreationLdifTemplate_ statement that includes adding a _member_ that points to a Mickey Mouse dn.

FYI: Using an empty member value works for this specific problem but caused problems elsewhere in PSP-NG processing.

### Jacob Feisley - 2017-01-11T06:21:24.540+0000

We hit this same issue when attempting to implement PSPNG against OpenLDAP with groupOfNames.

I did want to chime in that on the discussion here:
https://lists.internet2.edu/sympa/arc/grouper-users/2016-09/msg00121.html

It was suggested that when the last user is removed, the group should be deleted. In our case this behavior would cause problems as the groups UUID would change and systems referencing it would break. The current mechanism we have in PSP is that it populates the member field on an empty group with an empty string, which is valid by the schema.

I think ideally it would be nice to have to parameters in PSPNG: one to define the empty behavior (i.e. dont create / delete vs using an predefined "empty" member) The second would define what an empty member is (i.e. empty string vs something well defined like "cn=null,ou=users,dc=example,dc=com")

### bert - 2017-02-28T17:37:07.620+0000

I've developed and am testing the supportsEmptyGroups property. Setting this to false will change pspng's ldap-group provisioning to postpone group creation until a member is added to a group and will delete the group when its last member is removed.

While I've tried to annotate the process, some of the flows/logging is probably going to remain slightly confusing (especially when an incremental removal of a last member fails), as we don't want to slow down all the group removals by always reading the groups before removal. 

For those that care... When a membership removal fails with a schema-related error, an urgent full-sync is queued for that group. That full sync inherently reads all the memberships and has global knowledge of what needs to happen, and empty groups are deleted.

More details of what will happen when a last-member is removed and processed incrementally:
1. The removal is coalesced with all the other ldap changes from the changelog
2. This collection of coalesced operations will fail (as one of the removals will violate the schema)
3. PSPNG backs off and retries the ldap operations individually, eventually finding which removal(s) caused the schema violation
4. The group(s) involved are queued for a full sync
5. All the changelog operations are marked as successful
6. The Full-Sync thread will read a group from the full-sync queue, and all its members are read from grouper. When a group doesn't have any members and the provisioner's config says supportsEmptyGroups=false, the full-sync will result in the group being deleted.

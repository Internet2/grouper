# GRP-7191  LDAP provisioning wedges permanently when ldaptive BlockingConnectionPool deadlocks during pool validate/grow (only a restart recovers)

After a transient LDAP connectivity blip to Active Directory, an entire ldaptive connection pool becomes permanently unusable. Every daemon worker that calls getConnection blocks forever, so all LDAP-backed loader jobs and provisioners on that node stop (in our case a kite/AD provisioner incremental plus several O365 LDAP loaders sat STARTED for about 4.5 hours). The pool never self-heals; only a JVM restart clears it. Seen on Grouper with ldaptive 2.4.2, Java 17, AD over LDAPS reached through a firewall/load balancer that can silently drop idle TCP sessions.

Root cause from two thread dumps taken about 90 seconds apart: the pool background validation task holds the pool internal ReentrantLock while trying to grow the pool, and blocks indefinitely collecting a connection-create result. Lock holder stack: ExecutorCompletionService.take -> org.ldaptive.concurrent.CallableWorker.execute (CallableWorker.java 111 then 90) -> AbstractConnectionPool.createAvailableConnections (801) -> AbstractConnectionPool.grow (645) -> AbstractConnectionPool.validate (1123) -> AbstractConnectionPool.lambda-initialize-2 (605). Meanwhile all pool consumers park acquiring the same lock at BlockingConnectionPool.getConnection (BlockingConnectionPool.java 77) via PooledConnectionFactory.getConnection -> SearchOperation.execute.

Key observation: at the time of both dumps NO thread is actually opening a connection (no NettyConnection.open or socket-connect frame anywhere) and the ldaptive create-executor worker threads are idle in ThreadPoolExecutor.getTask. So createAvailableConnections is blocked in take waiting for a create result that nothing is producing -- a lost or never-completing task -- and because it runs while holding the pool lock, it wedges every getConnection caller until the process is restarted. This is the ldaptive-side defect and is being reported upstream separately (create work should not run under the pool lock, and take should not wait unbounded on a lost result).

Grouper-side factors that make this worse and that Grouper can address independent of the upstream fix, in edu.internet2.middleware.grouper.ldap.ldaptive.LdaptiveConfiguration: (1) the pool type is hardcoded to PooledConnectionFactory / BlockingConnectionPool; there is no way to select the less deadlock-prone SoftLimitConnectionPool, which creates connections outside the pool lock and would not freeze all checkouts. (2) validatePeriodically is force-enabled to true whenever any validation (checkin/checkout/periodic) is on, and the periodic validate task is exactly the code path that deadlocked. (3) ldap.<id>.timeout maps to ldaptive connectTimeout; our AD systems had it set to 2000000 ms (about 33 minutes) and no responseTimeout at all, so a stuck connection-create can hold the lock for an extremely long time.

Requested Grouper-side work: (a) track the upstream ldaptive fix and pick it up on the next ldaptive upgrade; (b) allow selecting the connection pool implementation (at least offer SoftLimitConnectionPool) so a stuck create cannot freeze all checkouts; (c) ship sane default connectTimeout and responseTimeout for LDAP systems (33 minutes is far too high) and document responseTimeout as a settable property; (d) reconsider force-enabling validatePeriodically. As an interim mitigation sites can lower ldap.<id>.timeout to a few seconds and add ldap.<id>.responseTimeout, but that only shortens the freeze window rather than eliminating it, since grow-under-lock can still occur on a plain getConnection.

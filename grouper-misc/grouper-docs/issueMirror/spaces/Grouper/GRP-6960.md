# GRP-6960  Performance follow-ups: ABAC change-log throughput and member-listing latency — ideas to revisit

Tracking JIRA for performance ideas discussed alongside GRP-6907 (pass-through change-log batching) and GRP-6956 (page-size bump), plus the Ruth-flagged UI slowness follow-on to GRP-6876. These are scoped follow-ups, not commitments; each gets its own ticket when work starts.

Already shipped or in flight (for context, do not redo here)
 * GRP-6907: pass-through change-log batching.
 * GRP-6956: raise {{changeLog.changeLogTempToChangeLogQuerySize}} 1000 → 5000 and {{changeLog.tooManyChangeLogUpdatesSize}} 10000 → 50000 in {{{}grouper-loader.base.properties{}}}.
 * GRP-6876: {{group_set_member_member_field_idx}} on {{{}grouper_group_set(member_id, member_field_id){}}}.
 * In flight (separate JIRA): {{hibernate.jdbc.batch_size}} 200 → 1000 in {{{}grouper.hibernate.base.properties{}}}.

Idea 1 — Drop unused string02..string12 indexes on grouper_change_log_entry_temp

{{grouper_change_log_entry_temp}} has 12 single-column indexes ({{{}change_log_temp_string01_idx{}}} through {{{}change_log_temp_string12_idx{}}}). A non-test codebase scan shows only {{string01}} is queried (36 references in the {{Hib3PIT*DAO}} classes' NOT EXISTS subqueries for PIT reconciliation). {{string02..string12}} have zero query references. Raw SQL filters against the temp table use only {{id}} and {{{}created_on{}}}. Every row inserted and every row deleted touches all 12 indexes; 11 of those are pure write amplification on a high-churn table. Approximately 22M wasted secondary-index modifications per 1M-row ABAC burst. Experiment plan: drop the 11 indexes in test, run a representative ABAC backlog through the daemon, measure insert and delete wall time, confirm PIT reconciliation queries (which use {{{}string01_idx{}}}) remain fast. Rollback is trivial (CREATE INDEX in seconds on a short-lived temp table). If experiment is favorable, ship a permanent change with install SQL updates, GrouperDdl version class, upgrade task, and AI DDL reference.

Idea 2 — Member-listing UI: route through grouper_sql_cache_mship instead of grouper_memberships_all_v

Measured on Penn prod (Postgres 16) after GRP-6876 indexes: the {{MembershipFinder}} HQL that backs the UI member-list page runs in 51μs for an empty group and ~5s for a 389K-member group. The cost at the tail is materializing the flattened view, deduping, and sorting — not bad plan choice. Rewriting the query to read from {{{}grouper_sql_cache_group{}}}/{{{}grouper_sql_cache_mship{}}} (already flat, no DISTINCT needed) gives ~5x speedup on the 389K case: ~1s. Tradeoff is daemon-sync freshness lag (seconds to minutes). Same Java code path ({{{}MembershipFinder{}}}) backs both the UI and the WS {{{}GetMembershipsRequest{}}}, so the change must be opt-in by caller, not a global swap, to avoid silently breaking WS consumers, rules engine, loader incremental, sync, etc.

Idea 3 — Overload QueryOptions.secondLevelCache(true) as the cache-table routing signal

Implementation approach for Idea 2. The existing {{QueryOptions.secondLevelCache(true)}} flag has zero non-test callers in the codebase that set it to {{true}} today (only 14 explicit {{false}} calls on save paths). Default behavior when unset is no caching (verified at {{{}HibUtils.java:288{}}}). Proposal: when {{{}queryOptions.getSecondLevelCache() == Boolean.TRUE{}}}, {{MembershipFinder}} (or its DAO) routes to the cache-table HQL; otherwise unchanged live-view HQL. UI controllers add {{.secondLevelCache(true)}} to their {{QueryOptions}} at the call site to opt in. WS, rules, loader, sync stay live. No new public API. Risks to document: semantic overload (the flag now signals two cache layers — JVM L2 and DB cache table); future copy-paste to lower layers ({{{}ByHql.setCacheable(true){}}} has 131 callers and must not pick up the routing logic); javadoc on the QueryOptions method should call out the membership-finder overload.

Idea 4 — PIT-vs-live index audit

GRP-6876 was a case where the PIT mirror table ({{{}grouper_pit_group_set{}}}) had an index ({{{}pit_gs_member_member_field_idx{}}}) that the live table ({{{}grouper_group_set{}}}) was missing, hidden for years until a slow enough symptom surfaced. The fix added the missing live-side index. Likely there are more of these. Audit: for each non-temporal index on {{{}grouper_pit_X{}}}, check whether {{grouper_X}} has the analogous index. PIT-only indexes on {{{}start_time{}}}, {{{}end_time{}}}, {{source_id}} are PIT-specific and don't need a live analog. Indexes on business columns (member ids, owner ids, field ids, type ids) are the candidates. Estimated 1-2 hours of mechanical work; expected to surface at least one more latent slow-query landmine.

Idea 5 — Direct-JDBC bulk insert for pass-through change-log entries

GRP-6907 added the {{passThroughBatch}} accumulator but it still flushes through the same Hibernate session as everything else. For pass-through entries (ABAC {{{}dataRowFieldAssign{}}}, {{{}dataRowAssign{}}}, {{{}dataFieldAssign{}}}) there is no per-row Java processing — no PIT updates, no cache sync, no flattening. They could be inserted via raw JDBC {{addBatch()}} directly into {{{}grouper_change_log_entry{}}}, bypassing the Hibernate session/dirty-check/flush overhead for that specific batch. Keep the Hibernate path for entries that need per-row processing. Larger code change than the config bumps; reserve until measurements show GRP-6956 + the hibernate.jdbc.batch_size change aren't sufficient.

Idea 6 — Single-statement temp-table delete per page

{{ChangeLogTempToEntity.java}} deletes processed rows from {{grouper_change_log_entry_temp}} in 1000-id {{IN (…)}} chunks. At the new page size of 5000, that is 5 delete statements per page. Could be replaced with one {{DELETE FROM grouper_change_log_entry_temp WHERE id <= :maxIdProcessed}} per page (or a single TRUNCATE if the page drained everything). Small win, simple code change. Defer until measurement shows the delete cost is meaningful.

Idea 7 — Existence short-circuit and very-large-group handling for WS

Two related shapes:
 * "Does group X have any members" implemented as a list-with-pageSize=1 query goes through {{grouper_memberships_all_v}} and pays the full join cost. A dedicated existence check that hits {{grouper_memberships}} (or {{{}grouper_sql_cache_mship{}}}) with {{LIMIT 1}} would be order-of-magnitude cheaper. Worth grepping for callers that ask the existence question via a list call.
 * WS {{GetMembershipsRequest}} on very large groups (300K+) measures around 5 seconds on Penn prod — not the original 30-second pathology, but still on the slow side and the source of historical 502s. The structural fix is API-shape: mandatory paging cursors, refuse to materialize beyond a threshold, or an {{allowLargeResult=true}} opt-in. Index changes alone will not get this below a few seconds because the cost is real materialization work over the flattened view.

Explicitly rejected (do not revisit without new evidence)
 * Dropping {{{}member_sort_string0_idx{}}}. The original concern was that it might be causing the planner to choose a pathological {{index-scan-with-filter}} plan on {{{}ORDER BY sort_string0 LIMIT 100{}}}. Penn prod measurement after GRP-6876 indexes shows healthy linear scaling with group size from microseconds to ~5s at 389K members — no sign of the bad plan being chosen. The index legitimately supports other paginated sorted-list paths. {{pg_stat_user_indexes}} showing low {{idx_scan}} is not a reliable signal here; it undercounts sort-only usage. Leave it in place.
 * Persisting the change-log sequence-number cache across pages within a single daemon run. {{SELECT MAX(sequence_number) FROM grouper_change_log_entry}} is an index-extreme lookup on the PRIMARY KEY (verified across postgres/oracle/mysql install SQL), so it costs single-digit milliseconds at any realistic table size. Eliminating it would save under a second on a 1M-row run. Not worth the code change.
 * Size-branching the membership query (small groups → live view, big groups → cache table). The right axis is {_}freshness contract{_}, not group size. UX expectations on small-group membership freshness are unforgiving regardless of size. Pick the cache vs live decision per screen/endpoint, not per group size.

Acceptance

This is a tracking ticket; close it once each idea above has either spawned a dedicated JIRA, been measured-and-deferred with notes, or been explicitly dropped.

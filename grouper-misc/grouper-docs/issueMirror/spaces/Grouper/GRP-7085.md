# GRP-7085  Provision faculty users to Interfolio (RPT and optional FS)

h2. Background

Faculty access to Interfolio (RPT = review/promotion/tenure, FS = faculty search) was driven by a nightly CSV faculty load to Interfolio plus a manual GSH "RPT user differences" report. Replace that with a real Grouper provisioner driven by group membership.
h2. What was built

A new Interfolio provisioner in Grouper ({{{}edu.internet2.middleware.grouper.app.interfolio{}}}) that talks to Interfolio's HMAC-SHA1 (INTF) APIs:
 * Creates and updates users via the IAM API; looks them up via the byc/core users search.
 * On *provision* (member added to a provisionable group): create the user, then subscribe to *RPT* (always) and to *FS* (controlled by an {{enableFs}} config, default true) — so a deployment can do RPT-only or RPT+FS.
 * On *deprovision* (member removed): unsubscribe from RPT (and FS if {{{}enableFs{}}}). Interfolio does not authorize a hard delete for our credentials, so the account remains and only product access is removed.
 * A reusable *external system* holds the connection (HMAC keys, tenant/database id, IAM and byc/core hosts) and is configurable in the UI with a Test button.
 * The provisioner is configurable in the UI (external system + {{{}enableFs{}}}).

h2. Out of scope
 * *Faculty180 / FAR:* a separate Interfolio auth realm our credentials are not authorized for (needs its own API key and string database id from Interfolio). Methods are stubbed/documented but not enabled.
 * *Sync-back* to the generic {{grouper_prov}} reporting tables: planned follow-up.

h2. Testing
 * API-level: user create/search/update, duplicate-email and immutable-UID validation, subscribe/unsubscribe RPT and FS — against a mock service.
 * Full provisioner sync: RPT+FS (default) and RPT-only ({{{}enableFs=false{}}}), including deprovision/unsubscribe on member removal.
 * All passing.

# GRP-7450  Deleting a report instance stored in the database orphans its grouper_file row

When a report instance whose file is stored in the database (reporting.storage.option = database, the default) is deleted, its grouper_file row is never deleted, so it is orphaned forever.

GrouperReportInstanceService.deleteReportInstances only handles S3 and filesystem storage: if the instance is not in S3 it calls GrouperReportLogic.deleteFromFileSystem, which treats the report instance file pointer as a file path. For database storage the pointer is a grouper_file id, so no file matches and nothing is deleted. Then the report instance attribute assign is deleted, so nothing points at the grouper_file row any more.

Callers that leak: GrouperReportClearJob (report retention cleanup, two places) and GrouperReportConfigService (deleting a report config deletes all its instances).

GrouperReportLogic.deleteFileFromDatabase(reportInstance) already does the right thing (deletes the grouper_file row by id, no-op if the pointer is blank) but it is only called from UiV2GroupImport.

Fix: in deleteReportInstances, delete database stored files with deleteFileFromDatabase (e.g. if the pointer is a grouper_file id, GrouperFileDao.existsById), else filesystem. Also consider a one time cleanup of existing orphans: grouper_file rows with system_name of the report system name whose id is not referenced by any report instance file pointer attribute value. Check whether workflow file deletes have the same issue.

# GRP-7409  Data provider full sync: load each subject id range batch with joins instead of member id IN lists

h3. Background

Follow-up to GRP-7408. In range mode (the default, fullSyncSubjectIdRetrieval=range), GrouperDataProviderLogic.syncFull() splits all subject ids into batches of fullSyncSubjectIdBatchSize and, per batch, calls syncFullLoadGrouperDataForRange(from, to). That first resolves the batch to member internal ids with Hib3MemberDAO.selectByDataProviderAndSubjectIdRange(), then syncFullLoadGrouperDataForMemberInternalIds() loads the existing data with four DAO calls, each of which chunks the member ids into IN lists (1000 per query after GRP-7408):

{code:java}// GrouperDataProviderLogic.syncFullLoadGrouperDataForMemberInternalIds (current)
GrouperDictionaryDao.selectByDataProviderAndMembers(providerId, memberInternalIds);   // 2 IN lists per chunk
GrouperDataFieldAssignDao.selectByProviderAndMembers(providerId, memberInternalIds);
GrouperDataRowAssignDao.selectByProviderAndMembers(providerId, memberInternalIds);
GrouperDataRowFieldAssignDao.selectByProviderAndMembers(providerId, memberInternalIds);{code}

Measured at Penn on the affiliation provider (525k members, 577k row assigns, 3.6M row field assigns, batch size 100000): millisRetrievedFromGrouper 2,025,539 of a 37 minute full sync, while millisRetrievedFromTarget was only 138,414. Each individual chunk query is fast (well under a second); the cost is the number of round trips plus object mapping. At 200 per chunk that was about 8,000 queries; at 1000 it is still about 1,600.

h3. Proposal

For range mode only, load each table for the whole batch in one query by joining to grouper_members and filtering on provider and the lowercased subject id range, the same filter selectByDataProviderAndSubjectIdRange already uses. That is 4 queries per batch regardless of batch size (about 24 for the example above instead of about 1,600).

h4. SQL for each table

{code:sql}-- row field assigns
select gdrfa.*
  from grouper_data_row_field_assign gdrfa
  join grouper_data_row_assign gdra on gdra.internal_id = gdrfa.data_row_assign_internal_id
  join grouper_members gm on gm.internal_id = gdra.member_internal_id
 where gdra.data_provider_internal_id = ?
   and lower(gm.subject_id) >= ? and lower(gm.subject_id) <= ?

-- row assigns
select gdra.*
  from grouper_data_row_assign gdra
  join grouper_members gm on gm.internal_id = gdra.member_internal_id
 where gdra.data_provider_internal_id = ?
   and lower(gm.subject_id) >= ? and lower(gm.subject_id) <= ?

-- field assigns
select gdfa.*
  from grouper_data_field_assign gdfa
  join grouper_members gm on gm.internal_id = gdfa.member_internal_id
 where gdfa.data_provider_internal_id = ?
   and lower(gm.subject_id) >= ? and lower(gm.subject_id) <= ?

-- dictionary text referenced by either
select gd.internal_id, gd.the_text from grouper_dictionary gd
 where gd.internal_id in (
   select gdfa.value_dictionary_internal_id
     from grouper_data_field_assign gdfa
     join grouper_members gm on gm.internal_id = gdfa.member_internal_id
    where gdfa.data_provider_internal_id = ?
      and lower(gm.subject_id) >= ? and lower(gm.subject_id) <= ?
   union
   select gdrfa.value_dictionary_internal_id
     from grouper_data_row_field_assign gdrfa
     join grouper_data_row_assign gdra on gdra.internal_id = gdrfa.data_row_assign_internal_id
     join grouper_members gm on gm.internal_id = gdra.member_internal_id
    where gdra.data_provider_internal_id = ?
      and lower(gm.subject_id) >= ? and lower(gm.subject_id) <= ?){code}

h4. New DAO method (example, one per DAO)

{code:java}/**
 * full sync: row field assigns for all members of a data provider whose lowercased subject id
 * is in the batch range.  one query per batch instead of IN list chunks of member ids
 */
public static List<GrouperDataRowFieldAssign> selectByProviderAndSubjectIdRange(
    Long dataProviderInternalId, String fromSubjectIdLower, String toSubjectIdLower) {
  if (dataProviderInternalId == null) {
    throw new NullPointerException();
  }
  return GrouperUtil.nonNull(new GcDbAccess().sql(
      "select gdrfa.* from grouper_data_row_field_assign gdrfa "
      + " join grouper_data_row_assign gdra on gdra.internal_id = gdrfa.data_row_assign_internal_id "
      + " join grouper_members gm on gm.internal_id = gdra.member_internal_id "
      + " where gdra.data_provider_internal_id = ? "
      + " and lower(gm.subject_id) >= ? and lower(gm.subject_id) <= ?")
    .addBindVar(dataProviderInternalId)
    .addBindVar(fromSubjectIdLower)
    .addBindVar(toSubjectIdLower)
    .selectList(GrouperDataRowFieldAssign.class));
}{code}

h4. Logic change

{code:java}// GrouperDataProviderLogic.syncFullLoadGrouperDataForRange (proposed)
private void syncFullLoadGrouperDataForRange(String fromSubjectIdLower, String toSubjectIdLower) {

  // still needed: the member wrappers must include members that have data in grouper for this range
  Set<Long> memberInternalIds = GrouperDAOFactory.getFactory().getMember()
      .selectByDataProviderAndSubjectIdRange(providerId, fromSubjectIdLower, toSubjectIdLower);

  // same as syncFullLoadGrouperDataForMemberInternalIds() but each load is one range query
  dictionary   = GrouperDictionaryDao.selectByDataProviderAndSubjectIdRange(providerId, from, to);
  fieldAssigns = GrouperDataFieldAssignDao.selectByProviderAndSubjectIdRange(providerId, from, to);
  rowAssigns   = GrouperDataRowAssignDao.selectByProviderAndSubjectIdRange(providerId, from, to);
  rowFieldAssigns = GrouperDataRowFieldAssignDao.selectByProviderAndSubjectIdRange(providerId, from, to);
  // then the existing processData*Wrappers() and indexDataByMember()
}{code}

h3. Notes and gotchas

* Keep the existing IN list methods for incremental sync, list mode (fullSyncSubjectIdRetrieval=list) and the straggler pass (syncFullLoadGrouperDataForSubjectIds).
* The join must return data for exactly the members selectByDataProviderAndSubjectIdRange returns for the same bounds (members with field or row data for this provider). A mismatch would make the sync think data is missing and delete or re-insert it; the failsafe (percentFieldAssignsAllowedToBeRemoved) should catch a gross error, but add a test.
* Range bounds are inclusive and compare lower(subject_id) with the database collation; the Java-side batching sorts the same lowercased strings. Keep the straggler pass as the safety net for any collation differences.
* There is no index on lower(grouper_members.subject_id); the range filter is applied after joining from the provider side (grouper_data_row_assign has an index on data_provider_internal_id). At Penn the existing range query takes about 2 seconds for 210k members, so this is acceptable; a function index on lower(subject_id) is optional.
* Result sets are large (hundreds of thousands of rows per batch, which is already what gets loaded into memory today). GcDbAccess already sets fetch size 1000 on prepared statements; on Postgres the fetch size only streams when autocommit is off, so check memory with a large provider.
* Consider lowering the default fullSyncSubjectIdBatchSize guidance if memory per batch becomes the limiter; the number of queries no longer depends on it.

h3. Testing

* Compare row counts loaded by the old member-id path and the new range path for the same batch.

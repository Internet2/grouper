# GRP-7346  Scope the config cache notification per config file, so a change to one config file does not invalidate all config on every node

Follow on from GRP-7298. When any config property changes, ConfigPropertiesCascadeBase.clearCacheThisOnly() empties the entire configFileCache, so the next read rebuilds every config class rather than only the one whose file changed.

The caches are already granular enough to do better. ConfigDatabaseLogic.databaseConfigCache is keyed per config file name, and configFileCache is keyed by class where each class maps to one main config file.

The obvious objection is elConfig values, since a config EL expression is evaluated with allowStaticClasses true and can therefore read any other config file. That turns out NOT to be a blocker. EL is evaluated at read time, not baked into the cache. The cached object (this.properties) holds the RAW unevaluated key.elConfig text, and propertyValueStringHelper evaluates it fresh on every read. The separate propertiesHelper(true) path that does evaluate EL at build time only feeds properties(), which is used by config screen and validation code such as GrouperCheckConfig and GrouperInfo, not by propertyValueString. So a config object holding an EL value that references another config file will resolve correctly against the other file even if only that other file was invalidated.

Two things to settle when doing this. First, confirm no config file appears in more than one config class cascade (base plus overlay plus database); if one does, invalidation has to key off the file and map back to every class whose cascade includes it. Second, decide what the cross JVM notification carries: GrouperCacheDatabase.customNotifyDatabaseOfChanges(ConfigDatabaseLogic.DATABASE_CACHE_KEY) currently uses a single key for all config, so other JVMs are told that config changed without being told which file. Going granular locally without carrying the file name would make one JVM smarter than its peers.

Payoff: after GRP-7298 a 200 property import still does 9 full config rebuilds, which is one per config class. Per file invalidation should make that 1. It also helps every single config save, not just imports.

To measure, set ConfigPropertiesCascadeBase.CONFIG_CACHE_INSTRUMENTATION to true and rebuild; it counts config cache clears and full rebuilds, and GrouperUiFilter logs them per request.

### Chris Hyzer - 2026-09-20T12:58:29.135-0400

Scoping this, after looking at what the cross JVM cache notification already does and at how lopsided the config actually is in production.

Motivation, config rows per file in a production database: grouper.properties 11767 rows (428 kB of values), grouper-loader.properties 5930, grouper.client.properties 581, grouper.text.en.us.properties 369, subject.properties 100, grouper-ui.properties 19, grouper-ws.properties 10, grouper.cache.properties 7. About 18800 rows in total, and the largest file is over 1600 times the size of the smallest. Today, editing one of the 19 rows in grouper-ui.properties invalidates everything, including the 11767 row grouper.properties config, on every node.

The mechanism to fix this already exists and does not need a new table. GrouperCacheDatabase maintains grouper_cache_overall (a single row holding nanos_since_1970, the cheap probe for has anything changed at all) and grouper_cache_instance (one row per cache name). A background thread reads the one row overall table first and only reads the instance rows if it moved.

Config currently registers ONE cache name for all eight config files: custom__edu.internet2.middleware.grouperClient.config.db.ConfigDatabaseLogic.databaseConfigs. That is why the cross JVM path cannot tell which file changed, and why GrouperConfigHibernate.clear(GrouperCacheDatabaseClearInput) has no choice but to clear everything.

Proposal: scope the config cache name per config file, using the convention the framework already supports. GrouperCacheDatabase, when it cannot find a clearable registered under an exact cache name and the name contains four underscores, strips the suffix and looks the clearable up by prefix. SourceManager already relies on this: it registers the base name SourceManager.reloadSource and notifies with that name plus four underscores plus the source id, and its clear handler pulls the source id back out with substringAfterLast.

So for config: keep registering ConfigDatabaseLogic.DATABASE_CACHE_KEY as today, notify with DATABASE_CACHE_KEY plus four underscores plus the config file name, and have GrouperConfigHibernate.clear pull the file name back out and invalidate only the config for that file. GrouperConfigHibernate.updateLastUpdated already knows which file changed. No schema change, no DDL, no new table.

On the in memory side, ConfigPropertiesCascadeBase.clearCacheThisOnly should take an optional main config file name and remove only the cached config objects whose getMainConfigFileName matches, falling back to clearing everything when it is not given. Match against already cached instances rather than going through ConfigFileName.getConfig(), because that would build a config object as a side effect of invalidating one. GrouperUiApiTextConfig.clearCache should take the same argument so that editing grouper.text.en.us.properties does not drop the other locales. Both must keep the batch suppression guard, see GRP-7353.

Deliberately NOT doing, and why. A new config change log table, or reusing the Grouper change log, were both considered and rejected. First, ConfigDatabaseLogic carries an explicit comment that it must not use anything from the Grouper API, because the API database framework reads config and that would be circular; the Grouper change log is API layer, whereas GrouperCacheDatabase is safe because it uses GcDbAccess raw JDBC. Second, a change log is event based, so a node that has been down longer than the retention window would silently miss changes and serve stale config; the timestamp tables are state based and a node converges no matter how long it was away. For config, which changes rarely, that property is worth more than precision. Selecting max(last_updated) and count(*) from grouper_config grouped by file would also work, but scans about 19000 rows to learn what an 8 row table already says; worth keeping in mind as a fallback or consistency check, not as the poll.

Also not doing: splitting ConfigDatabaseLogic.databaseConfigCache refresh per file. That cache is keyed per file but is populated wholesale by one query with a single databaseConfigCacheLastRetrieved timestamp, so making it per file means per file timestamps in the bootstrap config path, which is the riskiest code here. Worth revisiting after measuring, since re-reading 19000 rows on any config change is not nothing.

How this layers with GRP-7348: tier 1 is grouper_cache_overall, one row, did anything change. Tier 2 is grouper_cache_instance per config file, which file, and that is this issue. Tier 3 is diffing keys by last_updated within the one changed file and applying only the delta, which is GRP-7348. They compose, and tier 2 makes tier 3 much cheaper: a grouper-ui.properties change would diff 19 rows instead of 19000.

Fixed in commit a1c4134ed942 on GROUPER_7_BRANCH.

Notification side: GrouperConfigHibernate.updateLastUpdated now takes the config file that changed and notifies under DATABASE_CACHE_KEY plus the four underscore separator plus the file name, and registerDatabaseCache registers a scoped cache name for each ConfigFileName alongside the base name. The clear handler pulls the file name back out of the cache name it is given, and an unscoped name still means all config, so a node running older code that notifies without a scope still works.

In memory side: ConfigPropertiesCascadeBase.clearCacheThisOnly takes an optional main config file name and removes only the cached config objects whose getMainConfigFileName matches, and GrouperUiApiTextConfig.clearCache does the same for its per locale cache. Both match against the objects ALREADY in the cache rather than going through ConfigFileName.getConfig(), which would build a config object as a side effect of invalidating one. Both keep the batch suppression guard from GRP-7353. The import path in UiV2Configure also scopes its single clear at the end to the file that was imported, otherwise the per property writes would be scoped but that one clear would still discard every other file's config.

Worth recording for anyone touching this area. customNotifyDatabaseOfChanges checks customDatabaseClearables for an EXACT registered cache name and silently does nothing if it is absent. The prefix lookup in GrouperCacheDatabase that strips the separator is on the RECEIVING side only. So a scoped name has to be registered, which is why registerDatabaseCache now loops over ConfigFileName; SourceManager registers each of its scoped names for the same reason. Missing this would have stopped every config change notifying other nodes, with no error anywhere.

Verified on a running instance. A scoped row appears per config file in grouper_cache_instance, for example ending in four underscores then grouper-loader.properties and another ending in grouper-ui.properties. After changing one property in grouper-ui.properties, which has 19 rows in production, the next request did 1 config rebuild rather than invalidating everything. After a 400 property import into grouper-loader.properties, the following config screen view did 1 rebuild, where before this change it did 4. The import itself was unchanged at 237 MB and 4 rebuilds against a 226 MB and 4 rebuild baseline, so no regression.

Not done, deliberately, and noted in the earlier comment: ConfigDatabaseLogic.databaseConfigCache is still cleared as a whole. It is keyed per config file but is populated wholesale by one query with a single databaseConfigCacheLastRetrieved timestamp, so per file invalidation there needs per file timestamps in the bootstrap config path. Worth revisiting, since a production database has about 18800 config rows and re-reading all of them on any config change is not free. Note that cache also does a full refresh on its own every grouper.config.secondsBetweenFullRefresh seconds, 3600 by default, so it is a backstop rather than the fast path.

Next in this area: GRP-7348 would diff keys by last_updated within the one changed file and apply only the delta, which this issue makes much cheaper, since a grouper-ui.properties change now points at 19 rows rather than all 18800.

### Chris Hyzer - 2026-09-20T14:09:57.140-0400

Correction to the comment above, which quoted the wrong interval and undersold this fix.

The propagation path is not the hourly refresh. The GrouperCacheDatabase background thread polls every grouper.cache.database.checkIncrementalAfterSeconds, which defaults to 5 SECONDS. On each poll it reads the single row grouper_cache_overall and, only if that timestamp moved, reads grouper_cache_instance and clears the caches named there. A full re-read of the cache tables happens every grouper.cache.database.checkFullAfterSeconds, default 3600.

The two ConfigDatabaseLogic settings quoted earlier, grouper.config.secondsBetweenUpdateChecksToDb at 600 and grouper.config.secondsBetweenFullRefresh at 3600, are that class's own independent backstop for when nothing notified it. They are not how a config change reaches other nodes.

So before this change, a single property edit to a 19 row file caused every node in the environment to discard ALL config, including the 11767 row grouper.properties, within about five seconds, and rebuild it. That is the cost this issue removes, and it is considerably larger than the earlier comment implied.

For completeness, on the node where the change is made there is no polling at all: updateLastUpdated writes the notification row AND calls clearConfigsInMemory in the same request, so saving a daemon config and running it immediately picks up the new values on that node. The scoping does not affect that, since the file whose config is dropped is exactly the file that was saved.

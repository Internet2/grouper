# GRP-7319  Entra provisioner fails to match a service principal as a group owner - strips the resource reference and retains only object id

The groupOwners field of the Entra provisioner can be a list of user object ids, or a call to provisioningGroupWrapper.groupMembers(groupName, 'entityAttributeValueCacheX'). Alternatively, it can be hard-coded to a resource reference to a service account -- e.g., {{https://graph.microsoft.com/beta/servicePrincipals(appId='<appId>')}} or {{https://graph.microsoft.com/beta/directoryObjects/<id>}} _(note: currently this requires the beta/ version, since v1.0 does not return service accounts in the /owners query)_. But retrieving the current owners for comparison, using {{GET /groups/{id}/owners}} during the {{retrieveIndividualTargetGroupsAndEntities}} phase, converts both kinds of owner uniformly down to their bare Azure object id when populating the {{groupOwners}} attribute on the target provisioning group.

This will match, add, and remove users in Entra with no issues. But for service accounts, the full reference in the provisioner config does not match the bare id in the target provisioning group. The result is that it tries to insert the full reference again, resulting in a (harmless) error "One or more added object references already exist for the following modified properties: 'owners'". It will also try to delete the mismatched bare id, resulting in a (harmless) error "Resource '685ec840-715a-43b9-b4d9-xxxxxxxxxxxx' does not exist or one of its queried reference-property objects are not present". While the errors are harmless and it does correctly insert the owner service account as the full reference, it (1) needlessly tries to update the owners for every group on a full sync, and (2) Adds to the update count equal to the number of provisioned groups, masking the accurate count for true group changes.

Use case:

*groupOwners:*

{{${set = provisioningGroupWrapper.groupMembers('some-group-of-owners', 'entityAttributeValueCache0'); set.add("https://graph.microsoft.com/beta/directoryObjects/685ec840-715a-43b9-b4d9-xxxxxxxxxxxx"); set}}}

*Suggested fix:*

* In {{retrieveGroupOwnersHelper2}}'s response parsing ({{GrouperAzureApiCommands.java:2024-2034}}), read each owner's {{@odata.type}} alongside its {{id}}. For {{#microsoft.graph.servicePrincipal}} (and any other non-user directory object type), build the full reference using the connector's existing configured {{resourceEndpoint}} — the same property this class already reads for every other Graph call — rather than a bare id; leave user-type owners as bare ids, since that's what the existing {{/users/{id}}}-prefixing write path already expects:
{noformat}ArrayNode ownerValues = (ArrayNode) GrouperUtil.jsonJacksonGetNode(bodyNode, "value");

List<String> ownerIds = new ArrayList<String>();

String resourceEndpoint = GrouperUtil.stripLastSlashIfExists(GrouperLoaderConfig.retrieveConfig().propertyValueString(
    "grouper.azureConnector." + configId + ".resourceEndpoint", "https://graph.microsoft.com/v1.0/"));

if (ownerValues != null && ownerValues.size() > 0) {
  for (int k=0; k<ownerValues.size(); k++) {
    JsonNode singleOwnerNode = ownerValues.get(k);
    String ownerId = GrouperUtil.jsonJacksonGetString(singleOwnerNode, "id");
    String odataType = GrouperUtil.jsonJacksonGetString(singleOwnerNode, "@odata.type");
    if (StringUtils.equals(odataType, "#microsoft.graph.servicePrincipal")) {
      ownerIds.add(resourceEndpoint + "/directoryObjects/" + ownerId);
    } else {
      ownerIds.add(ownerId);
    }
  }
}
{noformat}
No {{/beta}}-specific code or version substitution is needed anywhere — this reuses whatever {{resourceEndpoint}} the connector is already configured with. If Microsoft ever moves this behavior to a different API version, or a future default changes which version returns service-principal owners, no Java change is required — only the connector's {{resourceEndpoint}} config value.
* *Document/require, for admins:*
** The connector's {{grouper.azureConnector.<configId>.resourceEndpoint}} must point at a Graph API version whose {{/groups/{id}/owners}} actually returns servicePrincipal-typed owners — currently that's {{https://graph.microsoft.com/beta/}}, not {{v1.0}}. Note this is a connector-wide setting: pointing it at beta affects every Graph call this connector makes (group/user CRUD, memberships, etc.), not just the owners lookup, so treat it as a deliberate, tested change rather than a narrow owners-only fix.
** A hard-coded service-account owner value in {{groupOwners}} config must be written as {{<resourceEndpoint>/directoryObjects/{id}}} (object id, not appId), using the exact same {{resourceEndpoint}} value the connector is configured with, so it textually matches what the munged GET output above now produces. The {{servicePrincipals(appId='...')}} form can't be reconstructed from the {{/owners}} GET response (which only returns object id, never appId) and will remain permanently mismatched if used.
* Remove the dead normalization block in {{AzureProvisioningTranslator.java:109-130}} (the {{adjustedOwners}} set that's built but never assigned back). It implements the opposite approach — shrinking the source's full reference down to a bare id — which this fix supersedes and which would also break inserts for service-account owners (a bare id resolves against {{/users/{id}}} on the write side, which doesn't exist for a service principal).

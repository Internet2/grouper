# GRP-7071  viewSubject is slow (~30s) for non-admin users: N+1 per-group privilege resolution in membership security filtering

Problem

Loading a subject's memberships in the UI (UiV2Subject.viewSubject, URL /UiV2Subject.viewSubject?subjectId=...&sourceId=...) takes ~30s end-to-end for a non-admin (non-wheel) viewer. The same screen is fast for an admin/wheel viewer.

The RDS PostgreSQL slow-query log shows only ~3 statements totaling < 500ms for the whole request, and RDS and Fargate CPU/memory/IO stay within normal ranges. So the 30s is not in those queries and is not resource-bound; it is latency/serialization bound.

Suspected root cause (traced in Grouper source)
 * UiV2Subject.filterHelper builds a MembershipFinder with assignCheckSecurity(true) and group paging (assignQueryOptionsForGroup).
grouper-ui/java/src/edu/internet2/middleware/grouper/grouperUi/serviceLogic/UiV2Subject.java (viewSubject ~561, filterHelper ~604-642)
 * The DAO pages the groups in SQL (the LIMIT query in the report), then applies security as a POST-query filter rather than in SQL:
Hib3MembershipDAO.findAllByGroupOwnerOptionsHelper -> getAccessResolver().postHqlFilterMemberships(...) ~1406
grouper/src/grouper/edu/internet2/middleware/grouper/internal/dao/hib3/Hib3MembershipDAO.java
 * The default access adapter does NOT push privilege filtering into SQL: BaseAccessAdapter.hqlFilterGroupsWhereClause returns false (~94). That is why the listing query has no privilege subquery.
grouper/src/grouper/edu/internet2/middleware/grouper/privs/BaseAccessAdapter.java
 * postHqlFilterMemberships -> PrivilegeHelper.canViewMemberships (~116) loops over every membership and calls canViewMembership -> dispatch -> canRead -> AccessResolver.hasPrivilege(group, subject, READ).
grouper/src/grouper/edu/internet2/middleware/grouper/privs/PrivilegeHelper.java (canViewMemberships ~716-735)
 * CachingAccessResolver.hasPrivilege (~152) on a cache miss calls getPrivileges(group, subject), which loads that one group's privileges with its own DB query. For a non-admin this yields roughly one small privilege query per group evaluated (an N+1).
grouper/src/grouper/edu/internet2/middleware/grouper/privs/CachingAccessResolver.java
 * For an admin/wheel viewer this short-circuits (wheel implies all privileges, near-100% cache hits), which is exactly why admins are fast and non-admins are slow.

Net: the per-group privilege resolution generates many tiny, individually sub-threshold queries that never appear in the slow-query log, but the sum of the serialized Fargate-UI-to-RDS round trips is the ~30s, while RDS sits nearly idle. Cost scales with the number of groups evaluated times the per-group privilege-resolution round trip.

How to confirm (cheap, no code change)
 * pg_stat_statements: sort by calls and total_exec_time (not mean). Expect a getPrivileges-style group/membership/privilege statement with a very high call count, tiny mean, large total.
 * Or set log_min_duration_statement=0 for one viewSubject request by the non-admin and count the statements.
 * A/B the same subject as an admin vs the non-admin; admin fast, non-admin ~30s on identical data confirms the privilege-filter path.

Proposed fix
 * Primary (localized, lower risk): before the per-membership loop in PrivilegeHelper.canViewMemberships (or in the DAO just before postHqlFilterMemberships), batch-load the viewing subject's privileges for ALL candidate owner groups in a single query and prime the hasPrivilege cache. The subsequent per-membership hasPrivilege checks then become in-memory cache hits. This converts O(number of groups) DB round trips into O(1).
 * Alternative (structural, longer term): implement hqlFilterGroupsWhereClause for the default access adapter so the paged group query filters by privilege in SQL. This also fixes the related wart where a post-filtered page can return fewer rows than the page size.

Mitigations available now (ops, partial)
 * Reduce the page size for this screen if it is large; fewer rows = fewer per-group privilege resolutions.
 * Co-locate the grouper_ui Fargate task and the RDS writer in the same AZ to cut the per-round-trip latency that multiplies the N+1.
 * Verify the hasPrivilege ehcache regions are adequately sized and the TTL is not too short, so repeat/within-session checks hit cache.

Acceptance / verification
 * viewSubject for a non-admin with many memberships returns in well under a few seconds.
 * Statement count per request drops from O(groups) to a small constant (confirm via pg_stat_statements / log_min_duration_statement=0).
 * Same groups shown as before (security results unchanged), verified admin vs non-admin.

Environment
 * Grouper version: <fill in - not stated in the report>
 * DB: RDS PostgreSQL (r6gd.xlarge, work_mem 128MB)
 * grouper_ui / grouper_ws on Fargate; separate grouper_api on EC2 m5.4xlarge

Proposed product direction (investigate later)
 * Add a summary tab to the subject view, mirroring the group screen (UiV2Group), so the default landing does not immediately run the full membership security filter. Memberships move behind a tab the user opts into.
 * Default the memberships listing to a smaller page size. Fewer rows on initial load means fewer per-group privilege resolutions, independent of the deeper batch/SQL-pushdown fix.

Does paging work?  i.e. if the user cannot see the first X groups will it display the page size of groups?

Also consider using sql membership cache to speed things up (eventual consistency).

h1. Design: bulk-prefetch parent stems for Grouper UI list screens (GRP-7071, parent-stem part)
h2. Context

Grouper 4.x UI screens that list many rows (e.g. {{/UiV2Subject.viewSubject}}) are slow: DB query execution is fast (<500ms) but end-to-end is ~30s, and time scales with the number of rows on the page. Root cause for the parent-stem portion: each rendered row calls {{{}GuiObjectBase.getParentGuiStem(){}}}, which does a per-row DB lookup ({{{}Group.getParentStem(){}}} -> {{{}Hib3StemDAO.findByUuid{}}}). With high app-to-DB latency this N+1 becomes seconds of wall clock. Fix: load all parent stems for a page in ONE query and inject them into the Gui objects before rendering.

Codebase: {{/Users/<...>/grouper_v7}} (or your checkout). All paths below are relative to that.
h2. Goal
 * One query per page for parent stems, not one per row.
 * Fail fast: if a screen renders a parent stem without prefetching, throw a descriptive exception (do NOT silently lazy-load). This guarantees no N+1 sneaks back in and forces every list path to prefetch.

h2. Change B - bulk privilege resolution (resolver + UI)

Replaces the branch's procedural approach (CachingAccessResolver.cacheGroupPrivilegesInBulk + PrivilegeHelper instanceof chain-walk). Problems with that version: the cache decorator runs queries and reconstructs privilege logic that already lives in the base adapter (drift risk), it is reached by fishing a concrete class out of the chain with instanceof (not OO), it caches all access privs rather than the ones an action needs, and it depends on the ehcache staying warm/enabled for the benefit to survive.
h3. Principles
 # Object-oriented: a real method on the AccessResolver interface, resolved polymorphically through the chain. No instanceof, no logic in the cache layer.
 # The CachingAccessResolver never runs a query - it serves cache hits and delegates misses to the chained resolver, then caches what came back.
 # Fetch only the privileges an action needs, not all access privileges.
 # Set the resolved privileges on the Gui object and read them from there. Do NOT rely on the session privilege cache being warm - cache config (TTL, size, disable) must not erode the benefit.

h3. New resolver method (on the AccessResolver interface)

Map<Group, Set<AccessPrivilege>> getPrivileges(Collection<Group> groups, Subject subject, Set<Privilege> privilegesToCheck)

Returns, per group, the subset of privilegesToCheck the subject actually holds. One batched query, scoped to the requested privilege fields. Per-layer responsibilities (each keeps its own job - this is the OO point):
 * ValidatingAccessResolver: validate args, delegate.
 * WheelAccessResolver: full wheel/sysadmin -> every group gets all of privilegesToCheck; readonly wheel/sysadmin -> every group gets only the read/view members of privilegesToCheck; else delegate. (Mirror WheelAccessResolver.java:318/:488; readonly-sysadmin must NOT get UPDATE.)
 * CachingAccessResolver: for each (group, priv) in groups x privilegesToCheck, read the existing hasPrivilege cache; gather the groups with any uncached needed priv; delegate getPrivileges(missGroups, subject, privilegesToCheck) to the decorated resolver in ONE call; cache each returned (group, priv) boolean; return hits + newly resolved. Runs NO query of its own.
 * GrouperSystemAccessResolver: root subject -> every group gets all of privilegesToCheck.
 * GrouperAllAccessResolver: union in the privileges held by the GrouperAll subject (mirrors getPrivileges semantics - GrouperAll applies to all access privs here, not the secure-filter's manage restriction).
 * GrouperAccessAdapter / GrouperNonDbAccessAdapter (base): the single batched query, reusing the field-to-privilege mapping it already owns (priv2list / list2priv, GrouperAccessAdapter.java:88).

Base query, scoped to page and to needed privilege fields (reuse the branch's batched DAO method - that part is good):
owner_group_id IN (:pageGroupIds)
AND member_id IN (:loggedInMemberUuid [, :allMemberUuid])
AND field_id IN (:neededAccessFieldIds) <- only the fields for privilegesToCheck
AND enabled = 'T'
Fold rows (owner_group_id, field) into Map<Group, Set<AccessPrivilege>>. Reuse MembershipDAO.findAllByGroupOwnersAndMember(Collection, memberUUID, enabledOnly) from the branch (Hib3MembershipDAO, 100-id batches) as the underlying fetch, or an equivalent scoped to neededAccessFieldIds to fetch fewer rows.

Semantics note: getPrivileges returns exactly the privileges held; ADMIN is not auto-expanded to UPDATE in the stored fields. The caller asks for the implication-expanded set per capability (e.g. UPDATE_PRIVILEGES = \{UPDATE, ADMIN}, AccessPrivilege.java:159) and the getter ORs them - matching PrivilegeHelper.canUpdate (PrivilegeHelper.java:578-589).
h3. UI: set on the Gui object, read from the object (no cache dependency)

File: grouper-ui/.../beans/api/GuiGroup.java

Fields:
 * private Set<Privilege> loggedInPrivilegesChecked; // which privileges were resolved for this group (null = not prefetched)
 * private Set<AccessPrivilege> loggedInPrivilegesHeld; // the subset the logged-in subject holds

Bulk seed:
 * public static void cacheLoggedInPrivileges(Collection<GuiGroup> guiGroups, Set<Privilege> privilegesToCheck):
 ** call grouperSession.getAccessResolver().getPrivileges(groups, loggedInSubject, privilegesToCheck) ONCE
 ** on each GuiGroup set loggedInPrivilegesChecked = privilegesToCheck and loggedInPrivilegesHeld = the returned set (empty if none)
 ** the result is stored on the object; getters never call the resolver again and never depend on the ehcache

Getters read the fields, fail fast (config-gated) if the capability's privileges were not in the prefetched checked-set, with a descriptive message:
 * isCanRead (GuiGroup.java:591): require READ_PRIVILEGES checked -> held.contains(READ) || held.contains(ADMIN)
 * isCanUpdate (GuiGroup.java:567): require UPDATE_PRIVILEGES checked -> held.contains(UPDATE) || held.contains(ADMIN)
 * isCanAdmin (GuiGroup.java:579): require ADMIN_PRIVILEGES checked -> held.contains(ADMIN)
 * isCanGroupAttrRead (GuiGroup.java:603): require the group-attr-read set checked -> held.contains(GROUP_ATTR_READ) || held.contains(ADMIN)

assert helper: if loggedInPrivilegesChecked == null or does not contain the required privilege(s), throw RuntimeException naming the privilege, the group, and the cacheLoggedInPrivileges call to add. This guarantees a screen that prefetched the wrong subset fails loudly instead of silently returning a wrong false.
h3. Each screen passes the privilege set its getters use (only what is needed)
 * subjectContents.jsp uses only canUpdate -> prefetch UPDATE_PRIVILEGES (\{UPDATE, ADMIN}).
 * A screen that uses canRead and canUpdate -> prefetch \{READ, UPDATE, ADMIN}.
This keeps the query scoped to the fields actually needed.

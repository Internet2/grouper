# GRP-7205  LDAP group loaders failing due to missing SQL attribute grouperLoaderDeletePreviouslyManagedGroups

  LDAP loader jobs fail with the following exception during syncGroupList:

  edu.internet2.middleware.grouper.exception.AttributeNotFoundException: Group etc:configuration:loader:xxxxx-members doesn't have attribute: grouperLoaderDeletePreviouslyManagedGroups
      at edu.internet2.middleware.grouper.Group.getAttributeValue(Group.java:3012)
      at edu.internet2.middleware.grouper.app.loader.GrouperLoaderType.attributeValueOrDefaultOrNull(GrouperLoaderType.java:2689)
      at edu.internet2.middleware.grouper.app.loader.GrouperLoaderType.shouldDeletePreviouslyManagedGroups(GrouperLoaderType.java:2203)
      at edu.internet2.middleware.grouper.app.loader.GrouperLoaderType.syncGroupList(GrouperLoaderType.java:1340)
      ...



  Root cause — two contributing issues:

# GrouperLoaderType.shouldDeletePreviouslyManagedGroups(Group) (GrouperLoaderType.java:2199-2220) intentionally checks the SQL-loader attribute grouperLoaderDeletePreviouslyManagedGroups
first, and only falls back to the LDAP-specific grouperLoaderLdapDeletePreviouslyManagedGroups attribute if the SQL one is blank. This is by design (it lets a global/legacy SQL setting
apply across loader types), so it isn't itself a bug — but it means every LDAP loader run unconditionally probes an attribute that will never be assigned to an LDAP loader group.
# That probe goes through attributeValueOrDefaultOrNull(Group, String) (GrouperLoaderType.java:2687-2694), which calls group.getAttributeValue(attributeName, false, false) — explicitly
passing exceptionIfNotFound = false. However, Group.getAttributeValue (Group.java:2982-3018) has a code path for legacy (pre-attribute-framework) attributes where the exceptionIfNotFound
argument is never consulted:
- If the attribute isn't in this.attributes (line 2993-2995), the method looks it up as a legacy attribute via findLegacyAttributeByName (line 3001).
- If a matching legacy attribute def exists, but the group's type assignment for that legacy attribute's group type (internal_getGroupTypeAssignments()) is null (line 3010) — i.e., the
group was never given that group type at all — the method throws AttributeNotFoundException unconditionally at line 3012, before ever checking exceptionIfNotFound (which is only checked
afterward, at line 3015, on a path that's unreachable here).

  Since grouperLoaderDeletePreviouslyManagedGroups is defined via the legacy SQL-loader group type, and an LDAP loader group was never assigned that group type, execution always hits line
  3012 and throws, regardless of the caller passing exceptionIfNotFound=false.



  Suggested fix:

* In Group.getAttributeValue, honor exceptionIfNotFound in the groupTypeAssignment == null branch (Group.java:3010-3013) the same way it's honored just below at line 3015-3018 — i.e., if
(exceptionIfNotFound) { throw ... } return ""; instead of throwing unconditionally.
* Audit other callers of getAttributeValue(..., exceptionIfNotFound=false) that could be relying on the current (broken) unconditional-throw behavior, in case fixing it changes their
control flow.
* In shouldDeletePreviouslyManagedGroups(Group), have LDAP loader groups check only the LDAP-specific attribute (grouperLoaderLdapDeletePreviouslyManagedGroups) and skip the SQL-specific
  probe (grouperLoaderDeletePreviouslyManagedGroups) entirely — e.g., branch on the loader type up front (LDAP vs. SQL) rather than always checking the SQL attribute first and falling back
  to LDAP. This avoids querying an attribute that can never apply to an LDAP loader group in the first place, independent of whatever fix is made to Group.getAttributeValue.

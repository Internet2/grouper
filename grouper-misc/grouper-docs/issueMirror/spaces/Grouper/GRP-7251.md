# GRP-7251  Incremental sync does not remove membership rows from grouper_prov_mship mirror

When a membership is removed from a group and an incremental provisioning cycle runs, the removal reaches the target correctly but the generic provisioner reporting mirror keeps the stale row. grouper_prov_mship ends up with one membership more than the target has.

Reproduce with ScimProvisionerGenericTableTest.testIncrementalMembershipRemoveConvergesSameCycle. Two groups (test:testGroup, test:otherGroup) each hold SUBJ0 and SUBJ1, so removing SUBJ1 from testGroup leaves SUBJ1 provisioned via otherGroup and isolates the membership remove. After a full-sync seed and a priming incremental, SUBJ1 is removed from testGroup and an incremental runs. The target is correct (mock_scim_membership has 3 rows) but countByProvisioner for grouper_prov_mship returns 4 instead of 3.

Cause: loadDataToGenericProvisionerTablesIncremental in GrouperProvisioningLogic never syncs grouper_prov_mship through GcTableSync the way it does the user, group, and attribute tables. Memberships are hand-rolled instead - an explicit delete (delete from grouper_prov_mship where prov_user_internal_id in (...) and prov_group_internal_id in (...)) and an insert-if-absent. That delete only runs for entries in membershipTargetIdsToDelete, which is populated from provisioning membership wrappers where isDeleteResultProcessed() is true and getGrouperTargetMembership() is non-null. For this removal the set comes out empty, so nothing is deleted from the mirror.

This was previously masked. The FROM side of the generic-table syncs was built with GcTableSyncTableData.setRows(), which stores rows verbatim, while the TO side is built with init(), which runs normalizeRow() and coerces every value to its column canonical java type. The same internal_id was therefore a Long on one side and a BigDecimal on the other. MultiKey compares with equals(), so no row ever compared equal and grouper_prov_group rows were deleted and reinserted with fresh internal ids on every incremental cycle. The membership rows hanging off those groups went with them by cascade and were reinserted from current state, so the mirror happened to land on the right count. Once the FROM side is also built with init(), group rows compare equal and stay put, there is no cascade, and the missing explicit delete becomes visible.

Diagnostic: the debug map key loadGenericIncrMshipDeletes is only written when membershipTargetIdsToDelete is non-empty. Its absence means the set was empty; a value of 0 would instead mean the set was populated but the target_user_id / target_group_id subselects matched nothing. That single key separates the two causes.

Affects the generic provisioner reporting tables (loadMembershipsToGenericGrouperTable) on any provisioner, not just SCIM.

## Comments

### Chris Hyzer - 2026-08-15T12:00:03.385-0400

Second failing test, same root cause: ScimProvisionerGenericTableTest.testIncrementalMembershipReplaceConvergesSameCycle also leaves grouper_prov_mship at 4 instead of 3. Identical scenario (two groups each holding SUBJ0 and SUBJ1, SUBJ1 removed from testGroup) but with replaceMemberships=true, so the group's full member set is re-sent as a PATCH op=replace instead of a per-member remove.

Replace mode makes the gap clearer. membershipTargetIdsToDelete is built from provisioning membership wrappers where isDeleteResultProcessed() is true, and in replace mode there is no per-member delete operation at all - the group is simply re-sent with its current members. So the set is empty by construction, not just incidentally. The insert-if-absent block adds any missing membership rows but nothing ever removes a row that is no longer wanted, in either mode.

Suggests the fix should not be to populate membershipTargetIdsToDelete more thoroughly, but to reconcile grouper_prov_mship for the touched groups the way the full flush does - i.e. sync the membership axis through GcTableSync scoped to the groups in the incremental cycle, rather than the hand-rolled delete plus insert-if-absent pair.

# GRP-7596  Rule if/then EL saved by a sysadmin runs unrestricted again (not in the JEXL sandbox)

Since v7.9.1, v6.5.1 and v4.26.1 (2026-Nov security review), rule if and then expression language runs in the restricted JEXL sandbox for every rule, including rules saved by a sysadmin. Constructors (new(...)) and class objects (''.class.forName(...)) are refused, so existing sysadmin rules stop working, e.g. the documented pattern "Grouper rules pattern - Veto delete membership if immediate membership has attribute value", which uses new("edu.internet2.middleware.grouperClient.jdbc.GcDbAccess") and rules.accessToApiInEl.group. The 7.9.1 upgrade instructions only have a step for send-email rules (GRP-7575), nothing for if/then EL rules.

Only wheel or root can save if/then EL rules in the UI and RuleService (GRP-7359), and non-wheel users can only save send-email templates with the predefined variables. So sysadmins should be able to write whatever expression they want. Most sites do not need more than the sandbox allows, so this is a switch, off by default: the sandbox stays as a second line of defense behind the save-time check.

Change:

1. Make sure every path that writes the rule if/then EL attributes (ruleIfConditionEl, ruleThenEl) is wheel or root only: RuleService, and attribute assignment through WS, GSH and the API. Add the check to GrouperAttributeAssignValueRulesConfigHook, like the send-email template check (RuleEmailTemplateCheck). This must ship with or before step 2.

2. New switch rules.allowUnrestrictedEl (grouper.properties, default false). If true, rule if/then EL runs unrestricted (as before v7.9.1), since only a sysadmin could have saved it. If false, it runs in the sandbox as in 7.9.1.

3. Send-email: a rule that uses only the predefined variables always runs in the sandbox. One that uses anything else (only a sysadmin could have saved it), or a "template: name" subject or body (a file the site wrote), runs unrestricted if rules.allowUnrestrictedEl is true.

3a. So sites find the switch: (1) rule EL that fails while sandboxed throws (or for send-email, logs) an error that names rules.allowUnrestrictedEl and the rule id; (2) saving if/then EL in the rules UI that uses something the sandbox refuses (new(...), .class, forName, getClass, the group/member/membership/subject/rule objects) saves the rule and shows a warning naming the switch, and other save paths (WS, GSH, API) log the same warning; (3) a new configuration review check warns when the switch is off and rules exist that the sandbox will refuse, listing the rule ids.

4. Remove rules.accessToApiInEl.group. Today it decides whether the live objects (group, member, membership, subject, and the rule objects) are put in the EL variables, keyed on the rule's act-as subject, not on who wrote the rule. Instead, put them in whenever the expression runs unrestricted (rules.allowUnrestrictedEl on). Sandboxed expressions keep only the string variables and safeSubject, since the sandbox allows public methods on passed-in objects (group.delete() would run). Keep the key in grouper.base.properties, blank, with a comment that it is no longer used.

5. Configuration review screen: RulesAccessToApiInElConfigurationCheck reports an ERROR if rules.accessToApiInEl.group is set at all (no longer used, clear it). The new RulesElSandboxConfigurationCheck is in 3a.

6. Existing rules are grandfathered. Once step 1 is in, every if/then EL value in the database is either from before the upgrade or saved by a sysadmin, so no per-rule marker is needed. Audits (attributeAssignValue add/update) are not used to decide trust: they can be pruned, turned off for an attribute def, show GrouperSystem for GSH/loader saves, and are missing for SQL loads.

7. Upgrade instruction (report only, nothing is blocked or changed): sites with if/then EL rules run the read-only ruleElCheck.gsh (attached), which lists every if/then EL rule with its owner, act-as subject and last audited saver, flags rules whose last saver was not a sysadmin, and flags rules the sandbox refuses. If it flags any the sandbox refuses and a sysadmin wrote them, set rules.allowUnrestrictedEl = true. Also note that rules.accessToApiInEl.group is no longer used (the configuration review screen reports an error if it is set).

8. Other restricted expressions (permission limits, external subject descriptions, UI labels, scripted groups) are unchanged.

9. Tests, and update the rules wiki pages (rules EL variables, the veto pattern page, rules.accessToApiInEl.group) to say what works in which version.

Workaround: none in rule EL on v7.9.1, v6.5.1 and v4.26.1. Reading the attribute through the API (membership.getAttributeValueDelegate()...) does not work for this pattern: the rule fires after the membership and its attribute values are deleted in the same transaction, so the delegate finds nothing, which is why the documented rule uses GcDbAccess (its own connection). Until this change is installed, use a custom Java rule or a hook. After it is installed, set rules.allowUnrestrictedEl = true and the original rule runs unchanged (SFU is fine setting it).

Attached ruleElCheck.gsh, the read-only report for the step 7 upgrade instruction. Run it in GSH as an administrator. It works on Grouper 2.6 through 7.x (APIs checked on the 2.6, 4, 6 and 7 branches; tested on local v7 dev). It lists every rule with if/then EL, its owner, act-as subject and last audited save, marked OK (last saved by wheel/root or GrouperSystem), REVIEW (last saved by someone who is not wheel/root now) or NO AUDIT, and flags EL that the 7.9.1/6.5.1/4.26.1 sandbox refuses (new, .class, forName).

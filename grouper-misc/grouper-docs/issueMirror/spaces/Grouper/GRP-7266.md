# GRP-7266  allow the MCP and OAuth URLs published to clients to be configured separately from grouper.ws.url

  Grouper builds everything MCP and OAuth publish to clients from grouper.ws.url:

  the OAuth issuer identifier, the MCP resource identifier and token audience, the

  token/registration/jwks endpoints in the authorization server metadata, the

  resource metadata URL in the WWW-Authenticate challenge, and the origin the MCP

  Origin check compares against.



  When Grouper WS sits behind a gateway or reverse proxy, clients reach it at a

  different address than the one Grouper is deployed at, so every one of those

  values is wrong. A client that implements RFC 9207 rejects the authorization

  response because the iss parameter names the backend rather than the address it

  connected to; a client that checks the resource in the protected resource

  metadata per RFC 9728 has the same problem one layer down.



  The current workaround is to set grouper.ws.url to the public address. That

  works, because nothing outside MCP and OAuth reads the property today, but it

  overloads it: the property is documented as the URL of Grouper WS, and anything

  added later which wants the real deployed address would silently get the gateway

  address instead.



  Add a separate property for the address clients use, defaulting to

  grouper.ws.url so existing deployments are unaffected:



    # base URL clients use to reach the MCP endpoint and its OAuth endpoints, when

    # Grouper WS is behind a gateway or reverse proxy.  Defaults to grouper.ws.url.

    grouper.mcp.baseUrl =



  Behavior:

* when blank, everything behaves exactly as today

* when set, it is used wherever an address or identity is published to or

    verified against a client

* trailing slash stripped, matching GrouperConfig.getGrouperWsUrl

* grouper.ws.url stays required whenever MCP is enabled, and the existing

    mcpUrlConfigurationError check is unchanged



  Where it applies:

* GrouperOAuthStore.retrieveIssuerIdentifier and retrieveMcpResourceIdentifier.

    These two cover the iss parameter, the token iss and aud claims, their

    verification in GrouperOAuthSigningKey, and the resource parameter check in

    UiV2OAuth, since those all call through here

* GrouperMcpWellKnownServlet: issuer, token_endpoint, registration_endpoint,

    jwks_uri

* GrouperMcpProtectedResourceServlet: resource, authorization_servers

* GrouperMcpServlet.resourceMetadataUrl, used in the WWW-Authenticate challenge

* GrouperMcpServlet.configuredOrigin: accept only the client facing origin

* UiV2Mcp: the MCP info page should show users the address they connect to



  The value must stay configuration only and identical at issuance and

  verification. It must not be derived from the request or from a forwarded

  header, for the reasons already documented on retrieveIssuerIdentifier.

# GRP-7292  Provisioner failsafe sends a failsafe email on every run instead of once

Reported by Yoann Delattre on the Grouper Slack, running Grouper 7.3.2.

When a provisioner failsafe triggers, a failsafe notification email is sent on every subsequent run of the job (in his case about once a minute, since the incremental provisioner job runs frequently). The emails keep coming until the failsafe is manually approved/overridden. Expected behavior is one email when the failsafe first trips, not one per run.

Loader failsafe does not show this behavior; only the provisioner failsafe does.

Relevant config from the reporter:

{noformat}loader.failsafe.groupList.managedGroups.minManagedGroups = 200
loader.failsafe.groupList.managedGroups.use = true
loader.failsafe.sendEmail = true
loader.failsafe.sendEmailToAddresses = mymail@example.com
loader.failsafe.use = true
otherJob.dataProviderLdapPers.failsafeMaxOverallPercentFieldAssignRemove = 8
otherJob.dataProviderRspLille.failsafeMaxOverallPercentFieldAssignRemove = 8
provisionerDefault.failsafeMaxOverallPercentGroupsRemove = 20
provisionerDefault.failsafeMaxOverallPercentMembershipsRemove = 20
provisionerDefault.failsafeMaxPercentRemove = 20
provisionerDefault.failsafeUse = true
provisionerDefault.showFailsafe = true{noformat}

Suggested fix: only send the failsafe email on the transition into the failsafe state (or throttle/dedupe repeated notifications for the same provisioner while the failsafe remains tripped).

## Comments

### Chris Hyzer - 2026-08-31T04:03:06.217-0400

h3. Proposed design

{panel:bgColor=#fffae6}
v7 only. This requires DDL (a new column on grouper_failsafe), so it is not backportable to v6 or earlier release branches.
{panel}

h4. Root cause

GrouperProvisioningFailsafe.processFailsafesFailIncrementalIfFullFailsafeIssue() calls notifyEmailAboutFailsafe() unconditionally on every incremental run while a full sync failsafe is outstanding. The reporter's incremental runs about once a minute, so he gets an email a minute. There is no dedupe on that path. The three actual trip paths (processFailsafesMinManagedGroups, processFailsafesMaxGroupPercentRemove, processFailsafesMinOverallNumberOfMembers) are also unguarded, but the full sync runs infrequently enough that it is not what he is seeing.

h4. Desired behavior

Send the failsafe notification email when any of these is true:

* no email has ever been sent for this job name
* the last email for this job name was more than N hours ago (N globally configurable, default 6)
* a failsafe approval happened since the last email - so approve, then a fresh failsafe problem, notifies immediately instead of waiting out the window

h4. Schema: one new column on grouper_failsafe

No new table. grouper_failsafe is already one row per job name and already owns last_failsafe_issue_started, last_success, approved_once, so the notification timestamp belongs beside them.

{noformat}last_failsafe_email_micros   bigint   null{noformat}

Nullable, deliberately. Null is a meaningful state (never emailed for this job), it is the first arm of the send gate, the three reset paths write null back to re-arm the email, and existing rows come through the upgrade as null so the first trip after upgrade notifies. A NOT NULL column with any sentinel default would either mail every currently tripped job at once on upgrade or suppress the first mail for 6 hours.

Micros, not millis, per the ongoing micros conversion. Note that every other timestamp on this table (last_run, last_failsafe_issue, last_success, last_approval, approved_until) is still millis, so the gate must never compare this column against a sibling. Sized bigint 20 to match the newer micros columns (created_on_micros, event_micros in GrouperDdl5_22_0) rather than the 12 used by the older millis columns on this table.

Goes in the next GrouperDdl7_x_0 class: add column, column comment, upgrade task, plus the three install SQL files (postgres, oracle, mysql), no not null and no default in any of them.

Considered and rejected: a new column on grouper_loader_log (failsafe_emailed T/F). Wrong grain - that is a per run row, but the question is per failsafe episode, so answering it means scanning prior run rows. Worse, loader_log is purged by the retention daemon so the answer can disappear while the failsafe is still tripped, and provisioner runs also write grouper_sync_log, which would split the state across two logs.

h4. Config: global

New property alongside the existing loader.failsafe.email.* block in grouper-loader.base.properties:

{noformat}# If a failsafe stays tripped, resend the notification email at most this often (hours).
# Set to -1 to only email once per failsafe episode (never resend).
# An approval always re-arms the email, regardless of this setting.
# {valueType: "integer", defaultValue: "6"}
loader.failsafe.email.resendAfterHours ={noformat}

Blank value with the default in the JSON comment, and the same default in code so the two agree.

h4. Code

1. New gate in GrouperFailsafe. One UPDATE, so concurrent daemons cannot double send - rowcount 1 means this caller won the right to send.

{code:java}/**
 * Should we email about this failsafe now?  True if we have never emailed for
 * this job, or the last email is older than loader.failsafe.email.resendAfterHours,
 * or an approval has re-armed it.  Stamps last_failsafe_email_micros when it
 * returns true.
 * @param jobName
 * @return true if the caller should send the email
 */
public static boolean shouldSendFailsafeEmailAndStamp(String jobName) {

  insertRow(jobName);

  // micros per the ongoing conversion; last_updated stays millis since it is an existing column
  long nowMicros = System.currentTimeMillis() * 1000L;

  int resendAfterHours = GrouperLoaderConfig.retrieveConfig()
      .propertyValueInt("loader.failsafe.email.resendAfterHours", 6);

  // -1 means never resend: only the "is null" arm below can fire
  long resendCutoffMicros = resendAfterHours < 0
      ? Long.MIN_VALUE
      : nowMicros - (resendAfterHours * 3600L * 1000L * 1000L);

  int rowsUpdated = new GcDbAccess().sql(
      "update grouper_failsafe set last_failsafe_email_micros = ?, last_updated = ? "
      + "where name = ? and (last_failsafe_email_micros is null or last_failsafe_email_micros < ?)")
    .addBindVar(nowMicros).addBindVar(System.currentTimeMillis())
    .addBindVar(jobName).addBindVar(resendCutoffMicros).executeSql();

  return rowsUpdated > 0;
}{code}

2. Approval re-arms the email. assignApproveNextRun() adds last_failsafe_email_micros = null to its UPDATE - that is the literal encoding of approve, then a new problem, notify. assignSuccess() and removeFailure() null it too, alongside the last_failsafe_issue_started they already null.

3. Call sites. All four notifyEmailAboutFailsafe() calls in GrouperProvisioningFailsafe become:

{code:java}if (GrouperFailsafe.shouldSendFailsafeEmailAndStamp(jobName)) {
  this.grouperFailsafeBean.notifyEmailAboutFailsafe();
}{code}

The one that matters for this report is processFailsafesFailIncrementalIfFullFailsafeIssue(). The same guard belongs on the loader side callers of notifyEmailAboutFailsafe() so loader and provisioner behave alike.

h4. Aside

assignApproveNextRun() currently writes neither last_approval nor approval_member_id even though both columns exist in the DDL - they are dead today. Worth populating in the same commit, since both UI call sites (UiV2Admin.daemonJobsSubmit failsafeApprove and UiV2GrouperLoader.failsafeApprove) have the logged in subject in hand.

h4. Net effect for the reporter

One email when the full sync trips, silence from the minute by minute incrementals, a reminder every 6 hours while it stays tripped, and an immediate email if he approves and it trips again.

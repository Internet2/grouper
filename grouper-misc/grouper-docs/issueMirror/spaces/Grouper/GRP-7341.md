# GRP-7341  Provisioning diff has no churn detection — can't distinguish "member removed" from "member's identifier changed"

*Claude:*

Grouper's provisioning diff is stateless: each run compares current Grouper membership against
current target state fresh, with no memory of what happened between runs. {{grouper_sync_member}}
and {{grouper_sync_membership}} do store the last-synced subject identifier per {{memberId}}, but that
data is currently only used to reconstruct deletes when a member disappears entirely — it is never
diffed against the entity's newly-resolved identifier to detect "this identifier changed since the
last successful sync."

This means a subject identifier edit (e.g. renaming a mapped attribute in the subject source
config, per GRP-7317, or any other source-side identifier change) looks identical, from
provisioning's point of view, to a legitimate membership removal — both result in the old
identifier no longer resolving, and the diff routes straight to a delete.

h2. Suggested approach

If the same underlying {{member.uuid}}/{{memberId}} persists and only its identifier was edited in
place, a targeted fix is realistic: at diff time, compare {{grouper_sync_member}}'s stored identifier
against the freshly resolved one for the same {{memberId}}, and flag a mismatch as suspicious
(log/warn, possibly skip the delete and require manual resolution) rather than routing to a plain
delete.

h2. Known limitation

If the identifier edit instead caused the old member row to be replaced/recreated (rather than
edited in place), {{memberId}} continuity breaks and this narrower fix would not catch it. That case
would need a broader check — either against the member changelog (identifier changes are recorded
there via {{MEMBER_UPDATE}} entries) or against USDU's duplicate/deleted-subject bookkeeping — neither
of which provisioning currently reads. Recommend scoping the first pass to the {{memberId}}-persists
case only, and tracking the changelog/USDU-based case as a further follow-up if needed.

h2. Relationship to other GRP-7317 follow-ups

* Complements, but does not depend on, the {{isUnresolvableSubject}} delete-branch fix — that fix
handles subjects Grouper flags as unresolvable; this handles subjects that still resolve, just to
a changed identifier.
* This is architecture-level work (touches the diff engine's core comparison logic), not a quick
fix — recommend keeping it lower priority and separate from the GRP-7317 UI validation fix and
the unresolvable-delete fix so neither of those smaller, higher-value fixes gets blocked on it.

h2. Related tickets (GRP-7050, GRP-7052)

GRP-7050 and GRP-7052 address staleness in the target-side link/matching cache
({{member_from_id2/3}}, {{member_to_id2/3}}, {{group_from_id2/3}}, {{group_to_id2/3}} on
{{grouper_sync_member}}/{{grouper_sync_group}}) by forcing a recalc when a membership error suggests a
stale link (GRP-7050) or when the target object's own id changes (GRP-7052).

This ticket is about a different column and a different failure mode: the {{subject_identifier}}
column on {{grouper_sync_member}}/{{grouper_sync_membership}} — Grouper's own last-synced _source-side_
subject identifier. Today that column is only read to reconstruct deletes when a member disappears;
it is never diffed against the subject's freshly-resolved identifier to detect drift between sync
runs. Neither GRP-7050 nor GRP-7052 touches this column or adds that comparison, so this gap remains
open after both of those fixes.

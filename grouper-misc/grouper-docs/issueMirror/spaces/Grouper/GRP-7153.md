# GRP-7153  Azure provisioner: Directory_ExpiredPageToken while paging group members kills the whole full-sync job

When the Azure provisioner pages a group's members (GrouperAzureApiCommands.retrieveAzureGroupMembers, GET /groups/{id}/members?$select=id&$top=999&$skiptoken=...), Microsoft Graph returns a server-driven continuation token ($skiptoken) inside each page's @odata.nextLink. That pagination cursor is tied to the enumeration and is short-lived: it expires only a few minutes after the walk starts (observed ~3m14s), independent of the bearer token, and every page shares the same clock (fetching a later page does not extend it). A large group (~108k members, ~109 pages at ~1.8s each, ~200s total) can exceed that window mid-walk, especially when 429 throttling sleeps or thread contention stretch the wall-clock. Graph then returns 400 with error code Directory_ExpiredPageToken.

The continuation token cannot be resumed or renewed once expired; there is no client-side or offset paging available for the members endpoint ($skip is unsupported and keyset ordering is not reliably supported), so the only recovery Graph offers is to start a fresh enumeration, which yields a new cursor with a new clock.

Today only HTTP 429 is handled in that walk; any other non-2xx/404 code falls through to the generic guard in executeMethod and throws an uncaught RuntimeException (Invalid return code 400, expecting 200, 404, 429). That aborts fullProvisionFull for all configured groups in the run, not just the one group whose cursor expired.

Fix (this issue): detect Directory_ExpiredPageToken and, because the cursor cannot be resumed, discard it and restart that group's member walk from page 1 with a fresh enumeration. Bound the restarts with a configurable max-restart count (azureGroupMembersExpiredTokenMaxRestarts, default 3) so a group that genuinely cannot be enumerated within the cursor lifetime fails with a clear message rather than looping forever. This mirrors the existing 429 recovery. A restart succeeds when the original failure was transient -- throttling or thread contention that stretched an otherwise in-budget walk past the window; the subsequent provisioner run recovered on its own, consistent with a transient cause. A mock fault-injection hook plus a JUnit test exercise the expire-then-recover path.

Related: the bearer-token refresh-margin hardening is tracked on GRP-7152 and is unrelated to this cursor expiry. A separate follow-up could broaden per-group error containment so one group's unrecoverable membership-retrieval failure does not abort the other groups in the run (the failed group must be skipped and reported, never treated as empty).

# GRP-7263  Add a System summary admin screen showing deployment size, scale and activity

Add a new admin screen under Miscellaneous, called System summary, that gives an admin a single view of how big and how busy this Grouper deployment is.

h3. Motivation

There is no one place that answers the question of what shape and scale a Grouper install is. That question comes up constantly: capacity planning, sizing a database, deciding whether an upgrade will be painful, comparing notes with other sites, and attaching context to a support request. Today an admin has to piece it together from the daemon jobs screen, ad hoc SQL, the existing Instrumentation screen, and the daily report email.

h3. Proposed content

Roughly the following sections. Exact metric list is not settled and should be trimmed for a first pass.

* Core object counts: folders, groups (broken out by type such as policy, composite, loader managed, ABAC), attribute defs and def names, members by subject source, immediate memberships, privileges, group set rows, attribute assignments.
* Storage: largest tables by row count and size, change log backlog depth, PIT retention actually in effect, total schema size. Approximate counts from optimizer statistics are fine and should be labeled as approximate.
* Subject sources: how many, of what type, and subject counts where the source can supply them.
* Activity: UI and WS request volume per day, distinct users taking action per day (with the caveat that audit only captures writes), distinct WS and MCP callers, number of admins.
* Provisioning: number of provisioners by type, enabled versus disabled, and per provisioner the provisionable groups, entities and memberships, full sync duration over time, incremental lag and recent error counts. Rank the largest few.
* Data providers and ABAC: providers, data fields, data rows, row counts, sync durations, count of scripted or ABAC groups.
* Jobs and loaders: total jobs split built-in versus custom, enabled versus disabled, loaders by type, largest loaders by memberships and by runtime, total daemon processing time per day, failures in the last week.
* Configuration surface: rules, external systems, reports, GSH templates, hooks, and a count of non default config properties as a rough proxy for how customized the install is.
* Environment: Grouper version and patch level, database vendor and version, Java version, and the set of running UI, WS, daemon and other instances.

A useful headline would be a single derived size classification computed from a few weighted thresholds, so the top of the page states plainly whether this is a small, medium, large or very large deployment, with the evidence below it.

h3. Computation and freshness

Several of these numbers are too expensive to compute on page load on a large install. The intent is that a daemon computes a snapshot on a schedule and stores it, the screen renders the most recent stored snapshot with a computed-at timestamp, and there is a way to request a fresh computation. Keeping successive snapshots is what makes the screen genuinely useful, because it turns point-in-time counts into growth trends, which is what actually drives a hardware or upgrade conversation.

h3. Storage

Not decided. The snapshot needs to be persisted somewhere, and the requirements to weigh are: cheap to write, cheap to render a whole snapshot, queryable across snapshots for trend display without resorting to database specific syntax, portable across Oracle, Postgres and MySQL, purgeable on a retention policy, and exportable in some self describing form for support and for sites that want to feed it elsewhere. Whether that is a document style blob, narrow metric rows, conventional columns, or some combination is an open design question to settle before implementation.

Retention also needs a decision. Thinning older snapshots to something like one per month, kept indefinitely, would give an unlimited growth chart at negligible cost.

h3. Relationship to the existing Instrumentation screen

The existing Instrumentation feature collects a small fixed set of counters (UI requests, WS requests, and API adds and deletes of folders, groups and memberships) plus one record per running instance, and it stores them through the attribute framework under the instrumentation data folder. That storage choice has real costs: it generates change log and point in time rows for what is purely telemetry, it inflates the attribute assignment counts that this new screen would be reporting on, the values cannot be indexed or queried so every read loads and parses everything, and purging old data means deleting attribute assignments.

The proposal is that System summary supersedes that screen, and that the underlying instrumentation collection moves off the attribute framework onto storage better suited to time series counters. The per instance counters and the periodic snapshot have quite different write patterns (many application instances writing continuously versus one daemon writing occasionally) so they may well want different storage even if they are presented together.

Migration of existing instrumentation data is probably not worth doing, since it is a rolling window of counters, but the old attribute defs should not be removed in the same release that stops writing to them.

h3. Relationship to the daily report email

The daily report job overlaps with this: it already computes overall counts of memberships, groups, members and folders, plus counts of what changed in the last day, a loader summary for the last day, listings of recent jobs, and an environment dump.

Rather than duplicating that computation, the daily report should become a consumer of the same snapshot. The two answer different questions and want different cadences: the daily email is about what happened yesterday and what is broken, which is fast moving and needs to be pushed and needs to arrive even when the UI is down; the size and shape numbers move slowly and belong on a screen, or in a much less frequent email.

That also invites trimming the daily email. The listing of successful jobs is most of its length and is better served by the daemon jobs screen, and the environment dump duplicates what the new screen would show. Existing job name and email configuration should keep working, and sites that parse or archive the current plain text output need a way to keep the old format.

h3. Open questions

* Storage format and retention, as above.
* Whether the snapshot should be pinned to a versioned, self describing schema from the first release, which matters if anything outside Grouper is ever expected to read it.
* Which metrics make the first pass. The full list above is more than a first release needs.
* How much of the screen should be exportable, and whether names of provisioners, loaders and groups belong in an export or should be reducible to counts only.
* Whether an admin should be able to subscribe to the summary on a slower cadence such as weekly or monthly.
* Whether a few of the numbers should carry inline guidance, for instance flagging a full sync that takes longer than its own schedule interval, or a change log that is backing up.

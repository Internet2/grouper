# GRP-6626  if there are orphaned type assignments it can cause issues

 It's a bug that makes orphans toxic to other operations. Line 934: return null should be continue. Here's the impact:

The return null on line 935 is a bug. When there are multiple marker assignments on the same object and one of them has no type name (orphaned), this method short-circuits and returns null instead of continuing to check the other assignments. This means:

saveOrUpdateTypeAttributes (line 375): Calls getAttributeAssign to find existing. If the orphan is iterated first, it returns null, so the code thinks there's no existing assignment and calls addAttribute — creating a duplicate marker. Now there are two markers: the orphan and a new valid one. If the type is later deleted, deleteTypeAttribute might hit the orphan first and return null again, leaving the valid one behind. This could cascade into more orphans.

deleteTypeAttribute (line 872): Same issue — if the orphan is iterated first, the valid assignment can't be found and can't be deleted.

copyConfigFromParent (line 612): Calls deleteTypeAttribute first, then re-creates from parent. Same getAttributeAssign bug applies.

However, the original creation of the orphan is likely not from this bug — it's probably from some other code path (API, WS, direct attribute manipulation) that assigned the marker without setting the type name. The return null bug on line 935 just makes the situation worse by preventing cleanup and potentially creating duplicates.

The fix is simple: change return null to continue on line 935 of GrouperObjectTypesConfiguration.java

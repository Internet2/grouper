# GRP-7246  OAuth authorization code redemption is not atomic

The MCP OAuth token endpoint redeems an authorization code with a select, then a series of checks, then a separate delete. Two concurrent redemptions of the same code can both read a live row, both pass every check, and both be issued a token — nothing between the two statements holds a lock, and since WS runs on multiple nodes, no JVM-level guard would help either.



This is not exploitable. Winning the race requires already holding the code, the code_verifier, and the client secret, which makes you the legitimate client; an attacker with only a stolen code fails PKCE at GrouperOAuthServlet.java:265 whether they race or not. Filed as a correctness fix, not a security fix.

# GRP-7062  SCIM2 provisioner should recover from a 409 "uniqueness" on entity create (link the existing target object) instead of failing the daemon

PROBLEM

During a full sync, the SCIM2 provisioner creates an entity that does not appear in the bulk target retrieve, but actually already exists in the target. The target returns HTTP 409 with scimType "uniqueness", the create throws, and because errorHandlingProvisionerDaemonShouldFailOnObjectError defaults to true, the whole daemon run goes to ERROR. The entity's memberships then also fail as collateral.

This is recoverable: the existing target object can be fetched by a matching/search attribute and linked, but today the provisioner only does a retrieve-before-create when disableEntitiesInsteadOfDelete=true (and even then only as a side effect of that delete-oriented flag). When that flag is off -- the normal case where the target is not authoritative for deletes -- a 409 uniqueness is fatal.

ROOT CAUSE

Two things combine:
 # Targets can return an incomplete or overlapping bulk listing (eventual consistency, unstable page ordering, or duplicate pages). GrouperScim2ApiCommands.retrieveScimUsers dedups by id and stops paging as soon as a page returns no new ids (the {{!foundNewUser}} early return, around GrouperScim2ApiCommands.java line 1303). If the target returns overlapping pages, the tail of the list is silently dropped, so an existing active user can be absent from the retrieved set. (Observed with Robin: the run reported duplicateTargetGroups=40, i.e. the /Groups list came back doubled, and an active user missing from the bulk /Users pull was still returned by filter=userName eq.)
 # The missing user has no match, so full sync routes it to create. GrouperScim2ApiCommands.createScimUser only accepts 200/201 (GrouperScim2ApiCommands.java around line 1048), so the 409 propagates as an object error. The graceful link path in GrouperScim2TargetDao.insertEntity (around line 1058, calling retrieveEntityHelper) is gated on isDisableEntitiesInsteadOfDelete().

IMPACT

Any SCIM target whose bulk listing is not guaranteed complete/stable can fail full sync whenever a previously-existing entity is (re)added in Grouper but absent from the current bulk read. Daemon goes ERROR; the entity and its memberships do not provision until the target's listing happens to include it again.

PROPOSED FIX

On entity create that returns 409 with scimType "uniqueness" (or, more generally, a uniqueness conflict), retrieve the existing target object by matching/search attribute and link it (capture its id into the sync link, set provisioned) instead of throwing -- independent of disableEntitiesInsteadOfDelete. Reactivate only if configured to. Concretely, in GrouperScim2TargetDao.insertEntity, on the createScimUser failure path, call retrieveEntityHelper(scimConfiguration, targetEntity, false); if found, treat as a successful link; otherwise rethrow. (executeMethod can surface scimType/status so uniqueness 409s are distinguished from other 409s.)

Optionally expose this as an explicit config (e.g. linkEntityIfExistsOnCreate / recoverFromCreateConflict) rather than overloading disableEntitiesInsteadOfDelete, so the reconcile behavior is available without changing delete semantics.

FOLLOW-UP (possibly a separate ticket) -- bulk retrieve data safety

retrieveScimUsers / retrieveScimGroups should capture the target's reported totalResults and, when the unique retrieved count is materially less than totalResults, log a WARN (or fail) instead of silently returning a partial set. A silent partial read causes spurious creates (this bug) and, if entity deletes were enabled, could cause spurious deletes. Consider terminating paging on startIndex vs totalResults rather than on the first all-duplicate page, to tolerate targets that return overlapping pages.

WORKAROUND

Set disableEntitiesInsteadOfDelete=true on the provisioner; this triggers a filtered retrieve-before-create that links the existing user. Safe only when no entity deletes are configured.

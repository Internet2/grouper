### Gary Brown - 2008-08-05T16:48:33.290+0000

Searching subjects and listing members (including those with a privilege) may be different. For searching the SourceAdapter may return `complete` subjects including attributes though they could use a lazy strategy. This is part of the Subject API and so isn`t something Grouper can manipulate.

Whenever Grouper returns Memberships there are potentially two queries to run for each Membership - i.e. Membership.getMember().getSubject()

looks up the memberUuid and then the subjectId. If, whenever, we query Memberships we also join to Member we can instantiate the nested Member object and use a LazySubject so that no further queries are necessary - unless we require actual subject attributes. If, as often will be the case, we want to sort Subject lists on something other than id then the sorting code will force each subject to be instantiated. Sorting can be configured so that there is a limit to the size of resultset - but it isn`t ideal

At Bristol we have ~30000 person identities. Pre-caching that number in memory is practical and gives good performance improvements.

The main disadvantage of LazySubject is that you won`t get a SubjectNotFound exception where you expect to and it becomes necessary to wrap the SubjectNotFoundException you may get retrieving attributes with a GrouperRuntimeException.

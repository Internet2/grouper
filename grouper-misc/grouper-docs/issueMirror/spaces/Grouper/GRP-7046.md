# GRP-7046  Provisioner should write progress to log and database periodically during retrieve from target

At large scale (Michigan: Okta target with approx 105k groups and 800k users), the retrieve-from-target phase of a full sync runs for hours. The heartbeat already calls logPeriodically() about once a minute, but the debug map has no running counters during target retrieve so the log lines do not show pace, and nothing is written to the database until the job ends, so an admin cannot tell from grouper_sync_log or the UI whether the job is progressing or hung.

Proposed:
 * Target DAO retrieve methods (users, groups, memberships) increment running counters in the debug map as pages come back (e.g. targetUsersRetrieved=250000), so periodic log lines show count, elapsed, and rate.
 * On the heartbeat interval, also persist progress to the database: update the grouper_sync_log record and/or grouper_sync_job heartbeat/percent complete, and/or the grouper_loader_log job message.
 * Config for the interval (default approx 60 seconds) and to enable/disable the database writes.

## Comments

### Chad Redman - 2026-06-25T17:04:10.910+0000

This is currently implemented with a flag property in the base provisioner, and 3 subproperties covering groups, entities, and memberships:

- Log progress while retrieving target data
    - Log progress every retrieved group count
    - Log progress every retrieved entity count
    - Log progress every retrieved membership count

It's independent of the other debug log settings, so you can still see the output even when you don't want other verbose logging.

As for the logging, I think it's more convenient simply to output a log line at every interval. First, the progress will be streaming to the container log, so easy to track and read. Second, putting it in the debugMap means only a single point of data at all times, which means there is no straightforward way to track the speed throughout the run. Third, the debugMap is hard to read, and these will be just more buried numbers.

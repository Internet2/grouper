# GRP-7512  LogicGate records provisioner creates duplicate contacts and churns records; add cleanup and audit

The LogicGate records provisioner (LogicGateRecordsProvisionerDao) created duplicate contact records and churned thousands of records every full sync.

Causes: the full sync paged through every record in the workflow, including about 196k inactive ones, unsorted, with a GET per record, so runs took 6 to 10 hours. Each new person was created twice: the new record id was not captured and the read-back after insert could not match, so the person stayed unmatched and was inserted again. The duplicate check when reading never fired, so a person with two records could not be matched and both records were retired, then the person was recreated on the next run.

Fixes: read with the v2 records API filtered by step with field values inline (minutes instead of hours), and fail on a short read. Capture the record id on create and set the id attribute so the read-back matches. On 401 get a new token and retry once (LogicGate cancels a client's token when another token is issued for it).

New: the provisioner keeps one live record per person and no inactive records. Per person it keeps the record with the most direct links, then the oldest, moves the direct links of the other records (contact groups and workflow records like action plans) to the kept record, and deletes the other records. People who left are deleted. A person who is provisionable but only has inactive records gets the best one reactivated instead of a new record created. Every action is written with a snapshot of the record and its links to table prov_logicgate_audit, including read-only runs (read_only column), and changes that touched links or failed are emailed in a report.

New settings (documented in grouper.base.properties): logicGateApi.maxDeletesPerRun, auditRetentionDays, reportEmails, threads, reverseLinkScanThreshold. The existing logicGateApi settings (Url, client, secret, userAttributes) are documented there too.

# GRP-7228  WS bearer token external system: short-lived oauthClientCredentials token crashes token cache (Time to live in minutes must be greater than 0)

Clicking Test on an oauthClientCredentials WS bearer token external system (and every provisioner call using one) can fail with RuntimeException: Time to live in minutes must be greater than 0, thrown from ExpirableCache.put via WsBearerTokenExternalSystem.retrieveBearerTokenForConfigId.

Root cause: the token grant succeeds, but the cache time-to-live is computed as expiresInSeconds/60 (integer division to whole minutes). When the access token lifetime is short (for example a Jamf Pro API-client token under ~60 seconds), this truncates to 0, and ExpirableCache.put rejects a time-to-live of 0. So the failure is purely in caching the token, not in obtaining it.

Fix: only cache the token when the computed minutes are at least 1. For a sub-minute token, skip the cache and fetch a fresh token on each call. Caching a sub-minute token for a full minute is not a safe alternative because it could be served after it has expired, causing a later 401.

Immediate workaround for admins: raise the API client access token lifetime in the target (for example to 300 seconds) so expires_in divided by 60 is at least 1.

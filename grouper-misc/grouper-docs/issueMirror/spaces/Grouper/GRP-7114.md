# GRP-7114  sync-back follow-ups (duo update seam, capability-driven validation, update-refresh verification)

Duo group updates: fix the field-name seam so a "description" change reaches the target. GrouperDuoApiCommands.updateDuoGroup gated the desc param on the raw Duo field "desc", but the DAO passes the target attribute name "description"; honor both. Un-skips testDuoGroupUpdateConvergesNextRead.

Revert the update-refresh drain-mark where it is unsafe. The mark (recordTargetNativeGroupWrite(id, null)) drops the object's snapshot and relies on the drain re-read to restore it; that only works if the provisioner's drain re-read captures the object. Duo's by-name retrieveGroup serves from a cache without capturing, so the mark left grouper_prov_group null; interfolio's retrieveEntity has the same no-capture pattern. Reverted both (updates converge on the next bulk read instead); ldap left un-marked (unverified + rename/DN risk).

Make the groups=>memberships validation capability-driven. The both-or-neither coupling now keys off canRetrieveMembershipsAllByGroup in both the config validation and the runtime (computeGroupsFromSyncBackCacheThisRun), instead of being hardcoded. Group-centric targets (Okta) are unchanged; a target that fetches memberships by entity or all-at-once can serve groups from the cache independently.

Verify the committed update-refresh marks with group-update-converge tests carrying a pass-A (write-pass) assertion: dropbox and truefoundry (both capture on the drain re-read, so safe). adobe is inert (updateGroup rejects any non-name attribute, name is the match key), so it needs no test.

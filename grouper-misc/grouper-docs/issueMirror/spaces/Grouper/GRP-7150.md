# GRP-7150  Data provider full sync: option to retrieve source data by subject id list instead of range (LDAP without ordering index)

GRP-6864 batches data provider full sync by subject id range to reduce memory. For each batch the DAO wraps the configured filter with an ordering comparison on the subject id attribute: (and baseFilter (attr greater-or-equal from)(attr less-or-equal to)). For LDAP providers this requires an ordering matching rule plus ordering index on the subject id attribute.

Many LDAP attributes (for example a hex regid GUID) only have equality and presence indexes, not ordering. So each range query degrades to an unindexed subtree scan and the server read-times-out (seen in the field as resultCode CONSTRAINT_VIOLATION with SocketTimeoutException Read timed out during selectDataBySubjectIdRange). LDAP admins are often unwilling to add ordering indexes.

Proposal: add a per-provider config, grouperDataProvider.CONFIGID.fullSyncSubjectIdRetrieval with values range or list, default range (preserves current behavior, best for SQL providers with an indexed primary key). In list mode, the per-batch loop feeds the batch subject id slice through the already-existing list helpers (syncFullLoadGrouperDataForSubjectIds and syncFullRetrieveSourceDataForSubjectIds -> selectDataBySubjectIds), which query exact ids via equality OR filters batched at 800. Equality filters use the equality index every LDAP already has, so no ordering index is needed.

Extra benefit: list mode also avoids the lexicographic-ordering mismatch between the Java String sort and the LDAP server collation, which is the reason the range path needs a straggler pass. Querying exact ids means no ids silently fall outside a computed range, so the straggler pass is unnecessary in list mode. Tradeoff to document: list mode issues more round trips (about 13 equality batches per 10000-id batch) versus one range query, but each is indexed and reliable.

### Chris Hyzer - 2026-07-19T01:54:05.832-0400

Workaround on current 6.x code without waiting for this fix: add an ordering index (ordering matching rule) on the LDAP subject-id attribute so the range comparisons (attr greater-or-equal from)(attr less-or-equal to) are indexed rather than an unindexed subtree scan. That resolves the read-timeout on range mode directly. If adding the index is slow, raising the read timeout on the ldap connection is a stopgap. The list-mode config in this ticket is the alternative for sites that cannot add an ordering index.

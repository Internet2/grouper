# GRP-7301  UI accessibility: unique ids and aria-controls for more-actions menus (group family first)

The literal id=more-action-button is hardcoded on about 50 more-actions dropdown triggers across the UI (the *MoreActionsButtonContents.jsp family). Each is a single static include, so a given menu type appears at most once per screen - but group sub-screens include groupHeader.jsp (which carries the group more-action-button) AND their own more-actions menu, producing two elements with the same id on one page.

Confirmed live on the Group rules screen: two elements with id=more-action-button (Show more actions for this group, plus Show rules actions), a live duplicate-id violation (WCAG 1.3.1 / 4.1.2). The same pattern applies to the other group sub-screens that pull in the header: attestation, loader, object types, reports, deprovisioning, workflow, and so on. It also blocks adding aria-controls to these menus (item 3 for object screens), since neither the trigger id is unique nor, for most, does the target ul have an id.

Fix: because these menus are one-per-type (no per-row loops), give each trigger a distinct literal id and its ul a matching id where absent, add aria-controls pointing at that ul plus aria-haspopup where missing, and keep role=button on the anchors (they are a-tags, not native buttons). No runtime JS depends on the trigger id (the app JS targets the ul ids, e.g. group-more-options); the only five references are Playwright browser tests (GrouperUiBrowserGroupEdit, GroupDelete, ProvisioningAssignGroup, ProvisioningRemoveGroup, TemplateRun), all acting on the group menu, which will be retargeted to the group menu new id.

Rollout is screen-family by screen-family with a live full-page duplicate-id scan on each sub-screen. This ticket starts with the group family, where the duplicate is confirmed; the remaining families follow. Split out of GRP-7299 as item 16 of the accessibility action plan.

Scope settled after investigation: the only object headers that shared id=more-action-button with their sub-screen menus (the cause of live duplicate ids) are group and subject. Both are now fixed - group family (10 menu JSPs + 5 browser tests) and subject family (3 menu JSPs: subject header + provisioningSubject + provisioningSubjectMembership). Verified live: group rules/attestation and subject view show zero duplicate ids, with each trigger aria-controls resolving 1:1.

The folder header already uses a distinct id (moreActionsButton) from a prior a11y fix, so folder sub-screens have no duplicate. The remaining ~35 more-actions menus (folder sub-screens plus single-menu list/config screens) render only one per screen, so they have no live duplicate ids - their only remaining need is additive aria-controls, which is accessibility item 3 (menu ARIA) rather than the duplicate-id concern of this ticket. That aria-controls sweep is deferred to a separate item-3 follow-up.

# GRP-7187  Convert a normal group to a composite in place by relabeling immediate memberships to composite (no delete/add, no change log or PIT churn)

Problem. Today, making a group composite requires zero immediate members (AddCompositeMemberValidator, error GROUP_ACTM). The composite membership rows then materialize asynchronously via the compositeMemberships change log consumer, firing a MEMBERSHIP_DELETE for each old immediate and a MEMBERSHIP_ADD for each new composite, even for members whose effective (flattened) membership never actually changed. Result: change log noise, downstream provisioning churn, and a PIT gap across the switch.

Constraint. membership_uniq_idx is UNIQUE on (owner_id, member_id, field_id) and does NOT include mship_type, so an immediate row and a composite row cannot coexist for the same member. Therefore add-then-remove is impossible; an in-place relabel is the only viable approach.

Approach. Bypass the validator, create the grouper_composites row, flip the group self group_set from immediate to composite, then per member: overlap (immediate today and in the composite result) gets a raw UPDATE setting mship_type to composite and via_composite_id, which emits no change log entry and leaves PIT continuous; a genuine join inserts a composite row (MEMBERSHIP_ADD); a genuine leave deletes the immediate row (MEMBERSHIP_DELETE). So only real joins and leaves reach the change log.

Because the overlap relabel is raw JDBC that bypasses the Hibernate membership hooks, the implementation must also refresh the group last-membership-change timestamp and evict the Hibernate second level cache for the touched membership objects. Related to GRP-7172 (general convert composite to and from direct memberships without a delete/add cycle).

## Comments

### Chris Hyzer - 2026-07-28T11:08:25.236-0400

Final design (implemented as CompositeInPlaceConverter). Convert a normal group that already has immediate members into a composite (owner = left [type] right) by relabeling the overlap in place, so no member whose effective membership is unchanged produces a change log or PIT entry.

Steps: (1) partition the current immediate members against the composite result; (2) delete genuine leaves via the normal API (real MEMBERSHIP_DELETE); (3) relabel the overlap immediate rows to composite with a single set-based HQL update (mship_type immediate to composite) that bypasses the membership hooks, so no change log entry and no PIT record, and the member never stops being a member; (4) evict the second level cache; (5) call the normal Group.addCompositeMember, which creates grouper_composites, flips the self group_set to composite, fires GROUP_COMPOSITE_ADD, and drives resyncComposite to add genuine joins and repair via_composite_id on the relabeled rows. resyncComposite keys its diff on member set plus mship_type=composite, so it leaves the relabeled overlap rows alone.

Why relabel and not add-then-remove: membership_uniq_idx is UNIQUE on (owner_id, member_id, field_id) without mship_type, so an immediate row and a composite row cannot coexist for the same member. Relabel in place is the only option.

Atomicity: the whole conversion runs in one transaction and commits at the end. The intermediate state (composite-type rows before the composite object exists) is never committed, so no other session or the findBadMemberships daemon can observe it, and a concurrent immediate-member add that would make addCompositeMember reject the group causes a clean all-or-nothing rollback. Trade-off: a very large group holds one long-running transaction (row locks, WAL/undo, vacuum pressure), so convert the largest reference groups in a maintenance window. FindBadMembershipsDaemon remains the reconcile backstop.

Tests: CompositeConvertInPlaceTest covers a union whose result equals the current members (asserts zero membership change log entries), an intersection whose result equals the current members (zero entries), and a case that differs by one member each way (exactly one MEMBERSHIP_ADD and one MEMBERSHIP_DELETE, nothing for the overlap).

Availability: v7.3.2+ and v6.3.1+.

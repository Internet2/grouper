# GRP-7140  ABAC data provider sync churns delete/insert every run for TIMESTAMP columns with sub-millisecond precision

  Problem

 

  When a data provider query selects a database timestamp column with sub-millisecond precision (Postgres TIMESTAMPTZ / TIMESTAMP, Oracle TIMESTAMP, MySQL DATETIME(6)), every subsequent full-sync run deletes and re-inserts all grouper_data_field_assign (or grouper_data_row_field_assign) rows for that field — even when the source data is completely unchanged. The stored value_integer values are correct (milliseconds since epoch), but the sync's "did this value change?" check falsely reports every row as changed.

 

  Reproduce

 

  1. Configure a data provider SQL query that selects a TIMESTAMPTZ column (or any timestamp type with microsecond precision) into a data field declared fieldDataType = timestamp.

  2. Run OTHER_JOB_<providerName> once — rows populate correctly. Verify grouper_data_field_assign.value_integer holds milliseconds since epoch.

  3. Run the same job again without changing the source data.

  4. Expected: zero deletes, zero inserts in the loader log.

  5. Actual: every row is deleted and re-inserted with the same value. grouper_data_field_assign_hst shows history entries for the same underlying values on every run.

 

  Not reproducible with:

  - Provider queries that supply the value as BIGINT millis (Long path).

  - DATE-typed columns (JDBC returns java.sql.Date, whose getTime() returns whole seconds → whole millis).

  - Any source producing whole-millisecond precision.

 

  Root cause

 

  GrouperDataProviderLogic computes the per-run diff for a field's assignments with Set.removeAll(...):

 

  Set<Object> dataFromProvider = ...;   // built from convertValueHelper(Object)

  Set<Object> dataFromGrouper = ...;    // built from convertValueHelper(Long, String)

 

  Set<Object> dataToDelete = new HashSet<>(dataFromGrouper);

  dataToDelete.removeAll(dataFromProvider);       // relies on equals()

 

  Set<Object> dataToInsert = new HashSet<>(dataFromProvider);

  dataToInsert.removeAll(dataFromGrouper);        // relies on equals()

 

  For a timestamp field both sides deposit java.sql.Timestamp objects into the sets. Timestamp.equals(Timestamp) compares both seconds and nanoseconds. The two sides carried different nanos:

 

  - dataFromGrouper value came from GrouperDataFieldType.timestamp.convertValueHelper(Long, String) → new Timestamp(millis). nanos = (millis % 1000) * 1_000_000 — no sub-millisecond component (correct, since storage is millis).

  - dataFromProvider value came from GrouperDataFieldType.timestamp.convertValueHelper(Object) → GrouperUtil.timestampObjectValue(value, true), which for a Timestamp input returned the argument unchanged. If the JDBC driver delivered microsecond precision (as it does for Postgres TIMESTAMPTZ), that

  Timestamp had non-zero nanos beyond the millis component.

 

  Concretely, a TIMESTAMPTZ value of 2026-07-17 14:33:12.345678+00:

 

  - Storage: value_integer = 1784112792345 (millis, truncated).

  - Grouper-side Timestamp: seconds = 1784112792, nanos = 345_000_000.

  - Provider-side Timestamp: seconds = 1784112792, nanos = 345_678_000.

  - equals() → false.

 

  So dataToDelete contained the Grouper-side Timestamp (not present in the provider set), and dataToInsert contained the provider-side Timestamp (not present in the Grouper set). The sync deleted and re-inserted the row. Next run, same thing — the newly-inserted row rounds back to millis on the next read.

 

  The bug did not surface earlier because the other three branches of GrouperUtil.timestampObjectValue all construct a fresh new Timestamp(long millis) — which is inherently millis-precision — so their round-trip is stable. Only the input instanceof Timestamp branch preserved the incoming nanos, and only JDBC drivers delivering sub-millisecond precision hit that path.

 

  Consequences

 

  - Churn on every daemon run for any timestamp field populated from a sub-ms-precision source. The rows themselves are functionally correct, but the deletes and inserts:

    - flood grouper_data_field_assign_hst with meaningless history entries;

    - flood grouper_change_log_entry with DATA_FIELD_ASSIGN_DELETE / DATA_FIELD_ASSIGN_ADD pairs (with per-run limits blocking some events for very large populations);

    - increase daemon runtime proportional to the number of affected rows;

    - trigger downstream consumers (ABAC scripted-group full-sync, provisioning) to re-evaluate every dependent group on every run;

    - obscure real changes buried in the noise.

  - Silent — no error is logged, the loader log's "add" and "delete" counters go up in equal amounts every run, and the data ends up correct after each run.

 

  Same shape applies to the row-field path (GrouperDataRowFieldAssign) — it uses the same convertValueHelper(Object) before assignment.

 

  Fix

  

  In GrouperDataFieldType.timestamp.convertValueHelper(Object), normalize the result to millisecond precision before returning:

 

  @Override

  public Object convertValueHelper(Object value) {

    Timestamp t = GrouperUtil.timestampObjectValue(value, true);

    if (t == null) {

      return null;

    }

    return new Timestamp(t.getTime());   // truncate nanos beyond millis

  }

 

  t.getTime() returns milliseconds; new Timestamp(millis) sets nanos = (millis % 1000) * 1_000_000, matching the shape the read-back path produces from value_integer. Both sides of the diff become equals()-comparable, and the sync becomes a proper no-op when the source data is unchanged.

 

  No storage migration is required — the stored value_integer values were already correct (millis) throughout. The fix is purely to the in-memory Timestamp object used for comparison.

 

  Test plan

  

  - Unit / integration: add a test that populates a timestamp-typed data field from a TIMESTAMPTZ source (or simulate it by feeding convertValueHelper a Timestamp with non-zero sub-millisecond nanos), runs the full sync twice, and asserts:

    - the second run's loader log shows 0 inserts and 0 deletes;

    - grouper_data_field_assign_hst has no new entries after the second run;

    - grouper_change_log_entry has no DATA_FIELD_ASSIGN_ADD / DATA_FIELD_ASSIGN_DELETE for that field after the second run;

    - value_integer is unchanged.

  - Manual regression: re-run the affected daemon against a real source table and confirm the loader log reports 0 inserts / 0 deletes on the second and subsequent runs.

  - Non-regression: existing timestamp tests (any that use Long-, Date-, or String-typed provider inputs) continue to pass — those paths were already going through new Timestamp(millis) and won't behave differently.

 

  Related

 

  - GRP-6825 addressed a prior type-mismatch (Long vs Timestamp) in the same comparison, unifying both sides on Timestamp. This ticket completes the fix for the case where both sides are Timestamp but with different nanos precision.

# GRP-7566  SCIM provisioner paging stops early when target filters after paging (Snowflake), page by requested count

Reported by a school on Grouper 6.3.0 provisioning to Snowflake via SCIM 2. Snowflake pages over its whole index and then drops the records the bearer token cannot see. So a page can come back short, empty, or overlapping the previous page, and a later page can still have more results. totalResults is the full index count, not the visible count.

Current behavior in GrouperScim2ApiCommands (both the retrieve all users loop and the retrieve all groups loop, same in 6.3.0 and v7): paging stops when totalResults is 0, when Resources is missing or empty, when a page has no IDs we have not seen yet (foundNewUser / foundNewGroup is false), or when the returned startIndex equals the previous one. The next startIndex is startIndex + resourcesNode.size(), not + the requested count. With a filtering server like Snowflake every one of these stops early and Grouper misses objects.

Evidence from their logs, same provisioner, full sync: with groupPageSize 50 Grouper found 26 target groups, with groupPageSize 1000 it found 68 target groups. Users were 42 both times (users are fewer than one page here, but the user loop has the same logic). Their workaround is groupPageSize / userPageSize = 1000, which only works while one page covers the whole index.

Requested change: add a SCIM provisioner setting (e.g. provisioner.myScimProvisioner.scimPageByRequestedCount, default false so existing servers are not affected) in grouper-loader.base.properties with the default in the JSON comment, plus the provisioner config UI. When true, for both users and groups: advance startIndex by the requested count (pageSize), not by the number of results returned; do NOT stop on an empty page or a page with no new IDs; keep paging while startIndex <= totalResults; keep de-duping by id; keep the maxCalls endless loop guard. Consider whether the existing returned-startIndex-equals-previous check should also be skipped in this mode.

Test with the SCIM mock is REQUIRED, this is not done without it. Add a mock option that simulates Snowflake: page over the full index by startIndex/count, then filter out a configurable set of records (so some pages are short, some are empty, and later pages still have data), and return totalResults as the unfiltered count. Write a JUnit test (in the SCIM provisioner test class) with enough groups and users that several pages are empty or short in the middle, run a full sync with a small page size (e.g. 5) with the new setting on, and assert that every visible group and user is retrieved. Also assert that with the setting off the old behavior is unchanged. Remember the SCIM mock runs in a separate JVM, so per-test mock behavior has to be set via DB config and a config cache clear, not in-memory.

Note: per RFC 7644 the server should only count and page over resources the caller can see, so this is arguably a Snowflake bug too (the school has a ticket open with Snowflake), but Grouper should handle it.

# GRP-5707  Index member_sort_string0_idx slowing down Group.getMembers()

{code}
create index member_sort_string0_idx
    on grouper_members (sort_string0);
{code}

When viewing the group members page, the existence of this index sometimes makes a bad query plan, because it wants to use this first, getting all the grouper_members rows from it to get the top 50. Working with a customer, removing that index improved the page display from 90 seconds to 300 ms.

Without member.id being in the index, it's not very useful by itself.

As the customer, I'll add the query plan below. In the middle of this plan, the system is deciding to go through the Members (3M members) in Sorted order and run the filters on them, even though the filters would narrow down the result to 1 member in some test groups and 20k in the group below. FWIW, all the grouper tables are fully vacuumed and analyzed every morning. We have a test copy of the database, and it executes this query with the plan we expect (filter to the members of the group and then sort them), and we cannot determine why [the test copy is much less analyzed and vacuumed].

 

Finally, there is probably a group size where a sorted index on sort_string0 helps sort the members, but all our group-member results in the UI seem to be 300ms now (after the index was dropped) (1 member as well as 20k members) when they were 90-120 seconds when the index existed; we'll take the risk on our 100k member groups. Actually, I just tested loading a 90k-member group in the UI and it took <5sec.

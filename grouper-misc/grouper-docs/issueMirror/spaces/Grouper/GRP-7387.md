# GRP-7387  GRP-7336 follow up: restore StemFinder.findByUuid and check folder view privilege in the visualization screen

GRP-7336 added PrivilegeHelper.canStemView to StemFinder.findByUuid. That only counts direct naming privileges on the folder, so users who see a folder because they have privileges on something inside it (the stem view privilege model) get folder not found on Up one folder, folder paging and other links that pass stemId, and internal callers that look up a stem by uuid with the user session (e.g. AttributeDefName.getStem, AttributeDef.getStem) can throw StemNotFoundException.

Fix: restore StemFinder.findByUuid to its previous behavior, consistent with the other static StemFinder finders. Close the leak GRP-7336 reported where it is: the visualization screen (UiV2Visualization stemView and buildGraph via VisualizationContainer.getGrouperObject) now applies the same folder view check as the folder screen (StemContainer), shared in one method.

## Comments

### Chris Hyzer - 2026-09-28T01:15:28.480-0400

h3. What was wrong with the GRP-7336 commit (974f6152ae9d)

The leak in GRP-7336 was one screen: UiV2Visualization.stemView (and buildGraph) looked up the folder with StemFinder.findByUuid and showed its name, id, creator and id index without checking whether the user can see the folder. The commit instead added a check inside StemFinder.findByUuid itself. Two problems with that:

* Wrong rule. {{PrivilegeHelper.canStemView}} only counts naming privileges on the folder itself (stemAdmin, create, stemView, stemAttrRead, stemAttrUpdate). Most users see a folder because they can see something inside it: the stem view privilege model (grouper_stem_view_privilege table), or security.folders.are.viewable.by.all. Those users were told the folder does not exist.
* Wrong place. {{StemFinder.findByUuid}} is a low level lookup with about 90 callers (DAOs, rules, xml import/export, change log consumers, UI screens), most running with the user session and needing the folder object, not a visibility decision. Examples that broke: Up one folder on the folder screen (UiV2Stem.retrieveStemHelper passes stemId of the parent), folder paging/filter and view folder links, and {{AttributeDefName.getStem()}} / {{AttributeDef.getStem()}} which pass exceptionIfNotFound=true and so threw StemNotFoundException.
* It was also incomplete: findByName, findByIdIndex, findByUuids and the other static finders were unchanged, so the same information was still reachable a different way.

h3. What GRP-7387 does

* Restores StemFinder.findByUuid byte for byte to before GRP-7336. The static finders are lookups, not authorization.
* New {{PrivilegeHelper.canViewStemOrObjectInside(subject, stem)}}: the rule the folder screen already used, now in one place. Runs as root: first canHavePrivilege(stemView) on the folder, otherwise the secure StemFinder (new StemFinder().addStemId(id).assignSubject(subject).findStem()), which uses the stem view privilege table and honors folders.are.viewable.by.all and wheel / view only root.
* StemContainer.isCanViewPrivileges() calls it (no behavior change for the folder screen). VisualizationContainer.getGrouperObject() calls it for folders and throws StemNotFoundException both when the folder does not exist and when the user cannot see it, so the response does not reveal which.

h3. Pattern going forward

When a screen or web service looks up a folder from a request (stemId, stemName, stemIndex) and shows it to the user, check PrivilegeHelper.canViewStemOrObjectInside (or go through UiV2Stem.retrieveStemHelper, which does). Do not add authorization to the static StemFinder finders.

h3. Tests

TestStemFinder: testFindByUuidSecure (which asserted the broken behavior) is replaced by testFindByUuidIsNotAuthorization and testCanViewStemOrObjectInside (privilege on the folder, implied privilege, privilege on a group inside, nothing, null, folders viewable by all). TestStemFinder.setUp now calls super.setUp(): it used to reset the registry itself without clearing config overrides, so an override set in one test leaked into the next.

# GRP-7602  UI screen for sysadmins to manage custom composites and membership requirements

Custom composites and membership requirements can only be set up today by editing properties and UI text by hand. That means several keys per entry, numbered indexes that had to stay in order, text keys that have to match, and an attribute definition and attribute that have to be created separately and set up correctly.

Add a screen under *Miscellaneous > Custom composites and membership requirements* where Grouper system administrators can view, add, edit and delete both.

h2. Access

* Only members of the wheel group (or GrouperSystem) can see or use the screen. This is checked on the server for every action.
* It has the same controls as the configuration editor: the UI configuration must be on, and saves and deletes must come from an allowed source IP address.

h2. Where changes are saved

* Changes are saved to the database configuration, so they are audited, kept in the configuration history, and picked up by every UI, WS and daemon node.
* A value set in a configuration file on disk is shown read only and cannot be changed or deleted on the screen.

h2. Custom composites

* Each one has a UI key, a label, a type (complement or intersection) and a group, saved under the existing grouper.membership.customComposite.* keys, with the label in grouper.text.en.us.properties.
* The indexes no longer need to be consecutive. Deleting one removes only its own keys and label, and the others keep their index.
* An incomplete entry (only some of its keys set) is marked on the screen and skipped on the members screen.

h2. Membership requirements

* Each one has a config ID, a UI key, a veto message, a required group, whether to veto new additions, exempt subject sources, and an attribute. They are saved under the existing grouper.membershipRequirement.(config ID).* keys, with the veto message in grouper.text.en.us.properties.
* The form is built on the configuration module framework, like other configuration screens.
* The attribute can be one which already exists, a new attribute in an existing attribute definition, or a new attribute definition and attribute. The screen checks that the definition is a marker assignable to groups and folders and not multi-assignable or multi-valued, and creates a new one set up that way.
* The config ID, UI key and attribute cannot be changed once saved.
* Optionally, the attribute can be shown on the group create and edit screens as a checkbox (groupScreen.attribute.*). This entry is shared by every requirement on the same attribute.
* The edit screen shows what is wrong with a requirement, if anything, and links to the attribute.
* Deleting a requirement removes its configuration, its veto message, and its group screen entry if no other requirement uses the attribute. The attribute and its assignments are kept.

h2. Configuration review

* Add a check to Configure > Configuration review: an error for a membership requirement which is skipped because a key, its attribute or its required group is missing, and a warning for a custom composite which is incomplete, has a type which is not valid, or whose group does not exist.

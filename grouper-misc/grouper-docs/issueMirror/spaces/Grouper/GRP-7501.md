# GRP-7501  Provisioner incremental should evaluate failsafes on its own deletes, not only the full sync

Provisioner failsafe thresholds are only evaluated by the full sync. GrouperProvisioningLogic.provisionFull() calls processFailsafesAtStart() and processFailsafes(), but provisionIncremental() only calls processFailsafesAtStart(), which just blocks the incremental if the full sync job has an unapproved failsafe issue. The incremental never checks the size of its own deletes.

The most common ways a provisioned group gets emptied all flow through the incremental: a group is deleted or emptied, a composite factor changes, or the provisioning attribute is removed from a folder. The full sync will not catch it afterwards because by then the target already matches Grouper. Loader failsafes only protect loader-managed groups at the source.

Proposal: the incremental should evaluate the same failsafes the full sync does, using the same provisioner settings (failsafeUse, failsafeMinGroupSize, failsafeMaxPercentRemove, failsafeMaxOverallPercentGroupsRemove, failsafeMaxOverallPercentMembershipsRemove, failsafeMaxOverallPercentEntitiesRemove, etc). This is not opt-in: if failsafes are on for a provisioner, they apply to both full and incremental.

Per group: processFailsafesSetupGroupTotals() already gets the in-target membership count from grouper_sync_membership for only the groups with deletes, so the incremental can reuse it and apply failsafeMinGroupSize / failsafeMaxPercentRemove to the run's deletes.

Overall: apply the overall group / membership / entity percent removed checks to the incremental's deletes against the provisioner's current totals in the sync tables, to catch e.g. a provisioning attribute removed from a large folder.

On a trip: use the existing ERROR_FAILSAFE status, approval, and email flow. Hold the whole incremental (like the existing block when the full sync has a failsafe issue) so changes are not applied out of order. Once approved, the incremental proceeds.

Considerations: one bulk removal can arrive spread across several incremental runs (incrementals often run every minute), so a per-run check can be evaded. Consider a rolling window (percent removed from a group over the last N minutes) either in this issue or a follow-up. Also make sure legitimate large changes have a clear approve path and the failsafe summary in the daemon log shows what tripped.

# GRP-7525  Provisioner failsafe "approve once" not reset after approved full sync ends in error

When a provisioner full sync trips a failsafe and an admin approves it once, `grouper_failsafe.approved_once` is set to `T`. It should go back to `F` after the approved run. It only goes back if that run ends without an error status. If the approved run hits record-level errors, `approved_once` stays `T` and the failsafe issue stays set. Later failsafe trips are then approved automatically, until someone fixes the data or edits the DB by hand.

First seen on the CCure provisioner, but the cause is in the shared provisioning code, so it affects every provisioner.

*Root cause*

`GrouperProvisioner.provision()` (around line 984 in `GrouperProvisioner.java`):

```java

if (gcGrouperSyncLog != null && gcGrouperSyncLog.getStatus() != null && !gcGrouperSyncLog.getStatus().isError()) {

  if (!StringUtils.isBlank(this.getJobName())) {

    GrouperFailsafe.assignSuccess(this.getJobName());   // approved_once = 'F'

```

`GrouperProvisioningLogic.errorHandlingHandleError()` sets the sync log status to `ERROR` when a record error is configured to fail the daemon. This depends on `errorHandling.provisionerDaemonShouldFailOnObjectError` and the per-error-code settings, for example `errorHandlingTargetObjectDoesNotExistIsAnError`. `ERR` always counts as an error. When that happens, `assignSuccess` is skipped, so the approval is never consumed.

*Impact*

* Operators have to fix `grouper_failsafe` manually.

* While `approved_once` is stuck at `T`, a later, unrelated failsafe trip on the same job is silently approved, which defeats the failsafe.

*Suggested fix*

Reset `approved_once` as soon as an approved run gets past the failsafe check. That means in or right after `GrouperProvisioningFailsafe.processFailsafes()`, not when the whole run succeeds. Leave `last_success` and `last_failsafe_issue` alone, so they still reflect whether the run succeeded.

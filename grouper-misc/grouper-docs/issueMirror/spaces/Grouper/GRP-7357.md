# GRP-7357  Okta provisioner retry loop reuses stale Authorization header, causing spurious 401 on long-running full syncs

h2. Description

A full sync of {{Okta_MCOMM_UserGroups}} (QA, instance {{w4m4dlqr}}, {{fullProvisionFull}}) aborted after ~5h07m with:

{noformat}java.lang.RuntimeException: Invalid return code '401', expecting: 200, 404.
'https://okta-qa.iam.it.umich.edu/api/v1/groups/00g1zh4irckemzmAX1d8/skinny_users'{noformat}

Run stats at failure: {{retrieveOktaGroupMembers_calls=43586}}, {{retrieveOktaGroupMembers_millis=51188772}} (~14.2 CPU-hours across the thread pool), {{syncGroupCount=42440}}, {{syncMshipCount=1559681}}. A separate Okta admin email in the same window warned the org was at 90%+ of the {{/api/v1/groups/{id}/skinny_users}} rate-limit quota — corroborating evidence of very high call volume, though not causally proven to be the trigger (see Confidence note below).

Not related to GRP-7101 (network-exception retry broadening only, no HTTP status-code handling) or GRP-7052 (stale cached target-id, unrelated to auth).

h2. Root cause (verified by code reading; not yet confirmed against this specific incident's logs — see Confidence)

The Okta external system config ({{grouper.wsBearerToken.Okta_MCOMM_UserGroups.*}}) uses {{httpAuthnType=oauthClientCredentials}} with {{clientCredentialType=publicPrivateKey}}. This path already has a correctly-implemented, TTL-aware token cache ({{WsBearerTokenExternalSystem.retrieveBearerTokenForConfigId()}}, {{grouper/src/grouper/edu/internet2/middleware/grouper/app/externalSystem/WsBearerTokenExternalSystem.java:110-137}}) — verified the cache-key scoping, TTL math ({{expires_in - 5s}} margin, {{WsBearerTokenExternalSystem.java:125,131}}), and JWT client-assertion construction (RS256, fresh per token request, {{WsBearerTokenExternalSystem.java:194-236}}) are all correct. This rules out a naive "token just expired, nothing ever refreshes it" bug.

The actual gap:

* {{GrouperOktaApiCommands.executeMethod()}} ({{GrouperOktaApiCommands.java:63}}) calls {{WsBearerTokenExternalSystem.attachAuthenticationToHttpClient()}} *once*, before the _first_ HTTP attempt, attaching whatever bearer token is currently cached/valid to the request's {{Authorization}} header.
* {{GrouperHttpClient.executeRequest()}}'s retry loop ({{GrouperHttpClient.java:1049-1131}}) retries on network exceptions or a 429/503 throttle signal ({{GrouperOktaApiCommands.java:88-98}} sets {{retryForThrottlingOrNetworkIssuesSleepMillis=60s}}, default 5 retries with increasing backoff: 60s/120s/180s/240s/300s — up to ~15 minutes of cumulative sleep across retries).
* Critically, the retry loop *resends the same request object with the same pre-attached header*. {{attachAuthenticationToHttpClient()}} is never called again inside the retry loop, so no fresh/re-validated token is ever attached to a retried attempt.
* If a request is throttled (429/503) close to the cached token's expiry, the retry backoff sleep can outlast the token's remaining TTL. The retried request then presents an *expired bearer token* to Okta's resource API, which correctly returns 401 — but 401 is not itself a retry trigger ({{GrouperOktaApiCommands.java:92}} only checks 429/503), so it propagates straight up as the {{RuntimeException("Invalid return code '401'...")}} seen here ({{GrouperOktaApiCommands.java:118-122}}).

This mechanism plausibly explains the ~5h/~43K-call timing: that's roughly when cumulative call volume starts tripping Okta's rate limit often enough for a throttle-retry to land in this exposure window.

h2. Confidence / what's NOT yet confirmed

Attempted to confirm this specific incident involved a throttle-retry immediately preceding the 401, by checking for {{httpClient_ThrottleCount}} in the per-call debug map ({{GrouperHttpClient.java:1115}}, logged via {{GrouperOktaLog.oktaLog()}} in a {{finally}} block, {{GrouperOktaApiCommands.java:845-850}}). That per-call log line requires the {{edu.internet2.middleware.grouper.app.okta.GrouperOktaLog}} logger category to be at DEBUG, which was *not* enabled on QA at the time (the {{logCommandsAlways}}/{{debugLog}} provisioner-config flags that _were_ on feed a different logger, {{GrouperProvisioningObjectLog}}, not this one) — so the evidence needed to prove causation for this specific run is not recoverable from existing logs. The job's UI entry has also since aged out ({{viewLogs}} now returns "Invalid job name" for {{w4m4dlqr}}).

The code-path gap itself (retry reusing a stale, pre-attached auth header) is real and independent of this confirmation — it's worth fixing regardless of whether it's proven to be the exact cause of this incident. Recommend also enabling the {{GrouperOktaLog}} category at DEBUG on affected environments so a recurrence would capture the smoking-gun evidence.

Also checked and ruled out as unrelated: {{selectAllGroups=true}} (already enabled in this provisioner's config) only bulk-fetches the group list; Okta membership retrieval has no bulk endpoint and is unconditionally per-group regardless of this flag ({{GrouperOktaTargetDao.java:589}}, explicit code comment: "Okta has no retrieveAllMemberships call"). Not a viable mitigation for the call-volume side of this issue.

h2. Fix implemented

Added a generic re-authentication hook to {{GrouperHttpClient}}'s retry loop, following the existing {{GrouperHttpThrottlingCallback}} pattern, so a throttling/network-issue retry re-attaches fresh credentials before resending the request instead of reusing the header attached before the _first_ attempt:

# New interface {{GrouperHttpReauthenticationCallback}} ({{grouper/src/grouper/edu/internet2/middleware/grouper/util/GrouperHttpReauthenticationCallback.java}}) — one method, {{reauthenticate(GrouperHttpClient httpClient)}}.
# {{GrouperHttpClient}}: added {{grouperHttpReauthenticationCallback}} field + {{setReauthenticationCallback()}} setter, and invoke it inside {{executeRequest()}}'s retry loop immediately after the backoff sleep and before the retried request is sent ({{GrouperHttpClient.java}}, right after {{GrouperUtil.sleep(sleepMillis)}} at the former line 1111, now ~1126-1131).
# {{WsBearerTokenExternalSystem.attachAuthenticationToHttpClient()}}: registers the callback to simply re-invoke itself ({{attachAuthenticationToHttpClient(httpClient, externalSystemConfigId, grouperLoaderConfig, debugMap)}}) on retry — this naturally reuses the existing TTL-aware token cache ({{retrieveBearerTokenForConfigId()}}), so a still-valid cached token is reused with no extra token-endpoint calls, and an expired one gets refreshed before the retry goes out.

This is entirely within the shared auth framework — *no changes needed in* {{GrouperOktaApiCommands.java}} or any other provisioner. Every provisioner authenticating via {{WsBearerTokenExternalSystem}} (Azure, SCIM2, Google, Duo, Box, Remedy, TeamDynamix, TrueFoundry, in addition to Okta) gets the fix automatically. Only the retry path is touched; happy-path (non-throttled) behavior is unchanged.

Verified: {{grouper}} module compiles cleanly against this change ({{mvn -f grouper compile}}, after rebuilding {{grouperClient}} first per this repo's documented build order).

Added two unit tests to {{GrouperHttpClientTest.java}} ({{testReauthenticationCallbackInvokedOnRetry}}, {{testNoReauthenticationCallbackDoesNotBreakRetries}}), following the existing {{testExecuteRequestRetriesThenThrows}} pattern (connect to a closed local port to force network-retry behavior deterministically). {{testReauthenticationCallbackInvokedOnRetry}} asserts the callback fires exactly once per retry (2 retries → 2 callback invocations), not on the initial attempt. Ran the full {{util.AllUtilTests}} suite (per {{TESTING.md}}, against the dockerized Postgres test DB) — 111/111 passing, including these two. Not yet exercised against a live/simulated Okta 401-after-retry scenario end-to-end — recommend a manual QA re-run once the token-expiry window can be reproduced/shortened, before merging.

# GRP-7601  Disabled memberships are miscounted and under-audited, and the enabledDisabled daemon shows as a loader job

Description:

Several related problems around disabled memberships and their auditing make it hard to trace when and why a membership was disabled. They were seen in 6.4.1 while investigating members who were removed from a group.

Problems:

* The group summary detail counts disabled members. It shows 40 members when 0 are enabled.
* The enabledDisabled daemon shows up in the audit log as a loader job, which is misleading when tracing who made a change.
* Some audit entries log setting the disabled date, but not all. Some code paths may not log it, for example import or the main add-member screen. Also check when doing an import of multiple users, it logs disabled date for all of them, not just the first one
* The group UI audit log does not show the disabled date being set, even for an audit entry that records one. It only shows "edited member".
* The membership db view shows the actual disabled time, not the date that was originally set. If nothing audits the setting of the value, the original disabled date setting can't be traced and can only be assumed.

Expected:

* Summary counts include only enabled members.
* The enabledDisabled daemon is identified under its own name in the audit log, not as a loader job.
* Every path that sets or changes a disabled date writes an audit entry, including the UI add and edit screens, import, WS, GSH, and loader jobs.
* The UI audit display shows disabled-date changes (what was set, old and new values).
* The original disabled date can be recovered from the audit history.

# GRP-7223  MCP server should serve clients on spec revision 2026-07-28

Grouper accepted requests declaring any of the handshake-based protocol revisions but rejected 2026-07-28 with UnsupportedProtocolVersionError, so a client on that revision could only fall back to the legacy handshake. It is now served natively.



2026-07-28 is added to the supported protocol versions, advertised by server/discover and listed in the supported versions of an unsupported-version error. A request declaring it must carry what that revision requires: io.modelcontextprotocol/clientCapabilities in the request _meta, rejected with -32602 and HTTP 400 when absent; an Mcp-Method header matching the method in the body; and on tools/call an Mcp-Name header matching the tool name in the body. A header which is missing or disagrees with the body is rejected with HeaderMismatch (-32020) and HTTP 400, which prevents an intermediary routing on a header value while this server acts on a different value in the body. Header values in the base64 sentinel form are decoded before being compared. An unknown method is answered with HTTP 404 for a request on this revision, so a client can tell it apart from a 404 by a server which does not host an MCP endpoint at all; earlier revisions continue to get HTTP 200.



All of the above applies only to a request which declares 2026-07-28. A request declaring one of the earlier revisions, or declaring no version at all, is served exactly as before — those clients send none of this. initialize still answers 2025-03-26, so nothing changes for a client which negotiates through the handshake.



MissingRequiredClientCapabilityError (-32021) is not implemented because this server requires no client capability for any of its tools; it does no sampling, elicitation, or roots, so the error is unreachable. The presence check for the field is implemented, as that is what the spec requires.

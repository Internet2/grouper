# GRP-7474  Provisioner sync-back full sync deletes and re-inserts every grouper_prov_* row each run

On every full sync, {{GrouperProvisioningLogic.loadDataToGenericProvisionerTables}} reserves a brand-new {{internal_id}} for every user, group, attribute value, membership, and membership role. The table sync is keyed on {{internal_id}}, so no existing row ever matches. Every row in {{grouper_prov_user}}, {{grouper_prov_group}}, {{grouper_prov_user_attr_value}}, {{grouper_prov_group_attr_value}}, {{grouper_prov_mship}}, and {{grouper_prov_mship_role}} for that provisioner is deleted and inserted again on every run.

Impact at Penn (Duo provisioner, about 226k users and 3.6M attribute value rows):

* Full syncs went from about 18 minutes to 1.5-2 hours, so runs scheduled every 2 hours now overlap (one failed).
* The deletes and inserts are committed in batches, so other readers see the tables half empty during a run. The user count dropped from 102k to 40k within minutes while a sync ran. Reports built from these tables at that time were missing most users.
* This affects every provisioner with {{loadEntitiesToGenericGrouperTable}}, {{loadGroupsToGenericGrouperTable}}, or {{loadMembershipsToGenericGrouperTable}} enabled.

Fix:

* Reuse the {{internal_id}} a target user or group already has, by {{target_user_id}} / {{target_group_id}}, and reserve new ids only for new targets.
* Reuse attribute value rows by object, attribute, and value. Multi-valued attributes are handled: each existing row is reused at most once.
* Reuse membership roles by role name, and memberships by user, group, and role.
* Keep {{last_updated}} on unchanged rows, so the table sync sees no difference and writes nothing.
* An unchanged full sync now writes nothing, and deletes only remove objects, values, and memberships that are really gone from the target. The incremental path already reused user and group ids and is not changed.

Test: {{GrouperDuoProvisionerTest.testDuoFullSyncReusesSyncBackRows}}.

* Run a full sync twice with no changes: every sync-back row keeps the same {{internal_id}} and {{last_updated}}.
* Change one user’s Duo devices and run again: the user rows and the other user’s value rows are unchanged, and only the changed values are written.
* The SCIM and LDAP generic-table tests, the full-sync-from-sync-back suite, and the native sync unit tests still pass.

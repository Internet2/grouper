# GRP-7024  Datadog provisioner: retrieveRoles does not page, truncating role list and causing 409 on insert

DatadogApiCommands.retrieveRoles() called GET /api/v2/roles without page[number]/page[size],
so it only received Datadog's default first page (10 roles, sorted by name). Every other list
endpoint in the DAO (retrieveUsers, getRoleUsers, retrieveTeams, getTeamMemberships) already pages;
retrieveRoles was the only one that did not.

Impact:
In the whartonDatadog provisioner, roles that sort past the first page (WhartonOrgReadOnly,
WhartonOrgAdmin) were never returned by the retrieve. The provisioner concluded they were missing
in the target and tried to create them, which Datadog rejected:

  Invalid return code '409' ... Role with name 'WhartonOrgAdmin' already exists

This produced 2 group errors plus 12 membership errors (the memberships into those two roles)
on every full sync once the provisioner was switched from read-only to read-write.

Verified against prod: GET /api/v2/roles returned data[] of 10 with meta.page.total_count=14;
the 4 truncated roles were the W* ones, including the two managed roles.

Fix:
- retrieveRoles now pages through page[number] (0-indexed) and page[size], matching retrieveTeams.
- DatadogMockServiceHandler.getRoles now honors page[number]/page[size] and returns a meta.page
  block, so the multi-page path is actually exercised in tests (previously it returned everything
  in one response, which also meant a dataset >= page size would loop forever).
- Added DatadogProvisionerTest.testRetrieveRolesPaging: inserts 105 roles and asserts all 105 are
  retrieved across pages with no duplicates.

No target-side cleanup needed: once retrieveRoles returns all roles, the two existing roles match
by name, Grouper links them instead of inserting, and the group/membership errors clear on the
next full sync.

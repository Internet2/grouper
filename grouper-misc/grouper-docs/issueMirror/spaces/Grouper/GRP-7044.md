# GRP-7044  Group.delete() fails with AttributeAssignNotFoundException from RuleService.deleteRuleAttributes when the group has a rule attribute; rule-engine cache holds a stale assign id that DB removal doesn't clear

Deleting a group that has a rule attribute assignment ({{{}etc:attribute:rules:rule{}}}) fails. {{Group.delete()}} calls {{{}RuleService.deleteRuleAttributes(){}}}, which calls {{AttributeAssignFinder.findById(assignId, true)}} and throws {{AttributeAssignNotFoundException}} for the rule's attribute-assignment id, aborting the delete. The group is never removed.

Environment: Grouper 7.x (PennGroups prod). Rule on the group is a {{membershipAdd}} / {{subjectNotInSources}} veto (restrict membership to a subject source).

Steps to reproduce:
 # Create a group and assign a rule attribute ({{{}etc:attribute:rules:rule{}}}) with a {{membershipAdd}} veto condition.
 # Delete the group (via WS/MCP {{{}group_delete{}}}, GSH, or UI — all route through {{{}Group.delete(){}}}).
 # Delete fails with the stack above.

Observed:
 * The rule's attribute-assignment id _is_ resolvable via a normal attribute lookup (e.g. attribute_assignment_get returns it), but {{RuleService.deleteRuleAttributes}} -> {{AttributeAssignFinder.findById(..., exceptionIfNull=true)}} throws for that same id during delete.
 * Removing the rule attribute first ({{{}remove_attr{}}} on the assignment) does NOT fix it: after the row is gone, {{delete()}} still throws {{AttributeAssignNotFoundException}} referencing the same now-deleted id. This points to the rule engine holding a stale in-memory reference.
 * The stale reference did not clear on retry minutes later (so not a simple TTL expiry). Suspect {{RuleEngine}} cache is not invalidated when a rule attribute assignment is removed out-of-band, and {{deleteRuleAttributes}} iterates cached rule definitions and hard-fails on {{findById}} of an id no longer present.
 * Groups without a rule attribute delete normally.

Suspected fix area: {{RuleService.deleteRuleAttributes}} should tolerate a missing/already-removed assignment (use a non-throwing {{findById}} or skip), and/or the {{RuleEngine}} cache should be invalidated when rule attribute assignments change.

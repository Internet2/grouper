# GRP-7561  Provisioning incremental membership retrieval for group recalc is hundreds of times slower than the full sync retrieval

Environment: v7, LDAP provisioner, about 6,600 provisioned groups and 1.3M memberships, some groups with 10k+ members, Postgres, grouper_sql_cache_mship has 69M rows.

Problem: when a group is recalculated in the incremental, GrouperProvisioningGrouperDao.retrieveMemberships (not retrieveAll) builds batches of up to 450 OR'd conditions ([gg.id|http://gg.id] = ? / [gm.id|http://gm.id] = ? / ([gg.id|http://gg.id] = ? and [gm.id|http://gm.id] = ?)) against grouper_sql_cache_mship, and selects 18 columns per row, including the group description repeated on every row. Measured from the provisioner debug map (retrieveGrouperMshipsMillis):

* incremental: 7,105,484 ms for 1,247,506 memberships (29 groups)
* incremental: 2,903,875 ms for 734,808 memberships
* incremental: 3,981,701 ms for 1,182,540 memberships
* full sync retrieveAll: 11,264 ms for 1,321,582 memberships
So the incremental path is hundreds of times slower per row than the full path. Since the full sync waits for the incremental (waitForRelatedJobsToFinishThenRun), one slow incremental also blocks the full sync for hours, and normal provisioning (usually 1-2 seconds) stalls until it finishes.

Requested fix: for whole-group recalc, retrieve memberships by group only, using the same query shape as the retrieveAll query (no mixed OR list, only the id columns), and look up group and member details separately, once per group and once per member.

### Shilen Patel - 2026-11-13T10:01:31.226-0500

h3. Cause

When the incremental retrieves Grouper memberships ({{GrouperProvisioningGrouperDao.retrieveMemberships}}, non-retrieveAll branch), the caller passes three sets at once: the groups being recalculated, the entities being recalculated, and the group/member pair of every membership wrapper. For an LDAP provisioner, a group being recalculated already has a membership wrapper for each of its existing target memberships, so a recalc of a 10k-member group also sends about 10k individual pairs for that same group. Across the 29 groups in the first measurement that is about 1.2M pairs.

All of these go into batches of 450 OR terms (pairs first, then groups, then members). That is roughly 2,700 batches, each a 5-table join whose OR mixes {{gg.id = ?}}, {{gm.id = ?}} and {{(gg.id = ? and gm.id = ?)}}. Postgres can't use an index for an OR that mixes tables this way, so each batch scans or hashes large parts of {{grouper_sql_cache_mship}}. There is also no index on {{grouper_sql_cache_mship.member_internal_id}}. The full sync runs its join once; this path runs it thousands of times. That explains most of the difference.

h3. Proposed change (first step)

Before building the batches, skip any pair whose group is in the group-recalc set or whose member is in the entity-recalc set. This is a small change to {{retrieveMemberships}}: about 10 lines, one line replaced with a filtering loop.

For the reported case, the 29 recalculated groups become a single batch of {{gg.id = ?}} terms. An OR of terms on one column lets Postgres use the group index and drive the join from the group side. Only pairs for groups that aren't being recalculated remain, which is what a normal incremental already handles in a second or two.

h3. Why it gives the same results

Group, member and pair terms share the same select columns and the same base query (provisionable group, subject sources, field, include/exclude groups, deleted subjects). A pair term only adds {{and gm.id = ?}} to the group term (or {{and gg.id = ?}} to the member term), so whatever a skipped pair would return, the group (or member) query returns as the same row. A membership that no longer exists is returned by neither, so removals from the target are still detected.

Today those rows can come back twice (from a pair batch and from the group batch). Downstream, {{processWrappers}} indexes memberships by group/member, so the duplicates already collapse into one wrapper. Everything after that works from the wrappers. The only visible differences are the {{grouperMshipCount}} debug value (lower, since duplicates are no longer counted; some of the counts reported above may include duplicates) and the membership debug log. The full sync path ({{retrieveAll}}) is not touched.

h3. Difference from the requested fix

The request was: group-only retrieval, the same query shape as retrieveAll (id columns only), and group and member details looked up once each.

This change covers the group-only part: a recalculated group's memberships come back through its group term, not through one OR term per existing membership. It does not trim the select to the id columns or change how details are loaded; each row still carries all 18 columns, including the group description.

h3. Why stop there until it's tested

The hours come from the thousands of mixed batches, and this change removes them. Trimming columns saves row width, which is a much smaller cost: the full sync returns 1.3M narrow rows in about 11 seconds.

Doing the rest of the request is a moderate change (on the order of 100-150 lines) with much wider reach. The incremental would have to run an id-only membership query first, then load the groups and members it needs (that lookup already exists, after the membership query), and only then build the memberships, as the full sync does. Missing data would also need to be handled differently. Today, if a membership's group or member didn't load (for example, deleted between queries), the code falls back to the copy built from the wide row. With id-only rows that copy would be empty, so the membership has to be skipped instead, as the full sync does. That changes how every incremental for every provisioner type loads its data, and it needs the provisioning test suites plus race-condition tests.

It would bring a real memory benefit as well: today the incremental creates a new group object and a new entity object for every membership row (about 1.2M of each for those 29 groups) and then repoints them to the real objects.

h3. Proposed next steps

# Test the pair filter on the reporting environment and compare {{retrieveGrouperMshipsMillis}} for a recalc of the same groups.
# If a group-only recalc of very large groups is still slow, do the id-only query with separate group/member loading as a follow-up, applied to all incremental membership retrieval and matching the full sync's handling of missing groups and members.
# Separately, if entity-recalc retrieval is also slow, consider an index on {{grouper_sql_cache_mship(member_internal_id)}} (DDL, with an upgrade task).

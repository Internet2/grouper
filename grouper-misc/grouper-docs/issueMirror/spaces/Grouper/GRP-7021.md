# GRP-7021  sqlCacheFullSync/sqlCacheInitialPopulator approximate flattened_add_timestamp for groups with large group_set history

* Current populator pulls full PIT history (no {{active='T'}} on outer {{{}grouper_pit_group_set{}}}/{{{}grouper_pit_memberships{}}}) and overlap-collapses in Java per (owner, field). For groups with deep nesting history this fans out to millions of intermediate rows per call, making the job effectively non-completing on sites like UCLA (74 cache_group rows have >1000 active group_set rows; current populator has been running for weeks without finishing them).
 * Change the daemon to compute active group_set counts per (owner, field) at job start, then per cache_group choose one of two paths:
 ** If active pit_group_set count ≤ threshold → existing historical-correct path (overlap-collapse for accurate {{{}flattened_add_timestamp{}}})
 ** If active pit_group_set count > threshold → new active-only aggregation path:


 
 
SELECT gpitm.source_internal_id,
MIN(GREATEST(gpgs.start_time, gpm.start_time)) AS flattened_add_timestamp
FROM grouper_pit_group_set gpgs
JOIN grouper_pit_memberships gpm ON gpm.owner_id = gpgs.member_id
AND gpm.field_id = gpgs.member_field_id
JOIN grouper_pit_members gpitm ON gpitm.id = gpm.member_id
WHERE gpgs.owner_id = ? AND gpgs.field_id = ?
AND gpgs.active = 'T' AND gpm.active = 'T'
GROUP BY gpitm.source_internal_id;
 
 * New config property: {{otherJob.sqlCacheFullSync.approximateFlattenedAddTimestampWhenPitGroupSetCountAbove}} (default {{{}1000{}}}). Setting to {{-1}} disables approximation entirely (always use historical-correct path).
 * Pre-fetch step at job start: one {{SELECT owner_id, field_id, COUNT(*) FROM grouper_pit_group_set GROUP BY owner_id, field_id}} to populate an in-memory {{Map<MultiKey, Long>}} of active pit_gs counts. Cheap with the new {{pit_gs_owner_field_active_idx}} (see related Jira).
 * Semantic note for approximated groups:
 ** {{flattened_add_timestamp}} becomes "start of current effective interval" rather than "first-ever effective add" — {{MIN(GREATEST(gpgs.start, gpm.start))}} over currently-active rows only
 ** If a member was in the group, left, and rejoined, the approximation records the rejoin date, not the original
 ** {{sql_cache_mship_hst.start_time}} inherits this on deletion ({{{}SqlCacheMembershipDao{}}} line 300 copies {{flattened_add_timestamp}} without recalc) — so audit history for memberships in approximated groups will be permanently approximate for that cohort
 ** No live functionality reads {{flattened_add_timestamp}} (provisioning, change-log, UI, WS all unaffected). Index {{grouper_sql_cache_mship3_idx (sql_cache_group_internal_id, flattened_add_timestamp)}} still functions; results just reflect approximation semantics
 * Java collapse logic only runs for the ≤threshold path; the >threshold path replaces it with a single SQL {{{}GROUP BY ... MIN(GREATEST(...)){}}}. Net per-call: ~14× faster on a 389K-member group (measured on Penn prod with new active indexes — 58s → 4s end-to-end).
 * For UCLA's distribution this means 838,805 cache_groups (99.95%) keep historical-correct semantics and only 402 (or 74 at threshold=1000) get approximated. The pathological tail unblocks; the bulk of memberships keep audit accuracy.
 * Apply to:
 ** v4 {{SqlCacheInitialPopulatorDaemon}}
 ** v6/v7 {{SqlCacheFullSyncDaemon}}
 ** Same property name on all three (read via {{{}GrouperLoaderConfig.retrieveConfig().propertyValueInt{}}})
 * Depends on the new active indexes ({{{}pit_ms_owner_field_active_idx{}}}, {{{}pit_gs_owner_field_active_idx{}}}) — link to that Jira. Without those indexes the approximation path still helps (eliminates Java collapse, halves intermediate row count) but the heap-scan I/O floor remains.
 * Externalized text for the new config property's label/description (per Grouper guidelines for UI-visible wizard config).

{code:java}otherJob.sqlCacheFullSync.maxObjectFieldPairMembershipSyncBatchSize = 1
otherJob.sqlCacheFullSync.logBatchProgressInterval = 100000
otherJob.sqlCacheFullSync.switchToEstimatedStartDateWhenGroupSetsLargerThan = -1
otherJob.sqlCacheFullSync.maxAllowedEstimatedStartDateGroups = 50{code}

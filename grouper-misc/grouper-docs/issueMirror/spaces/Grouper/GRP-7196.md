# GRP-7196  Composite edit: add a confirmation screen showing the number of membership adds and removes before applying

When creating or editing a composite on a group in the Edit composite screen, applying the change can add and remove members. This is especially significant now that a group that already has members can be converted to a composite in place (GRP-7187): members not in the composite result are removed, and members newly included by the factors are added. Changing the factors or the operation on an existing composite has the same effect.

Request: before applying the change, show a confirmation screen that computes and displays the net effect on the group membership -- the number of members that will be added and the number that will be removed -- and require the user to confirm before proceeding. Ideally show a sample or full list of the affected members, or at least the counts, so the admin can catch an unintended large membership change (for example converting a populated group to a composite whose factors do not include most of the current members).

Rationale: converting a group with members to a composite, or changing a composite's factors, can drop many members at once. A preview plus explicit confirm prevents accidental mass membership changes. The counts can be computed from the difference between the group's current members and the composite result of the chosen factors and operation.

Related: GRP-7187 (convert a normal group with members to a composite in place without change log or PIT churn).

## Comments

### Chris Hyzer - 2026-07-29T11:39:35.795-0400

The adds/removes report should be exposed in the API too, not only the UI. Add a preview/dry-run on the composite API (e.g. CompositeSave) that computes and returns the effect of applying a composite change without applying it: the count of members that would be added and removed, and ideally the affected member lists. The UI confirmation screen consumes this API report, and programmatic and web service callers can retrieve the same preview before committing a composite change.

This keeps a single source of truth for the diff (current group members vs the composite result of the chosen factors and operation) shared by the UI and the API, rather than computing it only in the UI layer.

# GRP-7254  Remove ldaptiveEncodeControlChars config, ldaptive 2.5 always percent-encodes

The grouper-loader property ldaptiveEncodeControlChars set the java system property org.ldaptive.response.ENCODE_CNTRL_CHARS, which told ldaptive to percent-encode control characters in diagnostic messages and attribute values. It was added for Active Directory, which embeds non-ASCII data in diagnostic messages and turns logs binary.

As of ldaptive 2.5 that property no longer exists. Upstream commit a02d9fb (4 Apr 2025), titled encode attribute value and diagnostic msg toString by default, removed the static Result.ENCODE_CNTRL_CHARS field and the system property read behind it. Result.getEncodedDiagnosticMessage() now always percent-encodes, and LdapAttribute.getEncodedAttributeValues(), used by toString(), does too. Confirmed against the jars: the 2.4.2 Result.class and LdapAttribute.class reference the field and the 2.5.1 classes do not. The change is not mentioned in the 2.5.0 release notes or in any upgrade guide - it is only visible as an absence from the javadoc index.

So the Grouper side is dead code. Removed the System.setProperty call in GrouperStartup (and the now unused GrouperLoaderConfig import) and the ldaptiveEncodeControlChars key, its comment and its valueType metadata from grouper-loader.base.properties.

Note for anyone upgrading: the effective default flips. Sites that left ldaptiveEncodeControlChars at false, or set it explicitly to false, now get encoding regardless, because it is no longer optional in ldaptive. Sites that had set it to true get what they already wanted. Anything matching on raw attribute values containing control or non-ASCII characters in logs will now see percent-encoded text.

Depends on the ldaptive 2.5.1 upgrade.

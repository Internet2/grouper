# GRP-7256  Upgrade c3p0 to 0.14.1 and mchange-commons-java to 0.6.1 for security

Bump c3p0 from 0.12.0 to 0.14.1 and its supporting library mchange-commons-java from 0.4.0 to 0.6.1 in grouper-parent/pom.xml.

These are security releases that close out the remaining JNDI / Java-serialization attack surface in javax.naming.Reference handling. 0.13.0 (with mchange-commons-java 0.5.0) stops creating or decoding References that contain Java-serialized binary objects, storing all reference contents as strings instead. 0.14.0 disables indirect serialization via Reference by default (new false-biased param com.mchange.v2.naming.allowIndirectSerializationViaReference), adds a whitelist of classes JavaBeanObjectFactory may instantiate (com.mchange.v2.naming.referenceableJavaBeanClassWhitelist), and generates BeanInfo classes so that getConnection and getPooledConnection are not introspected as JavaBean properties. 0.14.1 is a follow-up that restores compatibility with older JDKs when BeanInfo-declared API is not present at runtime.

0.13.0 also fixes a race where JDBC 4.3 endRequest was called after the connection was checked back into the pool, which could let a new client have its statements and result sets cleaned out from underneath it.

Risk is low. Grouper only uses c3p0 programmatically: hibernate.c3p0.* properties through hibernate-c3p0, and direct setter calls on ComboPooledDataSource in GrouperLoaderDb and C3p0JdbcConnectionProvider. Grouper never binds a c3p0 DataSource into JNDI, never serializes one, and does not use userOverridesAsString, so the hardened code paths are not paths Grouper exercises. The whole API surface Grouper and hibernate-c3p0 5.6.15 use (ComboPooledDataSource setters, C3P0Registry.getPooledDataSources, PoolBackedDataSource.getConnectionPoolDataSource, DataSources.pooledDataSource, unpooledDataSource and destroy) is unchanged in 0.14.1, and the jar is still compiled to Java 7 bytecode. mchange-commons-java 0.6.1 adds no new non-optional transitive dependencies.

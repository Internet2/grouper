# GRP-7142  Support AWS role-based credentials (not just static access/secret key) via shared credential resolution for all AWS-integrated features

Three separate AWS integrations each build an AWS SDK client from a static access key / secret key pair, with no support for role-based credentials (EC2 instance profile, ECS/EKS task role, or any provider in `DefaultAWSCredentialsProviderChain`). Each duplicates the same construction logic independently:
 - `GrouperMessagingSqsSystem.java` (`AmazonSqsClientConnectionFactory.getAmazonSqsClient()`) — `grouper.messaging.system.<name>.accessKey`/`.secretKey`/`.awsRegion`
 - `GrouperWorkflowInstanceService.java` — `workflow.s3.access.key`/`workflow.s3.secret.key`
 - `GrouperReportLogic.java` — `reporting.s3.access.key`/`reporting.s3.secret.key`

In all three the key pair is required, with no fallback to a credentials provider chain. Deployments where AWS access is governed by IAM roles rather than long-lived user keys (ECS task roles, EC2 instance profiles, EKS IRSA — increasingly mandated by security policy) can't use any of these features without provisioning and rotating static keys.

*{*}Proposed solution{*}*
1) Add a single shared credential-resolution helper (e.g. in `grouperClient` util) that:
 - Returns `BasicAWSCredentials`/`AWSStaticCredentialsProvider` when access/secret key are configured (preserves current behavior)
 - Falls back to `DefaultAWSCredentialsProviderChain` when the key properties are blank/absent
 - Is reusable across all three call sites without each reimplementing the branch

Update `GrouperMessagingSqsSystem.java`, `GrouperWorkflowInstanceService.java`, and `GrouperReportLogic.java` to use it.

2) Enhance the SQS external system to allow configurable auth method

3) Migrate the SQS external system to a general AWS one, so it can be reused for workflow, reporting, or as a general AWS connection resource. It's probably easiest to include the SQS page properties, so that messaging can continue to utilize the external system properties for its config. Most of this migration could be achieved with creative label changes.

*{*}Acceptance criteria{*}*
 - Shared helper exists and is used by all three call sites; none constructs `BasicAWSCredentials` inline anymore
 - Existing deployments with keys configured keep working unchanged
 - Deployments that omit the keys authenticate via the environment's AWS role instead of failing
 - Config property docs updated to note access/secret key are now optional

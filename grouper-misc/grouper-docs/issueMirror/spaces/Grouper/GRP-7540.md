# GRP-7540  MCP institutional_tools: an input given under both its full and short name can bypass the readwrite data scope

h2. Summary

When an MCP client's read/write consent is limited to particular folders, groups or subjects (the data scope on the OAuth consent screen), a GSH template input with an {{mcpScopeType}} is checked against that scope before the template runs. A call can send the same input twice, once as {{gsh_input_target}} and once as {{target}}. The scope check reads the full-name value, and the template runs with whichever came last, so when the full name comes first, a value outside the consented scope reaches the template.

This is a consent-scope bypass, not a privilege escalation. The template's own security still applies (wheel, specified group, privilege on the object), so the client cannot do anything the user could not do. What it gets around is the narrower scope the user consented to for that client.

The scope bypass does not affect the UI AI assistant, since its session scope never narrows read/write to particular objects. The fix's refusal of an input given twice does apply to it (see the behavior change under Fix).

h2. Where

Before the fix, {{GrouperMcpInstitutionalTools.executeTemplate}} (grouper/src/grouper/edu/internet2/middleware/grouper/ws/mcp/GrouperMcpInstitutionalTools.java) read the {{inputs}} argument in two places, differently:

* Adding inputs to the template run (the "inputs" block, about line 815): every field becomes {{gsh_input_}} + name if it does not already start with it, and each one is added to the {{GshTemplateExec}} with {{addGshTemplateInput}}. Two fields that map to the same full name are both added, and the template gets the last one.
* The scope check (the "validate MCP scope restrictions on inputs" block, about line 831): for each input with an {{mcpScopeType}}, it reads {{inputsNode.get(fullName)}} if present, otherwise {{inputsNode.get(shortName)}}. So with both present it checks the full-name value.

{{readonlyJexlVariables}} (about line 488) already names inputs the same way and treats an input given twice as unreadable (it returns null, so the call is treated as a write), but that only decides read versus write, and does not stop the call.



h2. How to reproduce

Template with one input, {{gsh_input_targetGroup}}, with {{mcpScopeType}} groups, not {{mcpReadonly}}. Caller's read/write consent limited to folder {{approved:folder}}. Call:

{code:json}{"action":"execute","configId":"<template>","inputs":{"gsh_input_targetGroup":"approved:folder:testGroup","targetGroup":"outside:folder:otherGroup"}}{code}

The scope check approves {{approved:folder:testGroup}}. The template runs with {{outside:folder:otherGroup}}.

h2. Fix

* In {{executeTemplate}}, read the {{inputs}} argument once into a map keyed by full input name ({{gsh_input_...}}). If two fields map to the same full name, refuse the call with an error naming the input, e.g. "Input 'targetGroup' was given twice, as 'gsh_input_targetGroup' and 'targetGroup'. Give it once."
* Use that one map both to add the inputs to {{GshTemplateExec}} and for the {{mcpScopeType}} scope check, so the value checked is the value run.
* Read the inputs in one helper, {{callInputsByFullName}}, used by both {{executeTemplate}} and {{readonlyJexlVariables}}, so the read-only decision, the scope check and the template run cannot drift apart.
* Keep the existing behavior for a single input under either name.
* *Behavior change:* the refusal applies to every caller of {{institutional_tools}}, the UI AI assistant included, not only to clients with a limited data scope. A call which sends an input under both names used to run, with the last one winning, and now gets the error.

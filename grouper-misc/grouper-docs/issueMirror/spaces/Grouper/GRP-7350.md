# GRP-7350  configuration.cacheJsonMetadata condition is inverted, so config file metadata is never cached with the default setting

ConfigFileName.configFileMetadata() looks up a cached ConfigFileMetadata and then, if configuration.cacheJsonMetadata is TRUE, throws the cached value away. The condition is backwards.

grouper.hibernate.base.properties documents the flag as: if config metadata should be cached, default true, set to false if developing. So true means cache it. The code instead treats true as do not use the cache, which means that with the shipped default the heavyweight metadata generation runs on every single call, directly under a comment that says cache this since its heavyweight.

That generation is not cheap: it reads the base config file off the classpath, reads the matching extraMetadata.properties resource, compiles regex patterns and walks GrouperConfig.retrieveConfig().propertiesMap for each of them. configFileMetadata() is called from the config UI, GrouperCheckConfig, GrouperConfigurationModuleBase, GrouperExternalSystemUsageFinder, Hib3PITConfigDAO and the MCP config search index, so this is on a lot of paths.

The bug appears twice in the same method, once in the pre lock check and once inside the synchronized block (ConfigFileName.java lines 270 and 276 on GROUPER_7_BRANCH).

Fix is to negate both conditions so the cache is only bypassed when caching is turned OFF.

Note when testing: because the condition is inverted, a developer who set configuration.cacheJsonMetadata to false in grouper.hibernate.properties has been getting caching, and after this fix that same setting will correctly stop caching. So a dev box with false may look SLOWER after the fix, which is the documented intent of false (see config changes immediately while developing). Production, which runs the default true, gets caching it was supposed to have all along.

Found while investigating config import allocation for GRP-7298 and GRP-7347.

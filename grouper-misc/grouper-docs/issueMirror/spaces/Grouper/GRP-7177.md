# GRP-7177  DDL Deep Check on Oracle: FKs referencing a unique-but-not-PK column reported as missing (fix ddlutils Oracle FK reader)

DDL Deep Check in 7.3.1/7.3.2 reports foreign keys as missing against Oracle even though they physically exist (confirmed via SQL Developer). Affected FKs seen in the field: data_field_assign_hst_fk_1 (grouper_data_field_assign_hst), data_row_assign_hst_fk_1 (grouper_data_row_assign_hst), member_internal_id_fk (grouper_lifecycle_event), group_internal_id_fk and stem_id_index_fk (grouper_lifecycle_event_config), and grouper_sql_cache_group1_fk (grouper_sql_cache_group).

Common thread: every one of these FKs references a UNIQUE-but-not-primary-key column - grouper_members(internal_id), grouper_groups(internal_id), grouper_stems(id_index), grouper_fields(internal_id). Those internal_id / id_index columns are unique constraints/indexes, while the table primary key is the varchar id.

Root cause: the Oracle model readers (Oracle8ModelReader / Oracle10ModelReader) do not override FK reading, so it falls through to JdbcModelReader.readForeignKeys, which calls Oracle JDBC DatabaseMetaData.getImportedKeys. That Oracle driver call only returns FKs whose referenced constraint is a PRIMARY KEY; FKs that reference a unique-but-not-PK column are omitted from the metadata. So on the DB side the foreign key comes back null and GrouperDdlCompare.analyzeForeignKeys prints Missing foreign key, even though the constraint is present. This matches the existing code comment in GrouperDdlCompare (oracle needs the foreign keys to be associated with only primary keys ... these are not attached to primary keys but regular unique columns).

Proposed real fix: override readForeignKeys in the Oracle model reader to read foreign keys directly from the data dictionary (USER_CONSTRAINTS / USER_CONS_COLUMNS, joining R_CONSTRAINT_NAME to the referenced constraint whether its type is P or U) instead of relying on getImportedKeys. Then the database-side model actually contains these FKs, the comparison works, and the FKs get genuinely verified. Oracle8ModelReader already uses this custom-query pattern for indexes (its own USER_INDEXES / USER_IND_COLUMNS query), so this override follows an established pattern in the same class.

IMPORTANT - part of this fix: once the Oracle FK reader correctly returns unique-referencing FKs, REMOVE the existing hardcoded skip in GrouperDdlCompare.analyzeForeignKeys (the isOracle() equalsAny check that continues past grouper_data_field_assign_fk_2 and grouper_data_row_assign_fk). Those two were skipped precisely because of this same limitation; with the reader fixed they should compare cleanly and no longer need to be skipped. Do not just extend that skip list - that is the stopgap, not the real fix.

Related: GRP-7175 covers the parallel Deep Check false positive where Oracle NUMBER columns (grouper_audit_entry int01..int05, duration_microseconds, hibernate_version_number) are flagged as size/precision 38 should be 19 while the install DDL defines them as NUMBER(38). Same feature, different code path.

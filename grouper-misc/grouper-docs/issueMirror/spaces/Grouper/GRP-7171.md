# GRP-7171  User lifecycle daemons should sync grouper_lifecycle_event_config from config (support config import without a UI save)

User lifecycle event configs (grouperUserLifecycleEvent.* properties) live in grouper config. The full daemon (UserLifecycleFullDaemon) and incremental daemon read the event configs from the grouper_lifecycle_event_config cache table via UserLifecycleEventConfigDao.selectAll(). That cache table is populated only by UserLifecycleEngine.syncUserLifecycleEventConfigs(), which is called exclusively from the User lifecycle admin UI save handlers in UserLifecycleEventConfiguration.java (insertConfig, editConfig, deleteConfig).

Problem: if the event config is provisioned any other way than through that UI save (the config import screen, a direct grouper_config insert, or cross-environment promotion of properties), the cache row is never created and prepareAndStoreSqlCacheDependencies never runs. Both daemons then run as silent no-ops: selectAll returns nothing, so no lifecycle events are recorded, no history is scanned, and no error or job message is logged. This is very hard to diagnose because the config is clearly present in grouper_config and the UI lists the event, yet nothing happens.

Request: have the full daemon (and ideally the incremental daemon) call syncUserLifecycleEventConfigs(grouperConfig) at the start of each run, so grouper_lifecycle_event_config and the SQL cache dependencies are reconciled from the grouperUserLifecycleEvent.* config on every run regardless of how the config was set. This keeps the cache tables in sync with config and makes config import and cross-environment promotion work without requiring a manual open-and-save of each event in the UI.

Found in a Grouper v7 checkout while standing up user lifecycle events from an imported properties file: the import populated all grouperUserLifecycleEvent/Action/Policy/PolicyPart keys in grouper_config, but grouper_lifecycle_event_config stayed empty and the full daemon ran in about 11ms with total_count 0 until the event was opened and saved in the UI.

## Comments

### Chris Hyzer - 2026-07-20T21:48:30.000-0400

Second manifestation, hit while trying the open-and-save-in-UI workaround: editing an imported event throws a NullPointerException, so that workaround does not actually work for a config that was imported rather than created in the UI.

In UserLifecycleEventConfiguration.editConfig, lifecycleEventConfigBefore = UserLifecycleEventConfigDao.selectByText(CONFIGID) is read BEFORE syncUserLifecycleEventConfigs runs, then beforeGroupId = lifecycleEventConfigBefore.getGroupInternalId() dereferences it. For an imported config there is no row in grouper_lifecycle_event_config yet, so lifecycleEventConfigBefore is null and it NPEs.

Actual error: Cannot invoke GrouperLifecycleEventConfig.getGroupInternalId() because lifecycleEventConfigBefore is null, Problem calling method editUserLifecycleEventConfigSubmit on UiV2UserLifecycle.

So the edit path assumes the event was first created through the UI insert path. In addition to having the daemons sync from config, editConfig should tolerate a null before-value (treat it as an insert) so an imported or promoted config can be reconciled.

# GRP-7175  DDL Deep Check: Oracle NUMBER columns flagged as 38 should be 19, but install DDL defines them as NUMBER(38) - find why and fix

Using the DDL Deep Check feature in 7.3.1 (and now 7.3.2) we see warnings/errors against Oracle that are false positives. Several integer columns in grouper_audit_entry are reported as size/precision 38 should be 19, even though those columns are correctly defined as NUMBER(38,0) in Oracle (confirmed via SQL Developer). Affected columns: duration_microseconds, hibernate_version_number, int01, int02, int03, int04, int05.

Key finding: Grouper's own Oracle install DDL defines these columns as NUMBER(38), not NUMBER(19). In GrouperDdl_7_0_0_pre_V41_oracle.sql, CREATE TABLE grouper_audit_entry lists hibernate_version_number NUMBER(38), int01..int05 NUMBER(38), and duration_microseconds NUMBER(38). They are never defined as NUMBER(19) in any Oracle DDL script. So the deployed database matches Grouper's install DDL exactly, and it is the Deep Check's expected value of 19 that is wrong.

Ask: investigate why DDL Deep Check derives an expected precision of 19 for these Oracle NUMBER columns (likely deriving it from a generic bigint/long ddlutils type mapping to NUMBER(19) rather than from the actual install DDL of NUMBER(38)), and fix that discrepancy so the check's expectation matches what Grouper actually installs. The fix should be in the check logic, not in the schema, since the schema is already correct.

Sample warnings: Table grouper_audit_entry: Column duration_microseconds size 38 should be 19; Column duration_microseconds precision 38 should be 19; Column hibernate_version_number size 38 should be 19; Column hibernate_version_number precision 38 should be 19; Column int01 size 38 should be 19; Column int01 precision 38 should be 19; int02..int05 same pattern.

Separately: foreign keys that Deep Check complains about were verified to actually exist in the Oracle tables (confirmed via SQL Developer). While investigating the NUMBER precision expectation, also check whether the FK existence checks have a similar discrepancy causing existing FKs to be reported as missing.

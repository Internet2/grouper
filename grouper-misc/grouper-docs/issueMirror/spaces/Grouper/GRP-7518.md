# GRP-7518  GrouperUtil.mapAddValue locks the GrouperUtil class, deadlocks with callers holding a synchronized map

GrouperUtil.mapAddValue and mapAddValueObjectKey (long and int versions) were static synchronized, so every counter update in Grouper took one JVM wide lock (the GrouperUtil class), shared with other static synchronized GrouperUtil methods like uniqueId.

That deadlocks with a caller that already holds the map's own lock. Provisioner debug maps are Collections.synchronizedMap, whose methods lock the map: one thread held the map and called mapAddValue (wants the class), another was inside mapAddValue (holds the class) calling map.put (wants the map). The LogicGate provisioner full sync hung this way in prod, and other jobs on that daemon then blocked in GrouperUtil.uniqueId.

Fix: the four methods are no longer static synchronized; they synchronize on the map instead. For a synchronized map that is the same lock its own methods use, so the get and put stay atomic together, only one lock is ever taken, and counters on different maps no longer wait on each other. No callers change.

# GRP-7472  Investigate and fix: built-in UI templates assign object types and inherited-privilege rules as root on folders the user may not administer

In UiV2Template.newTemplateSubmit the caller only needs the create-group privilege on the base folder (retrieveStemHelper(request, false, true, true)). ServiceActionType.stem skips folders that already exist, and two action types then run as root through internal_callbackRootGrouperSession: grouperType (GrouperObjectTypesConfiguration.saveOrUpdateTypeAttributes) and inheritedPrivilege (RuleApi.inheritFolderPrivileges / inheritGroupPrivileges / inheritAttributeDefPrivileges, then RuleApi.runRulesForOwner).

Question: can a user with only CREATE on a folder run the app or policy group template with a key that matches an existing subfolder they do not administer, and get object types or inherited-privilege rules added to it? Later steps that create groups as the user may fail first, so this may not be exploitable. Not confirmed.

To do: write a test as a non-admin with CREATE on the base folder and an existing base:key folder owned by someone else; check whether any type assignment or rule is created. If it is, require STEM_ADMIN on each existing folder before the root-run steps (and in the builder from the companion template Jira).

Steps to reproduce:



{noformat}1. Prepare The Fixture
Use two separate browser profiles or browsers, both pointed at your local Grouper:

Admin session: GrouperSystem or another system administrator.
Runner session: an ordinary user who is not a system administrator.
As admin:

Create this disposable folder hierarchy using More actions → Create new folder. Use matching IDs and display names to make the confirmation labels easy to follow:
templateRepro
  victim
    security
On templateRepro, open Privileges and grant the runner CREATE only.
Make sure the runner has no effective ADMIN on templateRepro, templateRepro:victim, or templateRepro:victim:security, including through groups or inherited privileges. Do not configure an inherited privilege grant for this fixture.
Open templateRepro:victim:security → More actions → Types. Record the baseline: there should be no direct grouperSecurity type configuration.
The existing folders must be created by the admin, not the runner.

2. Check The Ordinary Wizard
As the runner:

Open templateRepro.
Select More actions → Run template.
Set Template to run to Application.
Leave “Create in this folder, do not create a subfolder” unchecked.
Enter Key = victim; leave the friendly name matching it.
Click Next.
With the code in this checkout, expect:

Error: not allowed to administer folder: templateRepro
That blocks the wizard’s Next operation—not necessarily the separately callable Submit operation.

3. Prepare, Revoke, Submit
In the admin session, temporarily grant the runner ADMIN directly on templateRepro. Keep CREATE granted separately. Do not grant ADMIN on either existing child folder.
In the runner session, reopen the Application template on templateRepro, enter Key = victim, and click Next.
On the action-selection screen, leave only these three actions checked:
Create folder: "templateRepro:victim"?
Create folder: "templateRepro:victim:security"?
Assign "grouperSecurity" type to folder:
  "templateRepro:victim:security"?
Uncheck everything else, including the entire service branch, any remaining ref type assignment, all group creation, all inherited privileges, and memberships. Wait for checkbox-triggered requests to finish.
Leave this runner tab open. Do not submit yet.
In the admin session, revoke the runner’s temporary ADMIN on templateRepro, leaving CREATE. Confirm there is no indirect ADMIN grant remaining.
Return to the already-open runner form and click Submit. Do not refresh, click Next, or change checkboxes after revoking ADMIN: those operations have the stronger check.
At submission time, the runner now has only CREATE on the base folder and does not administer the existing target folders.

4. Inspect The Result
In the admin session, reload:

templateRepro:victim:security
Open More actions → Types and check for a new direct grouperSecurity configuration.

If the direct type appears, you have reproduced an unauthorized type assignment at submission time.{noformat}

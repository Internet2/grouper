# GRP-7472  Investigate: built-in UI templates assign object types and inherited-privilege rules as root on folders the user may not administer

In UiV2Template.newTemplateSubmit the caller only needs the create-group privilege on the base folder (retrieveStemHelper(request, false, true, true)). ServiceActionType.stem skips folders that already exist, and two action types then run as root through internal_callbackRootGrouperSession: grouperType (GrouperObjectTypesConfiguration.saveOrUpdateTypeAttributes) and inheritedPrivilege (RuleApi.inheritFolderPrivileges / inheritGroupPrivileges / inheritAttributeDefPrivileges, then RuleApi.runRulesForOwner).

Question: can a user with only CREATE on a folder run the app or policy group template with a key that matches an existing subfolder they do not administer, and get object types or inherited-privilege rules added to it? Later steps that create groups as the user may fail first, so this may not be exploitable. Not confirmed.

To do: write a test as a non-admin with CREATE on the base folder and an existing base:key folder owned by someone else; check whether any type assignment or rule is created. If it is, require STEM_ADMIN on each existing folder before the root-run steps (and in the builder from the companion template Jira).

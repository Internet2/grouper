# GRP-7378  Flaky rules daemon tests: testRuleVetoDaemon and testRuleLonghandDaemon fail standalone

Two rules daemon tests fail deterministically in a dev environment, both standalone and in AllRulesTests: RuleApiTest.testRuleVetoDaemon (asserts initialFirings+1 equals RuleEngine.ruleFirings but gets +0, i.e. the daemon produced no firing for the pre-existing invalid membership) and RuleTest.testRuleLonghandDaemon (after invalidating a rule via raw SQL it expects the daemon to purge it - allRulesAttributeAssignValueContainers size 0 - but gets 1, i.e. the rule was not removed).

These are pre-existing and NOT caused by the rules UI privilege-escalation fix (GRP-7359). Confirmed by stashing that change and reproducing the identical failures on a clean tree; nothing in that fix touches RuleEngine or the OTHER_JOB_rules daemon path.

Leads: RuleEngine.daemon() loads rules from the DB with secondLevelCache(false) and does not consult ruleEngineCache (so clearing ruleEngineCache has no effect). For the longhand test the daemon still treats the raw-SQL-invalidated rule as valid - possibly Hibernate caching the pre-SQL value, or validate() tolerating the mangled enum. For the veto test runDaemonOnDefinitionIfShould() yields 0 firings. Note grouper.is.daemon is false in this environment (grouper.hibernate.properties).

Ask: determine why the OTHER_JOB_rules daemon does not fire/purge as expected in this environment (runtime tracing in RuleEngine.daemon likely needed) and make the two tests deterministic/robust.

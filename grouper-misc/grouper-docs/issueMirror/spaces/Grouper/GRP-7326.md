# GRP-7326  SQL_GROUP_LIST incremental loader fails when the group-list query targets a different database than Grouper's own schema

pls close 

DUPLICATE OF [https://todos.grouper.internet2.edu/browse/GRP-7184|https://todos.grouper.internet2.edu/browse/GRP-7184|smart-link] 

----

Problem encountered IRL, bug discovered / suggested via conversation with *Claude:*

GrouperLoaderIncrementalJob.lookupGrouperMembershipsForSubject() (GrouperLoaderIncrementalJob.java, ~line 1089-1125) builds a query to find a subject's current Grouper memberships in groups managed by a SQL_GROUP_LIST loader. When no specific group name or "groups like" filter is configured, it falls back to filtering by the loader's configured group-list query:

{code:sql}groupNameList = " and g123.name in (select group_name from (" + grouperLoaderGroupQuery + ")) ";
...
GcDbAccess gcDbAccess = new GcDbAccess().sql(sql);{code}

The raw grouperLoaderGroupQuery SQL is spliced directly into a subquery, and the whole statement is run via a bare {{new GcDbAccess()}}, i.e. against Grouper's own default DB connection — not the loader's configured source connection (grouperLoaderDbForLoaderSource).

This works only when the loader's group-list query happens to run against the same physical database as Grouper's own core tables (grouper_members, grouper_memberships_all_v, grouper_groups). When the loader's source is a separate database (e.g. IAMDB, reached via a distinct GrouperLoaderDb connection), the embedded query references objects (in our case a view, vw_grouper_group_metadata) that don't exist from Grouper's own connection, and the query fails outright:

{noformat}ORA-00942: table or view does not exist{noformat}

Contrast with the sibling method lookupSourceMembershipsForSubject() (same file, ~line 1130+), which is passed grouperLoaderDbForLoaderSource explicitly and correctly runs the loader's query against the loader's actual configured source connection. lookupGrouperMembershipsForSubject() has no equivalent — it always uses the default connection.

Repro:

# Configure a SQL_GROUP_LIST loader whose group-list query runs against a source database other than Grouper's own schema (no grouperLoaderGroupsLike or explicit group name filter configured, so the fallback subquery path is used).
# Insert a row into grouper_incremental for a subject with no mshipRecalcGroupName set (i.e. a full recalc row, not add_member/delete_member) for that loader.
# Let the incremental job process the row.
# Observe: RuntimeException wrapping ORA-00942 (or equivalent "object does not exist" error on other DBs) originating from GrouperLoaderIncrementalJob.lookupGrouperMembershipsForSubject via processOneSQLRow.

Impact:

Any subject-level recalculation via grouper_incremental fails for SQL_GROUP_LIST loaders whose source lives outside Grouper's own database — the incremental loader cannot determine the subject's existing Grouper memberships for that loader's groups, so it cannot reconcile source vs. Grouper state for that subject. This blocks the intended workaround of forcing a subject recalc by inserting into grouper_incremental, which is itself the recommended way to force-resync one subject's memberships for a loader.

Suggested fix:

lookupGrouperMembershipsForSubject() should not embed the raw grouperLoaderGroupQuery as a subquery run on Grouper's own connection. Instead, resolve the group name list from grouperLoaderDbForLoaderSource first (similar to how lookupSourceMembershipsForSubject already queries the source), then filter Grouper's own query using the resolved names as bind variables (g123.name in (?, ?, ...)) rather than a cross-database subquery. This mirrors the pattern already used elsewhere in the same class for querying the source vs. querying Grouper.

Discovered while investigating a stuck failsafe / ERROR loop on etc:loader:mcomm (unrelated group-rename race condition, tracked separately); this bug surfaced when attempting to manually force a subject recalc via grouper_incremental as a workaround.

# GRP-7434  AssetSonar provisioner retries calls that get 502, 503 or 504

In the first production full sync (1,879 writes) 9 calls got a 502 Incomplete response received from application from the AssetSonar gateway, about one every 20 seconds of sustained writing. The writes had committed: the next sync found nothing to do. With errorHandlingProvisionerDaemonShouldFailOnObjectError at its default, the first 502 aborts the run.

Retry any call on 502, 503 or 504 (never 4xx) with backoff: provisioner config assetSonarRetryCount (default 3) and assetSonarRetrySleepMillis (default 1000, doubling). Retrying is safe: a repeated update is idempotent, and a repeated create of a committed member gets the duplicate-email 403, which the existing lookup-by-email and reactivate fallback handles. Retried attempts log at WARN. The mock can commit a write and then return 502 for a given email.

## Comments

### Chris Hyzer - 2026-10-03T23:46:24.998-0400

Also in this change: probing the live tenant showed that creating an email held by an INACTIVE member is refused with HTTP 200 and {errors..., status: 403} in the body (an active member is a real HTTP 403), so the lookup-by-email and reactivate fallback never ran for inactive members (createMember threw 'no member_id'). Any 2xx whose JSON body has errors is now treated as the status in the body. The probe also confirmed email uniqueness is enforced case-insensitively including inactive members, so retrying a create cannot fork a member, and that a create without user[role_id] is refused with 400 Role Id is invalid (checked before the email). The mock reproduces all three.

# GRP-7069  Upgrade-task DDL checks re-read the entire schema per assert; cache the DDL model during the startup sweep (startup crawls on remote/high-latency DBs)

Problem
-------
On startup, Grouper runs the upgrade-task sweep (GrouperCheckConfig.checkConfig ->
GrouperDdlEngine.runUpgradeTasks -> UpgradeTasksJob.run). For every upgrade-task
version not yet recorded in the upgradeTasksMetadataGroup attribute, it calls
UpgradeTasksInterface.doesUpgradeTaskHaveDdlWorkToDo() (UpgradeTasksJob.java:182).

Each of those checks calls the GrouperDdlUtils assert* helpers, and each helper
re-reads the ENTIRE database model just to look up one object:

  GrouperDdlUtils.assertIndexExists       (GrouperDdlUtils.java:2070, reads at :2092)
  GrouperDdlUtils.assertForeignKeyExists  (GrouperDdlUtils.java:2131, reads at :2153)
  GrouperDdlUtils.assertPrimaryKeyExists  (GrouperDdlUtils.java:2180, reads at :2201)
  GrouperDdlUtils.assertPrimaryKeyExists  (GrouperDdlUtils.java:3313, reads at :3334)
  GrouperDdlUtils.assertIndexHasColumn    (GrouperDdlUtils.java:2018, reads at :2040)

Every one of these does:
  platform.getModelReader().setDefaultTablePattern("GROUPER%")   // GrouperDdl.java:3083
  Database database = platform.readModelFromDatabase(connection, ...)
  ddlutilsFindTable(...) / ddlutilsFindIndex(...)                // in-memory lookup of ONE object

readModelFromDatabase over GROUPER% walks JDBC DatabaseMetaData (getColumns,
getIndexInfo, getForeignKeys) for every grouper_* table in the schema (hundreds
of tables, one round-trip per table). So a single assert = a full-schema
introspection, and the result is discarded except for the one table/index asked
about. The pattern and schema are identical across all of these calls, so the
read is fully redundant.

(Note: assertTableThere is cheap - just "select count(*)" - GrouperDdlUtils.java:2858.
Only the index/FK/PK/column asserts are expensive.)

Impact
------
On a brand-new deployment, no versions are recorded yet, so the sweep runs
doesUpgradeTaskHaveDdlWorkToDo() for every version (currently through V42). Each
task that overrides it does several index/FK/PK asserts (e.g. UpgradeTaskV38 does
~11), and each assert is a full GROUPER% metadata read. On a remote / high-latency
DB this is hundreds of metadata round-trips x N asserts x M versions, so startup
crawls (observed live: stuck in DatabaseMetaData.getForeignKeys inside
assertIndexExists, slowly advancing version by version).

Root cause
----------
1. The assert* model reads are not shared. The same GROUPER% model is read from
   scratch on every assert call, even though it does not change between read-only
   checks.
2. UpgradeTasksJob.run() (line 182) computes doesUpgradeTaskHaveDdlWorkToDo()
   unconditionally, even on a from-scratch install where the result is then
   discarded (installedGrouperFromScratchWithRunScript true, set at
   GrouperDdlEngine.java:875, and runOnNewInstall() defaults to false in
   UpgradeTasksInterface.java:36, so the task is skipped/recorded regardless).

Proposed fix
------------
Primary: introduce a shared, cached DDL model used by the assert* helpers during
the upgrade-task sweep. Read the GROUPER% model once, reuse it for all read-only
asserts, and invalidate it whenever DDL is actually applied (i.e. after any task's
updateVersionFromPrevious / any CREATE/ALTER/DROP during the sweep). A thread-local
cache in GrouperDdlUtils is safe here because the sweep runs single-threaded under
the upgrade DB lock (GrouperDdlEngine.waitForOtherJvmsOrLockInDatabase). Suggested
shape: ddlModelCacheStart()/ddlModelCacheClear()/ddlModelCacheStop() in
GrouperDdlUtils, the assert* methods read through the cache, run() wraps the sweep
and clears the cache after each updateVersionFromPrevious.

Secondary (optional, big win for clean installs): make the line-182
doesUpgradeTaskHaveDdlWorkToDo() call lazy so it is not computed on the
from-scratch-install path where the result is unused. A genuine one-JVM fresh
install would then do zero of these reads.

Acceptance criteria
-------------------
- Brand-new deployment against a remote DB starts in reasonable time (no per-version
  full-schema re-reads).
- No behavior change: tasks are still correctly detected as needing / not needing
  DDL; re-running remains idempotent.
- Cache is invalidated when the schema changes mid-sweep, so a later task sees the
  tables/indexes an earlier task created.
- Steady-state startup (all versions already recorded) is unchanged - still
  short-circuits at UpgradeTasksJob.isThereWorkToDo (UpgradeTasksJob.java:243) with
  no schema read.

Suggested fields: Type Improvement (performance); Component DDL / startup; affects
new deployments and any startup with pending upgrade tasks, worst on remote/
high-latency databases.

# GRP-7010  GSH Java template compilation — per-template classloader registry

* Phase 4a of the GSH Java template compilation effort; design doc at {{grouper/temp/trash/gshCompileImprovement.html}}. Builds on the compiler wrapper (GRP-7006)
 * New class {{ByteArrayClassLoader}} extending {{{}ClassLoader{}}}, parent = app classloader. Accepts a {{Map<String, byte[]>}} of class name → bytecode (covers top-level + inner / anonymous / lambda classes) and defines them on lookup
 * New helper {{GshTemplateSourceParser}} that extracts the package + public class name from a Java source string via regex after comment stripping. Returns the fully-qualified class name, or a clear error if the source has no package declaration or no public class
 * New class {{GshTemplateClassLoaderRegistry}} — concurrent map keyed by template name (config id), holds {{(sourceHash, ByteArrayClassLoader, Class<? extends GshTemplateV2>)}}
 * Public API: {{resolve(templateName, javaSource)}} — parses FQN from source, hash-compares against the cache, returns the cached {{Class}} on match; on miss compiles via {{{}GshTemplateJavaCompiler{}}}, defines bytecode in a fresh {{{}ByteArrayClassLoader{}}}, swaps the registry entry, returns the new {{Class}}
 * Old loader becomes unreferenced on swap; eligible for GC once in-flight executions drain
 * Source string is given to the registry by the caller — registry does not read config or files itself. Whether the source came from inline config ({{{}javaTemplateSource{}}}) or a container file ({{{}javaTemplateSourceContainerPath{}}}) is a Phase 4b concern
 * JUnit tests: source parser cases (with/without package, with leading comments, {{{}public final class{}}}, no public class); registry cache hit / cache miss / source change creates new {{{}Class{}}}; compile errors surface through {{{}GshTemplateCompileResult{}}}; loaded class instantiates as a real {{GshTemplateV2}} subclass; inner-class bytecode loads correctly
 * Standalone — no integration with {{GshTemplateExec}} in this commit; that's Phase 4b

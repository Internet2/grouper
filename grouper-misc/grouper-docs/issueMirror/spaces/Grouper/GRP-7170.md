# GRP-7170  SCIM 2 provisioner evokes error when viewing errors and other screens.

in slack: [https://internet2.slack.com/archives/C7V0UQDJ4/p1784576323673729|https://internet2.slack.com/archives/C7V0UQDJ4/p1784576323673729|smart-link] 
The error is:
{{Error: Cannot invoke "java.sql.Timestamp.getTime()" because "ts" is null, Problem calling method viewProvisionerErrorsSubmit on edu.internet2.middleware.grouper.grouperUi.serviceLogic.UiV2ProvisionerConfiguration}}

## Comments

### Chris Hyzer - 2026-07-21T18:55:16.173-0400

Root cause: in GrouperProvisioningService.retrieveProvisioningErrors, the fetched errors are sorted by o2.getErrorTimestamp().compareTo(o1.getErrorTimestamp()). The three error-fetch queries only require error_code to be non-null, not error_timestamp. A grouper_sync_group / grouper_sync_member / grouper_sync_membership row can therefore have an error_code set but a NULL error_timestamp. Timestamp.compareTo(null) internally dereferences its argument (whose JDK parameter name is ts) via ts.getTime(), producing the NPE: Cannot invoke java.sql.Timestamp.getTime() because ts is null. That is why only the one provisioner with such a row fails, and why the error-rollup screens fail while the count/summary screens (which do not sort) still render.

Introduced 2023-03-28 in the original Show provisioning errors commit, so all releases with this screen are affected.

Fix: the comparator is now null-safe (null timestamps sort last, otherwise newest-first as before). No query change, so the anomalous error row stays visible instead of being hidden. Committed to the Grouper source.

# GRP-7204  LDAP full sync provisioning fails with "paged results cookie is invalid" because paged search pages are executed on different pooled connections

  h3. Summary

  LDAP-backed provisioners using paged search (ldap.<id>.pagedResultsSize) can fail mid-sync with an LDAP {{PROTOCOL_ERROR}}: {{diagnosticMessage=paged results cookie is invalid}}, aborting
  the full sync.

  Example stack trace (provisionerClass: LdapSync, state: retrieveAllDataFromGrouperAndTarget):

  \{noformat}
  java.lang.RuntimeException: Problem with ldap connection: personLdap
  Error querying ldap server id: personLdap, searchDn: ou=people,dc=xxxx,dc=edu, filter: '(xxxID=*)'
  ...
  Caused by: org.ldaptive.LdapException: resultCode=PROTOCOL_ERROR, diagnosticMessage=paged results cookie is invalid
        at org.ldaptive.control.util.PagedResultsClient.executeToCompletion(PagedResultsClient.java:205)
        at edu.internet2.middleware.grouper.ldap.ldaptive.LdaptiveSessionImpl.processSearchRequest(LdaptiveSessionImpl.java:558)
  \{noformat}

  h3. Root cause

  {{LdaptiveSessionImpl.processSearchRequest()}} (grouper/src/grouper/edu/internet2/middleware/grouper/ldap/ldaptive/LdaptiveSessionImpl.java:550) constructs the paged client directly
  against the shared, static connection pool:

  \{code:java}
  PagedResultsClient client = new PagedResultsClient(ldap, pageSize);
  ...
  response = client.executeToCompletion(searchRequest);
  \{code}

  where {{ldap}} is the {{PooledConnectionFactory}} returned by {{getPooledConnectionFactory(ldapServerId)}} (LdaptiveSessionImpl.java:161-170, 180-185) — a single static pool shared across
  the JVM for that ldap server id.

  In ldaptive 2.4.2 (the version pinned by grouper-parent/pom.xml, property {{ldaptive.version}}), {{PagedResultsClient.executeToCompletion()}} creates one {{SearchOperation}} up front but
  calls {{search.execute(request)}} once per page inside its {{do { ... } while (cookie != null)}} loop (org.ldaptive.control.util.PagedResultsClient, ldaptive tag v2.4.2, line ~198-211).
  Each call to {{SearchOperation.execute(SearchRequest)}} independently checks a connection out of the factory and returns it when done:

  \{code:java}
  try (Connection conn = getConnectionFactory().getConnection()) {
    conn.open();
    ...
  }
  \{code}

  (org.ldaptive.SearchOperation, v2.4.2, line ~711-715)

  So every page of a single paged search can be executed on a different physical LDAP connection. {{PooledConnectionFactory}}/{{AbstractConnectionPool}} defaults to {{minPoolSize=3}},
  {{maxPoolSize=10}} (org.ldaptive.pool.AbstractConnectionPool, v2.4.2, {{DEFAULT_MIN_POOL_SIZE}}/{{DEFAULT_MAX_POOL_SIZE}}) unless a site overrides it via
  {{ldap.<id>.customizePooling}}/{{minPoolSize}}/{{maxPoolSize}}, so with default config there are up to 10 candidate connections in rotation.

  LDAP servers tie paged-results cookie state to the specific connection/session that issued it. When page N+1 is served from a different pooled connection than page N, the server rejects
  the cookie, producing this error. The failure is intermittent and more likely on larger result sets (more pages = more chances of a connection handoff), matching the reported behavior
  (5018 entities, 14 queries before failure).

  h3. Suggested fix

  In {{processSearchRequest()}}, when using the paged code path (LdaptiveSessionImpl.java:549-559), check out a single {{Connection}} from the pool before starting the paged loop and pass
  {{PagedResultsClient}} a {{ConnectionFactory}} wrapper that always returns that same connection (no-op {{close()}}), releasing the real connection back to the pool only after
  {{executeToCompletion()}} returns. This guarantees all pages of one paged search share a single LDAP session regardless of the pool's configured size, without forcing the whole pool down
  to one connection for unrelated concurrent LDAP traffic against the same server id.

  h3. Workaround (config-only, no code change)

  For the affected ldap server id, force the pool to a single connection so paging always reuses the same session:

  \{noformat}
  ldap.personLdap.customizePooling = true
  ldap.personLdap.minPoolSize = 1
  ldap.personLdap.maxPoolSize = 1
  \{noformat}

  Caveat: this serializes all concurrent LDAP traffic against that server id (other loader jobs, UI lookups, etc. that share the id), not just the paged provisioning search. If that id is
  used elsewhere with real concurrency needs, define a separate dedicated ldap server id for this provisioner instead.

* ldaptive version: 2.4.2 (grouper-parent/pom.xml)
* provisionerClass: LdapSync

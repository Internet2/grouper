# GRP-7252  GcTableSync FROM side built with setRows is not type-normalized, so generic provisioner reporting rows are deleted right after being inserted

The generic provisioner reporting tables lose their attribute catalog and attribute values on every run. After a full provision, grouper_prov_group holds the expected row but grouper_prov_group_attr, grouper_prov_group_attr_value and grouper_prov_mship_role are empty, so no captured target attribute is ever reported.

Cause: GcTableSyncTableData.init() runs every row through normalizeRow(), which coerces each value to the canonical java type of its column. GcTableSyncTableData.setRows() stores the rows verbatim. The TO side of a sync is always built with init() because it comes back through a jdbc driver, but several FROM sides were assembled by hand with setColumnMetadata / setGcTableSyncTableBean / setRows. The same internal_id was therefore a Long in memory (reserved via TableIndex.reserveIds) and a BigDecimal when read back from the database. MultiKey compares with equals(), and Long.equals(BigDecimal) is always false, so no row ever compared equal and every TO row looked absent from FROM.

For tables synced in two phases that is destructive rather than merely wasteful. loadDataToGenericProvisionerTables syncs grouper_prov_group_attr with INSERTS_UPDATES_ONLY, then syncs the value rows, then re-syncs the catalog with DELETES_ONLY to drop entries no longer referenced. Deletes are computed as TO minus FROM, so the delete pass removed the exact rows the insert pass had just written, and the value rows went with them through the catalog foreign key. Same fingerprint on grouper_prov_mship_role. grouper_prov_group survived only because it is synced once with no second pass.

Observed in the debug map on an ldap full provision: loadGenericGroupAttrsInsInsertsCount=4 and loadGenericGroupAttrValuesInsertsCount=6, then loadGenericGroupAttrsDelDeletesCount=4 deleting the same internal ids. Logging the primary keys of both sides showed FromKeys=[1000006(Long)] against DbKeys=[1000006(BigDecimal)].

Fix: build the FROM side with init() instead of setRows(), passing the same table bean and column metadata the manual code assigned, so both sides are normalized identically. Changed in GrouperProvisioningLogic (syncGenericProvisionerTable, syncGenericProvisionerTableIncremental, syncGenericProvisionerTableByInternalIds, and the four loader-table syncs loadUsersAttributesToTable, loadUsersToTable, loadGroupsToTable, loadMembershipsToTable) and in LdapToSqlSyncDaemon (multivalued attribute table). GrouperZoomLoader and the single-valued LdapToSqlSyncDaemon block were left alone because they already convert each value with getColumnType().convertToType().

Also added FromUniqueKeys, FromKeys and DbKeys to the sync debug map. Only the TO side count was logged before, which made a table that was inserted and then deleted look like nothing was ever captured.

Blast radius beyond the reporting tables: the four loader-table syncs behind loadEntitiesToGrouperTable / loadGroupsToGrouperTable / loadMembershipsToGrouperTable run a single INSERTS_UPDATES_DELETES pass, so they did not lose data, but every row was deleted and reinserted on every run, update detection never fired, and internal ids churned. Note that fixing this exposes GRP-7251, an incremental membership mirror bug that was masked by that churn.

Verified with LdapProvisionerGenericTableTest and ScimProvisionerGenericTableTest.

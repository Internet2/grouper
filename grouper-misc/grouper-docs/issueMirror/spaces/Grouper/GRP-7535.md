# GRP-7535  AI assistant: offer tools with short descriptions and a tool_describe step, to cut the tokens sent on every model call

h2. Summary

The AI assistant in the Grouper UI sends every tool's full definition to the AI provider on every model call: a long description and a full input schema with a description on each parameter. For a user who can read and write, that was most of the roughly 20,000 input tokens on the first call of a conversation, for tools most conversations never use. The institution pays for all of it.

The assistant now offers tools *compact* by default. Each tool is listed with its name, a one line summary, "You MUST call tool_describe for this tool before calling it.", the institution's own lists (templates, recipes, documentation sources) and any recipe pointers, and an empty input schema. The model calls {{tool_describe}}, which the assistant answers itself, to read a tool's full definition before using it.

In testing, the first call of a conversation ("hi") went from about 19,900 input tokens to about 3,200 to 5,800, depending on the recipes and templates configured.

MCP is not changed: MCP clients still get full definitions.

h2. What changes in the AI assistant

* *Compact tools:* name, summary from {{GrouperAiAgentToolSummaries}}, the {{tool_describe}} sentence, the institution's configured lists, recipe pointers, and the schema {{{"type":"object","properties":{}}}}.
* *Offered in full:* a tool with no parameters (such as {{entity_whoami}}) or with no summary.
* *tool_describe:* added to the tool list and answered by the assistant from the full definitions. It is not a Grouper tool: not in the tool registry, not throttled, not in {{grouper_mcp_tool_log}}. It is answered in any session scope and counts as a look-up for {{grouper.ai.agent.maxLookupsPerStep}}.
* *System prompt:* one more line saying to call {{tool_describe}} for all the tools the model plans to use, in one call, before calling any tool whose full definition is not in the conversation, and that a {{tool_describe}} result is part of the tool list, not data.
* *Unknown arguments:* a call with a top level argument the tool's schema does not list is refused before it runs or is put in front of the user to approve, pointing the model at {{tool_describe}}. Tools ignore arguments they do not know, so a guessed parameter would otherwise return a wrong answer with no error. {{fieldName}} on the membership tools and {{enabled}} on the recipe tool are let through, since those tools read them. A JSON null is let through.
* *Conversation history:* {{tool_describe}} results are not cut by {{grouper.ai.agent.maxToolResultChars}}, are not replaced by the "removed to save space" stub at the next message, and are left out of conversation summaries.
* *After a summary:* the summary message says the tool definitions read earlier were removed and to call {{tool_describe}} again.
* *Approving changes:* the list offered earlier in the message is kept, and which tools are compact is read from it rather than from the configuration. The full definitions are read again only when that list was compact, and before the approved changes run.

h2. Configuration

* {{grouper.ai.agent.toolDefinitions.compact}}, default true. False offers every tool in full, with no {{tool_describe}}, no extra system prompt line and no unknown argument check: the assistant as it was.
* {{grouper.ai.agent.toolDefinitions.alwaysFull}}, blank by default. Comma separated tools to offer in full while the rest are compact, e.g. the ones most conversations use, so they need no describe step.

h2. Why not MCP

MCP was compacted the same way at first and was put back to full definitions.

* *It breaks calls.* An MCP client types a call's arguments from the schema in {{tools/list}}, not from anything the model read. With the empty schema, Claude Code sent {{group_add_member}}'s {{subjects}} array as a JSON string and the tool refused it. Any array or object parameter fails the same way.
* *It saves nothing.* Claude Code and Codex both load a tool's definition when the model uses it, not the whole list up front (checked with {{/context}} in Claude Code and {{/status}} in Codex), so compact definitions only added a {{tool_describe}} round trip.
* *The cost is the client's.* On MCP the tokens are the client's cost, not the institution's.

h2. Changes MCP clients do see

* *institutional_tools:* the description lists each template the caller can see, by configId and name, at the end. Action {{schema}} with a {{configId}} returns just that template instead of every template's inputs. A template the caller cannot see is refused the same as one which does not exist. The description and both forms of {{schema}} share one visibility method, {{retrieveVisibleTemplates}}.
* *doc_search:* the sentence about {{sourceConfigId}} moved before the list of sources, which is now last. The list no longer ends in ".." when a source description ends in a period.
* *Recipe pointers* on tool descriptions now end "You MUST read it with the recipe tool, action 'get', name '...', before using this tool for that case, and follow it." instead of "Read it with the recipe tool ...".
* *Constants:* the lists at the end of these descriptions start with {{AVAILABLE_TEMPLATES}}, {{AVAILABLE_RECIPES}}, {{AVAILABLE_DOCUMENTATION_SOURCES}} and {{RECIPE_POINTER_START}}, so the assistant's compact form can keep them.

h2. Known limitations

* *Skipped describe:* the model sometimes skips {{tool_describe}} when a call looks obvious, e.g. when a recipe pointer spells out the call. The unknown argument check catches a guessed parameter name, but not a guessed value under a correct name.
* *Stale definitions:* a definition read earlier in a conversation is not refreshed if it changes during the conversation.
* *History size:* {{tool_describe}} results stay in the conversation until a summary replaces them.
* *OpenAI and recipes:* OpenAI models follow recipe pointers less reliably than Claude, with full or compact definitions. When the model reads several tools up front, it can keep to that plan after a result shows a recipe applies. This is separate from this change.



h2. Manual tests: UI assistant

Each in a new conversation.

# Say "hi" and check the input tokens are a few thousand, not about 19,000.
# Ask "Which roles are in folder ref:hr?" and check one {{tool_describe}}, then {{group_find}} with {{typeOfGroups}} role.
# Ask "Add test.subject.2 to ref:hr:staff" and check one {{tool_describe}} for the tools it needs, one approval box, and the member added.
# Ask "Who am I?" and check {{entity_whoami}} is called with no {{tool_describe}} first.
# With a read only session scope, ask to create a group and check the {{tool_describe}} works and {{group_save}} is refused by the scope.
# With a recipe and an institutional template configured, ask to create a group the recipe covers and check it reads the recipe and runs the template with {{schema}} for that {{configId}}.
# Set {{grouper.ai.agent.verbatimExchanges = 1}}, send three messages, and check the message after the summary calls {{tool_describe}} again. Put the setting back.
# Set {{grouper.ai.agent.toolDefinitions.alwaysFull = group_find, entity_get}} and check those tools are called with no {{tool_describe}}.
# Set {{grouper.ai.agent.toolDefinitions.compact = false}} and check "hi" costs about 19,000 tokens and there is no {{tool_describe}}.
# Start a change, set compact to false before approving, approve it, and check it finishes normally.
# Repeat 1 to 3 with the other AI provider (Anthropic and OpenAI).

# GRP-7224  MCP OAuth access tokens should be bound to the MCP resource

Access tokens issued for the MCP server carried no aud claim, the resource parameter of an authorization request was ignored, and verification checked only the signature — not the issuer and not the audience. A token signed by the same key for any other purpose would therefore be accepted at the MCP endpoint. OAuth 2.1 requires a resource server to validate that a token was issued for it, and MCP requires tokens to be bound to the MCP resource per RFC 8707.



Access tokens are now issued with aud set to the canonical MCP resource URI, and verification requires both the issuer and that audience to match. An authorization request naming a different resource is refused with invalid_target rather than being issued a token that would not work there.



The resource identifier is derived from configuration (grouper.ws.url plus /mcp) rather than being carried through the authorization flow, because Grouper hosts exactly one MCP resource. This keeps the audience out of the client's control and avoids storing it against the pending request and the authorization code. It is configuration-only for the same reason the iss parameter is: a request-derived value can differ between the request that issues a token and the request that verifies it whenever a server is reachable under more than one hostname. When grouper.ws.url is not configured the audience cannot be determined, so binding and checking are skipped and a warning is logged once.



Note that access tokens issued before this change have no aud claim and are rejected, so clients re-authorize. Tokens are short lived, one hour by default.

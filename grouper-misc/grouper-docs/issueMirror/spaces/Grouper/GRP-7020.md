# GRP-7020  Add indexes on grouper_pit_memberships and grouper_pit_group_set including active column to speed up sqlCacheFullSync and sqlCacheInitialPopulator

* The PIT join query in {{sqlCacheFullSync}} (v6/v7) and {{sqlCacheInitialPopulator}} (v4) bitmap-scans {{grouper_pit_memberships}} via {{pit_ms_owner_field_idx (owner_id, field_id)}} and then post-filters {{active='T'}} against heap rows, removing ~64% of fetched rows as inactive. On large groups this is the dominant I/O cost.
 * Same pattern on {{grouper_pit_group_set}} with {{pit_gs_owner_field_idx (owner_id, field_id)}} — active is currently a heap-level filter.
 * Add two new indexes that include {{active}} so the filter becomes an Index Cond instead of a post-bitmap-scan filter:
 ** {{CREATE INDEX pit_ms_owner_field_active_idx ON grouper_pit_memberships (owner_id, field_id, active);}}
 ** {{CREATE INDEX pit_gs_owner_field_active_idx ON grouper_pit_group_set (owner_id, field_id, active);}}
 * Measured on Penn prod (warm cache, 389K-member group {{{}idpAffiliateOrAlum{}}}):
 ** Original correlated-EXISTS form, old indexes: 58s
 ** Original correlated-EXISTS form, new indexes: 23s (2.5× faster)
 ** Active-only aggregation form, new indexes: 4s (14× faster vs baseline)
 * Heavier benefit at sites with deep PIT group_set history (e.g. UCLA, which has 74 cache_group rows with >1000 active group_set rows each — the long tail blocking initial populator runs).
 * DDL changes to land in:
 ** {{GrouperDdl_Grouper_install_postgres.sql}}
 ** {{GrouperDdl_Grouper_install_oracle.sql}}
 ** Skip mysql install file
 ** New upgrade task ({{{}UpgradeTaskVxx{}}}) that creates both indexes if missing
 ** COMMENT ON INDEX in postgres/oracle install SQL and in the upgrade task (wrapped in {{{}GrouperDdlUtils.isPostgres() || GrouperDdlUtils.isOracle(){}}})
 * Backport to v4, v6, v7. Same DDL on all three branches. v4 sites can apply just the indexes (no code change) as a low-risk speedup for stuck initial-populator runs.
 * Followup Jira (separate): redesign the populator to use active-only aggregation + {{GROUP BY ... MIN(GREATEST(gpgs.start_time, gpm.start_time))}} instead of the historical overlap-collapse — captures the 14× speedup. Hybrid threshold (per-group choice between exact and approximation) is a third Jira.

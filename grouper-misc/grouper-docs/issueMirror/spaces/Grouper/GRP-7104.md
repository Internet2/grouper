# GRP-7104  SCIM provisioner diagnostics: strategy discovery reports read-only attributes as working (verify PATCH by reading the value back)

*Background*

GRP-7064 added SCIM patch-strategy discovery to provisioning diagnostics: for each candidate {{scimNamePatchStrategy}} / {{{}scimEmailPatchStrategy{}}}, it PATCHes the target and reports the strategy as working or not. It decides "works" purely on whether the PATCH threw an exception ({{{}runtimeException == null && grouperTargetEntity.getException() == null{}}}).

That is a false positive against real SCIM targets that return a 2xx for a read-only or derived attribute and silently ignore the change. Verified against a live CrowdStrike SCIM tenant: a PATCH to {{email}} returns {{200 OK}} but never applies (email is derived from userName). With the current logic every email-patch strategy is reported green ("Works"), which is exactly the misconfiguration the discovery feature is meant to prevent.

*Change (diagnostics only)*

{{GrouperProvisioningDiagnosticsContainer.appendScimPatchStrategyDiscovery()}} now reads the value back from the target after each PATCH and classifies the outcome into three states:
 * *Does not work* - the PATCH was rejected (e.g. 400 for an unsupported path or an immutable attribute).
 * *Accepted but ignored* - the PATCH returned 2xx but a read-back shows the value did not change (read-only / derived attribute). Not counted as a working strategy.
 * *Works* - the PATCH succeeded and the read-back confirms the new value stuck.

New helper {{readBackScimEntityAttributeValue()}} re-fetches the entity by id and reads the attribute via {{{}toProvisioningEntity(){}}}. If the read-back call itself fails, it falls back to "Works (could not read the value back to verify)" so a transient error is not reported as ignored.

This is scoped to diagnostics. The runtime PATCH path is unchanged - a read-back GET after every runtime PATCH would double the target's API calls on every sync, and the runtime already reconciles on the next sync (and the separate schema-cross-check work would prevent mapping a read-only attribute in the first place).

*Notes / constraints*
 * All candidates continue to write the same test value, because the email-filter discovery that runs immediately after looks the entity up by that value and relies on it being present in the target.
 * Behavior against the SCIM mock is unchanged (the mock applies accepted patches, so read-back matches and the outcome is still "Works"); the new "Accepted but ignored" path only triggers against a real 2xx-but-ignore target.

*Testability follow-on*

The mock cannot currently exercise the "Accepted but ignored" branch because it always applies accepted patches. Add a mock read-only-attribute mode (e.g. {{{}grouperTest.scim2.mock.readOnlyAttribute.mode=emailValue{}}}) where {{patchUser}} returns 200 but skips the write, plus a test asserting discovery reports "Accepted but ignored" and excludes that strategy from the working set.

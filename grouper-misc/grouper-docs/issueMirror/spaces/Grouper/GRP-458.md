# GRP-458  Manage Groups in UI should perform well when user is admin of many groups

Richie James reported this

## Comments

### shilen - 2010-07-23T12:55:29.582+0000

Part of the issue here is that the UI calls the Member.has* methods.  So for instance, if a user has admin privileges to 100K groups, then the call to Member.hasAdmin() will take a while.  

The code under Member.hasAdmin() seems like it could use a lot of improvement.  The main problem seems to be in how GrouperUtil.retrieveByProperty() works.  But in addition to fixing that, it seems like hasAdmin() can be optimized to return all the groups that a person can admin in one query rather than getting the memberships and then performing queries on the groups.  However, even if that's fixed, for a UI hasAdmin would still be slow.  If you can admin 100K groups, then the amount of time to get 100K records from the database would be more than what you would expect to wait for when clicking the Manage Groups link I think.  And of course the problem is worse if you can manage a million groups so this doesn't scale.  So the UI might need another strategy for this.  

I'm attaching a screenshot that shows the problem with GrouperUtil.retrieveByProperty() after running hasAdmin() on a member that can admin 90K groups.  Though I killed the process before it completed since it wasn't going to complete anytime soon.

### mchyzer - 2010-07-25T02:57:37.972+0000

this is fixed, it does an efficient query which looks for stems the user has groups inside to edit... same for optin (join groups).  I think the main savings is not the query with lots of rows, but another query for each row returned (each group).  If you call Member.hasAdmin() that is fixed as well, it is one query with all groups returned.

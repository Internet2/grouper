# GRP-7458  Provisioning: an unexpected error on one object should not fail the whole run; count them and fail only past a configurable threshold

From the Sept 9, 2026 Grouper call action items.

Provisioners already handle expected per-object problems (invalid data, length/required/matching validation, target object does not exist) as object errors, controlled by the errorHandling* settings (errorHandlingProvisionerDaemonShouldFailOnObjectError, errorHandlingLogCountPerType, etc). But an unexpected exception while processing a single group, entity, or membership (e.g. a runtime exception in a translation script, a target DAO call, or an unexpected target response) generally propagates and fails the entire full or incremental run, so one bad object blocks everything else from provisioning.

Proposal: catch unexpected exceptions at the per-object level, record them as object errors (error code e.g. UNEXPECTED, visible in the provisioning errors UI and sync tables), keep a counter for the run, and continue. Only fail the run when the count exceeds a configurable threshold, e.g. provisioner.<configId>.errorHandlingUnexpectedErrorMaxCount (absolute) and/or a percent of objects processed. Log the first N stack traces per run. Exceptions that are clearly not object-specific (cannot connect to target, auth failure, failsafe) should still fail the run immediately.

Related: GRP-7233 (select-after-insert count mismatch throws and discards the entire run's sync state and object errors).

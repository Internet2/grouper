### Liam Hoekenga - 2026-09-04T15:58:02.269-0400

Confirmed a second occurrence of this on etc:loader:mcomm (source = IAMDB, view vw_grouper_group_metadata), not just the HR ref groups loader — same exact failure signature, same code path. Filed as [#7326|https://todos.grouper.internet2.edu/browse/GRP-7326] before realizing it's this ticket; marking GRP-7326 as a duplicate.

Root cause, pinned down to the exact method:

GrouperLoaderIncrementalJob.lookupGrouperMembershipsForSubject() (GrouperLoaderIncrementalJob.java, ~line 1089-1125) builds a query to find a subject's current Grouper memberships in groups managed by a SQL_GROUP_LIST loader. When no specific group name or "groups like" filter is configured (i.e. the loader relies on its full group-list query — which is also the path deletePreviouslyManagedGroups needs), it falls back to filtering by that query:

{code:sql}groupNameList = " and g123.name in (select group_name from (" + grouperLoaderGroupQuery + ")) ";
...
GcDbAccess gcDbAccess = new GcDbAccess().sql(sql);{code}

The raw grouperLoaderGroupQuery SQL is spliced directly into a subquery, and the whole statement runs via a bare {{new GcDbAccess()}} — Grouper's own default DB connection, not the loader's configured source connection (grouperLoaderDbForLoaderSource).

This only works when the loader's group-list query happens to run against the same physical database as Grouper's own core tables (grouper_members, grouper_memberships_all_v, grouper_groups). Whenever the loader's source is a separate database — IAMDWDEV in the original report, IAMDB/mcomm in this one — the embedded query references objects that don't exist from Grouper's own connection:

{noformat}ORA-00942: table or view does not exist{noformat}

Contrast with the sibling method lookupSourceMembershipsForSubject() (same file, ~line 1130+), which is passed grouperLoaderDbForLoaderSource explicitly and correctly runs the loader's query against the loader's actual configured source connection. lookupGrouperMembershipsForSubject() has no equivalent — it always uses the default connection. This asymmetry is the bug.

Repro (generalizing beyond the original "switched to deletePreviouslyManagedGroups" trigger — the underlying trigger is just "no groupNameFilter and no grouperLoaderGroupsLike configured, so the fallback subquery path runs"):

# Configure a SQL_GROUP_LIST loader whose group-list query runs against a source database other than Grouper's own schema, with no grouperLoaderGroupsLike or explicit group name filter (this is required by deletePreviouslyManagedGroups, but also happens any time a loader is configured this way for other reasons).
# Trigger a subject-level recalc for that loader — either indirectly (near-realtime/incremental processing an add/delete event with no mshipRecalcGroupName), or directly by inserting a row into grouper_incremental for a subject with no mshipRecalcGroupName set.
# Observe: RuntimeException wrapping ORA-00942 (or equivalent "object does not exist" on other DBs), from GrouperLoaderIncrementalJob.lookupGrouperMembershipsForSubject via processOneSQLRow.

Impact:

Any subject-level recalculation for a SQL_GROUP_LIST loader whose source lives outside Grouper's own database fails outright — the incremental loader cannot determine the subject's existing Grouper memberships for that loader's groups, so it can't reconcile source vs. Grouper state. This affects:

* deletePreviouslyManagedGroups (the original trigger), and
* the general workaround of forcing a subject resync by inserting into grouper_incremental — which is the standard way to force-resync one subject's memberships for a loader, and is itself broken by this bug for any cross-database loader.

Suggested fix:

lookupGrouperMembershipsForSubject() should not embed the raw grouperLoaderGroupQuery as a subquery run on Grouper's own connection. Instead, resolve the group name list from grouperLoaderDbForLoaderSource first (same pattern lookupSourceMembershipsForSubject already uses), then filter Grouper's own query using the resolved names as bind variables (g123.name in (?, ?, ...)) instead of a cross-database subquery.

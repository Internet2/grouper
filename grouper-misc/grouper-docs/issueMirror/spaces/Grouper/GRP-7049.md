# GRP-7049  Option for full sync to not block incremental during retrieve from target, only during compare/apply

The provisioner takes the related-jobs lock at the start of provision() (waitForRelatedJobsToFinishThenRun right after initialize), so a full sync blocks incremental for its entire run, including the hours-long read-only retrieve phase. At Michigan scale, real-time provisioning is paused for hours while full retrieves data.

Proposed: add an option so full sync does not hold the exclusive lock while retrieving data from the target, then acquires the lock when the real logic starts (compare, assign actions, send changes). Incremental keeps running during retrieve and pauses as today once full needs the lock.

Considerations:
 * Incremental changes made during the retrieve can make the target snapshot stale; the compare phase should tolerate this (capture incremental changes made during retrieve and apply them to the in-memory snapshot, or accept rare redundant updates and protect deletes with the usual safeguards).
 * Default off; config like provisioner.<configId>.fullSyncDoesNotBlockDuringRetrieve = true.

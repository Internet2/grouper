# GRP-7344  Grouper WS MCP OAuth server does not serve AS metadata at the RFC 8414 path for issuers with a path component

{noformat}Affected:  v7.5.0

Summary - When I clear authentication and try to re-authenticate again it fails. I have to actually disable the mcp connection, enable it and then able to re-authenticate again.

The MCP OAuth authorization server metadata is served only at the OIDC-style path-append location. RFC 8414 §3.1 specifies path-insert for issuers containing a path component. Clients that follow RFC 8414 receive a Tomcat 404 HTML page and fail Dynamic Client Registration.

Observed, issuer https://grouper-ws.myschool.edu/grouper-ws

GET /.well-known/oauth-authorization-server/grouper-ws   -> 404  (RFC 8414 location)
GET /grouper-ws/.well-known/oauth-authorization-server   -> 200  (actual location)
GET /grouper-ws/.well-known/oauth-protected-resource     -> 200  (correct, names issuer)
GET /grouper-ws/mcp/oauth/register                       -> 405  (endpoint healthy, wants POST)

Impact

The registration endpoint is deployed and functional; only discovery fails. Clients that cache a client registration from a first successful enrollment keep working indefinitely, so the defect is latent. It surfaces when the cached registration is discarded — clearing stored credentials leaves the server unreconnectable, and re-enrollment fails at Dynamic Client Registration with HTTP 404 and an HTML body.

Suggested fix

Additionally serve the existing authorization-server metadata document at /.well-known/oauth-authorization-server/{path} — i.e. /.well-known/oauth-authorization-server/grouper-ws. An alias is sufficient; no content change needed. Keeping the current path-append location preserves compatibility with OIDC-style clients.

Reference: RFC 8414 §3.1, "Authorization Server Metadata Request"{noformat}

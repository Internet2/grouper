# GRP-7235  Interfolio provisioner: retrieveEntity fails when the byc user search returns more than one hit

InterfolioTargetDao.retrieveEntity looks users up through the byc users/search endpoint. That endpoint does not return institution_user_id, so when matching on the UID the dao could only infer the answer from the fact that it had searched by it, and it accepted the result only when exactly one user came back. Any other number of hits produced no match at all.

byc users/search is a free text search across name and email, so a short institution identifier readily matches other people. Searching for one faculty pennkey returned six users, of whom only one was the intended person. The dao returned nothing, and the entity was treated as absent from the target even though it was present.

In practice this surfaced on select-after-insert during a full sync. 244 users were created successfully, and the read-back that follows creation then failed to find 47 of them because their pennkeys were not selective enough in a free text search. Every one of the entities examined afterwards did exist in the target, under the exact email the provisioner had just written.

Fix: when the search returns more than one hit, disambiguate on email against the email of the entity being retrieved, and only then treat it as a match. This mirrors what GrouperInterfolioApiCommands.resolvePid already does for the update path, where the same ambiguity was anticipated. The single hit path is unchanged, and a search that returns nothing usable still yields no match.

Related: the framework behavior when a select-after-insert read-back comes up short is tracked separately, as is the absence of any way for a dao to report that a retrieve was ambiguous rather than empty.

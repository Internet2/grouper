# GRP-7232  ExpirableCache: seconds-granularity put; cache sub-minute OAuth tokens instead of skipping the cache (GRP-7228 follow-up)

Follow-up to GRP-7228. That change stopped a sub-minute OAuth token (e.g. a Jamf API-client token that expires in 59 seconds) from crashing the token cache -- but it did so by SKIPPING the cache for such tokens, which meant re-requesting a token on every API call during a sync.

This adds seconds-granularity caching so a short-lived token is cached for its real lifetime instead of being skipped. ExpirableCache gets a put(key, value, timeToLive, ExpirableCacheUnit) overload -- the SECOND unit and the millis putHelper already existed, only the public entry point was minutes-only. WsBearerTokenExternalSystem now caches the token for expires_in minus a 5 second margin, using the SECOND unit.

Also hardens GrouperGoogleApiCommands, which had the same whole-minutes pattern (tokenCacheMinutes could return 0 for a sub-minute token and throw). It now computes and caches in seconds (tokenCacheSeconds), preserving the 30 minute cap and 5 minute buffer for normal long-lived Google tokens. AzureGrouperExternalSystem, TeamDynamixExternalSystem, and CustomUiAzure were already safe -- they store the expiry inside the cached value (MultiKey of expiresOn and token) and use the default time to live -- so no change was needed there.

Adds a regression test: ExpirableCacheTest.testPutSeconds verifies a 30 second time to live caches (the minutes put would reject it), that the whole-minutes put still rejects a 0 minute value, and that a 1 second entry expires.

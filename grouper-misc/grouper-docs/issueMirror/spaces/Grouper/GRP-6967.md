# GRP-6967  Generic provisioner sync back — wire SCIM with JsonNode capture, per-protocol defaults, and Grouper-side linkage

* Add {{GrouperScim2ProvisioningTargetNativeSync}} extending the base sync sibling and override {{grouperProvisioningTargetNativeSyncClass()}} on {{GrouperScim2Provisioner}} to wire it in.
 * Hook capture in {{GrouperScim2ApiCommands}} (the axis-typed protocol seam) rather than the DAO. 8 hook sites across {{retrieveScimUser}} / {{retrieveScimUsers}} / {{retrieveScimGroup}} / {{retrieveScimGroups}} pass the raw {{JsonNode}} so capture isn't bound to the typed bean's fields. Bulk methods capture per-resource inline (where each {{JsonNode}} is in scope) and drain the membership cache in {{{}finally{}}}.
 * Switch the build path from typed-bean to JsonNode-driven: {{buildNativeUserFromJson(JsonNode)}} / {{buildNativeGroupFromJson(JsonNode)}} resolve each configured native-attribute entry via JSON Pointer, coerce by declared type ({{{}string|integer|boolean|timestamp{}}}) with JSON-intrinsic-type auto-detect fallback.
 * Add {{effectiveNativeAttributeConfigsEntities()}} / {{…Groups()}} + protected {{getDefaultNativeAttributeConfigsEntities()}} / {{…Groups()}} hooks on the base sync class. Operator-configured {{nativeAttributesEntities}} / {{nativeAttributesGroups}} wins; blank falls back to the per-protocol default list. LDAP's defaults stay empty (existing behavior: capture from the regular target query). SCIM defaults: 5 user fields ({{{}userName{}}}, {{{}displayName{}}}, {{{}active{}}}, {{{}externalId{}}}, {{emailValue}} at {{{}/emails/0/value{}}}) and 2 group fields ({{{}displayName{}}}, {{{}externalId{}}}). {{id}} deliberately excluded — already the {{target_user_id}} / {{target_group_id}} column.
 * Populate Grouper-side linkage columns ({{{}member_internal_id{}}} on {{{}grouper_prov_user{}}}, {{group_internal_id}} on {{{}grouper_prov_group{}}}) by reading the in-memory {{ProvisioningEntityWrapper}} / {{{}ProvisioningGroupWrapper{}}}s at end-of-run. Grouper internal id from {{grouperProvisioningEntity}} / {{{}grouperProvisioningGroup{}}}; target id from {{targetProvisioningEntity}} / {{targetProvisioningGroup}} (post-match) with fallback to the translated-Grouper view. No DB query — fast path only. Target-side orphans (target_ids the daemon never processed) stay null, which is the correct strict-native semantic.
 * Tests:
 ** Unit tests {{GrouperScim2ProvisioningTargetNativeSyncTest}} for the JsonNode build path (defaults, skip-on-missing, {{{}id{}}}-not-captured), the membership cache drain, and dispatcher no-crash when no provisioner is active.
 ** Integration test {{ScimProvisionerGenericTableTest}} against the in-process AWS SCIM mock with four scenarios: basic full provision, incremental, orphan capture (target has entities Grouper doesn't), and multi-sync data evolution (initial state → changes → second sync verifies reporting reflects the new state including catalog id stability + target-side drift capture).
 ** Orphan test pins down the SCIM default attribute names landing in the catalog, sanity-checks {{id}} is NOT in the catalog, and verifies Grouper-known rows get linkage populated ({{{}member_internal_id IS NOT NULL{}}}, joins back to {{{}grouper_members{}}}) while orphans stay unlinked.

# GRP-7363  Okta provisioner discards hours of retrieved data on one connection reset during pagination

*Claude:*

GrouperHttpClient already retries transient network errors like "Connection reset"
(GRP-7101), giving each Okta API call up to 5 retries / ~15 minutes of backoff. But
once that per-call retry budget is exhausted on a single page, the exception
propagates out of GrouperOktaApiCommands.retrieveOktaUsers(...) /
retrieveOktaGroups(...) / retrieveOktaGroupMembers(...), and the entire in-memory
list of results accumulated from all prior successful pages in that call is thrown
away. The next scheduled run restarts pagination from page 1.

Observed in provisioner-w4pbql43.log: an Okta full sync ran 2h14m, successfully
paged through 2,282 /users API calls, then failed on Connection reset on what
would have been the final page(s) and lost the entire run.

Fix: add a page-level retry wrapper inside these three pagination loops
(configurable retry count/sleep per external system, e.g.
grouper.wsBearerToken.<configId>.pageRetrievalMaxRetries and
.pageRetrievalRetrySleepMillis), so a page that exhausts GrouperHttpClient's own
retry budget gets substantially more patience before the whole multi-hour
retrieval is abandoned. Single-call lookups (retrieveOktaUser, retrieveOktaGroup,
etc.) are unaffected and continue to fail fast.

# GRP-7182  SCIM2 sync-back: ConcurrentModificationException in GrouperScim2ProvisioningTargetNativeSync.captureMembershipsFromCache under multi-threaded retrieve

When a SCIM2 provisioner runs with sync-back (native target reporting) active and threadPoolSize greater than 1, the provisioner run aborts intermittently with a ConcurrentModificationException during entity retrieval. Since errorHandlingProvisionerDaemonShouldFailOnObjectError fails the run on an object error, the whole incremental or full run fails.

Root cause: GrouperScim2MembershipCache stores each group member user-id set as a Collections.synchronizedSet, and addMembership() writes into those sets from the parallel retrieve threads. GrouperScim2ProvisioningTargetNativeSync.captureMembershipsFromCache() drains the cache by iterating those value sets directly, without holding the set monitor. A synchronizedSet only guards individual method calls, not iteration, so a concurrent add() from another retrieve thread trips the fail-fast iterator. The backing map is a ConcurrentHashMap, so the map level is safe; only the value sets are exposed.

Reproduction conditions: SCIM2 provisioner (GrouperScim2Provisioner); sync-back active; threadPoolSize greater than 1; a run retrieving several entities concurrently (a large changelog backlog or a full sync). It is a race, so it is intermittent and load-dependent, and is not specific to one provisioner configuration.

Fix: in captureMembershipsFromCache, iterate a point-in-time snapshot instead of the live set -- for (String userId : new ArrayList<>(userIds)). new ArrayList<>(userIds) copies via the synchronizedSet synchronized toArray(), which is safe. Alternatively, GrouperScim2MembershipCache could use ConcurrentHashMap.newKeySet() for the value sets.

Workarounds: disable sync-back (native reporting), or set threadPoolSize to 1.

Affects version: 7.x (any version with the SCIM2 native sync-back cache).

# GRP-7364  Provisioner daemon job disappears from Daemon Jobs list after a one-time future-dated scheduled run fires

*Claude:*
A daemon job (e.g. a provisioner full sync) scheduled with a Quartz cron expression pinned to a specific one-time future date/time (e.g. 0 5 0 23 9 ? 2026) disappears from the Daemon Jobs list in the UI after that scheduled run fires — even though the underlying config still exists.

Steps to reproduce

# Create a daemon job (e.g. Provisioning full sync, provisioner config id Okta_MCOMM_UserGroups) with a Quartz cron set to fire once at a specific near-future date/time.
# Let the scheduled run fire.
# Go back to Miscellaneous > Daemon jobs — the job is no longer listed.
# Attempting to view logs for the job gives: Error: Invalid job name 'OTHER_JOB_provisioner_full_Okta_MCOMM_UserGroups', Problem calling method viewLogs on edu.internet2.middleware.grouper.grouperUi.serviceLogic.UiV2Admin
# Attempting to create a new daemon job with the same config id gives: Error: the 'Config id' is already in use, please select another or edit that config — proving the config row still exists even though the job is gone from the list and can't be viewed.

*Root cause*
The Daemon Jobs list (UiV2Admin.daemonJobsHelper(), grouper-ui UiV2Admin.java ~line 414) is built entirely from scheduler.getJobKeys(...) — i.e., whatever Quartz currently has live — with no reference to the Grouper config store. Job scheduling (GrouperLoader.java ~lines 960-999, 1717-1785; GrouperLoaderType.java ~line 5115) builds JobDetails via JobBuilder without .storeDurably(true), so the job is non-durable. Quartz's own behavior for a non-durable job is to auto-delete its JobDetail/JobKey once its last trigger fires and has no remaining/next fire time — which is exactly what a one-shot cron pinned to a single date produces. The Grouper config row (keyed by config id) is untouched by this, since nothing in the scheduling path deletes it, so the config and the Quartz-visible job fall out of sync. viewLogs() (UiV2Admin.java ~lines 1425-1438) also does a hard checkExists() against Quartz with no config-store fallback, producing the "Invalid job name" error once Quartz drops the job.

*Suggested fix directions (not yet implemented — filing for future prioritization)*

# Add .storeDurably(true) when building JobDetails for jobs with one-shot/non-repeating triggers, so Quartz retains the JobDetail after the trigger exhausts its fire times.
# Change the Daemon Jobs list (and viewLogs) to enumerate from the Grouper config store as the source of truth, using Quartz state only as a status overlay, so a config with no live Quartz job still shows up (e.g. as "not currently scheduled" / "completed") instead of vanishing.

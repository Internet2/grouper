# GRP-7230  MCP unauthenticated challenge points clients at a metadata URL taken from the request

When a request to the MCP endpoint does not authenticate, Grouper answers with 401 and a WWW-Authenticate header carrying a resource_metadata parameter, which is where the client goes next to find out which authorization server protects this resource. That URL was built from the scheme, host, port and context path of the request that arrived, so its host came from the Host header of the request rather than from Grouper's own configuration.



Security impact is medium. A client which follows a resource_metadata URL under someone else's control is handed that party's authorization server metadata, including an authorization_endpoint, and sends the user's browser there to log in. That is a phishing route to an institutional login page. What holds the severity down is reachability: the 401 is returned to whoever sent the request, so setting the Host header only affects the response the sender receives. Reaching another client requires something in front of Grouper which caches responses without regard to Host, or a reverse proxy which carries a Host from one request into another. Both are misconfigurations rather than defaults, and no authorization code or token is exposed by this on its own.



The URL is now taken from grouper.ws.url. When that property is not configured there is nothing else to build it from, and omitting the parameter would leave a client with no way to discover where to authenticate, so the request is still used and a warning naming the property is logged once. A deployment in that state already has no token audience and no issuer claim, both of which come from the same property.



This matches how the Origin check in the same servlet already decides which origin is Grouper's own, and for the same reason: a value taken from the request is a value chosen by whoever sent it.

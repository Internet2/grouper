# GRP-7351  Config screen add, edit, delete and import should confirm at the top rather than redraw the whole property listing

Every mutation on a config file screen calls UiV2Configure.buildConfigFileAndMetadata, which builds a gui object for every property in the file and re-renders the entire listing. The user has just added, edited, deleted or imported one thing and only needs a confirmation message; redrawing every property to tell them that is disproportionate, and the cost scales with the size of the config file rather than with the size of the change.

buildConfigFileAndMetadata is called from 9 places in UiV2Configure, including configurationFileItemEditSubmit, configurationFileAddConfigSubmit, removeProperties and configurationFileImportSubmit. The suggestion is that these show a confirmation at the top of the screen and leave the existing listing alone, instead of rebuilding it.

Measured on a dev instance with grouper-loader.properties holding roughly 476 properties: a config screen render allocates about 750 MB, and it does not matter whether one property or four hundred were imported, because the cost is driven by the number of properties in the file. Breaking that down by JFR allocation samples after GRP-7347 work so far: JSP rendering (GrouperUiUtils.convertJspToString) about 29 percent, full config rebuilds about 15 percent, JSON serialization (GrouperUtil.jsonConvertToNoWrap) about 9 percent, and reading the rendered JSP into a string about 8 percent. So not redrawing the listing removes most of the rendering share.

Note the response itself is only 6 to 14 kB, so three quarters of a gigabyte to produce it is wildly out of proportion regardless of which caller is at fault.

Partly done already on one path: configurationFileImportSubmit no longer calls buildConfigFileAndMetadata, because the import response only reports counts and the guiV2link redirect sends the browser to the config screen, which builds the listing itself on the next request. That alone took the import request from about 460 MB down to about 208 MB for a 400 property import. The same reasoning applies to add, edit and delete.

Care is needed with two things that buildConfigFileAndMetadata does up front, ConfigPropertiesCascadeBase.clearCache() and GrouperUiApiTextConfig.clearCache(). Whatever replaces the call has to keep those, or the next screen shows stale values.

Related: GRP-7347 (config screen allocation), GRP-7346 (per config file cache invalidation), GRP-7348 (apply only changed rows instead of rebuilding config).

### Chris Hyzer - 2026-09-20T12:41:09.203-0400

Fixed in commit ff2d13fac413 on GROUPER_7_BRANCH, with the import part in 2d402a4c44ad.

Each mutation now updates only what changed instead of calling buildConfigFileAndMetadata and redrawing the whole listing. Measured on a dev instance against a full config screen render of roughly 600 MB:

edit: 104 MB, re-renders just the edited row. single delete: 43 MB, removes the row. bulk delete: 58 MB, removes the checked rows. import: 121 MB and no follow up render at all, where before it was 121 MB plus a 607 MB redirect render. add was already fine, it renders the add form rather than the listing, so it was left alone.

How it works. The row markup moved out of configure.jsp into configurationFileRowContents.jsp, which renders the CELLS of one row rather than the tr, so it can be dropped into an existing row_N with newInnerHtmlFromJsp, the same way configurationFileEditEntry.jsp already was. configurationFileRowSingle.jsp is a thin wrapper that supplies the taglibs and reads the row from the request container. The listing loop uses a static include rather than jsp:include, so it pays no per row dispatch. ConfigurationContainer gained currentIndex, the edit form carries the row index back, and the delete link now passes index as the edit link already did.

The deletes do not build the config model or render anything at all: the rows to remove are already known on the client, from the index on the delete link or from the checked checkboxes.

Import no longer sends the browser on to the config listing. An import reports counts, and that listing is every documented property of the file, so it was a slow and not very useful confirmation. The explicit config cache clears are kept on that path so the change takes effect on this node immediately, and other nodes pick it up through the database as usual.

All paths keep a fallback to the old full redraw if the row cannot be identified, so an old page or a stale link degrades to slow rather than broken.

Verified end to end, not just measured: the right row edited and updated among 4746 rows, the right row deleted with its neighbours intact, bulk delete removing only the checked rows, import staying on the import screen with its summary and the imported values visible on the listing afterwards, and configure.jsp still rendering identically (105 sections, contiguous row ids, pre block for multi line values).

Worth recording for anyone working on this screen: the listing renders about 4650 rows for a config file that has 64 rows in the database, because it shows every documented property from the base metadata and not just the ones that are set. That is why redrawing it was so expensive. See GRP-7347 for the remaining cost of rendering that listing.

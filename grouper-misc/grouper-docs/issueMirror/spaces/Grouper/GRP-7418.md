# GRP-7418  MCP admin and SQL authorization groups do not enforce the documented sysadmin requirement

The config comments for grouper.mcp.users.adminReadonly and grouper.mcp.users.adminReadWrite say members must also be a Grouper sysadmin (or readonly sysadmin for admin readonly), but the code only checked group membership plus the OAuth consent scope. A non-sysadmin added to either group could read all config, daemon logs, run LDAP filters against every configured LDAP system, look up users in external systems, or run any daemon job. grouper.mcp.users.canRunSqlReadonly had no sysadmin check either, and it reaches whole databases with no row level security.

Fix: the requirement is now enforced in GrouperToolAccess. adminReadonly requires wheel or readonly sysadmin, adminReadWrite and canRunSqlReadonly require wheel. The same check is used by the MCP tool list, tool execution, the UI MCP page and the OAuth consent page. Upgrade note: non-sysadmin members of these groups lose that MCP access; GRP-7415 adds limited (non-sysadmin) groups for granting specific tools, databases, and external systems instead.

h3. Upgrade instructions (low impact)

Before upgrading, check who is in the MCP SQL and admin groups (by default etc:mcp:mcpUsersCanRunSqlReadonly, etc:mcp:mcpUsersAdminReadonly, etc:mcp:mcpUsersAdminReadWrite). Anyone who is not a Grouper sysadmin (wheel), or readonly sysadmin for admin readonly, will lose that MCP access after the upgrade. Most deployments only put sysadmins in these groups and need do nothing. If a non-sysadmin needs to keep some of this access, add them to the new limited group instead (etc:mcp:mcpUsersCanRunSqlReadonlyLimited, mcpUsersAdminReadonlyLimited, mcpUsersAdminReadWriteLimited) and open the specific databases, tools, or external systems to them with limitedAccessGroup config, see GRP-7415.

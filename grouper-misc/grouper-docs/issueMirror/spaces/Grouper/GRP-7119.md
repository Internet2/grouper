# GRP-7119  Fix provisioning replace memberships issue

*Affects:* 7.3.0 -- regression from the GRP-7115 fan-out ({{{}0ec4a2{}}}), fixed in follow-up commit {{{}2eef3f8{}}}.

*Root cause:* The fan-out made {{isSelectMembershipsInGeneral()}} return {{true}} for group-centric targets (SCIM, Azure/Entra) even when {{{}selectMemberships=false{}}}, because they read members via the group pull. That's correct, but several replace-path branches had used {{!isSelectMembershipsInGeneral()}} as a proxy for "blind replace-only target." Once the flag flipped, those branches broke.

*Symptom:* A group-centric SCIM/Azure provisioner in {{replaceMemberships}} mode reports phantom membership inserts on every idempotent full sync (with {{in_target_start}} reset each run), and can flap a membership that moves between two groups.

*Fix -- key the branches on the real condition ({{{}isReplaceMemberships(){}}} / raw {{{}isSelectMemberships(){}}}) instead of the derived flag:*
 * {{GrouperProvisioningCompare}} (~1935): take the full-replace path whenever {{{}isReplaceMemberships(){}}}, not gated on {{{}!isSelectMembershipsInGeneral(){}}}.
 * {{GrouperProvisioningLogic}} (~7664): also mark stale sync memberships for delete when {{{}isReplaceMemberships(){}}}, so they're excluded from the replace payload.
 * {{GrouperProvisioningLogic.retrieveIndividualTargetMembershipsIfNeeded()}} (~7999): early-return in blind replace ({{{}isReplaceMemberships() && !isSelectMemberships(){}}}); otherwise it reads zero memberships, flips every one to not-in-target, and the replace re-inserts them all.

*Affected configs:* group-centric targets with {{replaceMemberships}} on. At Penn: {{qlikProd}} (SCIM generic, {{{}selectMemberships=false{}}}, {{{}replaceMemberships=true{}}}); {{trueFoundry}} also uses replace.

*Verify:* full sync over an unchanged population shows {{{}insert=0{}}}/{{{}delete=0{}}}; a member moved between two provisioned groups does not flap.

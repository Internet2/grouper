# GRP-7393  MCP config search Lucene index is not refreshed when config changes (up to 1 hour stale)

The MCP admin_config_search tool in lucene mode (the default) can return config values up to an hour old after a config change. GrouperMcpConfigSearchIndex only rebuilds in rebuildIfNeeded() when a search comes in and the last build is older than DEFAULT_REINDEX_INTERVAL_SECONDS (3600). Nothing calls forceRebuild(), and a config change does not touch the index, so an AI client checking whether a config edit took effect can be told the old value.

Seen during the PennGroups 7.6.0 upgrade: after readonly flags were removed from grouper.properties and grouper-loader.properties, admin_config_search kept reporting the old values. Regex mode reads the live config from ConfigFileName.getConfig(), so it is not affected by this index issue.

Suggested fix: mark the index stale whenever config is cleared in memory, so the next search rebuilds it. GrouperConfigHibernate.clearConfigsInMemory(configFileName) runs for both local config edits and cross-JVM cache notifications (GrouperCacheDatabase, GRP-7346 per-file scoping), so it is the right place to hook in. Setting a dirty flag (or lastIndexBuildMillis = 0) instead of rebuilding right away keeps it cheap, since the rebuild only happens on the next search. Rebuilding just the one config file would also work, but a full rebuild on the next search is simpler.

Files: grouper/src/grouper/edu/internet2/middleware/grouper/mcp/GrouperMcpConfigSearchIndex.java (rebuildIfNeeded, forceRebuild, lastIndexBuildMillis) and grouper/src/grouper/edu/internet2/middleware/grouper/cfg/dbConfig/GrouperConfigHibernate.java (clearConfigsInMemory).

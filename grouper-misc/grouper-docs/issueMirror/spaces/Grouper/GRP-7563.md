# GRP-7563  Deprovisioned users can be added back within 5 minutes due to cache

MembershipVetoIfDeprovisionedHook can allow a membership add for a subject who has just been deprovisioned, because it decides whether the subject is deprovisioned from an in-memory cache that isn't invalidated when someone is deprovisioned.

*Steps to reproduce* (Grouper training environment image):

# Enable deprovisioning (deprovisioning.enable = true, affiliation employees).
# Add a subject (rkirby) to a group, for example ref:certs:network_aup_acknowledged. This is the first membership add since deprovisioning was enabled, which builds the deprovisioned-subjects cache.
# Deprovision rkirby for employees through Miscellaneous > Deprovisioning > Deprovision user. rkirby is added to etc:deprovisioning:usersWhoHaveBeenDeprovisioned_employees.
# On the group, set the deprovisioning settings: affiliation employees, direct configuration yes, deprovision yes, "Allow deprovisioned assignments" no (the default).
# Immediately add rkirby to the group again.

*Expected*: the add is refused with "Entity … has been deprovisioned and is not eligible to have a membership or privilege in …".

*Actual*: "Success: entity was added to group". The same add is refused once the cache has expired, about 5 minutes later. Changing the order of steps 3 and 4 gives the same result.

*Cause (from code review)*: MembershipVetoIfDeprovisionedHook calls GrouperDeprovisioningLogic.shouldAddSubject, which calls subjectDeprovisionedInAffiliations, which calls deprovisionedSubjectsForAffiliation(affiliation, true). With useCache = true this returns deprovisionedSubjectCache(), an ExpirableCache whose lifetime is deprovisioning.cacheMembersForMinutes (default 5). Nothing clears it when a user is deprovisioned or added to usersWhoHaveBeenDeprovisioned_. GrouperDeprovisioningOverallConfiguration.cacheClear() only clears the separate per-object configuration cache (120-second TTL), and OTHER_JOB_deprovisioningFullSyncDaemon and CHANGE_LOG_consumer_grouperDeprovisioningIncremental don't clear the subjects cache either.

*Impact*: for up to 5 minutes (or the configured value) after a deprovision, the veto doesn't apply, so a deprovisioned user can be re-added to a group that should refuse them. The training lesson (Lesson 11) sequence hits this every time.

*Suggested fix (any of)*:

* Invalidate deprovisionedSubjectCache when a user is deprovisioned or when membership in a usersWhoHaveBeenDeprovisioned_** group changes.
* Have the veto check the deprovisioned group membership directly (useCache = false) when the cache would otherwise allow the add.
* At minimum, document that the setting delays enforcement, and that it is read once when the cache object is first created.

*Workaround*: wait for the cache TTL to expire, or set deprovisioning.cacheMembersForMinutes low before the first membership add after deprovisioning is enabled.

# GRP-7465  UI datetime-local with date but no time (Firefox) silently submits blank, creating non-expiring memberships

Reported by a user: in Firefox, the datetime-local picker for membership start/end date (add member on group screen) fills in only the date and leaves the time blank. The field briefly shows red, but the outline goes away on blur. Clicking Add then creates the membership with NO start/end date, i.e. a non-expiring membership. Chrome auto-fills the time, so it only happens there if the user deletes the time manually.

Root cause: per the HTML spec, an incomplete datetime-local has value = empty string and validity.badInput = true. ajax() in grouperUi.js sends element.value, so the server receives a blank endDate and treats it as no end date (UiV2Group.addMemberSubmit). The server already rejects a date with no time, but never sees it.

Proposed fix (send to server so it is validated and logged there):

* grouperUi.js ajax() form element loop: if element.type is datetime-local and element.validity.badInput, send a sentinel value (e.g. __incompleteDateTime__) instead of the empty value. Bump the JS cache-buster.
* GrouperUtil.stringToTimestampTimeRequiredLocalDateTime (and ...TimeRequiredWithoutSeconds): if input is the sentinel, log a warning and throw, so existing per-field validation messages (e.g. groupViewToDateInvalid on #member-end-date) are shown.
* Verify every datetime-local endpoint surfaces a validation message: UiV2Group, UiV2Membership, UiV2Subject, UiV2LocalEntity, attribute assign screens (UiV2AttributeDef, UiV2GroupAttributeAssignment, UiV2StemAttributeAssignment, UiV2MembershipAttributeAssignment), UiV2SubjectPermission, group/stem history charts, daemon performance chart.
* Check group import (groupImport.jsp start/end date) goes through ajax(); if not, handle it too.

# GRP-7218  MCP server should reject requests declaring a protocol version it does not support

MCP spec revision 2026-07-28 removed the initialize handshake; each request instead declares its protocol version, in the MCP-Protocol-Version HTTP header and in io.modelcontextprotocol/protocolVersion in the request body's _meta. Grouper ignored both and served every request under its own semantics, so a client on a newer revision had no way to learn the server did not speak its version — the spec's compatibility matrix calls out this exact case as failing ambiguously.



A request declaring a version this server does not accept is now rejected with UnsupportedProtocolVersionError (-32022) and HTTP 400, listing the supported versions in data.supported so the client can retry with one of them. If the header and the _meta value are both present and disagree, the request is rejected with HeaderMismatch (-32020) and HTTP 400, since an intermediary could route on one value while this server acts on the other.



The accepted versions are 2025-11-25, 2025-06-18, and 2025-03-26. These all use the handshake and the request and response shapes this server implements; what the later revisions added is advertised through capabilities rather than changing the transport. server/discover advertises the same list, and initialize still answers 2025-03-26.



A request declaring no version at all is served exactly as before. The spec explicitly permits treating such a request as 2025-03-26, which is what keeps existing clients working — verified against a live 2025-era client across initialize, tools/list, and tools/call.

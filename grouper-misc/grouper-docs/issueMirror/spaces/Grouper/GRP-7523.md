# GRP-7523  Incremental provisioning converting to full does not honor failsafe

* When an incremental decides to convert, GrouperProvisioningLogic.runFullSyncFromIncremental() (line 6033) ends the incremental provisioner.

* It then builds a brand-new provisioner with GrouperProvisioner.retrieveProvisioner(configId) and calls provision(fullProvisionFull) on it.

* It copies the heartbeat, debug map and output to the new provisioner, but not jobName. jobName is only set in GrouperProvisioningFullSyncJob.java:55 and ProvisioningConsumer.java:64, and the new provisioner never goes through either.

* Before sending changes, provisionFull() calls processFailsafesAtStart() and then processFailsafes() (lines 861-862).

* processFailsafesAtStart() returns immediately when the job name is blank. processFailsafesSetupBean() also returns early on a blank job name, so the failsafe bean is never configured.

* The bean's useFailsafe starts from loader.failsafe.use, which defaults to false. In GrouperFailsafeBean, every check short-circuits when useFailsafe is false.

* processFailsafes() therefore passes without checking anything, and the 32k removals go through.

* Your scheduled full has its job name set, so it did check the failsafe and tripped.

* The incremental's own processFailsafes() (line 5516) is on the non-full branch, so it never runs for a converted job either.

* The debug map would confirm this. A converted run should show a failsafe value like disabled or nothing, where a normal full shows enabled ... passed or TRIPPED. I haven't looked at your logs, so this is worth checking.

  Suggested fix: in runFullSyncFromIncremental(), assign a job name to grouperProvisionerFullSync before calling provision(). The choice of name matters:

* The full job's name (OTHER_JOB_<configId>) would share failsafe and approval state with the scheduled full. That is probably the right choice.

* The incremental's own job name would keep a trip tied to the changelog consumer.

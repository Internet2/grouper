# GRP-7542  Scripted groups: a script could use a group the user can't read, and the analysis showed whether a hidden group exists

h2. Summary

Saving a scripted (JEXL) group checks READ on each group its script uses, but only on groups the SQL cache already has. A group it doesn't have was treated as empty and nothing was checked, so a script could name a group its author can't read. Separately, the analysis behind the Analyze button and the save told the user whether a group they can't see exists.





h2. Problems fixed



* A script could use a group that doesn't exist yet. The save allowed it. If someone later created a group with that name, for example in a folder the script's author can't see, its members flowed into the scripted group without READ ever being checked.

* A script could use a group by an old name, after a rename or move. The cache only knows current names, so the group counted as empty and the script quietly selected the wrong people. For example, with !memberOf it selected everyone. If the old name was later freed and reused, the new group's members flowed in unchecked.

* A group created moments ago, and not in the SQL cache yet, skipped the READ check the same way.

* The analysis showed whether a group exists. For a group the user can't see, it said "You are not allowed to read the group". For a group that doesn't exist, it said "(missing group or cache attribute)". Comparing the two told anyone who can analyze a script which group names exist, in any folder.

* The analysis's "unresolvable or deleted entities match this script" warning is built from every group's real members, with no privilege check. Until now the analysis stopped before that check for a cached group the user couldn't read. Once such a group is treated as missing, as above, the warning could have listed up to 10 of its members' subject ids. So it is changed in the same commit.





h2. Changed



* When saving a script, every group it uses (memberOf, memberOfAny and recent memberships) must exist by that exact name, and the user must be able to READ it. Otherwise the save is refused. The message is the same whether the group doesn't exist, has another name now, or can't be seen: "A script can only use groups which exist by their current name and which you can read.  This one is not: 'name'". A group the user can see but not read still gets "You are not allowed to read the group: 'name'", since they already know it exists.

* In the analysis, a group the user can't VIEW is treated exactly like a group that doesn't exist: it counts as empty and shows the missing-group text. A group the user can VIEW but not READ still gets "You are not allowed to read the group".

* The unresolvable-entities warning uses the same query the analysis built for the whole script, so a group the user can't see counts as empty there too.

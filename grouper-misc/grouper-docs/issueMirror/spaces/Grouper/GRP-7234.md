# GRP-7234  Provisioning: target DAO has no way to report why retrieveEntity found nothing, so ambiguous matches cannot be reported as MAT

TargetDaoRetrieveEntityResponse carries either a target entity or null. When a DAO looks for an entity and cannot return one, null is the only signal available, and it collapses several genuinely different situations into one indistinguishable answer: the object is not in the target, or the object is probably in the target but the DAO could not identify which of several candidates it is, or the search itself was not usable for the requested attribute.

GcGrouperSyncErrorCode already has the vocabulary for the middle case. MAT is documented as grouper object matches multiple target objects, and it is already handled in GrouperProvisioningLogic.errorHandlingHandleError, gated by errorHandlingMatchingValidationIsAnError. So the error code and its configuration already exist. What is missing is any way for a target DAO to say it. The DAO returns null, the framework sees only absence, and the specific and actionable diagnosis is lost before it reaches gcGrouperSyncMember and the provisioning UI.

Concrete case. A target whose only usable read endpoint is a free-text search over name and email was queried by a short institution identifier. The search returned six users, only one of which was the intended person. The DAO could not prove which, so it returned null, and the framework recorded the entity as simply not retrieved. The administrator sees an unexplained failure, when the truthful and actionable message is that the search value matched several target objects and needs a more selective search attribute.

Request: allow the retrieveEntity and retrieveEntities responses to carry an optional per-object error code and message, which the framework stamps onto the corresponding sync object rather than inferring one. Existing DAOs that return null keep working unchanged and continue to get the generic treatment. DAOs that know more can then report MAT with a message naming the search value and how many candidates came back.

Related: the run-fatal handling of a select-after-insert count mismatch is tracked separately. That issue should stamp ERR for the generic case; this issue is what would let a DAO supply the more precise MAT instead.

## Comments

### Chris Hyzer - 2026-08-10T14:18:17.267-0400

Correction to the description above, which overstates the gap.

The framework already reports ambiguous matches as MAT, with a good message, in one path. GrouperProvisioningMatchingIdIndex, around line 1284 for entities and the equivalent blocks for groups and memberships, detects when a matching ID resolves to more than one target object and sets MAT on both the wrapper and the sync object, with the message Matching ID X matches N target entities. GrouperProvisioningLogic.createMissingEntitiesFull then skips those entities rather than inserting them, tallying them under the debug key provisioningEntitiesToInsertWithMatchError. So for ambiguity detected against the bulk retrieved target index, the vocabulary, the message, the persistence and the do-not-insert behavior are all already in place and working.

The real gap is narrower than the description implies. It is the DAO driven individual retrieve, used by select-after-insert and by retrieve of individual missing entities. There the DAO performs its own lookup against the target and returns either an entity or null. If that lookup is ambiguous, the DAO has no way to say so, and the framework never gets the chance to apply the MAT handling it already has. That is the case worth fixing here: give the retrieve responses an optional per-object error code and message so a DAO can report the same MAT condition the index path already reports.

Also worth noting for whoever picks this up: the multiple target objects flavor of MAT appears to have no unit test. SqlProvisionerTest.testSimpleGroupLdapPaMatchingIdMissingValidation asserts MAT on a group, a member and several memberships, but that exercises the other producer of MAT, the matching ID is required and missing validation in GrouperProvisioningValidation. Searching the test tree turns up no coverage of the MatchingIdIndex multiple match branch, and none of the createMissingEntitiesFull skip branch or its provisioningEntitiesToInsertWithMatchError counter. Any change here would be landing on untested behavior, so tests for the existing index path are probably worth adding alongside.

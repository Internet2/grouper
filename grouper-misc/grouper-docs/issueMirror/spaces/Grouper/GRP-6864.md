# GRP-6864  batch data provider full sync by subject ID range to reduce memory consumption

The data provider full sync previously loaded all source data and all Grouper data into memory at once before comparing and writing changes. For large data providers (hundreds of thousands of members with many fields), this caused excessive memory consumption.

This change replaces the previous approach with subject ID range batching, where source and Grouper data are retrieved and processed in configurable batches (default 10,000 subject IDs per batch). Each batch is fully self-contained: retrieve source data, load Grouper data, compare, write changes, and release memory before moving to the next batch.

*How it works:*
 # At the start of a full sync, distinct lowercased subject IDs are collected from all configured source queries (SQL and LDAP) and from existing Grouper member data. These are unioned into one sorted list.
 # The sorted list is divided into batches based on the configured batch size. For each batch, the first and last subject ID define a range.
 # For each batch:

 * 
 ** A fresh GrouperDataProviderIndex is created (releasing the previous batch's data)
 ** Existing Grouper data (field assigns, row assigns, row field assigns, dictionary text) is loaded for members whose subject ID falls in the range
 ** Source data is retrieved using range queries: {{WHERE LOWER(subject_id_col) >= ? AND LOWER(subject_id_col) <= ?}} for SQL, or {{(&(baseFilter)(attr>=from)(attr<=to))}} for LDAP
 ** Changes are compared, failsafe is checked, and changes are written to the database
 ** The loader log is saved after each batch so counts are visible during the sync

4. After all batches, any subject IDs that appeared in the initial distinct list but were not returned by any range query (stragglers) are processed in a final pass using batched IN-clause queries.

*Configuration:*
 * {{grouperDataProvider.<configId>.fullSyncSubjectIdBatchSize}} (default 10000) in grouper.properties — number of subject IDs per batch. Setting very high effectively disables batching. Per-provider setting configurable in the UI.

 * {{otherJob.<daemonName>.failsafeMinSubjectCount}} (no default, opt-in) in grouper-loader.properties — minimum number of Grouper subjects required before the subject ID count failsafe check applies. If not set, the subject ID count failsafe is disabled.

 * {{otherJob.<daemonName>.failsafeMaxOverallPercentFieldAssignRemove}} (existing, unchanged) in grouper-loader.properties — maximum percent of field assigns allowed to be removed before failsafe triggers.

*Failsafe checks:*

Three levels of failsafe protection, all using the {{failsafeMaxOverallPercentFieldAssignRemove}} threshold:
 # Before batching (opt-in): if {{failsafeMinSubjectCount}} is configured and there are at least that many Grouper subjects, check if too many Grouper subject IDs are missing from the source subject IDs. Aborts before any batches run.
 # Per batch: if too many of the current batch's field assigns in Grouper are being removed, abort before writing that batch's changes.
 # Running total: if too many field assigns across all batches processed so far are being removed, abort before writing the current batch's changes.

*Code refactoring:*
 * {{syncFull()}} broken into: {{{}syncFullSetup(){}}}, {{{}syncFullLoadGrouperDataForRange(){}}}, {{{}syncFullLoadGrouperDataForSubjectIds(){}}}, {{{}syncFullLoadGrouperDataForMemberInternalIds(){}}}, {{{}syncFullRetrieveSourceDataForRange(){}}}, {{{}syncFullRetrieveSourceDataForSubjectIds(){}}}, {{syncFullValidateQueryFieldConfigs()}}
 * {{calculateAndStoreChanges()}} broken into: {{{}calculateConvertSourceDataForMember(){}}}, {{{}calculateCompareMemberData(){}}}, {{{}calculateCheckFailsafe(){}}}, {{{}calculateTrackReadOnlyCounts(){}}}, {{{}calculateGenerateInternalIdsAndChangeLog(){}}}, {{{}calculateGenerateHistory(){}}}, {{{}calculateWriteChanges(){}}}, {{{}calculateReportChangeCounts(){}}}, {{calculateReportDuplicateRowKeys()}}
 * Per-call state moved to inner {{ChangeState}} class; per-batch state (member wrappers, assigns, dictionary text, members to add) moved to {{GrouperDataProviderIndex}} which is replaced each batch
 * {{retrieveSourceData()}} split into fetch and process phases via {{retrieveSourceDataProcessRows()}} so pre-fetched rows from range queries can reuse the subject resolution logic

*DAO additions:*
 * {{GrouperDataProviderQueryTargetDao.selectDistinctSubjectIds()}} — returns ordered distinct lowercased subject IDs from the source (SQL uses {{{}ORDER BY{}}}, LDAP sorts in Java)
 * {{GrouperDataProviderQueryTargetDao.selectDataBySubjectIdRange()}} — retrieves source data for a subject ID range
 * {{GrouperDataProviderQueryTargetDao.selectDataBySubjectIds()}} — retrieves source data for specific subject IDs (straggler pass), batched internally at 800 to avoid bind variable limits
 * {{MemberDAO.selectByDataProviderAndSubjectIdRange()}} — selects member internal IDs by provider and subject ID range
 * {{MemberDAO.selectDistinctSubjectIdsByDataProvider()}} — selects distinct lowercased subject IDs from Grouper for a provider
 * {{GrouperDataEngine.setGrouperDataProviderIndex()}} — allows replacing the index between batches

*Tests added:*
 * {{testSqlProviderFullBatchBySubjectId}} — 4 subjects, batch size 2, reuses existing comprehensive assertions
 * {{testSqlProviderFullBatchBySubjectIdSizeOne}} — 4 subjects, batch size 1 (most extreme batching)
 * {{testSqlProviderOneRowPerSubjectFullBatchBySubjectId}} — one-row-per-subject with batch size 2
 * {{testSqlProviderFullBatchBySubjectIdNineSubjects}} — 9 subjects, batch size 2, verifies field/row assigns, debug map accumulated counts
 * {{testLdapProviderFullBatchBySubjectId}} — LDAP provider with batch size 2
 * {{testSqlProviderFullSyncFailsafeSubjectIdCount}} — tests failsafe check #1 (subject ID count)
 * {{testSqlProviderFullSyncFailsafePerBatch}} — tests failsafe check #2 (per-batch field assign removes)

*Also reverted* the member batching from GRP-6798 which batched the processing/writing phase but still loaded all data into memory upfront. Post-GRP-6798 improvements are retained: readonly mode, debug map change examples, improved duplicate key logging, count fixes, and SubjectSourceCache threshold.

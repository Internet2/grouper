# GRP-7294  Box provisioner offset paging can duplicate records, and the group members loop can spin forever

Box pages /users, /groups and /groups/ID/memberships by offset. If the underlying set shifts between calls, a record can be returned on two pages. Three methods in GrouperBoxApiCommands handle that badly.

1) retrieveBoxUsers and retrieveBoxGroups add every entry from every page to the results list with no dedupe. A duplicated user makes the provisioner see two target entities for one login, and it then parks that person with a MAT error (Matching ID [login, val: someone] matches 2 target entities), so that person provisions nowhere until the next run happens to page cleanly.

Observed at Penn on v7: one full sync reported targetEntitiesRetrieved of 49131 while only 49130 were distinct, and raised a MAT error for a login that has exactly one account in box. We confirmed the single account with a direct GET /2.0/users with user_type=all and filter_term, which returned total_count of 1. The very next full sync retrieved 49139, all distinct, with no MAT error at all. So the duplicate was transient paging overlap rather than duplicate data in box.

2) retrieveBoxGroupMembers is worse. It accumulates into a Map keyed by user id, so a repeat is already collapsed, and then it uses memberIdToMembershipId.size() both as the next offset and as the termination test against total_count. On a repeat the map size does not grow, so the next offset points back at a page already read. The loop can then re-read the same page indefinitely and never reach total_count. The only escape is an empty entries array.

Suggested fix: dedupe results by the box id (box primary key, so the same id cannot carry two different logins or names) in retrieveBoxUsers and retrieveBoxGroups, and in all three methods count RAW entries returned by box for the paging offset and the termination test rather than the size of the deduped collection. Note that adding dedupe WITHOUT switching to a raw counter would break paging in users and groups in exactly the way it is already broken in the members loop, because both currently derive the offset from results.size().

Worth considering separately: marker based pagination where box supports it for these endpoints. Offset paging over a changing set can also SKIP a record, which dedupe does not address.

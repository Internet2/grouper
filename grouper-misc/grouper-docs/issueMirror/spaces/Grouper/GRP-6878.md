# GRP-6878  Config edit of sample properties in non-base files mutates cached metadata

GRP-6865 fixed editing config properties whose key exists in both base and non-base files by setting the {{key}} on the {{ConfigItemMetadata}} so {{isSampleProperty()}} returns false and the edit form displays the current value.

However, the {{ConfigItemMetadata}} objects are shared via a global cache ({{{}configFileNameToConfigFileMetadataCache{}}} in {{{}ConfigFileName{}}}). Calling {{setKey()}} directly on the cached object permanently mutates it for the lifetime of the JVM. This means:
 * After the first edit of a sample/pattern property, {{isSampleProperty()}} permanently returns {{false}} for that metadata entry across all subsequent requests
 * The sample key pattern (e.g. {{{}grouper.provisioner.$$target$$.name{}}}) gets replaced with a concrete key (e.g. {{{}grouper.provisioner.myLdap.name{}}}), which could break pattern matching for other instances of the same sample
 * No thread safety on the mutation — two concurrent requests could race

Fix: clone the {{ConfigItemMetadata}} via {{GrouperUtil.clone()}} before mutating the {{{}key{}}}, and set the clone on the request-scoped {{{}GuiConfigProperty{}}}. The cached metadata remains untouched.

# GRP-7524  A full provisioner can start while an incremental-converted-to-full sync is already running

**Description**

When an incremental provisioner converts to a full sync, it can run at the same time as a scheduled or manual full for the same provisioner. Nothing makes the second full wait or fail. This allows two fulls to work on the same sync state and target at once. Combined with GRP-7523, one of them has no failsafe.

**Observed (reported by the customer)**

* The incremental starts at 01:00 and converts to full. A manual full starts at about 03:00, while the inc→full is still running.

* Later incrementals wait for the full, as expected.

* Both fulls run at the same time. The inc→full ends at 04:09, and the scheduled full ends at 05:35 with a failsafe trip.

**Analysis (code reading, not yet reproduced)**

* The cross-job lock is `GcGrouperSyncJob.waitForRelatedJobsToFinishThenRun`. It's a database lock on `grouper_sync_job` rows, one per sync type. It waits only on rows of a different sync type that are `running`, or `pending` for a small job, with a heartbeat under 90 seconds old.

* `GrouperProvisioningLogic.runFullSyncFromIncremental()` ends the incremental provisioner. That sets the incremental row to `notRunning`. It then starts a new full provisioner, which uses the full sync-type row, the same row the scheduled full uses.

* Therefore the inc→full marks the full row `running` and keeps its heartbeat live. A later full then hits the early return in `waitForRelatedJobsToFinishThenRunHelper` ("if we are already running then we good": job state `running` and `isHeartBeatAlive()`). It takes the other run's `running` state as its own and proceeds without waiting.

* Same-type overlap is otherwise prevented only by Quartz `@DisallowConcurrentExecution` on `GrouperProvisioningFullSyncJob`. The inc→full runs inside the changelog consumer job, so that annotation doesn't cover it. It also wouldn't cover a full started from another JVM.

* Not yet confirmed: that the scheduled full's job object sees the full row as `running` at start. This depends on how `initialize()` loads the row.

**Steps to reproduce** (from the customer's test)

# Set a low failsafe threshold and a low convert-to-full threshold.

# Make a large membership removal (about 43k) that takes more than 2 minutes for the incremental to report.

# Let the incremental start and convert to full.

# After the conversion, start the full manually.

# Check that both fulls run at the same time.

**Expected:** The second full waits, or fails fast with a clear message, while a full (including an inc→full) is running for the provisioner.

**Suggested fix**

* Give the sync job row an owner (instance id or run id). In the early-return check, a full that finds the row `running` with a live heartbeat but owned by a different run must wait or abort.

* A fail-fast message is simplest and also covers fulls started from different JVMs.

* Alternatively, have the inc→full also hold the incremental row. That doesn't solve full against full.

**Evidence to collect:** `grouper_sync_job` rows (state and heartbeat for both sync types) during the overlap window. Also check for the "waiting for other jobs to finish" job message, which the second full should have shown but didn't.

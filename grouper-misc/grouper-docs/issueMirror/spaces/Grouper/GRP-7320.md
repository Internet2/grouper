# GRP-7320  Set tomcat maxHttpHeaderSize to 32768 in the container so large SSO cookies do not cause a 400

The grouper container generates its tomcat connectors at startup in librarySetupFilesTomcat.sh (setupFilesTomcat_turnOnHttp and setupFilesTomcat_turnOnHttps), and neither generated Connector sets maxHttpHeaderSize. That leaves tomcat at its default of 8192 bytes for the entire request header block, cookies included.

Sites that front grouper with SSO exceed 8192 without much trouble: shibboleth session and state cookies, oidc or jwt cookies, and similar. When that happens tomcat rejects the request itself with HTTP Status 400 - Request header is too large, thrown from Http11InputBuffer.parseHeaders, before the request ever reaches grouper. The user just sees a tomcat error page, and there is nothing in the grouper logs, so it is a confusing one to diagnose.

Fix is to add maxHttpHeaderSize of 32768 to the generated http and https connectors, alongside the maxParameterCount of 10000 that is already hardcoded there. 32768 is four times the tomcat default and covers the SSO cookie cases. The ajp connector is intentionally left alone since it does not accept that attribute; it sizes packets with packetSize instead.

There is precedent for this kind of container level default: GROUPER_TOMCAT_MAX_HEADER_COUNT was added earlier for the same class of problem, when newer chrome started sending too many headers. A site that needs a different value can still overlay its own server.xml, which the container leaves untouched.

Applies to the v7 and v4 containers.

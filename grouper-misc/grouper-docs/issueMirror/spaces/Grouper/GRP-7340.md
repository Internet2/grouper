# GRP-7340  Entity Actions -> provisioning -> provisioner [Actions] -> Fix entity in target

I don’t know whether this should be classified as an improvement or a new feature.

If you’re looking at a subject entry in grouper, and follow this action path..

{{Entity Actions → provisioning → provisioner name [Actions] → Fix entity in target}}

..I believe that the intended function there is to maker sure that entity object is accurate in the target system, if that provisioner is configured to affect entities.

There is a second path / action that I think would be valid for this menu.   When the group incremental functionality was introduced ([https://todos.grouper.internet2.edu/browse/GRP-6949|https://todos.grouper.internet2.edu/browse/GRP-6949|smart-link] ), the incremental loader gained the ability to fix a single group in a target, especially useful for “Fix group in target”.   That supplements the original incremental functionality, which was subject based (e.g. update all of {{bjensen}} memberships managed by {{myLoader}}).  

I would love to see a {{Fix entity’s groups in target}} option for this action menu.

### Liam Hoekenga - 2026-09-17T14:44:49.073-0400

*Claude summary:*

h2. Request

On an entity's page, {{Entity Actions -> provisioning -> provisioner name [Actions]}} currently
offers:

* Fix entity in target
* View details

Add a third option: *Fix entity's groups in target* — recalculates all of the entity's group
memberships in that target, mirroring "Fix group in target" (GRP-6949) on the group side.

h2. Current mechanism (how the existing two actions work)

* JSP dropdowns:
** {{grouper-ui/webapp/WEB-INF/grouperUi2/provisioning/provisioningSubjectProvisionersTableHelper.jsp:66}} (entity)
** {{grouper-ui/webapp/WEB-INF/grouperUi2/provisioning/provisioningGroupProvisionersTableHelper.jsp:52}} (group)
* Servlet handlers in {{UiV2Provisioning.java}}:
** {{runSubjectSync()}} (line 4085) / {{runGroupSync()}} (line 4013) — build a {{ProvisioningMessage}},
drop it on the target's incremental queue, run blocking.
** {{runMembershipSync()}} (line 4159) — syncs one specific group+member pair. Closest existing
building block for the new feature.
* {{GrouperProvisioningData.addIncrementalEntity(...)}} (line 859) has a {{recalcMemberships}} flag
that, when true, forces the target to recompute _all_ of that entity's group memberships —
exactly the behavior wanted. Today it's only ever set from a global config flag
({{GrouperProvisioningBehavior.isSelectEntityMembershipsForRecalc()}}), never from an ad hoc
per-request UI action.
* No group-side or loader-side bulk "fix all members of a group in target" analog exists either —
this is a genuinely new capability, not resurrecting dead code.

h2. Two implementation options

h3. Option A — Surgical, no protocol change

New servlet method enumerates the entity's current group memberships and loops the same logic
{{runMembershipSync}} uses ({{setMembershipsForSync}}) for each one.

* Pro: touches nothing shared; low risk.
* Con: N messages for N group memberships; more queue/consumer overhead per click.

h3. Option B — Extend the shared message format

Extend {{ProvisioningMessage}} / {{ProvisioningMembershipMessage}} so {{setMemberIdsForSync}} can carry
an explicit "recalc this entity's memberships" flag, letting the incremental consumer
({{GrouperProvisioningLogicIncremental.java}}) do the recalc itself via the existing
{{recalcMemberships}} plumbing.

* Pro: single message, more efficient, reuses the exact mechanism the config-level flag already
drives.
* Con: changes a wire format used by every provisioner — needs care/compat review.

h2. Other scope notes

* New JSP link would go in {{provisioningSubjectProvisionersTableHelper.jsp}} next to lines 66-67,
gated the same way as "Fix entity in target".
* New text key alongside {{provisioningConfigTableActionsRunMemberSync}} in
{{grouper/conf/grouperText/grouper.textNg.en.us.base.properties}} (existing keys at lines 8820-8821).

# GRP-7462  AI assistant in the Grouper UI, sharing one tool layer with MCP

An AI assistant in the Grouper UI (Miscellaneous > AI assistant), built on the same tool layer MCP clients use. Steps 5 to 8 of the design; steps 1 to 4 were GRP-7367. Ships in 7.8.0, with upgrade task V46.

[https://docs.grouper.internet2.edu/wiki/spaces/Grouper/pages/271908865/Grouper+AI+assistant+in+the+UI|https://docs.grouper.internet2.edu/wiki/spaces/Grouper/pages/271908865/Grouper+AI+assistant+in+the+UI|smart-link] 

h2. UI runs MCP tools as the logged in user

* *Per-request subject resolver:* {{GrouperWsRequestContext.assignSubjectResolverForRequest}}. Each front door says per request how the logged in user is found, so the UI and WS cannot answer for each other in one webapp. The static resolver stays as a fallback.
* *Tool session:* while a tool runs, the web service logic uses the session the tool executor started as the caller ({{GrouperToolExecutor.retrieveToolGrouperSession}}).
* *Tool list in core:* moved from {{GrouperMcpServlet}} to {{GrouperToolExecutor.retrieveToolDefinitions}}, so MCP and the UI offer the same tools.
* *Scope in the UI:* carried in the consent scope flags ({{GrouperMcpAuthUser.isConsentScopeEnforced}}). It can only narrow what the MCP groups allow.
* *Tool log:* new column {{grouper_mcp_tool_log.entry_path}} ({{mcp}} or {{ui}}), shown as "From" on the MCP tool log screen.

h2. Agent loop

* *Providers:* Anthropic Messages API and OpenAI Responses API over plain HTTP. Key and address come from a web service bearer token external system. https is required unless {{grouper.ai.agent.allowInsecureEndpoint}} is set. The key header and response bodies are never logged.
* *Tools:*
** Look-ups run straight away.
** Changes wait for the user's approval, each shown as a summary built by Grouper from the call, escaped so it can't mislead.
** Anything outside the session scope is refused without asking.
** Running an {{institutional_tools}} template not marked {{mcpReadonly}} counts as a change: it needs approval, and for MCP clients it counts as {{readwrite}}.
* *Limits per message:* a step cap, a cap on look-ups per step ({{maxLookupsPerStep}}), long tool results cut off, and a Stop button between steps.
* *Long conversations:* older exchanges are summarized, with the latest kept word for word. Long tool results from earlier questions are replaced with a short note.
* *Who the user is:* each request starts with a labelled message giving the user's subject id, source and name, so "add me" works. The system prompt and tools stay the same for everyone, so they stay cached across users.
* *Rate limits:* on HTTP 429 the agent waits and retries, following {{Retry-After}} or 20 seconds at a time, up to {{grouper.ai.agent.rateLimitMaxWaitSeconds}} (default 90). Stop ends the wait. If the limit doesn't clear, the user is told the AI service is busy.
* *Conversation too long for the model:* the user is told to start a new one.
* *Fail safe:*
** Access is checked before every model call and look-up, so removing someone stops a running turn.
** A response cut off or stopped for an unknown reason runs none of its tool calls.
* *Config:* {{grouper.ai.agent.*}}, off by default. The model is required, with no built-in default.

h2. Screen

* *Conversation:* answers as plain text. Each tool call can be expanded to show its arguments and result.
* *Scope:* the user picks what the assistant may do this session, among what their MCP groups allow.
* *Approvals:* all changes checked to start, a "Make N changes" button that counts the checked boxes, and "Decline all". A single change gets "Make this change" and "Decline". The form carries a fingerprint of the changes it showed, so a stale form in another tab can't decide on changes it never showed.
* *Status:* limits, errors and waiting for approval are shown in the conversation, above the approval box.
* *Background:* requests run on their own per-node thread pool ({{maxConcurrentTurnsPerNode}}). The page polls, shows elapsed time and any rate limit wait, and has a Stop button.
* *Not set up:* an incomplete setup tells the user the assistant isn't set up, with the detail in the log.
* *Session:* the conversation lives in the UI session, so multi-node UIs need sticky sessions.

h2. Access, limits and usage

* *Access group:* {{grouper.ai.agent.users}} (default {{etc:aiAgent:aiAgentUsers}}, created empty). Members also need at least one MCP group. MCP tools cannot change it.
* *Limits, checked when a message starts:*
** {{maxQuestionsPerUserPerDay}} and {{maxTokensPerConversation}} are required once the assistant is on ({{-1}} for none).
** {{maxTokensPerUserPerDay}} is optional.
** Tokens counted are uncached input plus output.
** If usage can't be read, new messages are refused.
* *Group overrides:* {{grouper.ai.agent.limitOverride.<configId>.*}} give a group higher limits. The highest wins, and an override can only raise a limit.
* *Time zone:* days are counted in {{grouper.ai.agent.timeZone}}, blank for the server's.
* *New table* {{grouper_ai_agent_usage}}: per user per day, with messages, model calls, input, cached input and output tokens.
* *New table* {{grouper_ai_agent_call_log}}: one row per call to the AI provider, whether it worked or failed. It holds the user, conversation, provider, model, outcome, stop reason, tool call count, tokens, the provider's request id, start and duration. The request id header is configurable ({{grouper.ai.agent.requestIdHeaders}}, default {{request-id, x-request-id, x-litellm-call-id}}). No conversation text is kept.
* *Usage report:* Miscellaneous > Administration > AI assistant usage, sysadmins only. Tokens per person over a date range, sorted by tokens counted toward the limits. No cost estimate: actual charges come from the provider's or gateway's billing.
* *Audit:* changes made through the assistant use the new engine {{grouperUiAiAgent}}, as the logged in user.
* *Stack traces:* the {{grouper.mcp.users.canSeeStackTraces}} restriction now applies whenever a tool runs, including from the UI assistant.
* *Cleanup:* {{loader.retain.db.ai_agent_usage.days}} and {{loader.retain.db.ai_agent_call_log.days}}, both default 365.

h2. Row limits for list tools (MCP and UI)

* *Result bound:* every tool declares how big its result can get ({{GrouperTool.resultBound()}}, no default). A test pins the few tools that aren't bounded.
* *Cap per front door:* the executor caps {{pageSize}} for paged tools.
** MCP: {{grouper.mcp.maxPageSize}}, default none, so MCP is unchanged unless set.
** UI assistant: {{grouper.ai.agent.maxPageSize}}, default 200.
** Either can be set per tool.
* *What's capped:* a larger, missing, below 1, non-numeric or {{null}} {{pageSize}} is lowered to the cap.
* *Note:* a page that comes back full carries a note saying it was capped.
* {{folder_find}} pages: it gains {{pageSize}} and {{pageNumber}} for its approximate name and parent folder searches. With no {{pageSize}}, it returns every match as before.

h2. Upgrade

Upgrade task V46 (7.8.0) adds {{grouper_mcp_tool_log.entry_path}} and the tables {{grouper_ai_agent_usage}} and {{grouper_ai_agent_call_log}}, with indexes and column comments. New installs get them from the install DDL.

# GRP-7108  SCIM provisioner diagnostics: probe for unstable multi-page pagination (no sort + population over filter maxResults)

*Background*

When a SCIM target does not support sorting and the population exceeds the advertised filter {{{}maxResults{}}}, a full sync pages sequentially and can duplicate or skip objects if the target's page order is not stable across requests. This was observed against a live CrowdStrike SCIM tenant ({{{}sort.supported=false{}}}, and overlapping page windows returned inconsistent ordering). Diagnostics does not surface this risk, so it only manifests once a population grows past one page.

*Change*

Add a "Pagination stability probe" section to provisioning diagnostics. It reads {{sort.supported}} and {{filter.maxResults}} from {{{}/ServiceProviderConfig{}}}, counts the entities in the target, and reports:
 * population within one page (count <= maxResults) - not a concern.
 * population spans multiple pages and {{sort.supported=false}} - warns that a sequential full sync may duplicate or skip entities if the target's order is not stable.
 * population spans multiple pages but sorting is supported - notes paging should be stable.

New pieces:
 * {{{}GrouperProvisioningDiagnosticsContainer.appendScimPaginationProbe{}}}, wired into the diagnostics run.
 * The generic SCIM mock's advertised filter {{maxResults}} is made configurable so the probe can be tested against a small population, plus a test that asserts the warning fires.

*Failsafe*

Best-effort and self-contained (try/catch/finally, plus a nested catch around the entity-list call), so any error degrades to a note. The warning is advisory (not an error) and does not fire when the population fits within a single page.

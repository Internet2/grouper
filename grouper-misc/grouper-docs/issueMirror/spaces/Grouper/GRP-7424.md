# GRP-7424  Folder create hangs forever: self-deadlock between the main transaction and StemViewPrivilegeLogic when a privilege-inheritance rule fires (Grouper 7.5.0, PostgreSQL)

Subject: Folder create hangs forever: self-deadlock between the main transaction and StemViewPrivilegeLogic when a privilege-inheritance rule fires (Grouper 7.5.0, PostgreSQL)

ENVIRONMENT

* Grouper 7.5.0 (web services report serverVersion: 7.5.0). Seen through both the web services and the UI.
* PostgreSQL <version> on AWS RDS, PostgreSQL JDBC driver, c3p0 pool.
* idle_in_transaction_session_timeout = 1d, statement_timeout = 0.

SUMMARY
Creating a folder (stem) under a parent folder that has a privilege-inheritance rule sometimes hangs forever. The request never completes: our gateway returns a 504 after 60 seconds and nothing is logged. The folder-create transaction stays open, holding its locks, until the session is ended manually or idle_in_transaction_session_timeout ends it (1 day for us). Every retry of the same folder name queues behind it.

ROOT CAUSE
One request uses two separate database connections, and each ends up waiting on the other:

# Connection A is the Hibernate transaction opened by StemSave. It inserts into grouper_stems, grouper_stem_set, grouper_memberships, grouper_group_set, grouper_stem_view_privilege and grouper_change_log_entry_temp, and has not committed.
# Still inside Stem.internal_addChildStem, the rule engine fires the privilege-inheritance rule, which calls Stem.grantPriv -> StemViewPrivilegeLogic.addStemPrivilegeIfNeeded.
# That method runs its insert through GcDbAccess.executeSql on a different pooled connection, B, outside transaction A.
# B's insert into grouper_stem_view_privilege conflicts with rows A inserted but has not committed, so Postgres blocks B until A ends.
# A can never end, because the Java thread that would commit it is waiting for B.


Postgres cannot detect this as a deadlock because one side of the wait is in the application.

EVIDENCE: pg_stat_activity (both sessions from the same web services node)
pid 10904 (A): idle in transaction, wait Client/ClientRead, 3h09m, last query: select ... from grouper_members where subject_id=$1 and subject_source=$2 and subject_type=$3
pid 31885 (B): active, wait Lock (blocked by 10904), 3h18m, query: insert into grouper_stem_view_privilege (member_uuid, stem_uuid, object_type) values ($1, $2, 'S')
Locks held by A: RowExclusiveLock on grouper_stems, grouper_stem_set, grouper_stem_view_privilege, grouper_memberships, grouper_group_set, grouper_change_log_entry_temp, plus its transactionid lock.
Seen three times across two days, on different nodes and under different parent folders. Each time we ended A, the next queued retry of the same folder name went through, fired the rule and got stuck the same way.

STEPS TO REPRODUCE (as we understand them)

# Add a privilege-inheritance rule to a parent folder that grants folder privileges to new child folders.
# Create a child folder under it with web services stemSave (saveMode=INSERT) or in the UI.
# Sometimes the request hangs as described. Not every create: others under the same parent succeeded. Our guess is it happens only when addStemPrivilegeIfNeeded actually has a row to insert.

IMPACT

* Folder creates through the UI and web services time out with no error logged.
* The folder name stays blocked until someone intervenes, or up to idle_in_transaction_session_timeout.
* Automated retries pile up; at one point we had 26 blocked sessions.

WORKAROUNDS

* Ending the stuck transaction with pg_terminate_backend, after ending any queued retry for the same name.
* Creating the folder elsewhere and moving it into place (moving doesn't fire the rule), then adding the inherited privileges by hand.

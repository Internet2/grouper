# GRP-7401  Config delete with duplicate or EL rows deletes the same row twice in DbConfigEngine

DbConfigEngine.configurationFileItemDeleteHelper had two problems in the loops that find the rows to delete. For a duplicate non EL row it called current.delete() and then configurationFileItemDeleteHelper(current, ...), which deletes the same row again, and then kept the already deleted row, so the first row was never deleted. In the EL loop the duplicate check tested grouperConfigHibernate instead of grouperConfigHibernateEl, so a key with a value row and one .elConfig row deleted the EL row in the loop and again afterwards.

Before GRP-7395 both deletes ran in the caller's transaction. Since GRP-7395 GrouperConfigHibernate.delete() commits in its own transaction, so the second delete of an already deleted row would fail.

Fix: delete each extra row exactly once and skip it, keep the first row for the normal delete below, and check the EL duplicate against grouperConfigHibernateEl.

### Chris Hyzer - 2026-09-29T10:12:48.233-0400

Also fixed the same pattern in DbConfigEngine.validateConfigEdit (the edit path). A duplicate value row was deleted but then kept as the row to edit, so the edit saved a row that no longer existed; now the extra row is deleted and the first one is kept. The EL loop checked grouperConfigHibernate instead of grouperConfigHibernateEl, so a key with a value row and one EL row deleted the EL row in the loop and then either deleted it again (non EL edit) or returned the deleted row to be edited (EL edit); now it checks the EL variable and the existing both-rows block decides which one to keep.

### bert - 2018-09-21T12:01:10.955+0000

A couple comments:

1) Full Syncs usually happen in the background while Changelog processing continues, and Full Syncs are queued at two priorities

2) The FullSyncs scheduled by this updateStem command  indeed happen in the background and are scheduled at the lowest priority. So it certainly is a lot of activity, but shouldn't slow incremental provisioning.

3) In general, PSPNG is trying to be conservative and not overly analytical about how change events need to be handled. This means that Full Syncs are scheduled fairly aggressively in order to make sure things are correct.

4) Unfortunately, PSPNG only has one kind of Full Sync that corrects both membership and non-membership information. This means that things like a Folder update will cause membership to be checked when it could not have changed the membership.

5) When I said "Group Name," I'm afraid that I probably should have said Group Extension.

...

Now, to help me understand what's needed here I'm going to restate your observations. Please tell me if I get it wrong.

 

You have several provisioners, and you edited a Folder that was a parent folder of groups provisioned by just two of those provisioners.

1) A full sync of some groups in some provisioners is warranted in this case

2) It would be ideal if the Full Syncs were limited to the Provisioners and Groups descended from the Folder

3) It might be reasonable for each Provisioner to recalculate the groups it provisions, compare it to a list of groups it provisioned before, and Full Sync and/or deletes the differences. When I consider this, I worry about what group List to compare it to... when was it queried/cached... maybe after the change occurred, which means the comparison would be invalid.

4) I guess, in general, how should PSPNG be able to tell that only two provisioners were affected? The Folder Update could be adding groups to the SelectionExpression of other provisioners.

5) Here's an idea...

5a) When a folder (or group) changes (StemUpdate, GroupUpdate), do a full sync of only the groups underneath the folder (or the group itself) in the provisioners that the select them for provisioning

5b) What to do with changes that effectively deselect groups from a provisioner? Some choices: i) Don't process them incrementally, but instead just let the scheduled cleanups take care of it; ii) Schedule a background cleanup task in all provisioners; iii) Try to work some magic described in (3) above. I'm inclined to make ( i ) vs ( ii ) configurable, with (ii) as the default.

 

What do you think?

Thanks!

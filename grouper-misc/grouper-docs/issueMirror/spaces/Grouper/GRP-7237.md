# GRP-7237  Bug report: attributeDefSave WS call cannot set assignToGroup=T

h2. Summary

Calling {{WsRestAttributeDefSaveRequest}} (POST to {{attributeDefs}}) with
{{assignToGroup: "T"}} on an existing {{AttributeDef}} returns
{{resultCode: SUCCESS_NO_CHANGES_NEEDED}} and leaves {{assignToGroup}} at {{"F"}}
in both the response body and on every subsequent read. Every other
{{assignTo*}} flag we tested ({{assignToStem}}, {{description}}) updates
correctly through the identical code path. This reproduces consistently
across privilege levels, including full {{etc:SysAdminGroup}} membership, so
it is not a privilege gap.

* Grouper WS server version: {{7.3.2}}
* Client API version: {{v2_6_000}}
* Environment: {{grouper-ws-dev.dsc.umich.edu}}

h2. Reproduction

Target {{AttributeDef}}: {{test:flowTestDef}} (uuid
{{b63550cf9e1a44bb88364f3fa8c6a74b}}), currently has all {{assignTo*}} flags
{{"F"}}.

Request body (POST {{/grouper-ws/servicesRest/v2_6_000/attributeDefs}}):

{code:json}{
  "WsRestAttributeDefSaveRequest": {
    "wsAttributeDefsToSave": [
      {
        "wsAttributeDef": {
          "uuid": "b63550cf9e1a44bb88364f3fa8c6a74b",
          "name": "test:flowTestDef",
          "attributeDefType": "attr",
          "valueType": "string",
          "multiAssignable": "F",
          "multiValued": "F",
          "assignToGroup": "T",
          "assignToAttributeDef": "F",
          "assignToAttributeDefAssignment": "F",
          "assignToEffectiveMembership": "F",
          "assignToEffectiveMembershipAssignment": "F",
          "assignToGroupAssignment": "F",
          "assignToImmediateMembership": "F",
          "assignToImmediateMembershipAssignment": "F",
          "assignToMember": "F",
          "assignToMemberAssignment": "F",
          "assignToStem": "F",
          "assignToStemAssignment": "F"
        },
        "wsAttributeDefLookup": { "uuid": "b63550cf9e1a44bb88364f3fa8c6a74b" },
        "createParentStemsIfNotExist": "F"
      }
    ]
  }
}{code}

Response:

{code:json}{
  "results": [
    {
      "wsAttributeDef": { "...": "...", "assignToGroup": "F", "...": "..." },
      "resultMetadata": { "resultCode": "SUCCESS_NO_CHANGES_NEEDED", "success": "T" }
    }
  ],
  "resultMetadata": { "resultCode": "SUCCESS", "success": "T" }
}{code}

Expected: {{resultCode: SUCCESS_UPDATED}}, {{assignToGroup: "T"}} in the
response, and {{assignToGroup: "T"}} on every later read
({{findAttributeDefNames}}).

Actual: {{SUCCESS_NO_CHANGES_NEEDED}}, {{assignToGroup}} unchanged at {{"F"}}.
Confirmed on a fresh read in a separate process/session immediately
afterward — not a client-side or second-level cache artifact.

h2. Isolating the field

To rule out privilege and serialization issues, we varied one thing at a
time against the same def:

||Attempt||Result||
|{{assignToGroup: "T"}} (string), full request as above|{{SUCCESS_NO_CHANGES_NEEDED}}, unchanged|
|Same, but with {{grouper_manager}} granted {{ATTRIBUTE_READ}}/{{ATTRIBUTE_UPDATE}} on {{test:}}|same|
|Same, but with {{grouper_manager}} added to {{test:etc:security:Admins}}|same|
|Same, but with {{grouper_manager}} temporarily added to {{etc:security:Admins}} (org-wide admin)|same|
|Same, but with {{grouper_manager}} temporarily added to {{etc:SysAdminGroup}}|same|
|Same request but omitting {{uuid}}, looking up by {{name}} only ({{wsAttributeDefLookup: {"name": "test:flowTestDef"}}})|same|
|Adding {{"saveMode": "UPDATE"}} explicitly|same|
|*Same request but flipping* {{assignToStem: "T"}} instead of {{assignToGroup}}|{{SUCCESS_UPDATED}}, {{assignToStem}} correctly becomes {{"T"}}|
|Same request changing only {{description}}|{{SUCCESS_UPDATED}}, description correctly updated|

So: escalating privilege all the way to org-wide sysadmin made no
difference, and other boolean flags on the exact same {{WsAttributeDef}}
object in the exact same request DO persist. The problem is specific to
{{assignToGroup}} on this def, not a privilege or transport/serialization
issue.

We also found a second attribute def on the same WS backend with
{{assignToGroup: "F"}} that we did not attempt to modify —
{{etc:attribute:umich:mcommunity:mcommunityMarkerDef}} (uuid
{{2f06793c328f441b8ad0675c003070ef}}) — which is used in production-style
daemon Groovy scripts via
{{group.getAttributeDelegate().assignAttributeByName(markerDefName)}} to
assign the marker directly to a {{Group}}. That call path is Java API /
root-session, not WS, so it may not actually require
{{assignToGroup=true}} the same way {{WsRestAssignAttributesRequest}} does —
we haven't confirmed whether that script would fail with
{{AttributeAssignNotAllowed}} given the current {{"F"}} value. Flagging it
only as a second data point that {{assignToGroup=F}} shows up more than
once on this instance; we did not try to fix it or determine if it's
expected to be {{F}}.

h2. Where we stopped

We traced the relevant server code
({{GrouperServiceLogic.attributeDefSave}} →
{{WsAttributeDefToSave.save()}} → {{AttributeDefSave.save()}}, all in the
{{grouper}} and {{grouper-ws}} source trees) and confirmed the code _should_
compare {{AttributeDefSave.this.assignToGroup != theAttributeDef.isAssignToGroup()}}
and call {{theAttributeDef.setAssignToGroup(...)}} + {{.store()}} if they
differ, using the exact same code shape as the {{assignToStem}} branch that
works correctly. We did not go further into the DAO/Hibernate mapping
layer or actually attach a debugger/log to the running dev server, so we
can't yet say whether:

* something upstream of that comparison (e.g. {{WsAttributeDefToSave.save()}}
reading {{this.getWsAttributeDef().getAssignToGroup()}}) is misreading the
incoming field for {{assignToGroup}} specifically, or
* there's a DB-level constraint/trigger/second-level-cache invalidation
issue specific to the {{assign_to_group}} column on this dev database, or
* this is an existing known upstream Grouper bug in 7.3.2 worth checking
against the project's issue tracker.

h2. Question for the Grouper developers

Is there a known issue with {{WsRestAttributeDefSaveRequest}} / {{AttributeDefSave}}
not persisting {{assignToGroup}} specifically (as opposed to sibling flags
like {{assignToStem}}), on server version 7.3.2? If not, we're happy to
provide a live repro against {{grouper-ws-dev.dsc.umich.edu}} (uuid
{{b63550cf9e1a44bb88364f3fa8c6a74b}}, {{test:flowTestDef}}) for further
debugging.

# GRP-7560  Provisioning incremental should not re-queue error codes that are configured as not an error

Environment: v7, LDAP provisioner to Active Directory, groupAttributes membership, insertEntities=false, about 6,600 provisioned groups and 1.3M memberships, some groups with 10k+ members.

Problem: GcGrouperSyncMemberDao.retrieveMemberIdsWithErrorsAfterMillis and GcGrouperSyncMembershipDao.retrieveGroupIdMemberIdsWithErrorsAfterMillis select any row where error_code is not null. So with errorHandlingTargetObjectDoesNotExistIsAnError=false, DNE entities and memberships are still re-queued by addErrorsToQueue every 3 minutes (errorHandlingMinutesLevel4), and sometimes 120-180 minutes back. In our case that is about 9,000 users with no account in the target and 33,000 memberships. One run re-queued 13,749 items. 12,049 of them landed in 10 large groups, which crossed membershipsConvertToGroupSyncThreshold (500) and turned into full group recalcs that took up to an hour each. These re-queues also dominate convertToFullSyncScore (6,000-7,500 on runs that took seconds), so scoreConvertToFullSyncThreshold cannot be tuned to catch the expensive runs.

Requested fix: addErrorsToQueue should only re-queue error codes that can succeed on retry without a Grouper-side change:

* ERR (exception): keep retrying, this is what the queue is for.
* DNE, MAT (target-side): only retry when configured as an error (errorHandlingTargetObjectDoesNotExistIsAnError / errorHandlingMatchingValidationIsAnError). Otherwise leave them for the full sync, which re-reads the target anyway.
* INV, LEN, REQ (Grouper-side data validation): the result cannot change until the Grouper data changes, and that already generates a change log event. Only retry when configured as an error, or never re-queue them.
* MEM, SKP (intentional states, not failures): never re-queue.
Simplest version: if errorHandlingHandleError would say the code is not an error, do not re-queue it.

# GRP-7233  Provisioning: select-after-insert count mismatch throws and discards the entire run's sync state and object errors

In GrouperProvisioningLogic.createMissingEntitiesFull, after inserting entities the framework re-reads them via retrieveEntities to capture target ids. If the number retrieved does not equal the number inserted, it throws a RuntimeException: Searched for N entities after creating them, but retrieved M, maybe the server is caching results and is not returning the created entity or a matching/searching config needs to be adjusted.

The problem is not the detection, it is the blast radius. That exception unwinds out of provisionFull before errorHandling() and storeAllSyncObjects() run. Everything the run learned is thrown away: no gcGrouperSyncMember error codes or messages are persisted for objects that genuinely failed, in_target and related sync flags are not updated for objects that genuinely succeeded, and insert_count, update_count and delete_count on the loader log all stay at zero. The daemon log reports a run that appears to have done nothing, while the target has in fact been modified.

Real-world case that motivated this. A full sync inserted 258 entities. 244 creates succeeded (confirmed by the target accepting two follow-on entitlement calls against each returned id, and later confirmed by looking the users up in the target directly). 14 were rejected by the target with per-object HTTP 400s and had legitimate per-object error codes to record. The select-after-insert then retrieved only 197 of the 244, because the target's search endpoint is a free-text search that returned multiple ambiguous hits for short search values. The resulting throw discarded all of it: the 197 successes, the 47 ambiguous-but-created entities, and, most damagingly, the 14 real per-object errors that an administrator needs in order to act. The loader log recorded insert_count 0 for a run that created 244 accounts.

Suggested behavior: treat a select-after-insert miss as a per-object condition rather than a run-fatal one. Mark the entities that could not be re-read with an error code, leave the successfully retrieved ones intact, let the run proceed through errorHandling() and storeAllSyncObjects() so sync state and object errors are persisted, and then let errorHandlingProvisionerDaemonShouldFailOnObjectError decide whether the job status ends up ERROR. That keeps the existing signal, an administrator still sees a failed job, but the run stops destroying the diagnostic information needed to understand why, and stops leaving the sync tables contradicting the target.

Note the code at that site already carries the comment: maybe this should be an exception??? which suggests the run-fatal choice was never firmly settled. Also worth noting that when this fires, the final state end log line is emitted without syncObjectStoreCount, which is a useful tell that the store phase never ran.

## Comments

### Chris Hyzer - 2026-08-10T14:15:11.326-0400

Acceptance criteria, and the error code decision.

1. At the end of a run in which entities were inserted, the loader log must report an accurate insert count. Today it reports zero for a run that really created hundreds of accounts. Note this is not simply a matter of persisting a number that was already tallied: countInsertsUpdatesDeletes derives the counts by comparing each sync object inTargetStart and inTargetEnd against millisWhenSyncStarted, and it runs well after the throw, as does GrouperProvisioningOutput.copyToHib3LoaderLog. So nothing is counted at all today. Letting the run complete is what produces the number.

2. Entities that could not be re-read after insert must carry a per-object error code and message on gcGrouperSyncMember, so they are visible on the group provisioning membership screens in the UI. An administrator needs to see which specific users are affected, by name, not just a red job.

3. Use ERR for this condition, not DNE. DNE is documented in GcGrouperSyncErrorCode as object is missing in the target and not able to be inserted, and that is not an honest description here. The object may well exist in the target, for instance matched under different case or under a different identifier, and it was inserted successfully. There is also a practical hazard: DNE is gated by errorHandlingTargetObjectDoesNotExistIsAnError, which is commonly false, so stamping DNE would let these runs report SUCCESS while entities are silently unreconciled. ERR carries no such gate.

4. MAT, documented as grouper object matches multiple target objects, is the semantically exact code when the underlying cause is an ambiguous match, and it is already wired in errorHandlingHandleError gated by errorHandlingMatchingValidationIsAnError. However the framework cannot know that is the cause. All it observes at this site is that an entity it inserted did not come back from retrieveEntities. Reporting MAT requires the target DAO to say so, which needs a channel that does not exist today. That is tracked separately, see the linked issue. This issue should stamp ERR; a DAO that can supply a more precise code should be able to override it.

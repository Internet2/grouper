# GRP-7519  MCP and AI assistant: make a group a scripted (JEXL) group in one group_save action, with the same checks and analysis as the UI

Today an MCP client or the UI AI assistant makes a scripted (ABAC JEXL) group by hand, with two raw {{attribute_assignment_save}} calls: one assigns the scripted group marker attribute to the group, the other assigns the script as a value on that marker assignment.

h2. Problems

*1. A lot of searching first.* The client has to work out how scripted groups are stored. In one test it made 3 {{doc_search}}, 4 {{group_find}}, 1 {{attribute_def_name_find}} and 7 {{attribute_assignment_get}} calls before it had a plan.

*2. Two approvals for one change.* In the UI assistant the first approval box only marks the group as scripted, and the script comes in a second box. If the user approves the first and declines the second, or the second fails, the group is left marked as scripted with no script.

*3. The approval box does not say what is happening.*

* It reads "Change attribute assignments: (not given) attribute 'etc:attribute:abacJexlScript:grouperJexlScriptMarker' ...", which does not say the group is becoming a scripted group.
* The script is not in the box being approved, only in the assistant's text.
* "(not given)" is the operation, which defaults to {{assign_attr}}, but the box does not say so.

*4. It skips the checks the UI's scripted group screen runs* ({{UiV2GrouperLoader}}).

* *Who may edit.* The UI requires {{PrivilegeHelper.canEditAbacLoader}}: ADMIN on the group, and membership in {{grouper.abac.edit.if.in.group}} when that is set. {{attribute_assignment_save}} only checks privileges on the attribute definitions. So group admins who can use the screen are refused over MCP, and anybody granted ATTR_UPDATE on those attribute definitions so MCP works is no longer held to {{grouper.abac.edit.if.in.group}}.
* *Read access to the groups the script references.* The UI's analysis ({{GrouperLoaderJexlScriptFullSync.analyzeJexlScriptHtml}}) refuses a script naming a group the editor cannot READ. The raw attribute path does not run it, and the scripted group's membership is computed as root, so an editor could learn the members of a group they cannot read. WS and GSH have the same gap today; this does not change them.
* *The analysis itself.* The UI reports errors and warnings and shows how many members the script would produce before it saves. The raw attribute path saves without it.

h2. Change

*1. New* {{group_save}} actions {{setJexlScript}} and {{removeJexlScript}}. One call and one approval, with the same rules as the UI screen:

* check {{PrivilegeHelper.canEditAbacLoader}} on the authenticated user
* run the same analysis as the UI, and refuse on errors or on a referenced group the caller cannot READ
* save the marker, the script and the subject source ids together, as the UI does
* return the analysis, including the expected member count

The protected resource and OAuth readwrite scope checks apply as for the other {{group_save}} actions.

*2. A read only preview* which runs the analysis without saving: an {{analyzeJexlScript}} action, or {{setJexlScript}} without a confirm, like other two step tools. It returns errors, warnings and the expected member count, so the client can tell the user "this will have about N members" before anything is approved.

*3. Approval box text.*

* {{setJexlScript}}: "Make group X a scripted group with script: ...", with the whole script.
* {{removeJexlScript}}: "Stop group X being a scripted group".
* {{attribute_assignment_save}}: show the operation it will use when none is given, e.g. "assign_attr (default)", instead of "(not given)".

*4. Tool description and docs.* The {{group_save}} description says to use {{setJexlScript}} rather than {{attribute_assignment_save}} for scripted groups, and the MCP wiki user guide documents the new actions.

## Comments

### Chris Hyzer - 2026-10-22T23:03:18.076-0400

Review notes against the v7 code. The direction is right; the main gap is that "same rules as the UI" leaves out several checks the UI save actually runs.

Checks missing from the description (UiV2GrouperLoader JEXL_SCRIPT save, around lines 1200-1250):

1. Max ABAC group size. The UI save enforces GrouperAbac.maxAbacMembershipSizeForSubject(loggedInSubject) and refuses when the population count is over the limit. MCP is exactly where oversized scripted groups would get made.

2. Warnings block the save, not just errors. On save the UI throws "not allowed" if the analysis has an error OR a warning. The description only says refuse on errors.

3. Data field privacy realms, not just group READ. analyzeJexlScriptHtml also checks the privacy realm of every data field the script uses (hasAttribute / hasRow fields and globalAttributeValue), and with readOnly=false requires update level. The raw attribute path skips this too, which is arguably a bigger leak than group READ.

4. Syntax check. The UI calls GrouperAbac.validScript(script, grouperDataEngine) before the analysis.

Design points:

5. Put the logic in grouper core and have both the UI and MCP call it. Today the validation and the marker / script / subject source ids writes are inline in grouper-ui (UiV2GrouperLoader around lines 1670-1722), which the MCP code in grouper core cannot reach. A shared method (e.g. GrouperAbac.saveJexlScript(group, script, sourceIds, subject) returning the analysis) keeps them from drifting, like the shared loader job rule from GRP-7415.

6. Wrap the save in a transaction. The UI assigns the marker, the script and the source ids in separate calls under a root session with no transaction. If the goal is never marked as scripted with no script, say so.

7. Subject source ids parameter. The description says source ids are saved but gives no input for them. Match the UI: default to GrouperAbac.globalDefaultSubjectSourceIds(), and remove the attribute when the ids equal the defaults.

8. The preview should analyze with readOnly=false. The UI Analyze button uses readOnly=true, which turns cannot-edit-this-policy into a warning instead of an error. A preview meant to predict the save result has to run in save mode.

9. Where the preview lives. If analyzeJexlScript is a group_save action, category(arguments) must report it as a read, otherwise the UI assistant shows an approval box for a read-only call. group_save is only registered for readwrite tokens, so a read-only OAuth client could never preview; fine, but decide it on purpose. group_save has no confirm pattern today, so a separate action is cleaner than setJexlScript without a confirm.

10. Say what happens to the group's existing setup, in the approval text and the tool description: existing direct members are replaced by the script population on the next sync; an existing SQL/LDAP loader on the group is either refused or replaced; and for removeJexlScript, whether current members stay.

11. Minor: check (or document) that the script cannot reference the group itself. The WS and GSH gap noted in the description is worth its own follow-up ticket.

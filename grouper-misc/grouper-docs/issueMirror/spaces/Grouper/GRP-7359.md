# GRP-7359  Grouper UI rules editor: a non-sysadmin can create a rule that runs as GrouperSystem (privilege escalation)

h3. On upgrade

Legitimate use is unaffected: in the Rules UI, non-sysadmins only ever had the predefined rule patterns, and those still work (now with the caller's privilege on any referenced group/folder enforced). What changes: custom rules and rules using expression language (EL) can now only be added, edited, or deleted by Grouper sysadmins (wheel/root); and a non-sysadmin who administers an object can no longer edit or delete an existing custom/EL rule on it. Pattern-based rules are unchanged. Recommended: restrict all rule editing to a power-user institutional group via rules.restrictRulesUiToMembersOfThisGroupName.

h3. Technical details

The Rules UI submit saved rule attributes in a root (GrouperSystem) session without validating the caller's authority over what the rule affects, so a crafted request could create or modify a rule that affects groups or folders the requester has no privileges on. The UI only displays the predefined patterns to non-sysadmins (the custom builder is wheel/root only), so custom/EL authoring by a non-sysadmin was only reachable via a crafted POST.

Fix (RuleService.saveOrUpdateRuleAttributes and the two UI submit/delete paths): a non-sysadmin is limited to the recognized patterns, and must pass the selected pattern's validate() (which enforces the caller's privilege on any referenced group/folder); custom rules (blank or custom pattern) and any rule using EL (if-condition or then EL) are wheel/root only; adding, editing, or deleting an existing custom/EL rule is wheel/root only; a null configuring subject fails closed; the UI reads only the pattern's displayed inputs (not raw check/if/then/arg/EL params); and the service verifies the built rule actually matches its claimed pattern. Related: GRP-7381 (who can create sendEmail rules) and GRP-7380 (configuration review screen).

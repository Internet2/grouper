# GRP-6787  Thread pool is unbounded and can crash JVM with thread explosion

{quote}⚠️ *IMPORTANT: This is a memory/stability issue that can cause containers to crash. Upgrading is recommended.*
{quote}
{quote}The general-purpose executor service in {{GrouperUtil.retrieveExecutorService()}} uses a {{CachedThreadPool}} with no thread limit ({{{}Integer.MAX_VALUE{}}}). When a large number of tasks are submitted concurrently (e.g., data provider full sync with millions of field assignments), thousands of threads are created, each blocking on the C3P0 connection pool waiting for a database connection. This causes the JVM to run out of native memory for thread stacks and crash, killing the container.  An example is when a process (e.g. subject source data provider) has a lot of grouper_members fields to update, those use this thread pool.

*Root cause:* {{Executors.newCachedThreadPool()}} creates unlimited threads. With 1.47 million subjects and 30 data fields, the data provider sync submits thousands of concurrent tasks. Each task needs a DB connection, but the C3P0 pool only has ~50 connections. The result is 8,000+ threads all waiting at {{{}BasicResourcePool.awaitAvailable(){}}}, consuming ~8 GB of stack space and crashing the JVM.

*Fix:* Replace the unbounded {{CachedThreadPool}} with a bounded {{ThreadPoolExecutor}} that has:
 * Configurable max threads (default 100)
 * Bounded task queue (default 10,000)
 * {{CallerRunsPolicy}} for backpressure when the queue is full
 * Idle thread timeout so threads are reclaimed when not needed

*New configuration properties* in {{{}grouper.properties{}}}:
 * {{grouper.executorService.maxThreads}} (default 100)
 * {{grouper.executorService.keepAliveSeconds}} (default 60)
 * {{grouper.executorService.queueSize}} (default 10000){quote}

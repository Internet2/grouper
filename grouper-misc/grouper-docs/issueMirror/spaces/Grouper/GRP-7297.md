# GRP-7297  Provisioning: add crudOperationOrder to allow inserts before deletes

The order of provisioning operations is hardcoded in GrouperProvisionerTargetDaoAdapter.sendChangesToTarget(). For a DAO that does not implement canSendChangesToTarget or canSendMembershipChangesToTarget (for example Okta), the order is:

# membership deletes
# group deletes, inserts, updates
# entity deletes, inserts, updates
# membership inserts, updates, replaces

There is no config property or hook to change this.

The impact shows up on large full syncs. A recent fullProvisionFull for our Okta provisioner had 63,709 membership deletes and 17,178 membership inserts. The delete phase ran about 12.8 hours (deleteOktaMembership_millis: 45,923,704) before a single insert was attempted, so everyone gaining access that day waited behind the entire delete queue. On a large appointment-change day this inverts the priority: losing access late is a much cheaper failure than gaining access late.

We understand why deletes lead today. Membership deletes must precede group and entity deletes for targets that require an empty group before the group can be removed, and capacity-limited targets (seat, license, or quota caps, unique-attribute constraints) need room freed before inserts run. So we are not asking to change the default.

h3. Request

Add provisioner.<configId>.crudOperationOrder as a dropdown with two values: deletesFirst (the default, exactly the behavior above) and insertsFirst. Existing configurations must be unaffected.

Under insertsFirst, the adapter runs every creating operation before every removing operation:

# group inserts, updates
# entity inserts, updates
# membership inserts, updates, replaces
# membership deletes
# group deletes
# entity deletes

Membership inserts stay after group and entity inserts because they depend on them -- you cannot add a member to a group the target does not have yet. Membership deletes stay ahead of group and entity deletes so a group is emptied before it is removed.

The known tradeoff: a rename within a single run (old object deleted, new object inserted carrying the same unique group name, username, or email) will collide under insertsFirst, because the old object is still present when the insert runs. Capacity-capped targets have the same exposure. That is why this is opt-in rather than a new default.

A narrower variant we would also accept, if the above is too invasive: leave the group and entity blocks exactly where they are and only move the membership-delete block from first to last. That preserves group-delete-before-group-insert (so renames keep working) but gives up emptying a group before deleting it.

h3. UI

Render the option as the first field in the advanced section at the bottom of the provisioner config page, visible only when advanced options are expanded. Most deployments will never touch it, but a site hitting this should be able to find it without hunting.

h3. Note

A DAO that sets canSendMembershipChangesToTarget=true receives inserts, updates, and deletes in a single call and chooses its own order, so ordering is not centrally controlled on that path either. Whatever setting is added should be honored there, or at least documented as not applying.

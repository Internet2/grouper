# GRP-7353  Changing grouper.text config leaves stale text in memory, on other JVMs indefinitely, because clearConfigsInMemory misses the text config cache

GrouperConfigHibernate.clearConfigsInMemory() is the single chokepoint for dropping in memory config when config changes. It calls ConfigDatabaseLogic.clearCache(false) and ConfigPropertiesCascadeBase.clearCacheThisOnly(), but GrouperUiApiTextConfig keeps its OWN static cache of config objects keyed by language and country, and neither of those clears reaches it.

So after a change to grouper.text.en.us.properties or another text config, the old externalized text can stay in memory. The text configs are editable in the UI and stored in the grouper_config table like any other config, so this is a normal thing for an administrator to do.

clearConfigsInMemory is reached three ways, and the third is the serious one:

1. GrouperConfigHibernate.updateLastUpdated(), after a config row is saved or deleted in this JVM.

2. SourceManager, when subject sources are reloaded.

3. GrouperConfigHibernate.clear(GrouperCacheDatabaseClearInput), which is how a config change made in ANOTHER JVM is propagated (registered through GrouperCacheDatabase.customRegisterDatabaseClearable). Because that path also cannot reach the text config cache, text changed on one node is stale on every other node, and nothing in the UI can fix it there, since the screen that used to force a clear only runs on the node someone is looking at.

Fix: have clearConfigsInMemory also call GrouperUiApiTextConfig.clearCache(), so every path that means config changed invalidates all of the in memory config, including the cross JVM one.

Found while working on GRP-7352, which stops the config screen from clearing the JVM wide config caches on every view. That screen was incidentally masking this bug on whichever node the administrator happened to be viewing.

### Chris Hyzer - 2026-09-20T11:53:21.095-0400

Fixed in commit c4eb4d7d50bc on GROUPER_7_BRANCH, alongside GRP-7352. GrouperConfigHibernate.clearConfigsInMemory() now also calls GrouperUiApiTextConfig.clearCache(), so every path that means config changed invalidates all of the in memory config.

That covers all three ways into that method: a local config save through updateLastUpdated, subject source reloading in SourceManager, and most importantly the cross JVM path through GrouperCacheDatabase, which is why text changed on one node used to be stale on every other node indefinitely.

Verified end to end: changed configurationFilesMenuAddConfig in grouper.text.en.us.properties through the config import screen, and the new label appeared immediately with no forced cache clear anywhere in the view path.

# GRP-7338  "group actions -> provisioner -> provisioner name -> view logs" should do something

I don’t know if this is a bug fix or a feature request.

If you view a group, then choose

Group Actions → Provisoner → Provisioner Name [action] 

there is a option to “view log”.  I would argue that choosing “view log” should return log entries about that group and the provisioner - at least that group’s last trip through the given provisioner.

Instead it displays a header atop a consistently empty list..

## Comments

### Vivek - 2026-09-16T17:25:17.610-0400

{noformat}Summary of the change:

Populated the Group provisioning logs screen (UiV2Provisioning.viewProvisioningTargetLogsOnGroup), which was always empty because the provisioning framework never wrote per-group log rows — only job-owned rows. The read path queries grouper_sync_log for rows owned by the group's sync-group record, but GcGrouperSyncGroupDao.groupCreateLog(...) (the only method that writes such rows) was never called in production. Incremental provisioning runs now create one per-group log row per group they touch.

Change details
All in GrouperProvisioningLogic.java:

New method createPerGroupSyncLogsIncremental() — runs only for incremental syncs (isIncrementalSync() guard). For each group processed in the run it creates a group-owned GcGrouperSyncLog via the existing groupCreateLog(...) and populates:
syncTimestampStart / syncTimestamp, jobTookMillis
recordsProcessed — the group plus each of its membership wrappers loaded this run
recordsChanged — provisioned group + membership changes (insert/update/delete/replace), attributed to each group via the membership→group wrapper link
status — ERROR if the sync group has an error message, else SUCCESS
a short description
(server is auto-filled on store)
Two small private helpers: addToCountMap(...) and syncGroupForMembership(...).
Wired the call into provisionIncremental() immediately before storeAllObjects(), so the cached logs are flushed to grouper_sync_log in the same store pass (no new persistence code).
Added the GcGrouperSyncLog import.
Scope / notes
Incremental only — full syncs are unchanged (still represented by the overall job log), matching the screen's "not including overall full syncs" wording and avoiding one-row-per-group volume on large full runs.
No schema change — uses the existing grouper_sync_log table; existing retention (logDeleteOldLogs, 7-day default) prunes these rows.{noformat}

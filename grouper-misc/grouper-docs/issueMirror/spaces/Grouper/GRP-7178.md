# GRP-7178  Hook auto-registration is fragile: one failed registerHookIfNecessary at startup silently disables all later built-in hooks

GrouperHooksUtils.fireHooksInitHooksIfNotFiredAlready() sets hooksInitHooksCalled = true before running the built-in hook registrations, then calls each registerHookIfNecessary in sequence with no per-hook error handling. If any one of them throws (typically due to a grouper.properties misconfiguration), every registration after it in the list is skipped, and because the once-only flag is already set, the JVM never retries. The result is that built-in hooks are silently missing for the life of the JVM, with at most one stack trace at startup.

Real-world case (reported by Berkeley on 4.23.0): grouper.properties contained a stem.attribute.validator.regex.0 / vetoMessage.0 entry with no stem.attribute.validator.attributeName.0. StemAttributeNameValidationHook.registerHookIfNecessary threw (Dont configure a regex or vetoMessage without an attribute name), which aborted the registration sequence. GroupTypeTupleIncludeExcludeHook, GroupTypeSecurityHook, GrouperAttributeAssignValueRulesConfigHook, and GroupDoNotDeleteIfProvisionable never registered in any JVM (UI, WS, daemon, gsh).

Downstream symptom: with GrouperAttributeAssignValueRulesConfigHook unregistered, the ruleValid attribute is never computed, so assigning inherited privileges in the UI fails with an unhelpful blank error (Problem calling method privilegeInheritanceAddMemberSubmit on UiV2Stem), because RuleApi.inheritFolderPrivileges throws new RuntimeException(isValidString) where isValidString is null. Include/exclude group types and group type security were also silently inactive.

How to reproduce:

1. In grouper.properties set stem.attribute.validator.regex.0 to any regex (and optionally vetoMessage.0), and do NOT set stem.attribute.validator.attributeName.0.

2. Start a fresh JVM (gsh is easiest) and trigger hooks init by doing any attribute value assignment, or call GrouperHookType.hooksInstances(GrouperHookType.ATTRIBUTE_ASSIGN_VALUE, attributeAssignValuePostInsert, HooksAttributeAssignValueBean.class). It returns an empty list: GrouperAttributeAssignValueRulesConfigHook is not registered.

3. Call RuleApi.inheritFolderPrivileges (or use the UI privileges-inherited-to-objects-in-folder screen) on any folder. It throws a RuntimeException with a null message because the ruleValid attribute value was never computed. Assigning the seven rule attribute values manually and reading RuleUtils.ruleValidName() back shows null instead of T.

Suggested fix: wrap each built-in registration in fireHooksInitHooksIfNotFiredAlready in its own try/catch that LOG.errors loudly and continues, so one bad example-hook config cannot disable the rules engine and the other built-in hooks. Consider also retrying registration on a later invocation instead of latching failure permanently, and having RuleApi.inheritFolderPrivileges (and the group/attributeDef siblings) throw a descriptive message when the ruleValid attribute value comes back null or blank.

This needs a unit test that fails before the fix and passes after it. Outline: in setUp, inject the bad config (stem.attribute.validator.regex.0 set, attributeName.0 absent) via the test config override, then use reflection to reset GrouperHooksUtils.hooksInitHooksCalled to false, clear the GrouperHookType hookTypes/hookTypeMap caches, and reset the registered/registeredSuccess statics on the built-in hook classes so registration genuinely re-runs. Then trigger hooks init and assert two things: (a) GrouperHookType.hooksInstances for ATTRIBUTE_ASSIGN_VALUE attributeAssignValuePostInsert contains GrouperAttributeAssignValueRulesConfigHook even though StemAttributeNameValidationHook registration failed, and (b) end to end, RuleApi.inheritFolderPrivileges on a test folder succeeds and the ruleValid attribute value on the rule assignment is T. Before the fix, (a) returns an empty list and (b) throws the null-message RuntimeException; after the fix both pass. Tear down must remove the config override and reset the same statics/caches (and RuleEngine.clearRuleEngineCache) so other hook tests are not polluted.

# GRP-7316  Long running daemon jobs never refresh grouper_loader_log.last_updated, so the scheduler check can mark healthy jobs as ERROR

GrouperDaemonSchedulerCheck marks a job as ERROR when its grouper_loader_log status is STARTED or RUNNING and it cannot detect the job as running. Liveness is inferred entirely from the Quartz scheduler heartbeat, not from the job making progress, so a healthy long running job can be marked as errored if the scheduler instance misses its checkin window.

The candidate query already treats grouper_loader_log.last_updated as a heartbeat, excluding any job whose log row was updated within the last 60 seconds:

{noformat}long lastCheckinTime = System.currentTimeMillis() - 50000;

select id, job_name, gll.started_time, gll.parent_job_name
  from grouper_loader_log gll
 where status in ('STARTED', 'RUNNING')
   and last_updated < ?            -- bound to now minus 60 seconds{noformat}

Jobs that survive that filter are then checked against Quartz:

{noformat}select gqft.job_name
  from grouper_QZ_FIRED_TRIGGERS gqft, grouper_QZ_SCHEDULER_STATE gqss
 where gqft.job_name in (...)
   and gqft.instance_name = gqss.instance_name
   and gqss.last_checkin_time > ?  -- bound to now minus 50 seconds{noformat}

The problem is that nothing updates grouper_loader_log.last_updated while a job is running. A GSH template job, or any other long running daemon job, writes its log row at the start and again at the end, so after the first 60 seconds it is permanently a candidate. From then on the only thing keeping it from being marked as errored is the Quartz scheduler instance having checked in within the last 50 seconds. Any stall in that checkin thread, for example a long garbage collection pause, CPU starvation on a busy daemon container, or database slowness, is enough to mark a job that is running perfectly well as ERROR.

So the intended heartbeat exists in the query but is never fed. Proposal:

* While a job is running, periodically refresh its own grouper_loader_log row, for example every 20 to 30 seconds, so the existing last_updated filter actually protects running jobs. The natural place is upstream of the individual job implementations, in the loader job wrapper, so every daemon job benefits rather than each job type having to opt in.
* Do that refresh as a targeted SQL update of last_updated for that row id, not as a full ORM store of the in memory Hib3GrouperLoaderLog. The running job holds that object and stores it at the end; writing the whole object from a heartbeat risks clobbering counts and messages accumulated elsewhere, and would overwrite fields with stale in memory values.
* Consider widening the Quartz checkin tolerance, currently 50 seconds, or making both windows configurable. A single missed checkin should probably not be sufficient on its own to declare a job dead.

Separate but related request: the message this produces asserts a cause it has not established. It reads, marking job as error since its status was STARTED and it is not detected as running, the JVM abruptly stopped or died perhaps due to memory error. The only fact in evidence is that the job was not detected as running. Attributing it to the JVM dying, and specifically to a memory error, sends people investigating memory when the actual cause may be a missed scheduler checkin, a deploy, a task replacement, or a false positive of the kind described above. Suggest stating the observation and leaving the cause open.

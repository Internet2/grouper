# GRP-7291  Veto circular group memberships beyond the direct A -> A case

From a Grouper community discussion (Liam Hoekenga, Emilio Recio, Carey Black, Andrew Johnston, Shilen Patel): Grouper vetoes adding a group as a member of itself (A -> A), but it happily allows an indirect loop such as A -> B -> A or A -> B -> C -> A. The question raised was whether A -> A is the only forbidden circular membership.

Today the answer appears to be yes for plain memberships: the direct self-membership case is vetoed, but arbitrary-depth membership loops are allowed. Memberships still calculate correctly, but deep or wide loops cause real performance problems -- some operations take longer than expected and time out, and a site can end up with a loop that its users cannot easily unwind through the UI. Sites replicating nested LDAP groups into Grouper have no easy way to know they are creating one.

Scope of this issue: plain group-as-member memberships only. Composites, ABAC/JEXL scripted groups, and rules/loader-driven cycles have their own considerations and can be handled separately.

No config switch to allow circular memberships. Circular membership is not a feature we want to support: there are very few real use cases, supporting it is high complexity and cost to develop, and it is high risk if something goes wrong. The veto is unconditional and no subject can bypass it, including GrouperSystem.

* A -> A (direct self-membership). Already vetoed. Confirm the veto fires on every path: UI, web services, GSH, loader, MCP, import, and the low-level Membership/Hib3 APIs -- not just the UI.
* A -> B -> A and any deeper cycle (A -> B -> C -> ... -> A). Currently allowed. Veto it, unconditionally, on the same paths.
* The check should be a lookup against the grouper_group_set tables, which already hold the transitive closure. It is a single query asking whether the owner group is already reachable from the candidate member group -- no walking, no recursion, no re-computation.
* Removing a membership is never vetoed, so a site that already has a loop can still break it; the veto only blocks creating or re-creating one.
* No new API or web service call for this. The veto surfaces through the existing add-member paths and their normal error handling.
* Document the behavior briefly on the wiki: circular memberships at any depth are vetoed, there is no way to turn that off, and why.

Reference: Grouper community Slack thread on circular groups, August 2026.

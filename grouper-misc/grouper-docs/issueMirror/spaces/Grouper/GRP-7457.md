# GRP-7457  recalculateAllOperations doesn't fetch memberships

With recalculateAllOperations = true, it doesn’t seem to be fetching memberships, so deletes are ignored because it thinks it’s already been deleted.



From Claude:

Yes, I found a likely copy-paste bug that matches your logs: the "select some memberships" request for entities is never sent. I haven't changed any code.

**The bug.** In `GrouperProvisionerTargetDaoAdapter.java`, the retrieve block for "some memberships" has a group clause and an entity clause. The entity clause (line 1202) tests the wrong list:

```java

// line 1189-1196: group branch (correct)

... && GrouperUtil.length(request.getTargetGroupsForGroupSomeMembershipSync()) > 0) {

    targetDaoRetrieveMembershipsRequest.setTargetGroups(request.getTargetGroupsForGroupSomeMembershipSync());

// line 1197-1204: entity branch (wrong list in the condition)

... && GrouperUtil.length(request.getTargetGroupsForGroupSomeMembershipSync()) > 0) {   // should be ...TargetEntitiesForEntitySomeMembershipSync()

    targetDaoRetrieveMembershipsRequest.setTargetEntities(request.getTargetEntitiesForEntitySomeMembershipSync());

```

For an `entityAttributes` provisioner the group "some" list is empty, because it is only filled for `groupAttributes`. So `hasData` stays false and `retrieveMemberships` is never called. The entity list is filled correctly, which is why the log still prints "Target data request some entity mships entities (1)". That section logs the request object, not what was sent. It doesn't show a lookup. The `git log -S` output shows the clause was introduced in "improve provisioning" (`6d9eabaf2ebb`) and earlier commits.

**Why it matches your logs.**

* `selectSomeMemberships: 1` and `entitiesWithSelectSomeMemberships: 1` appear in the debug map, but `retrieveIncrementalTargetMemberships: 0` and `targetMembershipsRetrieved: 0` show nothing was fetched.

* "Target provisioning entities" shows `eduPersonEntitlement: <null>` because only the entity was fetched, and the search attributes didn't include the membership attribute for it.

* Compare then sees no target membership and logs `provisioningMembershipWrappersWithNoMatch=1`. It decides there is nothing to delete, which is the already-gone branch (`GrouperProvisioningMatchingIdIndex.java:1090`). The sync row is marked `in_target = F`.

**Why `recalculateAllOperations = false` fixes it.** With it true, every entity is recalc'd, so the delete depends on retrieving the entity's current memberships from LDAP and comparing. That is the "some memberships" path, and the bug blanks it out. With it false, the delete event is trusted and sent as an LDAP modify without that lookup. This replaces my earlier, vaguer explanation.

**Suggested fix:** change line 1202 to test `getTargetEntitiesForEntitySomeMembershipSync()`. I haven't made the change. Do you want me to make it and add a test? There is `LdapProvisionerIncrementalTest` (it already sets `recalculateAllOperations=true`) that I could extend with an entityAttributes delete case.

**Caveats:**

* I haven't run it or reproduced the failure; this is from reading the code against your log.

* The entity branch also depends on the DAO capability flags. The LDAP DAO sets `canRetrieveMembershipOneByEntity(true)` (line 1294), so the first part of the condition passes. I haven't traced `retrieveMemberships` itself past the adapter, so there could be a second problem after the request is sent.

* Groups probably have the same pattern on the other side, but that branch looks correct.

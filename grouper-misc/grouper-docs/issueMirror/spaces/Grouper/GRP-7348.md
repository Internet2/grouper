# GRP-7348  Keep config in memory and apply only the changed rows on poll, instead of rebuilding the whole config bean

Follow on from GRP-7298. Today, when config changes are detected, the cached config object is thrown away and the whole thing is rebuilt from scratch: every row for the config file is re-read and a new config bean is constructed. That is expensive even when a single property changed, and it is the reason a config change is measured in hundreds of MB of allocation rather than in bytes.

Proposal: keep the config bean in memory and update it surgically. On the poll that checks for database changes, select the lightweight identity and change columns per config file (id, config_key, last_updated) rather than the full rows, diff that against what is already held in memory, and then apply only the delta to the existing bean: insert the keys that are new, update the keys whose last_updated moved, and remove the keys whose rows are gone. Full row content (including the clob and bytes columns) only needs to be fetched for the ids that actually changed.

The grouper_config table already has what this needs: id, config_key, last_updated (bigint millis), and hibernate_version_number.

Things to work out while doing this. Detecting deletes requires seeing the full key or id list for the file on each poll, so the diff query has to return all ids for the file even though it skips the heavy columns; confirm that is cheap enough at realistic row counts. The bean also has to stay safely publishable while being mutated, since it is read concurrently from request threads, so either mutate a copy and swap the reference or make the underlying map concurrent. And elConfig values are resolved at read time rather than cached (see GRP-7346), so a changed key does not require recomputing anything else, which is what makes a surgical update safe in the first place.

This is complementary to GRP-7346. That issue reduces HOW MANY config classes get invalidated when something changes; this one reduces the cost of each invalidation from a full rebuild to applying a small delta. Together they should take a routine config save from rebuilding everything down to touching a handful of keys.

ConfigPropertiesCascadeBase.CONFIG_CACHE_INSTRUMENTATION (set true and rebuild) counts config cache clears and full rebuilds per request, which is the measurement to use for before and after.

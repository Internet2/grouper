# GRP-7101  `GrouperHttpClient`: only retries network errors whose stack trace contains "timed out"; `Connection reset` aborts the run

claude found this while looking at our okta provisioner issue..
----
 h2. {{GrouperHttpClient}}: only retries network errors whose stack trace contains "timed out"; {{Connection reset}} aborts the run

*Type:* Bug / Resilience
*Component:* {{grouper/util/GrouperHttpClient}} (used by all HTTP-based provisioners, not just Okta)
*Affected branch:* {{GROUPER_7_BRANCH}} (verified against current source)
*Environment observed:* Grouper 7.2.1, QA sync against {{okta-qa.iam.it.umich.edu}}

h3. Summary

{{GrouperHttpClient}} retries throttling (429/503) up to 5× with backoff, and _intends_ to retry transient network errors — but the network-error branch only triggers when the exception's stack trace contains the literal string {{"timed out"}}. A common transient error, {{java.net.SocketException: Connection reset}}, does *not* match that string, so it is thrown on the first occurrence.

For a provisioner making tens of thousands of HTTP calls over hours (typical of a full sync), a single transient TLS reset aborts the entire run.

h3. Steps to reproduce / observed behavior

Full sync of {{Okta_MCOMM_UserGroups}} (QA, {{selectAllGroups=false}}, run {{w1bvaloh}}):

* ~5 hours in, one of ~85K individual HTTP calls to Okta failed with:

{noformat}
java.lang.RuntimeException: Error connecting to
  'https://okta-qa.iam.it.umich.edu/api/v1/groups/00g1zh3uvb6QjoNa01d8/skinny_users'
Caused by: java.net.SocketException: Connection reset
{noformat}

* Full stack trace shows the failure inside {{GrouperProvisionerTargetDaoAdapter$8.callLogic}} (line 1537), running on a {{ThreadPoolExecutor}} worker. Not a threading defect — a plain socket reset.
* The entire full sync aborted at this point; no retry occurred.

h3. Root cause (in the source)

{{grouper/src/grouper/edu/internet2/middleware/grouper/util/GrouperHttpClient.java}}, method {{executeRequest()}} (approx. lines 946–972):

{code:java}
for (int i = 0; i < retryForThrottlingOrNetworkIssues + 1; i++) {
    boolean retry = false;
    try {
        this.executeRequestHelper();
        code = this.getResponseCode();
    } catch (Exception e) {
        String fullStackTrace = GrouperUtil.getFullStackTrace(e);
        if (StringUtils.isNotBlank(fullStackTrace) && StringUtils.contains(fullStackTrace, "timed out")) {
            retry = true;                                    // <-- only "timed out" is retryable
        }
        runtimeException = new RuntimeException("Error connecting to '" + this.url + "'", e);
    }
    // ... 429/503 handling below ...
    if (i <= retryForThrottlingOrNetworkIssues && retry) { /* sleep + continue */ }
    // else: throw
}
{code}

The retry counter ({{retryForThrottlingOrNetworkIssues}}, default 5) and the sleep/backoff logic are already wired — the gap is purely in _which_ exceptions flip {{retry}} to true. {{Connection reset}} (from {{java.net.SocketException}}) does not contain the substring "timed out" anywhere in its stack trace, so it falls through to the {{throw}}.

h3. Why this matters at scale

Any provisioner making a large number of HTTP calls is exposed. Rough odds: if per-call transient reset probability is even 1 in 100,000, a sync of ~85K calls has ~57% chance of at least one reset during the run. Empirically, we saw one on the very first attempt.

This particularly punishes provisioner code paths that fetch objects individually (many small calls), which is exactly the path Grouper takes when {{selectAllGroups=false}}. Fixing this ticket would also make the fix for the threading ticket more robust once it lands, because parallelized code paths tend to increase call rates and connection churn.

h3. Suggested fix

Broaden the "is this a transient network error?" check. Options in increasing order of change:

# *Minimal:* add additional substring matches: {{"timed out"}}, {{"Connection reset"}}, {{"Connection refused"}}, {{"Broken pipe"}}, {{"unexpected end of stream"}}. (Cheap, low-risk.)
# *Better:* switch to exception-type checks instead of string matching — retry when the underlying cause is a {{java.net.SocketException}}, {{java.net.SocketTimeoutException}}, {{org.apache.http.NoHttpResponseException}}, or {{javax.net.ssl.SSLException}} (which covers most TLS-layer transient errors). Excludes non-transient causes like {{UnknownHostException}}.
# *Best:* make the retry predicate injectable (a {{Predicate<Throwable>}} on {{GrouperHttpClient}}) with a sensible default set, so different callers can tune it if needed.

Existing throttling and backoff logic can be reused as-is — this is purely widening the trigger.

h3. Consider also

* Log a WARN (not just add to {{debugMap}}) when a retry fires for a network error, so operators can see transient issues without turning on DEBUG.
* The check is a substring match on the _entire_ stack trace text, so nested causes are captured — fine for the type-based approach too if you call {{Throwables.getRootCause(e)}} or walk {{getCause()}}.

h3. Scope

Independent of the GRP-7100. This affects *every* HTTP-based Grouper provisioner and any Grouper code that uses {{GrouperHttpClient}}, not just Okta. Fixing it does not change semantics for jobs that already complete successfully — it only prevents transient network blips from aborting long-running work.
